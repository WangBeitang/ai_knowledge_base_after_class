## 关键术语边界

- `Planner`：规划器，负责根据当前问题和 Observation 选择下一个 Action。阶段 9 训练的是 Planner Policy，不训练最终答案模型。
- `Action`：Planner 可输出的固定动作，例如 `local_search`、`hyde_search`、`web_search`、`answer`、`ask_clarification`、`refuse`。
- `Observation`：Action 执行后的可验证事实，例如召回数量、rerank 分数、命中的 chunk、错误码和耗时。
- `Trace`：一次查询的结构化轨迹记录，用来复盘 Planner 每一步 Action、Observation、Citation、成本和终态，不保存模型私有思维链。
- `Reward`：奖励或评分信号。它把一条 Trace 按格式、检索、引用、答案、行为和成本拆分评分，阶段 9 的 GRPO 会直接使用总分。
- `SFT`：监督微调，用审核通过的样本教模型输出合法 `PlannerDecision` 和基本路由。
- `GRPO`：强化学习优化方法，本项目只用于优化多步 Planner 轨迹，不放进线上查询路径。
- `expected_chunks`：人工期望命中的证据 chunk 列表，必须包含 `document_id + chunk_id + index_version`，用于判断检索和引用是否命中同一版证据。
- `split`：数据用途拆分，包含 `train/dev/test/demo_regression`。`test` 是 held-out test，即隔离测试集，不能参与调参、模型选择、Reward 权重选择或训练轨迹挑选。
- `leakage_group_id`：泄漏隔离组。同一来源文档、同一报警码、同一 SOP 或同一问题改写必须放在同一个 split，防止训练集和测试集互相泄漏。

## 数据处理方案

### 1. 来源分级

优先级 1：最适合直接做 RAG 问答的数据。

- 设备操作手册。
- 维护 SOP。
- 报警码说明。
- 安全注意事项。
- 零件、部件、易损件说明。
- 维修排查流程和点检表。

优先级 2：可以作为补充，但必须先结构化的数据。

- 公开制造业质量检测数据。
- 故障诊断数据。
- 预测性维护数据。
- 缺陷图像或传感器表格。

这类数据不能直接作为 RAG 文档，需要先转成“故障场景卡片”，例如：

```text
设备/部件
    -> 故障现象
    -> 可能原因
    -> 诊断步骤
    -> 处理建议
    -> 安全注意事项
    -> 证据来源和字段解释
```

优先级 3：社区或二次整理数据。

- 只能作为候选来源。
- 必须检查许可证、来源可信度、字段含义、是否允许再分发、是否允许训练使用。
- 许可证不明确时，只进入内部调研清单，不进入训练候选池。

### 2. 来源清单契约

`source_manifest.jsonl` 每行记录一个来源：

| 字段 | 含义 |
|---|---|
| `source_id` | 来源稳定 ID，全局唯一。 |
| `source_type` | 来源类型，例如 `manual/sop/alarm_code/table/image/community`。 |
| `title` | 来源标题。 |
| `publisher` | 发布方或维护方。 |
| `url_or_path` | 原始 URL 或本地路径。 |
| `collected_at` | 采集时间。 |
| `source_hash` | 原文件 hash，用于发现内容漂移。 |
| `license_name` | 许可证名称。 |
| `license_url` | 许可证说明地址，可为空但必须记录原因。 |
| `redistribution_allowed` | 是否允许再分发。 |
| `training_allowed` | 是否允许用于训练。 |
| `commercial_use_allowed` | 是否允许商业使用。 |
| `approval_status` | `approved/pending/rejected`。 |
| `reject_reason` | 拒绝或暂缓原因。 |

硬规则：

- `approval_status != approved` 的来源不能进入 `schema_approved_cases.jsonl`。
- `training_allowed != true` 的来源不能进入 SFT/GRPO 训练候选。
- 来源、许可证或字段含义说不清的数据，宁可丢弃，不进入训练。

### 3. 故障场景卡片契约

`fault_scenario_cards.jsonl` 每行表示一个可解释的故障或维护场景：

| 字段 | 含义 |
|---|---|
| `card_id` | 场景卡片 ID。 |
| `source_id` | 关联来源。 |
| `source_document_id` | 转成 RAG 文档后的 document ID，可为空。 |
| `source_section` | 来源章节、页码、表格名或字段名。 |
| `equipment_model` | 设备型号。 |
| `component_name` | 部件或零件名称。 |
| `alarm_code` | 报警码，可为空。 |
| `symptom` | 故障现象。 |
| `possible_causes` | 可能原因。 |
| `diagnostic_steps` | 排查步骤。 |
| `maintenance_actions` | 处理建议。 |
| `safety_notes` | 安全注意事项。 |
| `evidence_text` | 可追溯的原文证据或字段解释。 |
| `evidence_chunk_ids` | 对应 chunk 身份，必须带版本。 |
| `quality_flags` | 质量标记，例如 `missing_license/weak_evidence/ambiguous_identifier`。 |

场景卡片只解决“原始数据如何变得可解释”，不等于训练样本。只有能稳定映射到 `expected_chunks` 和答案要点的卡片，才可以生成 Planner case。

### 4. 候选样本生成

候选生成优先从每张故障场景卡片生成以下问题类型：

- 设备型号 + 报警码含义。
- 故障现象原因排查。
- 维护 SOP 步骤。
- 安全注意事项。
- 零件或部件定位。
- 主体歧义追问。
- 证据不足拒答。
- 明显实时问题的 Web 行为边界。

生成后的 `planner_case_candidates.jsonl` 必须尽量复用阶段 8 的 `PlannerEvalCase` 字段，不另起一套训练格式。新增来源追踪字段可以放在 `notes` 或阶段 8.5 的外部 manifest 中，避免破坏已落地 schema。

候选样本的最低要求：

- `case_id` 稳定且唯一。
- `leakage_group_id` 至少按 `source_id + source_section + equipment_model + alarm_code/SOP` 生成。
- 回答型样本必须有 `expected_chunks` 和 `expected_answer_points`。
- `expected_chunks.relevance` 必须明确标成 `required/supporting/acceptable`。
- `acceptable_action_paths` 必须反映业务预期，不能为了让轨迹拿高分而放宽到所有路径。
- `label_source` 对自动生成样本先标 `synthetic`，人工复核后才能成为高可信样本。
- `human_review_status` 默认 `pending`，不能默认写成 `reviewed`。

### 5. 质量门禁

新增数据必须经过九道门禁：

| 门禁 | 目的 | 不通过处理 |
|---|---|---|
| 来源门禁 | 检查来源和许可证。 | 写入 `rejected_cases.jsonl` 或保留在 pending 来源。 |
| 解析门禁 | 检查文本提取、表格解释和乱码。 | 不生成 case，只保留处理日志。 |
| chunk 门禁 | 检查空 chunk、重复 chunk、页眉页脚和弱证据。 | 禁用或不参与候选生成。 |
| 场景门禁 | 检查故障场景卡片是否可解释。 | 只保留卡片，不生成训练样本。 |
| schema 门禁 | 用 `PlannerEvalCase` 校验字段。 | 直接拒绝。 |
| 泄漏门禁 | 检查 `case_id`、`leakage_group_id` 和来源文档不跨 split。 | 重新分组或拒绝。 |
| 检索门禁 | 用当前 snapshot 检查 expected chunk 是否可召回。 | 进入人工复查，不直接训练。 |
| 人工门禁 | 审核关键样本的答案要点、证据强度和行为路径。 | pending/rejected 不导出训练。 |
| Reward 门禁 | 用 Reward v1.1 过滤低质量轨迹。 | 路线错误、成本异常或终局质量不足的轨迹不进入 SFT/GRPO。 |

## Reward v1.1 方案

### 1. 为什么必须在阶段 9 前升级

当前 Reward v1 是阶段 8 离线评测用的第一版综合分。它可以衡量检索和引用质量，但默认权重不完全符合阶段 9 的 Planner 训练目标：

- `retrieval + citation` 合计权重为 0.40，容易让 chunk 命中和 Citation 这类终局证据指标主导总分。
- `behavior + cost` 合计权重为 0.25，但 Planner 直接控制的恰恰是是否检索、是否 fallback、何时回答、何时追问/拒答以及是否多走无意义步骤。
- 同一个固定检索动作下，chunk 排名主要由检索器、reranker、chunk 质量和标注决定，不是 Planner 直接输出。

因此阶段 8.5 不再把二值检索、证据强度和 chunk 排名扩展成新的训练主指标。Reward v1.1 的重点改为：按策略可归因性、分项区分度和阶段 9 训练目标重新分配六路权重，让 GRPO 优先学习能稳定改善终局质量的检索路线。

### 2. 训练可归因性原则

Reward 权重不按“Planner 是否直接生成这个结果”机械分配。更稳的判断顺序是：

1. 这个分项是否会随不同 Planner Action path 稳定变化。
2. 这个变化能否主要归因于 Planner 策略，而不是固定检索器、reranker、缓存、标注噪声或答案模型随机性。
3. 这个分项是否适合作为训练信号，而不是只适合作为评测指标。
4. 这个分项权重过高时，是否会诱导模型背人工路径、滥用拒答、过度省步骤或追逐 chunk 排名。

Planner 直接控制的内容包括：

- 输出合法 `PlannerDecision`。
- 选择 `local_search`、`hyde_search`、`web_search`、`answer`、`ask_clarification` 或 `refuse`。
- 根据 Observation 决定是否继续检索、fallback、回答、追问或拒答。
- 控制 Action 步数、是否滥用 HyDE/Web、是否过早回答。

Planner 间接影响但仍可能提供训练信号的内容包括：

- 哪些 chunk 被召回。
- 最终 Citation 是否覆盖 expected chunk。
- 答案要点是否完整。

这些分项不能因为“间接影响”就完全排除训练权重；如果某些 case 中 `hyde_search`、`web_search` 或正确回答时机能稳定改善检索、引用或答案分，它们仍然是有效终局奖励。真正要降低权重的是那些主要由固定检索器和标注决定、在不同 Planner 轨迹之间几乎没有差异的分项。

Planner 基本不直接控制，且需要谨慎作为训练主信号的内容包括：

- 同一路检索器内部的 chunk 排名。
- reranker 对候选 chunk 的排序细节。
- chunk 本身质量和 expected chunk 标注粒度。

所以 Reward v1.1 的训练权重应该遵循：

| 分项 | 训练定位 | 权重方向 |
|---|---|---|
| `format` | 保证结构化输出和 Action 合法性 | 中等偏高 |
| `retrieval` | 终局证据质量约束；若随 Action path 稳定变化，可以保留辅助训练作用 | 降低但不置零 |
| `citation` | 防止无引用、伪造引用或引用错版本；更多用于终局质量校验 | 降低但不置零 |
| `answer` | 约束是否到达正确终态和答案要点；包含明显 Planner 终态信号 | 中等 |
| `behavior` | 训练该答、该拒、该追问、该 Web 的路线决策；防止把错误路线送进训练 | 最高但需防止背路径 |
| `cost` | 约束无意义 HyDE/Web、额外步骤和延迟；不惩罚必要 fallback | 中等偏高 |

### 3. 建议默认权重

Reward v1.1 第一版权重：

```text
format    = 0.15
retrieval = 0.12
citation  = 0.08
answer    = 0.15
behavior  = 0.35
cost      = 0.15
```

含义：

- `behavior + cost = 0.50`，作为第一版训练 Reward 的路线分主信号，但不是因为它们“唯一可控”，而是因为当前最容易归因于 Planner Action path。
- `retrieval + citation = 0.20`，保留终局证据质量约束，但暂不让 chunk 排名主导训练；如果 dev 多轨迹证明这些分项随策略稳定变化，可以小幅上调。
- `format + answer = 0.30`，保证输出合法、终态正确、答案要点不被完全忽略。

暂不调整 `score_retrieval` 内部公式，继续使用现有 `recall@k`、MRR、nDCG 和标识命中率。它们先作为评测指标和低权重终局信号保留，不在阶段 8.5.2 新增 `weighted_recall_at_k`、`weighted_ndcg_at_k` 或 required gate。

### 4. 训练前有效性验证

阶段 9 真正训练前，必须验证六路分项在不同 Planner 轨迹之间是否有有效差异。

验证方法：

```text
同一批 dev case
    -> 构造或采样多条 Action path
    -> 计算 format/retrieval/citation/answer/behavior/cost
    -> 观察每个分项在不同路径之间的方差和排序相关性
```

判断规则：

- 如果 `behavior/cost` 能明显区分正确路线和错误路线，且没有诱导过早拒答或机械背路径，保持较高权重。
- 如果 `retrieval/citation` 在不同 Planner 轨迹之间几乎不变，继续低权重，只作为报告指标。
- 如果某些 case 中 `hyde_search`、`web_search` 或正确回答时机确实显著改善证据质量，可以保留或小幅提高 `retrieval/citation/answer` 的辅助作用，但必须记录是策略差异造成的。
- 如果 `cost` 过高导致模型倾向不检索就拒答，需要降低 `cost` 或提高 `behavior/answer` 对正确回答的约束。
- 如果 `acceptable_action_paths` 标注过窄，导致模型只背人工路线而错过等价更优策略，需要扩展可接受路径或降低 path_match 的有效影响。

### 5. 版本与兼容边界

- `REWARD_VERSION` 升级为 `reward-v1.1`，旧的 `reward-v1` 结果只作为阶段 8 历史报告保留。
- 阶段 8.5 的新增评测、数据筛选和训练导出不再生成 `reward-v1` 结果。
- 阶段 8.5.2 只调整六路权重和对应说明，不改检索指标内部公式。
- dev 上可以调六路权重；test 运行前必须冻结 `reward_version` 和权重。
- SFT 导出 manifest 必须记录使用的 `reward_version=reward-v1.1` 或后续版本。
- 如果后续同时维护 Evaluation Reward 和 Planner Training Reward，必须显式记录权重 profile 或升级 `reward_version`，不能让同名版本在评测和训练中代表两套不同权重。

当前 20 条的数据等级明确定义为 `curated_seed_gold`（人工策划证据的种子 Gold）：

后续新增 Gold 统一使用“真实语料先入库，Gold 后生成”流程，不再先编写问题和逻辑 chunk 再倒向构造检索库：

```text
来源与许可证审核
  -> 下载并保留原始文件/hash
  -> 只做可重放的格式清洗或结构化转换
  -> 使用与生产环境相同的 parser/chunker/indexer 入库
  -> 获取真实 document_id/chunk_id/index_version
  -> 冻结语料快照
  -> 从快照内真实 chunk 筛选可回答事实
  -> 生成自然问题、答案点和预期 Action 路线
  -> 逐答案点反向验证来源支撑
  -> 独立二审
  -> 按 source/document/leakage_group_id 拆分 train/dev/test
  -> 冻结 Gold 版本、split manifest 和评测快照
```

原始文件处理边界：

- 设备手册、维护 SOP、报警码说明、UCI 官方描述和 `profile.txt` 这类可读文档，应尽量保留原文语义，通过生产解析和切分链路入库。
- CSV、传感器矩阵、音频和原始时序不能直接当作 RAG 文档。必须先由确定性脚本生成可解释的字段说明、统计摘要或故障场景卡，并保留原文件 hash、转换脚本版本和输出 hash。
- 不得让 LLM 对原始传感器数据自由总结后直接标为 Gold；无法用确定性转换或公开说明验证的结论只能进入 review/silver。

Gold 生成质量要求：

- `expected_chunks` 必须引用已冻结快照内的真实整数 `chunk_id`，同时固定 `document_id + index_version`。
- 问题不能只是对 chunk 原句的机械改写；应使用自然用户表达、同义改写，并按需要覆盖多 chunk、无答案、澄清和检索降级路线。
- 每个 `expected_answer_point` 都必须有明确证据映射；只有相关 chunk 但无法直接支持答案的样本不是 Gold。
- 生成时不得读取 held-out test；Reward 权重、Prompt、模型和训练轨迹也不得根据 test 结果选择。
- 后续 dev/test 必须来自独立真实文档及其生产切分后的真实 chunk；不得从当前两份人工整理证据文档继续拆分。

| 许可证不清导致数据不能训练 | 来源门禁前置，`training_allowed=false/pending` 的来源不进入训练。 |
| 自动生成的问题或答案要点幻觉 | 所有回答型样本必须绑定 expected chunk 和答案要点，关键样本人工审核。 |
| 同源问题跨 split 泄漏 | `leakage_group_id` 按来源、章节、设备、报警码或 SOP 生成，并在 split 校验中强制唯一归属。 |
| Reward v1.1 过度惩罚复杂问题 | 只在 dev 上调六路权重，test 前冻结；报告展示分项方差、扣分原因和是否可归因于 Planner 策略。 |
| `acceptable_action_paths` 过窄导致模型背人工路径 | 扩展等价可接受路径；训练前检查 path_match 的有效权重，不把人工路径当唯一正确策略。 |
| 模型为了 Reward 滥用 HyDE/Web | 保留 `R_cost` 和 forbidden actions，报告展示不必要 HyDE/Web 调用率。 |
| 原始传感器数据不可解释 | 先转故障场景卡片，不能解释清楚来源和字段含义就不生成 RAG 样本。 |
