# 阶段 9：公开数据集扩充与公共基准主实验方案

## 文档状态

- 状态：`proposal`（方案，尚未实现）。
- 创建日期：2026-08-03。
- 当前工程基线：SFT V2（监督微调第二版）和首轮正式 GRPO（群组相对策略优化）训练链路已经闭环。
- 本文目标：设计一条尽量少依赖人工编写数据、又能可信比较 SFT（监督微调）与 GRPO（群组相对策略优化）的公共基准训练路线。
- 本文不代表：公开数据已经下载、转换、审核、训练或评测完成。

## 结论

建议建设一个独立的公共基准主实验，但不把公开数据直接混入现有 75 条设备运维训练案例。

第一版选择：

1. 以 HotpotQA `distractor`（干扰段落设置）作为首个公共数据事实源。
2. 以 2WikiMultiHopQA 作为第二个同类数据源，在 HotpotQA 闭环后再接入。
3. R1-Searcher 只作为检索强化学习方法、难度分层和 Reward（奖励分数）设计参考，不把其公开文件误认为可直接导入的完整 Planner（规划器）轨迹。
4. DeepResearch-9K 暂列为第二阶段长轨迹 SFT（监督微调）候选，必须先确认许可证和工具协议适配成本。
5. ToolBench 与当前 RAG（检索增强生成）证据充分性任务偏差较大，第一版不使用。

总体实验边界：

```text
公共基准数据
    -> 证明 Planner SFT + GRPO 方法是否有效

现有 75 条设备运维数据
    -> 继续承担领域训练、Reward 校准和错误分析

未来新增领域 heldout（严格留出）数据
    -> 证明公共能力是否迁移到设备运维场景
```

现有 75 条数据已经参加过 SFT（监督微调）和 GRPO（群组相对策略优化），不能再作为独立迁移测试集，也不能用于证明未见数据上的泛化提升。

## 为什么现在需要公共基准

首轮正式 GRPO（群组相对策略优化）已经证明以下工程能力真实存在：

- 使用 Qwen3.5-4B 和 SFT V2 LoRA（低秩适配）初始化策略模型。
- 使用冻结 reference model（参考模型）约束策略偏移。
- 对 75 个唯一案例各采样 4 条 rollout（模型交互轨迹），共 300 条。
- 执行真实 Provider（动作执行器）并记录 Observation（观察结果）。
- 计算词元级策略概率、组内相对优势、clipped loss（裁剪策略损失）和 KL penalty（策略偏移惩罚）。
- 更新 LoRA（低秩适配）参数并保存可恢复 checkpoint（训练检查点）。

但这轮结果只能证明训练链路成立，不能证明 GRPO（群组相对策略优化）优于 SFT V2（监督微调第二版）。当前主要证据包括：

- 300 条 rollout（模型交互轨迹）中只有 114 条通过格式和终态契约。
- 186 条被 `invalid_format`（格式无效）封顶，其中 135 条为 `planner_output_invalid`（规划器输出无效），51 条为 `illegal_action_transition`（非法动作转移）。
- 当前 `answer`（进入答案生成）终态只产生占位文本，答案分不是 Planner（规划器）可以直接改善的真实能力。
- 75 条领域数据同时承担格式、路线、领域边界和效果证明，统计规模不足以稳定回答“GRPO 是否优于 SFT”。

因此，公共数据的价值不是替代当前系统，而是提供规模更大、答案和支持证据更标准、可以独立留出测试的数据基础。

## 目标和非目标

### 本方案要完成

- 建立公共数据来源、许可证、下载身份和 SHA256（文件内容哈希）清单。
- 把公共问答和 supporting facts（支持事实）转换为当前可审计的 `PlannerEvalCase`（规划器评测案例）。
- 建立只依据模型实际 query（查询）检索的冻结公共 Provider（动作执行器）。
- 为公共任务冻结独立的 Planner-pure Reward（仅规划器可控奖励配置）。
- 生成公共 SFT（监督微调）数据、公共 GRPO（群组相对策略优化）训练案例和独立测试集。
- 对 Base（基础模型）、Public-SFT（公共数据监督微调）和 Public-SFT+GRPO（公共数据监督微调加群组相对策略优化）使用同一评测入口比较。
- 只有独立测试证据成立时，才声称 GRPO（群组相对策略优化）带来提升。

### 第一版不做

- 不继续人工编写数百条设备运维案例。
- 不修改现有 75 条冻结训练数据来适配公共实验。
- 不把公开数据写入现有 `sft_v2_reviewed_75_v1` 或历史 GRPO（群组相对策略优化）目录。
- 不使用 heldout/dev/test（留出集/开发集/测试集）生成训练标签或选择训练轨迹。
- 不用 `snapshot_expected_chunks` 按标准答案伪造 Observation（观察结果）。
- 不让 `acceptable_action_paths`（可接受动作路线）或 supporting facts（支持事实）进入 Planner（规划器）提示词。
- 不在第一版公共任务中强行制造 `web_search`（联网检索）或 `ask_clarification`（追问澄清）Gold（标准答案）标签。
- 不先接入完整 Wikipedia 全库索引；第一版使用数据集正式提供的 distractor context（干扰候选上下文）。
- 不做超参数搜索，不同时引入 TRL、Verl 等第二套训练框架。
- 不把一次单 seed（随机种子）提升写成稳定方法结论。

### 第一版选 HotpotQA distractor 的原因

HotpotQA 官方数据具备以下优势：

- 训练和开发数据可公开获取，数据集采用 CC BY-SA 4.0。
- 每条案例已经包含问题、标准答案、候选上下文和 supporting facts（支持事实）。
- distractor（干扰段落设置）允许在每个案例的固定候选段落中执行真实检索，不需要第一版就建立完整 Wikipedia 全库索引。
- supporting facts（支持事实）只交给 Evaluator（评测器/裁判），可以自动计算检索是否命中，而不需要人工逐条绑定设备知识库 chunk（文本块）。
- 官方拆分可以作为第一层 train/dev/test（训练集/开发集/测试集）隔离边界。

## 公共任务动作空间

当前正式 `QueryAction`（查询动作）枚举保持不变，公共任务通过 task profile（任务配置）限制本轮可探索动作，不新建一套平行动作协议。

### 第一版开放动作

| Action（动作） | 公共任务语义 | Provider（动作执行器）行为 | 是否参与探索 |
|---|---|---|---|
| `local_search` | 使用当前问题或改写查询检索候选段落 | 在该案例冻结的候选段落中按模型真实 query 检索 | 是 |
| `hyde_search` | 首次检索证据不足后的假设答案增强检索 | 冻结 HyDE generator（假设答案生成器）根据模型实际 query 生成增强文本，再检索同一冻结语料 | 是 |
| `answer` | Planner（规划器）认为证据已经充分并停止检索 | 只标记终态；第一版不让 Planner 直接生成最终答案正文 | 是 |
| `refuse` | 无法可靠完成时的安全出口 | 安全终止，不执行检索 | 保留，但不把它当公开数据主要 Gold 路线 |

### 第一版不开放动作

| Action（动作） | 暂不开放原因 |
|---|---|
| `web_search` | HotpotQA distractor 是冻结本地候选语料，不具备天然联网 Gold 标签 |
| `ask_clarification` | 原始问题已经过数据集标注，通常不存在用户信息缺失型 Gold 标签 |

`refuse`（安全拒答）必须继续存在，因为当前 `PlannerContext.allowed_actions`（规划器上下文允许动作）要求它作为硬安全出口。不能为了提高训练分数而把探索中可能选错的动作从环境中动态禁掉，也不能根据标准路线把错误动作提前屏蔽。

## 调用和判分边界

正式调用顺序保持：

```text
Planner（规划器）读取当前 State（运行状态）和 Observation（观察结果）
    -> 输出 PlannerDecision（规划器决策）
    -> Provider（动作执行器）按模型实际 query 执行 Action（动作）
    -> 返回真实 Observation（观察结果）
    -> Planner（规划器）继续决策或终止
    -> Evaluator（评测器/裁判）读取隐藏 Gold（标准证据）并计算 Reward（奖励分数）
```

硬边界：

- Planner（规划器）不得读取 `supporting_facts`、标准答案、参考路线或期望 chunk（文本块）。
- Provider（动作执行器）只能读取模型实际 query、公共候选语料和当前运行配置。
- Evaluator（评测器/裁判）可以读取 supporting facts（支持事实）和标准答案，但只用于事后评分。
- Observation（观察结果）必须来自实际检索结果，不得由 `snapshot_expected_chunks` 或标准答案反向生成。
- `refuse`（安全拒答）保留为安全出口，但错误选择它应由 Reward（奖励分数）扣分，而不是在动作白名单中提前禁掉。

## 公共数据契约

### 复用的正式 Schema（结构约束）

继续复用 `PlannerEvalCase`（规划器评测案例），不新建无法与现有训练器互通的第二套 case（案例）结构。

公共字段映射：

| HotpotQA 字段 | 当前项目字段 | 处理规则 |
|---|---|---|
| `_id` | `case_id` | 增加 `hotpotqa-` 前缀，保持稳定唯一 |
| `question` | `query` | 原文保存，不自动翻译 |
| 官方 split（拆分） | `split` | train 只进训练；官方 dev 再冻结为本项目 dev/test |
| supporting fact title | `source_document_ids` | 生成稳定公共文档 ID |
| supporting fact title + sentence id | `expected_chunks` | 生成确定性公共 chunk 身份 |
| `answer` | `expected_answer_points` | 只供 Evaluator（评测器/裁判）和下游答案评测使用 |
| supporting facts（支持事实） | `acceptable_action_paths` 的判定依据之一 | 不直接唯一化路线，允许不同检索顺序 |
| official context（官方上下文） | 冻结语料快照 | 进入 Provider（动作执行器）候选池，不进入 Planner 提示词全文 |

公共 chunk（文本块）身份使用确定性规则生成，例如：

```text
document_id = hotpotqa:{normalized_title}
chunk_id = sha256(dataset_version + title + sentence_index + sentence_text)
index_version = 1
```

实际实现前必须冻结规范化规则；规则一旦变化，旧 `expected_chunks`（期望文本块）、审核决定和 fingerprint（内容指纹）全部失效，不能静默复用。

### 新增 task profile（任务配置）

正式训练器当前把 75 条领域案例身份门禁写死。公共实验不复制训练器，而是新增可配置 `task_profile`（任务配置），至少包含：

```text
profile_id
dataset_family
expected_case_count
group_size
allowed_actions
reward_profile
provider_profile
source_manifest_sha256
case_manifest_sha256
environment_snapshot_sha256
excluded_split_policy
```

现有领域正式配置继续使用自己的 75 条固定身份，不因公共任务配置化而放宽历史门禁。

## Frozen Public Provider（冻结公共动作执行器）

### 第一版实现

每条 HotpotQA distractor 案例自带固定候选段落。第一版 Provider（动作执行器）只在该案例候选池中执行检索：

```text
模型实际 query
    -> local_search：直接进入公共文本预处理
    -> hyde_search：先由冻结 HyDE generator（假设答案生成器）产生增强文本
    -> BM25/dense/hybrid（关键词/向量/混合）检索
    -> 固定 top-k
    -> 生成候选身份、分数和内容摘要
    -> 返回 Observation（观察结果）
```

Provider（动作执行器）不得读取 supporting facts（支持事实）决定返回哪些候选。标准证据只允许由 Evaluator（评测器/裁判）在检索完成后比对。
HyDE generator（假设答案生成器）的模型身份、提示词版本、采样参数和 SHA256 也必须写入环境快照，训练期间保持冻结，避免环境随策略一起变化。

### 公平性说明

按案例使用官方 distractor context（干扰候选上下文）会降低完整 Wikipedia 全库检索难度，但仍是公开数据正式提供的评测设置。第一版报告必须明确写成：

> HotpotQA distractor-context Planner experiment（HotpotQA 干扰候选上下文规划实验）

不能把结果写成 full-wiki open-domain retrieval（完整维基百科开放域检索）能力。

### 第二版升级条件

只有第一版完成以下闭环后，才考虑 KILT Wikipedia 或 HotpotQA fullwiki（完整维基百科设置）：

- 公共案例转换和数据隔离通过。
- PlannerDecision（规划器决策）严格 JSON 合法率通过门禁。
- Frozen Provider（冻结动作执行器）真实 query 检索通过。
- Public-SFT+GRPO（公共监督微调加群组相对策略优化）相对 Public-SFT（公共监督微调）的比较可以稳定复现。

## Public Planner Reward v1（公共规划器奖励第一版）

公共任务不直接复用设备领域 `reward-v1.1` 权重，另建独立冻结 profile（配置），但复用正式 Reward（奖励分数）框架和审计字段。

### 只奖励 Planner（规划器）可控行为

第一版训练 Reward（奖励分数）由以下部分组成：

- `format`（格式）：`PlannerDecision` 是否为严格 JSON，字段是否合法。
- `retrieval`（检索）：模型真实检索结果是否召回 supporting facts（支持事实）。
- `behavior`（行为）：证据充分时是否停止，证据不足时是否继续检索或增强查询。
- `cost`（成本）：是否重复检索、是否产生无效额外步骤、是否超过最大步数。

以下分项第一版不作为 GRPO（群组相对策略优化）主要训练信号：

- `answer`（答案）：当前 Planner（规划器）只决定进入答案终态，不直接生成答案正文。
- `citation`（引用）：可以保留为评测指标，但第一版不让它主导策略更新。

最终答案准确率由一个固定、冻结的 answer generator（答案生成器）在独立评测阶段计算，用于观察检索规划是否改善下游回答；不能把答案生成模型的波动错误归因给 Planner（规划器）。

### Reward（奖励分数）冻结流程

```text
公共 dev（开发集）案例
    -> 每条构造多条可执行正负 Action path（动作路线）
    -> Provider（动作执行器）真实执行
    -> 检查合理路线是否稳定高于错误路线
    -> 检查组内 Reward variance（奖励方差）
    -> 冻结权重、阈值、版本和 SHA256
    -> 之后才启动正式 Public-GRPO（公共数据群组相对策略优化）
```

不得使用公共 test（测试集）调整 Reward（奖励分数）权重或检索阈值。

## 数据规模

第一版采用逐级放大，不一开始处理数千条：

| 阶段 | 数量 | 用途 | 是否正式训练 |
|---|---:|---|---|
| feasibility probe（可行性探针） | 50 | 检查 Schema、真实检索、Reward 和许可证 | 否 |
| Public-SFT train（公共监督微调训练集） | 1000 | 学习严格 JSON、基本检索、继续/停止 | 是 |
| Public-GRPO prompt（公共群组相对策略优化问题） | 500 | 每条采样 4 个 rollout，共 2000 条 | 是 |
| public dev（公共开发集） | 200 | Reward 冻结、错误分析和训练前门禁 | 否 |
| public test（公共测试集） | 300 | Base/SFT/GRPO 最终盲测 | 否 |

第一版不承诺这些数字一定全部进入训练。经过许可证、重复、Schema（结构约束）、检索可执行性和来源门禁后，实际数量可以下降，但 manifest（清单）必须记录每类拒绝原因。

如果 500 条 GRPO prompt（群组相对策略优化问题）已经能提供稳定组内差异并完成方法比较，再扩展到 1000～2000 条；否则先修 Reward（奖励分数）或生成格式，不用数据量掩盖信号问题。

## 分阶段实施

### P0：50 条只读可行性探针

目标：证明公开数据可以无伪造地进入当前 Planner（规划器）链路。

工作：

1. 记录 HotpotQA 来源、许可证、文件 URL、版本、大小和 SHA256。
2. 只读取 50 条 train（训练集）样本，输出字段分布和异常矩阵。
3. 转换为临时 `PlannerEvalCase`（规划器评测案例），不写入正式训练目录。
4. 建立最小候选池检索 probe（探针），执行模型实际 query。
5. 检查 supporting facts（支持事实）是否可以映射成稳定公共 chunk（文本块）身份。
6. 构造至少一条成功召回、一条部分召回、一条空召回和一条重复检索轨迹。
7. 检查 Reward（奖励分数）排序是否符合预期。

完成门禁：

- 50 条均能通过来源和 Schema（结构约束）审计，或每条拒绝都有结构化原因。
- Provider（动作执行器）只使用实际 query，未读取 supporting facts（支持事实）控制返回结果。
- Observation（观察结果）能够稳定重放。
- 不需要修改冻结的 75 条领域训练数据。

停止条件：

- 数据许可证不能确认训练或再分发边界。
- supporting facts（支持事实）无法稳定映射到候选上下文。
- 必须用标准答案伪造 Observation（观察结果）才能得分。
- 当前 Schema（结构约束）无法在不破坏领域案例的前提下表达公共案例。

### P1：正式公共数据 recipe（转换规则）和冻结 Provider（动作执行器）

目标：把一次性 probe（探针）升级为可重复的数据入口。

交付：

- 公共来源 manifest（清单）。
- HotpotQA 转换 recipe（转换规则）。
- 确定性 document/chunk identity（文档/文本块身份）生成器。
- Frozen Public Provider（冻结公共动作执行器）。
- 公共 environment snapshot（环境快照）。
- 针对字段映射、split（拆分）、泄漏、检索和重放的最小测试。

门禁：

- 同一输入重复转换得到相同 SHA256。
- train/dev/test（训练集/开发集/测试集）之间没有 case_id 或 leakage_group_id（泄漏分组标识）重叠。
- Provider（动作执行器）不访问 test Gold（测试标准答案）。
- 只执行一次全量冻结，不边修边反复生成正式产物。

### P2：Public-SFT（公共数据监督微调）

目标：先解决严格 JSON 和基础动作行为，再进入 GRPO（群组相对策略优化）。

训练重点：

- `PlannerDecision.action/query/reason_code` 三字段严格 JSON。
- 初始检索、证据充分停止、证据不足增强查询。
- 不输出 `<think>`、解释文字或 JSON 之后的额外文本。
- 不重复执行同一检索动作。

进入 Public-GRPO（公共数据群组相对策略优化）前门禁：

- public dev（公共开发集）严格 JSON 合法率不低于 98%。
- 不存在系统性 `planner_output_invalid` 或 JSON 后附加文本。
- 非法动作转移率不高于 1%。
- Provider（动作执行器）契约失败为 0。
- checkpoint（训练检查点）可以重新加载并复现同一评测入口。

如果格式门禁未通过，只修 SFT（监督微调）数据或 decoding contract（解码契约），不通过增加 GRPO（群组相对策略优化）样本解决。

### P3：Public-GRPO（公共数据群组相对策略优化）

第一轮固定口径：

```text
500 个唯一 train-only prompt（仅训练问题）
每条 4 个 rollout（模型交互轨迹）
合计 2000 个 rollout
1 个完整 epoch（训练轮次）
真实 Frozen Public Provider（冻结公共动作执行器）
冻结 reference model（参考模型）
只更新 LoRA（低秩适配）参数
```

工程验收：

- 所有 Reward/advantage/policy loss/KL/total loss（奖励/相对优势/策略损失/策略偏移/总损失）均为有限数。
- 每个组恰好 4 条 rollout（模型交互轨迹）。
- reference model（参考模型）参数不变。
- LoRA（低秩适配）参数真实更新。
- optimizer/scheduler/RNG state（优化器/学习率调度器/随机数状态）可恢复。
- checkpoint（训练检查点）和 adapter（适配器）可重新加载。
- 未读取 public dev/test（公共开发集/测试集）或领域 heldout（留出集）。
- 组内 Reward variance（奖励方差）非零的 prompt 比例必须记录；如果大量组全同分，停止扩量并先修 Reward（奖励分数）。

### P4：公共独立测试和方法结论

使用完全相同的 public test（公共测试集）比较：

| 模型 | 用途 |
|---|---|
| Qwen3.5-4B Base（基础模型） | 原始能力基线 |
| Public-SFT（公共数据监督微调） | 判断 SFT 是否解决格式和基本路线 |
| Public-SFT+GRPO（公共数据监督微调加群组相对策略优化） | 判断 GRPO 是否带来额外策略提升 |

主要指标：

- `planner_decision_valid_rate`（规划器决策合法率）。
- `supporting_fact_recall_at_k`（支持事实召回率）。
- `correct_stop_rate`（证据充分时正确停止率）。
- `failed_retrieval_recovery_rate`（首次检索失败恢复率）。
- `duplicate_retrieval_rate`（重复检索率）。
- `mean_retrieval_steps`（平均检索步数）。
- `trajectory_success_rate`（轨迹成功率）。
- 固定答案生成器下的 answer EM/F1（答案精确匹配/F1），只作为下游评测指标。

方法结论门禁：

- 至少运行 3 个独立 GRPO seed（群组相对策略优化随机种子），或明确声明只是一轮探索性结果。
- 对主要指标报告 bootstrap confidence interval（自助法置信区间）。
- 只有 Public-SFT+GRPO（公共监督微调加群组相对策略优化）相对 Public-SFT（公共监督微调）在预先指定的主要指标上稳定提升，才写“GRPO 有效”。
- 如果提升只出现在 train/dev（训练集/开发集）或单个 seed（随机种子），结论写成“尚未证明稳定优于 SFT”。

### P5：设备运维领域迁移，后续阶段

公共主实验成立后，再比较：

```text
Domain-SFT V2（设备领域监督微调第二版）
Public-SFT（公共数据监督微调）
Public-SFT+GRPO（公共监督微调加群组相对策略优化）
Public-SFT+GRPO+Domain-SFT（公共策略训练后再做设备领域监督微调）
```

该阶段必须新建 20～30 条从未参与训练、Reward（奖励分数）调整、Prompt（提示词）调整或模型选择的设备领域 heldout（严格留出）案例。现有 75 条不能替代这套数据。

## 审核策略

公开数据有标准答案和支持事实，因此不需要像设备运维 Gold（标准案例）一样逐条人工编写，但仍需要分层审核：

1. 100% 自动检查：来源、许可证、Schema（结构约束）、ID、重复、split（拆分）、证据身份、指纹。
2. 100% 规则检查：supporting facts（支持事实）是否存在于候选上下文、标准答案是否为空、候选段落是否完整。
3. 抽样人工检查：第一版至少检查 50 条转换结果，覆盖成功、部分召回、空召回、查询增强和错误终止。
4. 高风险全审：转换异常、答案多义、支持事实缺失、同一问题跨 split（拆分）、检索结果和 Gold（标准证据）冲突。

自动转换通过不等于人工 Gold（标准案例）。manifest（清单）必须区分：

```text
source_verified
schema_validated
rule_validated
sample_reviewed
approved_for_sft
approved_for_grpo
```

## 预计难度和时间

这是单人、复用当前正式训练器、不做超参数搜索的工程估算：

| 工作 | 预计时间 | 主要风险 |
|---|---:|---|
| P0：50 条可行性探针 | 1～2 个工作日 | 字段和证据身份映射 |
| P1：正式 recipe、Provider 和数据冻结 | 3～5 个工作日 | 检索公平性、重放和 split 泄漏 |
| P2：1000 条 Public-SFT | 2～3 个工作日，加云端训练时间 | 严格 JSON 和额外文本 |
| P3：500×4 Public-GRPO | 2～4 个工作日，加云端训练时间 | Reward 方差和 GPU 成本 |
| P4：独立评测和报告 | 2～4 个工作日 | 多 seed 和统计置信度 |

完成一版可信公共主实验预计需要 2～4 周。公开数据可以显著减少人工编写问题和证据的工作，但不能省略环境、Reward（奖励分数）、数据隔离和评测适配。

## 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| R1-Searcher 公开文件不含可直接使用的完整 Planner 轨迹 | 无法零成本导入 SFT | 只参考方法；首版从 HotpotQA 原始 Gold 自动生成状态 |
| DeepResearch-9K 许可证不清晰 | 不能安全进入正式训练 | 在许可证确认前只做调研，不下载进正式流水线 |
| 公共任务动作空间较小 | 不能证明设备领域六动作全部有效 | 公共实验只证明通用检索/停止；领域动作仍由 75 条和未来 heldout 验证 |
| per-case distractor corpus（单案例干扰候选池）比全库容易 | 结果可能被夸大 | 报告明确实验设置；方法成立后再升级 fullwiki |
| Planner 输出仍有额外文本 | 大规模 GRPO 浪费 rollout | Public-SFT 先通过 98% JSON 门禁 |
| Reward 大量同分 | GRPO 没有有效相对优势 | 先做 dev 多轨迹排序与组内方差门禁，不直接扩量 |
| answer/citation 归因给 Planner | 训练信号被非策略能力污染 | 使用 Planner-pure Reward；最终答案单独评测 |
| 公共知识和设备知识发生遗忘 | 领域能力下降 | 公共和领域 adapter/训练阶段分开，对比后再决定混合或顺序训练 |
| 官方数据存在近重复或实体重叠 | 测试结果偏高 | 保留官方 split，并额外记录问题/实体/文档级泄漏报告 |

## 最终验收

公共主实验完成时必须同时回答：

1. 实际使用了哪个公开数据版本、许可证和 SHA256。
2. train/dev/test（训练集/开发集/测试集）各有多少唯一案例，是否存在泄漏。
3. Planner（规划器）实际开放了哪些 Action（动作），哪些动作没有被公共数据监督。
4. Provider（动作执行器）是否按模型实际 query 检索，是否读取 Gold（标准证据）影响返回结果。
5. Observation（观察结果）是否真实、冻结且可重放。
6. Reward（奖励分数）由哪些 Planner（规划器）可控分项组成，何时冻结。
7. Public-SFT（公共数据监督微调）是否通过严格 JSON 和动作合法性门禁。
8. Public-GRPO（公共数据群组相对策略优化）实际处理多少组和 rollout（模型交互轨迹）。
9. GRPO（群组相对策略优化）是否真实更新 LoRA（低秩适配）参数，reference model（参考模型）是否保持冻结。
10. Public-SFT+GRPO 是否在独立 public test（公共测试集）稳定优于 Public-SFT。
11. 结果是否来自多个 seed（随机种子），置信区间是否支持提升结论。
12. 是否读取或污染设备 heldout（领域留出集）、公共 dev/test（开发集/测试集）或历史候选池。
