# 阶段 3.5：用户维度导入历史隔离

## Summary

- 阶段 3 已经完成 document/task 元数据闭环，但它还是系统维度的状态记录。
- 阶段 3.5 要补上轻量用户维度：让前端用户刷新后能看到自己的导入历史，并避免用户之间互相看到导入记录和失败信息。
- 本阶段不做完整登录、注册、权限、组织、多租户，只做“当前用户拥有自己的 document/task”。
- 本阶段只做导入历史和状态查询隔离，不改变查询召回链路；查询内容隔离放到阶段 5，在阶段 4 的 chunk 用户字段落地后再实现。
- 当前 Mongo 和 Milvus 都是少量测试数据，不做历史数据回写和兼容迁移，可以删库重建。
- 字段设计预留 `tenant_id`、`visibility`，便于后续接入真实登录、多知识库权限和共享能力。

## 背景问题

阶段 3 解决的是：

```text
系统能记录 document/task 状态
系统能在 Mongo 中保存失败节点和错误信息
系统不再只依赖 task_utils 内存状态
```

但对普通前端用户来说，还存在几个产品问题：

- 刷新页面后，如果没有“我的导入历史”入口，用户仍然很难找回刚才失败的导入记录。
- 失败信息虽然更详细，但 `node_import_milvus`、`node_bge_embedding` 这类节点名对非开发人员价值有限。
- 如果所有用户共享同一个 document 列表，用户 B 看到用户 A 的失败记录会很奇怪。
- 后续阶段 4/5 如果只按 document/task 做状态管理，而不考虑用户维度，chunk 管理和查询召回会出现数据串扰风险。

所以阶段 3.5 的核心判断是：

```text
先做轻量用户隔离，不做完整权限系统。
```

## 目标

本阶段目标：

- 前端为匿名用户生成稳定 `user_id`。
- 后端从请求中解析当前用户。
- 新建 document/task 时写入 `owner_user_id`。
- 查询 document/task/status 时按 `owner_user_id` 过滤。
- 前端刷新后能展示当前用户自己的导入历史。
- 失败信息对普通用户展示友好摘要，技术细节保留在详情里。
- 保持现有查询召回逻辑不变，避免在 chunk 缺少用户字段时强行做查询隔离。

本阶段非目标：

- 不做账号密码登录。
- 不做 JWT 登录鉴权。
- 不做管理员角色。
- 不做 RBAC。
- 不做组织/租户管理后台。
- 不做 dataset 成员管理。
- 不做查询召回隔离。
- 不做历史数据迁移和旧数据兼容。
- 不做 Milvus 历史数据回写。

## 用户身份方案

### 第一版身份来源

前端首次访问导入页面时：

```text
localStorage.getItem("kb_user_id")
    -> 不存在则生成 user_xxx
    -> 写入 localStorage
```

注意：`user_id` 不是每次请求随机生成。

它应该是：

```text
首次访问生成一次
刷新页面继续复用
清空 localStorage 后才会变成新用户
测试时可以手动固定为 user_demo / user_a / user_b
```

后续请求统一带：

```http
X-User-Id: user_xxx
```

后端提供轻量解析函数，例如：

```text
get_current_user_id(request)
```

解析顺序：

```text
1. 读取 X-User-Id
2. 如果为空，使用 anonymous_user 或拒绝请求
```

建议本阶段采用“前端必须传 `X-User-Id`，后端缺失时返回 400”的策略。

原因是：如果后端自动把缺失用户都归到 `anonymous_user`，多个未带 header 的用户仍然会混到同一个历史列表里，反而掩盖问题。

### 后续升级路径

后续接入登录时，不需要推翻 document/task 结构：

```text
X-User-Id
    -> 替换为 JWT sub

owner_user_id
    -> 继续作为文档和任务归属字段
```

### user_id 和 session_id 的边界

`user_id` 和 `session_id` 不解决同一个问题。

| 字段 | 表示什么 | 适合做什么 |
|---|---|---|
| `user_id` | 用户身份或匿名用户归属 | 我的文档、我的导入历史、后续权限范围 |
| `session_id` | 一次对话会话 | 当前多轮问答上下文、一次聊天历史 |

因此阶段 3.5 的导入历史必须用 `user_id`，不能只用 `session_id`。

但聊天历史在当前阶段仍可以继续用 `session_id` 支撑多轮对话；“我的所有历史会话”放到阶段 7 管理 API 中处理，再把 `chat_message` 从仅按 `session_id` 升级为按 `user_id + session_id` 查询。

## 数据模型改造

### documents 新增字段

```text
owner_user_id: str
tenant_id: str
visibility: str
```

字段含义：

| 字段 | 当前阶段含义 | 后续扩展 |
|---|---|---|
| `owner_user_id` | 上传这份文档的用户 | 登录用户 ID |
| `tenant_id` | 暂时可为空或默认租户 | 多租户/组织隔离 |
| `visibility` | 默认 `private` | 支持 `private/shared/public` |

建议默认值：

```text
tenant_id = "tenant_default"
visibility = "private"
```

### tasks 新增字段

```text
owner_user_id: str
tenant_id: str
```

task 跟随 document 的用户归属。

### datasets 暂不强制改造

阶段 3 的默认 dataset 仍可保留：

```text
dataset_default_equipment_ops
```

本阶段暂时不做 dataset owner/members。

原因是：当前目标是“导入历史按用户隔离”，不是完整多知识库权限。dataset 级权限可以留到阶段 7 管理 API。

但为了后续阶段 4/5 不返工，document/task 先写 `tenant_id` 和 `visibility`。

## 查询隔离边界

阶段 3.5 不做查询召回隔离。

原因是当前 Milvus chunk 还没有稳定的：

```text
owner_user_id
visibility
document_id
dataset_id
```

如果现在强行按用户隔离查询，会出现两个问题：

- 很难在 Milvus 里可靠过滤当前用户的数据。
- 会影响现有查询测试和 demo 公共知识库测试。

所以阶段拆分为：

```text
阶段 3.5：document/task 导入历史按用户隔离
阶段 4：chunk 入库时写 owner_user_id / visibility / document_id
阶段 5：查询召回时按 public/shared + owner_user_id 做过滤
```

后续阶段 5 的理想召回范围是：

```text
可检索内容 =
    公共或共享文档
    +
    当前用户自己的私有文档
```

这样测试也更方便：

- 公共 demo 数据所有用户都能查。
- 用户私有上传内容只有自己能查。
- 用固定 `X-User-Id: user_a` / `user_b` 就能验证隔离。

## Repository 改造

`ImportMetadataRepository.create_import_metadata` 增加入参：

```text
owner_user_id
tenant_id = "tenant_default"
visibility = "private"
```

创建 document/task 时写入对应字段。

查询方法增加用户过滤：

```text
get_document(document_id, owner_user_id)
list_documents(dataset_id, owner_user_id, status, keyword, limit)
get_task(task_id, owner_user_id)
list_tasks(document_id, owner_user_id, limit)
```

建议行为：

- 查不到记录时返回 `{}`。
- 记录存在但 `owner_user_id` 不匹配时，也返回 `{}`。
- HTTP 层统一表现为 404，避免暴露“这个 ID 存在但不属于你”。

索引建议：

```text
documents:
  (owner_user_id, dataset_id, updated_at)
  (owner_user_id, document_id)
  (owner_user_id, status)

tasks:
  (owner_user_id, task_id)
  (owner_user_id, document_id, created_at)
```

## API 改造

### POST /upload

请求要求：

```http
X-User-Id: user_xxx
```

处理流程：

```text
1. 解析 owner_user_id
2. 创建 task_id/document_id
3. create_import_metadata 写入 owner_user_id/tenant_id/visibility
4. register_persistent_task 继续注册 task_id/document_id/dataset_id
5. 后台 invoke_graph 传入 owner_user_id
```

响应可以新增：

```text
owner_user_id
```

也可以不返回，前端本来就知道当前用户 ID。建议返回，便于调试和测试。

### GET /documents

请求要求：

```http
X-User-Id: user_xxx
```

只返回当前用户自己的 document。

支持原有筛选：

```text
dataset_id
status
keyword
limit
```

### GET /documents/{document_id}

只允许查看当前用户自己的 document。

行为：

```text
document 不存在 -> 404
document 存在但 owner_user_id 不匹配 -> 404
```

### GET /documents/{document_id}/tasks

先确认 document 属于当前用户，再返回这份 document 的 tasks。

或者直接按：

```text
document_id + owner_user_id
```

过滤 tasks。

### GET /status/{task_id}

优先读 Mongo 时按当前用户过滤：

```text
get_task(task_id, owner_user_id)
```

如果 Mongo 没有记录，再回退内存状态。

这里有一个边界：内存 `task_utils` 当前只按 task_id 存状态。如果没有 owner_user_id 校验，用户可能猜 task_id 查到别人的实时进度。

轻量方案建议：

- 对已持久化 task：必须 owner 匹配。
- 对 Mongo 未查到的 task：只允许查询当前页面刚上传后保存在前端内存里的 task，或者直接不回退内存。

更稳妥的选择是：

```text
阶段 3.5 中 /status/{task_id} 仍优先 Mongo；
如果 Mongo 查询失败才回退内存；
如果 Mongo 正常但查不到当前用户 task，不回退内存，直接返回空状态或 404。
```

这样可以降低 task_id 猜测带来的串扰风险。

## 前端改造

### 用户 ID 初始化

导入页面初始化：

```text
const userId = localStorage.getItem("kb_user_id") || generateUserId()
localStorage.setItem("kb_user_id", userId)
```

所有导入 API 请求带：

```http
X-User-Id: userId
```

### 我的导入记录

页面加载时调用：

```text
GET /documents
```

展示当前用户历史导入记录：

- 文件名
- 上传时间
- 状态
- 解析状态
- 索引状态
- chunk 数量
- 友好失败摘要
- 查看详情

### 失败信息友好化

不要把 `node_import_milvus` 直接作为主提示展示给非开发用户。

建议映射：

| failed_node | 用户主提示 |
|---|---|
| `upload_file` | 文件保存失败，请重新上传 |
| `node_entry` | 文件类型不支持或文件信息读取失败 |
| `node_pdf_to_md` | PDF 解析失败，请检查文件是否损坏或格式是否支持 |
| `node_md_img` | Markdown 图片处理失败 |
| `node_subject_name_recognition` | 文档主题识别失败 |
| `node_bge_embedding` | 文档向量化失败，请稍后重试 |
| `node_import_milvus` | 文档索引入库失败，请稍后重试 |
| 空或未知 | 导入失败，请稍后重试或联系管理员 |

详情区可以展示：

- `failed_node`
- `error_message`
- `task_id`
- `document_id`

## 对已完成阶段的影响

### 阶段 0

影响较小。

需要补充测试：

- 没有 `X-User-Id` 时 API 行为明确。
- 带不同 `X-User-Id` 时文档列表隔离。
- graph compile 仍不连接 Mongo。

### 阶段 1

`ImportGraphState` 建议新增：

```text
owner_user_id
tenant_id
visibility
```

节点仍然返回 partial state，不要把用户上下文散落到 service 内部临时拼接。

### 阶段 2

当前标准主题和别名索引仍按全局知识体系处理。

阶段 3.5 不要求标准主题 collection 按用户隔离。

需要明确边界：

```text
阶段 3.5 隔离导入历史和 document/task；
不完全隔离标准主题体系。
```

如果后续用户私有知识库需要强隔离，阶段 4/5 要把 chunk 检索按 `owner_user_id` 或 dataset 权限过滤。

### 阶段 3

影响最大。

阶段 3 的 document/task 元数据闭环要从系统维度升级成用户维度：

- document/task 创建时写 owner。
- document/task 查询时按 owner 过滤。
- 状态接口避免跨用户查询。
- 测试数据无需迁移，可以删库重建。

## 对后续阶段的影响

### 阶段 4

chunk 入库时必须带用户维度字段：

```text
owner_user_id
tenant_id
visibility
dataset_id
document_id
```

阶段 4 只要求 chunk 写入这些字段，为后续查询过滤准备数据；不要求立刻改变查询召回行为。

阶段 4 做 document_id 幂等时，也要注意删除/重建只能作用于当前用户有权限的 document。

### 阶段 5

查询检索在阶段 5 才正式增加权限过滤。

基础过滤条件从：

```text
dataset_id + subject_id + enabled=true
```

扩展为：

```text
dataset_id + subject_id + enabled=true + (visibility=public/shared 或 owner_user_id=当前用户)
```

这样既能保留公共 demo 知识库的测试便利性，又能避免用户 B 召回用户 A 的私有 chunk。

### 阶段 6

chunk 列表和启停 API 必须按用户过滤：

- 只能查看自己有权限的 chunk。
- 只能禁用自己有权限的 chunk。
- shared/public chunk 的编辑权限要等阶段 7 决定。

### 阶段 7

Dataset 和 Conversation 管理 API 需要正式接住用户/权限模型：

- dataset owner
- dataset members
- dataset visibility
- document owner
- shared/private/public 策略
- chat_message 增加 user_id
- 历史消息按 user_id + session_id 查询
- 当前用户会话列表
- 当前用户会话详情
- 收紧 `/status/{task_id}` 内存回退策略：只有 `task_utils` 中存在 `owner_user_id` 且与当前用户匹配时才返回内存状态；缺少 `owner_user_id` 或 owner 不匹配时返回 404，避免无归属内存任务被猜测查询。

阶段 3.5 的 `owner_user_id`、`tenant_id`、`visibility` 是阶段 7 的铺垫。

### 阶段 8

评测数据需要区分：

- 系统 demo 知识库评测。
- 用户私有知识库评测。

否则用户隔离会影响召回范围，导致评测结果难解释。

建议评测时使用固定测试用户：

```text
X-User-Id: user_eval
```

这样历史导入和私有召回范围稳定，不受浏览器随机用户影响。

## Test Plan

- Repository 测试：
  - 创建 document/task 时写入 `owner_user_id`。
  - `list_documents` 只返回当前用户记录。
  - `get_document` 不能读取其他用户文档。
  - `get_task` 不能读取其他用户任务。
- API 测试：
  - `POST /upload` 缺少 `X-User-Id` 返回明确错误。
  - 用户 A 和用户 B 上传后，`GET /documents` 互相隔离。
  - 用户 A 不能通过 `GET /documents/{document_id}` 查看用户 B 文档。
  - 用户 A 不能通过 `GET /status/{task_id}` 查看用户 B 任务。
- 前端轻量测试：
  - 首次访问生成 `kb_user_id`。
  - 刷新后仍使用同一个 `kb_user_id`。
  - 测试环境可以固定 `kb_user_id`，方便复现历史导入记录。
  - 文档列表能展示当前用户历史导入记录。
  - 失败节点能映射为友好提示。
- 回归测试：
  - `uv run pytest -q`

## Assumptions

- 当前没有生产数据，不做历史数据迁移。
- Mongo 和 Milvus 中的少量测试数据可以直接删库重建。
- 第一版用户 ID 来自前端 localStorage，不代表真实安全认证。
- 该方案解决的是“前端用户导入历史隔离”，不是完整权限安全方案。
- 该方案不解决查询召回隔离；查询隔离依赖阶段 4 的 chunk 用户字段，并在阶段 5 实现。
- 该方案不改造聊天历史模型；`chat_message` 的 `user_id + session_id` 维度放到阶段 7。
- 后续如果要面向真实多用户生产环境，必须接入正式认证和服务端签发的用户身份。
