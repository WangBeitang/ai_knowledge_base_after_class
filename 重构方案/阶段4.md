# 阶段 4：导入链路重构

## 背景与目标

阶段 3 已经补齐了 dataset/document/task 的 Mongo 元数据闭环，阶段 3.5 已经引入轻量用户维度，让导入历史和任务状态能按 `owner_user_id` 隔离。

但当前导入链路仍然存在几个关键短板：

- Milvus chunk 仍主要依赖 `file_title` 做旧数据清理，同名文件、重复导入、不同用户上传同名文档时容易互相影响。
- chunk 还没有稳定写入 `dataset_id`、`document_id`、`owner_user_id`、`tenant_id`、`visibility` 等字段，阶段 5 无法可靠做查询权限过滤。
- 图片增强使用 Markdown 文件名作为 MinIO 前缀，重复导入或同名文件可能覆盖图片资源。
- 文档删除、重建索引还没有形成稳定闭环，导入后的数据生命周期不可控。

阶段 4 的目标是让导入链路真正围绕 document 运转：

```text
entry -> pdf_to_md -> image_enrich -> split -> subject_recognition -> embedding -> index
```

本阶段完成后，应满足：

- 同一个 document 重复入库不会产生脏 chunk。
- 删除 document 后，相关 chunk 不会继续被查询召回。
- 重建索引能追踪版本，并且只作用于当前用户有权限的 document。
- chunk 写入用户归属和可见性字段，为阶段 5 查询过滤准备数据。

## 改造边界

本阶段要做：

- 改造导入链路的 document/index 元数据。
- 改造 PDF/MinerU、Markdown 图片增强、chunk 入库产物记录。
- 改造 Milvus chunk schema 和入库数据结构。
- 把入库幂等从 `file_title` 切换到 `document_id`。
- 补齐文档删除和重建索引的后端能力。
- 前端只补轻量操作入口，不做完整管理台。

本阶段不做：

- 不做查询召回权限过滤；查询过滤放到阶段 5。
- 不做完整登录、权限、RBAC、多租户管理。
- 不做 Dataset 管理 API；放到阶段 7。
- 不做 Chunk 列表、启停、编辑；放到阶段 6。
- 不做历史数据迁移；当前 Mongo/Milvus 测试数据可以删库或删集合重建。
- 不改变标准主题和别名 collection 的全局管理策略。

## 具体改造任务

### 1. 固化 document/index 元数据契约

目标：让 document 能表达当前索引版本、删除状态和导入产物位置，作为删除、重建和后续查询过滤的基础。

细分任务：

- `documents` 增加索引生命周期字段：
  - `index_version`：当前 document 的索引版本，首次导入为 `1`。
  - `deleted_at`：文档被删除的时间，未删除时为空。
  - `image_prefix`：当前 document 在 MinIO 中的图片对象前缀。
  - `parse_result_zip_path`：MinerU 解析结果 zip 本地路径。
  - `parse_result_dir`：MinerU 解析结果解压目录。
- `ImportGraphState` 增加 `index_version`，并在导入图启动时写入。
- 普通上传仍创建新的 `document_id`，默认 `index_version=1`。
- 重建索引复用原 `document_id`，新建 task，并将 `index_version` 递增。
- `tasks.task_type` 继续支持 `import`，新增 `rebuild_index`。
- 保持节点返回 partial state 的既有约定，不把完整 state 到处传递。

验收重点：

- document 详情能看到当前 `index_version`。
- 重建索引不会创建新的 document，只会创建新的 task。
- 删除状态由 Mongo document 表达，不依赖内存状态。

### 2. 记录 PDF/MinerU 与图片增强产物

目标：让解析产物和图片资源都挂到 document 下，避免同名文件或重复导入互相覆盖。

细分任务：

- PDF/MinerU 解析完成后，回写 document：
  - `md_path`
  - `parse_result_zip_path`
  - `parse_result_dir`
  - `parse_status`
- Markdown 直接导入时，也要稳定回写 `md_path` 和 `parse_status`。
- MinIO 图片前缀从文件 stem 改为 document 维度，例如：

```text
images/{document_id}/...
```

- 图片增强上传前，只清理当前 `document_id` 对应的旧图片前缀。
- 图片增强完成后，回写 document：
  - `image_prefix`
  - 增强后的 `md_path`
- 图片 URL 仍写入 Markdown 正文，后续 chunk 中的 `content` 可以保留图片说明和图片链接。

验收重点：

- 用户 A 和用户 B 上传同名 Markdown/PDF，图片资源不会互相覆盖。
- 没有图片目录或图片为空时，导入仍能正常进入切分和入库。

### 3. 重构 chunk 元数据与 Milvus schema

目标：chunk 从“文件标题维度的数据”升级为“document 维度、可权限过滤、可版本追踪的数据”。

细分任务：

- Milvus chunk collection 显式增加字段：
  - `dataset_id`
  - `document_id`
  - `owner_user_id`
  - `tenant_id`
  - `visibility`
  - `index_version`
  - `chunk_index`
  - `enabled`
  - `source_title`
- 保留已有字段：
  - `file_title`
  - `title`
  - `parent_title`
  - `part`
  - `content`
  - `subject_id`
  - `standard_subject_name`
  - `equipment_model`
  - `alarm_code`
  - `part_name`
  - `sop_type`
  - `safety_level`
  - `maintenance_stage`
  - `dense_vector`
  - `sparse_vector`
- 入库前统一补齐 chunk 元数据：
  - `dataset_id` 来自 state。
  - `document_id` 来自 state。
  - `owner_user_id` 来自 state。
  - `tenant_id` 默认 `tenant_default`。
  - `visibility` 默认 `private`。
  - `index_version` 来自 state。
  - `chunk_index` 按最终 chunks 顺序从 `0` 递增。
  - `enabled` 默认 `true`。
  - `source_title` 使用当前 `file_title`。
- `file_title` 只保留为展示和兼容字段，不再作为幂等删除条件。
- 当前 Milvus 测试集合可删除重建，不做旧 schema 在线兼容。

验收重点：

- 新入库 chunk 都带完整 document/user/visibility 字段。
- 新入库 chunk 都有稳定 `chunk_index`。
- 阶段 5 可以直接基于这些字段追加查询过滤表达式。

### 4. 改造按 document 维度的幂等入库

目标：把旧的 `file_title` 幂等改为 `document_id` 幂等，保证同一 document 重复入库不会残留旧 chunk。

细分任务：

- `index_chunks` 入库流程调整为：

```text
prepare_chunks_collection
-> delete chunks by document_id
-> normalize chunk metadata
-> insert chunks
-> write chunk_id back to state
-> update document index metadata
```

- 删除旧 chunk 时使用：

```text
document_id == 当前 document_id
```

- 插入成功后回写 document：
  - `index_status=completed`
  - `status=completed`
  - `chunk_count`
  - `subject_id`
  - `standard_subject_name`
  - `index_version`
- 如果入库失败，由现有失败收口逻辑标记 task/document failed。
- 重建索引时，先删除当前 document 的旧 chunk，再插入新 chunk。
- 如果重建失败，旧 chunk 已经被删除，避免继续召回过期内容。

验收重点：

- 同一个 `document_id` 多次入库后，Milvus 中只保留最新版本 chunk。
- 不同用户上传同名文件，互不删除对方 chunk。
- 不同 document 的同名 `file_title` 不互相影响。

### 5. 补齐文档删除与重建索引能力

目标：形成“导入后可查、可删、可重建”的最小闭环，并保证操作只能作用于当前用户自己的 document。

细分任务：

- 新增删除文档 API：

```http
DELETE /documents/{document_id}
X-User-Id: user_xxx
```

- 删除流程：
  - 按 `document_id + owner_user_id` 查询 document。
  - 查不到或 owner 不匹配时返回 404。
  - 删除 Milvus 中当前 document 的 chunk。
  - 删除或清理当前 document 的 MinIO 图片前缀。
  - Mongo document 标记为 `status=deleted`，写入 `deleted_at`。
  - 不物理删除 Mongo document 和 task，保留审计和历史排查能力。
- `GET /documents` 默认不返回 `status=deleted` 的记录。
- 显式传 `status=deleted` 时，可以查看当前用户自己的删除历史。
- 新增重建索引 API：

```http
POST /documents/{document_id}/rebuild
X-User-Id: user_xxx
```

- 重建流程：
  - 按 `document_id + owner_user_id` 查询 document。
  - document 不存在、owner 不匹配、已删除、原始文件不存在时拒绝重建。
  - 创建新的 task，`task_type=rebuild_index`。
  - `latest_task_id` 更新为新 task。
  - `index_version` 递增。
  - 使用原 `file_path/local_dir` 或新的重建工作目录重新执行导入图。
- 删除和重建都不允许跨用户操作。

验收重点：

- 删除 document 后，当前查询链路不会召回该 document 的旧 chunk。
- 用户 A 不能删除或重建用户 B 的 document。
- 重建后 document_id 不变，task_id 改变，index_version 递增。

### 6. 补测试、前端轻量入口与验收标准

目标：用测试锁住阶段 4 的关键契约，并给演示页面补最小可用操作入口。

细分任务：

- Repository 测试：
  - 创建 document 默认写 `index_version=1`。
  - 重建索引时递增 `index_version`。
  - 删除 document 写 `status=deleted` 和 `deleted_at`。
  - owner 不匹配时删除和重建都返回不可见。
- Index service 测试：
  - chunk 入库前补齐阶段 4 元数据。
  - 删除旧 chunk 使用 `document_id` filter。
  - 不再使用 `file_title` 删除旧 chunk。
  - insert 后正确回写 `chunk_id`。
- API 测试：
  - `DELETE /documents/{document_id}` 缺少 `X-User-Id` 返回 400。
  - 用户 A 删除用户 B document 返回 404。
  - 删除成功后文档列表默认不显示该 document。
  - `POST /documents/{document_id}/rebuild` 用户隔离正确。
  - 重建成功返回新 task_id，并保持 document_id 不变。
- 前端轻量入口：
  - 文档记录中增加删除按钮。
  - 文档记录中增加重建索引按钮。
  - 操作请求都携带 `X-User-Id`。
  - 删除或重建成功后刷新“我的导入记录”。
  - 失败时展示友好提示，技术详情仍放到详情区。
- 回归测试：

```bash
uv run python -m pytest
```

最终验收标准：

- 同一文档重复导入不会产生脏数据。
- 删除文档后查询不会召回旧 chunk。
- 文档重建索引后 chunk 版本可追踪。
- chunk 能保留用户归属和可见性字段。
- 用户不能删除或重建其他用户的文档。

## 接口与数据契约变化

### Document 元数据

`documents` 新增或明确以下字段：

```text
index_version: int
deleted_at: str
image_prefix: str
parse_result_zip_path: str
parse_result_dir: str
```

其中：

- `index_version` 首次导入为 `1`。
- `deleted_at` 未删除时为空字符串。
- `image_prefix` 指向 document 维度的 MinIO 图片前缀。
- `parse_result_zip_path` 和 `parse_result_dir` 主要用于 PDF/MinerU 解析产物追踪。

### Task 元数据

`tasks.task_type` 支持：

```text
import
rebuild_index
```

### ImportGraphState

新增：

```text
index_version: int
```

已有并继续贯穿导入链路：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
```

### Milvus Chunk 字段

chunk collection 新增：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
index_version
chunk_index
enabled
source_title
```

### API

新增：

```http
DELETE /documents/{document_id}
POST /documents/{document_id}/rebuild
```

已有接口调整：

- `GET /documents` 默认排除 `status=deleted`。
- `GET /documents?status=deleted` 返回当前用户自己的删除历史。
- `GET /documents/{document_id}` 对当前 owner 可返回 deleted document 详情，对其他用户仍返回 404。

## 测试与验收标准

建议新增测试文件或扩展现有测试：

- `tests/test_import_metadata_repository_stage4.py`
- `tests/test_import_index_service_stage4.py`
- `tests/test_import_api_stage4.py`
- `tests/test_import_frontend_stage4.py`

关键场景：

- 创建 document 时默认 `index_version=1`。
- 重建索引时 `index_version` 递增。
- chunk 入库数据包含阶段 4 全量元数据字段。
- `remove_old_chunks` 按 `document_id` 删除，而不是按 `file_title` 删除。
- 删除 document 后，Milvus 删除 filter 使用当前 document_id。
- 用户 A 不能删除或重建用户 B 的 document。
- 文档列表默认隐藏 deleted document。
- 前端删除和重建请求都携带 `X-User-Id`。

全量回归：

```bash
uv run python -m pytest
```

阶段 4 完成后的验收结论应能明确回答：

- 这份 document 当前索引版本是多少。
- 这份 document 对应哪些 chunk。
- 删除这份 document 后，旧 chunk 是否已经不可召回。
- 重建这份 document 后，新旧索引版本是否可追踪。
- 当前 chunk 是否已经带上阶段 5 查询权限过滤所需字段。

## 明确假设

- 本阶段只设计和实现导入链路重构，不实现阶段 5 的查询权限过滤。
- 当前 Mongo 和 Milvus 没有生产数据，不做历史数据迁移。
- Milvus chunk collection 可以删除重建，以便启用新的显式 schema。
- 文档删除采用 Mongo 软删除、Milvus chunk 硬删除。
- 同名文件再次上传仍创建新 document；只有重建索引才复用原 `document_id`。
- 标准主题和别名 collection 仍是全局知识体系，不按用户隔离。
- 前端只补轻量操作入口，不做完整管理台。
- 如果后续接入真实登录，`owner_user_id` 可替换为 JWT 中的用户 ID，阶段 4 的 chunk 字段不需要推翻。
