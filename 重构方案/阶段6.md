# 阶段 6：Chunk 可观测与启停

## 背景与目标

阶段 4 已经把 chunk 从“按文件标题清理”升级为“按 document 管理”，并在 Milvus chunk collection 中写入：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
index_version
chunk_index
enabled
source_title
```

阶段 5 已经让查询侧强制使用 `enabled == true`，并补齐了 Planner、Observation、Trace、Citation 和三路召回评测。也就是说，系统已经具备“只检索启用 chunk”的查询底座，但还缺少人工查看、禁用、恢复和审计能力。

阶段 6 的目标是学习 RAGFlow 的 chunk 可视化和人工干预能力，但第一版保持轻量：

- 能按 document 查看当前版本 chunk。
- 能查看 chunk 标题、顺序、正文预览、来源元数据和启用状态。
- 能人工禁用低质量 chunk，例如解析错误、页眉页脚、乱码、内容过期和人工误判。
- 禁用后查询不再召回该 chunk。
- 能恢复误禁用的 chunk。
- 能审计每次启停的操作人、时间、原因和关联版本。
- Retrieval Trace 能说明候选 chunk 是否启用、来自哪个召回 Action、是否进入 rerank、是否成为最终引用。

本阶段不做复杂编辑，也不改 chunk 正文和向量。

## 当前实现基线

需要以以下事实为改造起点：

- `app/rag/import_/index_service.py` 建立的 chunk schema 中，`chunk_id` 是 Milvus `INT64 auto_id primary key`，`enabled` 是 `BOOL`，入库默认 `true`。
- `normalize_chunk_document_fields` 已经按 `document_id + index_version + chunk_index` 回填 document 维度元数据。
- `remove_old_chunks(document_id)` 会按 document 清理旧 chunk，重建索引后旧 chunk 不应继续存在。
- `app/rag/query/chunk_retrieval_utils.py` 的 `build_chunk_access_filter` 已经强制拼入 `enabled == true`，同时按 dataset、public/shared/owner 可见性过滤。
- `CHUNK_OUTPUT_FIELDS` 已包含 `enabled`，但 `format_chunk_search_item` 目前没有把 `enabled` 放进 `RetrievalCandidate`。
- `RetrievalCandidate` 当前保留 document/chunk/dataset/index 身份、召回来源、RRF 分和 rerank 分，但没有显式保存当前 enabled 状态。
- `RetrievalTrace.channel_hits` 当前保存 channel、document_id、chunk_id、index_version、rank、retrieval_score、rerank_score、matched_identifiers 和正文 hash，但还不能直接表达 `enabled`、是否进入 rerank、是否成为 citation。
- 导入服务 `app/api/http/import_server.py` 已有 document 列表、详情、任务历史、删除和重建 API，但没有 chunk 管理 API。
- `app/infra/persistence/import_metadata_repository.py` 管理 Mongo 中的 datasets/documents/tasks，当前没有 chunk 启停审计集合。
- 本地 `pymilvus.MilvusClient` 没有 `update` 方法，只有 `upsert`、`delete`、`query`、`get`、`insert`。阶段 6 实施前必须验证 auto_id 主键 collection 能否安全 upsert 同一个 `chunk_id`，不能假设可以原地只改 `enabled`。

## 改造边界

### 本阶段要做

- 新增 chunk 管理数据契约和 API 响应模型。
- 新增 chunk 列表、详情、启用、禁用和启停历史 API。
- 新增 chunk 管理 service，统一处理权限、版本校验、状态变更和审计。
- 新增 Mongo `chunk_status_events` 审计集合。
- 明确 Milvus `enabled` 更新路线，硬约束是不能改变已有 `chunk_id`。
- 为 chunk 管理构建专用可见性过滤，不复用会强制 `enabled == true` 的检索过滤。
- 查询侧继续保证禁用 chunk 不参与召回。
- 扩展 `RetrievalCandidate` 和 `TraceChannelHit` 的可观测字段。
- 补充单元测试、API 测试、Trace 测试和禁用后不召回的查询测试。
- 同步 `docs/数据字典.md`，记录新增集合、API、枚举和字段含义。

### 本阶段不做

- 不修改 chunk 正文。
- 不重新向量化。
- 不做 chunk 合并、拆分、重排、相邻片段扩展。
- 不做 RAGFlow 式 parser/chunk 模板编辑。
- 不做完整管理台和复杂权限后台。
- 不决定 shared/public chunk 的最终编辑和启停权限策略，阶段 6 只给出保守边界。
- 不把禁用记录直接作为 GRPO reward。
- 不保存模型私有思维链，不在 Trace 中保存完整 chunk 正文。
- 不做历史 Milvus 数据在线迁移、双写 backfill 或灰度迁移。

## 核心设计决策

### 1. 当前启停状态和审计历史分开存储

`enabled` 表示 chunk 当前是否允许参与检索。它是查询过滤需要读取的状态。

启停历史不能塞进 Milvus chunk 记录。Milvus 适合向量检索和当前标量过滤，不适合保存不断增长的审计数组。因此阶段 6 新增 Mongo 集合：

```text
chunk_status_events
```

一条 event 表示一次启用或禁用操作。event 的中文含义是“事件记录”，用于审计和后续评测数据筛选。

### 2. 不允许通过删除重插来实现启停

当前 `chunk_id` 是 Citation、Trace、评测和人工标注共同引用的核心 ID。如果为了改 `enabled` 删除旧 row 再插入新 row，会导致：

- 新 chunk_id 改变。
- 旧 Trace 和新 chunk 状态无法稳定关联。
- 用户基于旧 chunk_id 做的质量标注可能套错版本。
- 禁用操作变相修改了索引产物。

所以阶段 6 的硬约束是：启停不能改变 `chunk_id`。

### 3. Milvus 状态更新先做验证，再选路线

阶段 6 开始实现时，第一步必须做一个小型验证：

```text
auto_id primary key collection
-> insert chunk
-> upsert same chunk_id with enabled=false
-> query same chunk_id
-> 确认 chunk_id 不变且 enabled 变更
```

验证结果决定最终落地路线：

| 路线 | 条件 | 当前状态来源 | 查询过滤方式 | 说明 |
|---|---|---|---|---|
| A：Milvus 直接更新 | `upsert` 能安全保持 auto_id `chunk_id` | Milvus `enabled` | 继续使用 `enabled == true` | 首选路线，最贴合阶段 4/5 的 schema 设计。 |
| B：Mongo 覆盖状态 | `upsert` 不能保证不改变 `chunk_id` | Mongo `chunk_status_overrides` | `enabled == true AND chunk_id not in [...]` | 降级路线，保留原始 Milvus row，不删除重插。 |

无论选择哪条路线，`chunk_status_events` 都必须写入。路线 B 是技术兜底，不应先于验证直接采用。

任务 1 已在当前环境完成验证，结论是选择路线 B。验证发现：

- 普通 `upsert` 只传 `chunk_id + enabled` 会报缺少其它必填字段，不能当作局部字段更新。
- `upsert(..., partial_update=True)` 能改变 `enabled`，但在 auto_id 主键 collection 上没有保留原 `chunk_id`；原 ID 查询不到记录，按 `document_id` 查询到的是新 `chunk_id`。
- 完整 entity upsert 同样不能作为阶段 6 启停方案，因为它不能满足“启停不改变 `chunk_id`”这个硬约束。

因此阶段 6 实现时不要写 Milvus `set_chunk_enabled` 原地更新逻辑；应保留 Milvus 原始 chunk 不动，把当前启停覆盖状态写入 Mongo `chunk_status_overrides`，查询时在原有 `enabled == true` 之外追加禁用 chunk 排除条件。

### 4. 管理过滤不能复用检索过滤

查询检索需要强制 `enabled == true`。但 chunk 管理页必须能看到 disabled chunk，否则用户无法恢复误禁用数据。

因此需要新增管理过滤构造器，例如：

```text
build_chunk_management_filter(
    dataset_id,
    document_id,
    owner_user_id,
    tenant_id,
    enabled=None | true | false,
)
```

它只表达 dataset、document、index_version、public/shared/owner 可见性和可选 enabled 条件，不默认排除 disabled chunk。

原有 `build_chunk_access_filter` 继续服务查询召回，保持 `enabled == true` 的硬过滤。

### 5. 列表可见范围和操作权限分开

阶段 5 的轻量可见性语义是：

```text
private -> 仅 owner 可见
public  -> 所有当前查询用户可见
shared  -> 同一 tenant 内可见
```

阶段 6 先沿用这套可见性做 chunk 列表和详情读取。

启用/禁用操作更敏感。由于 shared/public 的编辑和启停权限策略明确留到阶段 7，阶段 6 采用保守规则：

- private chunk：只允许 `owner_user_id == 当前用户` 操作。
- public/shared chunk：当前用户可见，但第一版不开放非 owner 启停。
- 非 owner 操作返回 403，不暴露其他用户私有文档是否存在。

阶段 7 引入 dataset members 或更完整权限后，再扩展 shared/public 的操作授权。

### 6. 以 `document_id + chunk_id + index_version` 绑定人工标注

单独保存 `chunk_id` 不够。重建索引后，同一 document 可能产生新的 chunk 序列，旧人工标注不能套到新版本。

所有启停事件、Trace 命中、评测弱标签都必须同时保存：

```text
document_id
chunk_id
index_version
```

如果前端从旧页面发起启停请求，body 中的 `expected_index_version` 与当前 document 或目标 chunk 不一致时，API 返回 409，要求刷新后再操作。

### 7. 禁用记录只是弱质量信号

chunk 禁用记录能帮助阶段 8 做检索评测和训练数据筛选，例如排除乱码、页眉页脚、解析错误 chunk。

但它不能直接等价为 GRPO reward。原因是：

- 用户可能误禁用。
- 禁用原因可能只针对某个查询场景，不代表该 chunk 永久无用。
- 自动脚本产生的禁用候选未经人工确认。

因此 event 需要记录 `source` 和 `human_confirmed`：

- `source=manual` 且 `human_confirmed=true`：可作为高可信弱标签候选。
- `source=system` 或 `human_confirmed=false`：只能作为待复核候选。

阶段 8 数据构建工具可以读取这些记录，但需要继续按评测任务规则筛选。

## 数据契约

### 新增 Mongo 集合：chunk_status_events

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `event_id` | string | 启停事件 ID | UUID，Mongo 唯一索引。 |
| `document_id` | string | 关联文档 ID | 必填。 |
| `chunk_id` | string/int | Milvus chunk 主键 | 必填，按实际类型保存。 |
| `dataset_id` | string | 所属知识库 | 从 chunk 或 document 投影。 |
| `owner_user_id` | string | chunk 所属用户 | 从 chunk 或 document 投影，不等同于操作者。 |
| `tenant_id` | string | 租户范围 | 当前通常为 `tenant_default`。 |
| `visibility` | string | chunk 可见性 | 记录操作发生时快照。 |
| `index_version` | int | 文档索引产物版本 | 防止旧版本标注误套新版本。 |
| `chunk_index` | int | document 内顺序 | 用于人工排查。 |
| `operator_user_id` | string | 操作人用户 ID | 来自 `X-User-Id`。 |
| `operation` | enum | `enable` 或 `disable` | 启用或禁用。 |
| `previous_enabled` | bool | 操作前状态 | 用于审计和幂等判断。 |
| `enabled` | bool | 操作后状态 | `disable` 对应 false，`enable` 对应 true。 |
| `reason_type` | enum | 机器可读原因类型 | 必填。 |
| `reason_detail` | string | 人工补充说明 | 可为空，最长建议 500 字符。 |
| `source` | enum | 事件来源 | 第一版 API 写 `manual`。 |
| `human_confirmed` | bool | 是否人工确认 | 第一版手动 API 写 true。 |
| `created_at` | ISO datetime string | 操作时间 | UTC ISO 字符串。 |
| `trace_id` | nullable string | 可选关联 Trace | 从 Trace 页面触发时可写，普通文档页为空。 |

建议索引：

```text
unique(event_id)
(document_id, chunk_id, index_version, created_at desc)
(operator_user_id, created_at desc)
(reason_type, created_at desc)
```

### 路线 B Mongo 集合：chunk_status_overrides

Milvus auto_id + upsert 验证失败后启用，用来保存“人工覆盖层”的当前状态。这里不再复用
`enabled` 作为主要字段，避免和 Milvus 原始 `enabled` 产生“Milvus=true、Mongo=false”
的语义混淆；实际实现使用 `manual_status` 表达人工判断层。

| 字段 | 类型/形态 | 含义 |
|---|---|---|
| `document_id` | string | 文档 ID。 |
| `chunk_id` | string/int | Milvus chunk ID。 |
| `index_version` | int | 文档索引版本。 |
| `dataset_id` | string | 所属知识库，用于查询侧按范围取禁用 ID。 |
| `owner_user_id` | string | chunk 所属用户，不等同于操作人。 |
| `tenant_id` | string | 租户范围，用于 shared 可见性过滤。 |
| `visibility` | string | 操作发生时的可见性快照。 |
| `manual_status` | enum | `disabled` 表示人工禁用；`enabled` 表示人工恢复；`none` 表示无覆盖。 |
| `latest_event_id` | string | 最近一次启停事件。 |
| `updated_at` | ISO datetime string | 状态更新时间。 |

主要索引：

```text
unique(document_id, chunk_id, index_version)
dataset_id, manual_status
owner_user_id, dataset_id, manual_status
document_id, index_version, manual_status
```

路线 B 查询侧只读取 `manual_status=disabled` 的记录，并继续保留 Milvus 原始
`enabled == true` 过滤，避免人工恢复覆盖错误地打开基础索引已经禁用的 chunk。

### 启停原因枚举

新增 `ChunkStatusReasonType`，每个枚举成员都需要中文注释。

| 枚举值 | 中文含义 | 典型场景 |
|---|---|---|
| `parse_error` | 解析错误 | PDF 转 Markdown 后段落错乱、表格丢列、图片说明错位。 |
| `header_footer` | 页眉页脚 | 重复页码、公司页眉、页脚版权信息被切成 chunk。 |
| `garbled_text` | 乱码 | OCR 或编码导致正文不可读。 |
| `outdated_content` | 内容过期 | 旧版 SOP、旧报警说明、已废弃操作流程。 |
| `human_misjudgment` | 人工误判 | 之前禁用错了，或人工确认该 chunk 不该作为坏样本。 |
| `manual_restore` | 人工恢复 | 恢复一个被禁用但仍有价值的 chunk。 |
| `other` | 其他原因 | 需要人工说明补充。 |

约束：

- 禁用时 `reason_type` 必填，优先使用前五类。
- 启用时 `reason_type` 必填，通常使用 `manual_restore` 或 `human_misjudgment`。
- `other` 必须填写 `reason_detail`。

## API 设计

所有接口都要求 `X-User-Id`。缺失或空白时返回 400，沿用阶段 3.5/5 的用户上下文策略。

### 1. 查询当前用户可见 chunk 列表

```http
GET /chunks?dataset_id=dataset_default_equipment_ops&document_id=doc_xxx&enabled=all&limit=100
X-User-Id: user_xxx
```

说明：

- `dataset_id` 默认使用当前默认知识库。
- `document_id` 可选；传入时只看该 document 当前版本 chunk。
- `enabled` 支持 `all`、`true`、`false`，默认 `all`。
- 路线 B 下，API 的 `enabled` 按 `effective_enabled` 过滤；也就是先叠加 Mongo
  `manual_status`，再判断最终是否可被查询召回。
- 第一版不做全文搜索和复杂排序，按 `document_id + index_version + chunk_index` 排序。
- 返回字段不包含向量和 `lexical_text`。

响应核心字段：

```json
{
  "code": 200,
  "items": [
    {
      "chunk_id": 1001,
      "document_id": "doc_xxx",
      "dataset_id": "dataset_default_equipment_ops",
      "index_version": 3,
      "chunk_index": 12,
      "enabled": true,
      "title": "报警 E021 处理",
      "parent_title": "故障排查",
      "source_title": "HAK 180 操作手册",
      "content_preview": "E021 表示...",
      "content_length": 327,
      "subject_id": "sub_xxx",
      "standard_subject_name": "HAK 180 烫金机",
      "equipment_model": "HAK 180",
      "alarm_code": "E021",
      "latest_event": null
    }
  ]
}
```

### 2. 按 document 查看 chunk

```http
GET /documents/{document_id}/chunks?enabled=all&limit=100
X-User-Id: user_xxx
```

这是 `GET /chunks` 的文档维度便捷入口。

行为：

- 先按 document 可见性校验用户是否能查看。
- 默认只展示 document 当前 `index_version` 的 chunk。
- document 不存在、已删除或不可见时返回 404。

### 3. 查看 chunk 详情

```http
GET /documents/{document_id}/chunks/{chunk_id}
X-User-Id: user_xxx
```

详情接口可以返回完整 `content`，但仍不返回向量字段。

用途：

- 人工判断是否页眉页脚、乱码、解析错误。
- 后续前端弹层展示完整正文。

### 4. 启用或禁用 chunk

```http
PATCH /documents/{document_id}/chunks/{chunk_id}/enabled
X-User-Id: user_xxx
Content-Type: application/json

{
  "enabled": false,
  "expected_index_version": 3,
  "reason_type": "header_footer",
  "reason_detail": "重复页脚，和设备维修内容无关"
}
```

行为：

- 校验 document 属于或可见于当前用户。
- 校验目标 chunk 属于该 document 当前 `index_version`。
- 校验当前用户是否有操作权限。阶段 6 第一版只允许 owner 操作。
- 如果 `expected_index_version` 与当前 document 或 chunk 不一致，返回 409。
- 如果目标状态与当前状态相同，返回当前状态，不重复写 event，避免审计噪声。
- 状态改变成功后写入 `chunk_status_events`。

### 5. 查看 chunk 启停历史

```http
GET /documents/{document_id}/chunks/{chunk_id}/events?limit=20
X-User-Id: user_xxx
```

行为：

- 只返回当前用户可见范围内的事件。
- 非 owner 可以查看可见 chunk 的事件摘要，但阶段 6 不开放非 owner 修改。
- 事件按 `created_at desc` 返回。


字段和枚举要写清楚中文含义，尤其是 `Trace`、`reason_type`、`index_version`、`human_confirmed` 这类后续会进入评测和训练数据的字段。

### 2. Milvus gateway

扩展：

```text
app/infra/vectorstore/milvus_gateway.py
```

新增方法建议：

```python
query_chunks(filter_expr, output_fields, limit)
get_chunk_by_id(chunk_id, output_fields)
set_chunk_enabled(chunk_id, enabled, full_entity=None)
```

注意：

- `query_chunks` 和 `get_chunk_by_id` 默认不返回向量。
- 如果路线 A 成立，`set_chunk_enabled` 内部封装 upsert，不让业务层直接操作 Milvus 细节。
- 如果路线 A 不成立，`set_chunk_enabled` 不实现删除重插，转由 service 调用 Mongo override 路线。

### 3. Chunk status repository

新增文件：

```text
app/infra/persistence/chunk_status_repository.py
```

职责：

- 创建 `chunk_status_events` 索引。
- 写入启停事件。
- 查询某个 chunk 的事件历史。

## 查询链路改造

### 1. RetrievalCandidate 增加 enabled

在 `app/rag/query/contracts.py` 的 `RetrievalCandidate` 中增加：

```text
enabled: bool | None
```

含义：

- local chunk 必须为 bool。
- Web 候选为 `None`，因为 Web 没有本地启停状态。
- 本地候选如果缺少 enabled，应在格式转换边界报错。

`format_chunk_search_item` 从 Milvus entity 中读取 `enabled` 并写入 candidate。

### 2. TraceChannelHit 增强可观测字段

在 `TraceChannelHit` 中增加：

```text
enabled: bool | None
retrieval_channels: list[RetrievalChannel]
entered_rerank: bool
became_citation: bool
```

字段含义：

- `enabled`：候选当时是否处于可检索状态。当前查询过滤下，本地命中通常应为 true。
- `retrieval_channels`：候选携带的召回来源集合，例如 original、HyDE、Web，以及本地 Action 启用的 dense、learned_sparse、BM25 模式通道。
- `entered_rerank`：该候选是否进入统一 rerank 候选集合。
- `became_citation`：该候选是否成为最终引用。

注意：当前 Milvus hybrid search 返回的是本地 Action 内部 RRF 后的结果，无法证明某个 chunk 单独命中了 dense、learned_sparse 或 BM25 的哪一条底层请求。因此 Trace 可以展示“本 Action 启用了哪些本地通道”和“候选来自 original/HyDE/Web”，但不能虚构逐底层通道命中事实。

### 3. 路线 B 的查询过滤兜底

如果 Milvus 不能安全原地更新 `enabled`，则查询侧需要在构建 access filter 时追加 Mongo disabled 排除条件：

```text
AND chunk_id not in [禁用 chunk_id 列表]
```

约束：

- 只查询当前 dataset、owner/tenant 可见范围内的 disabled chunk id。
- 禁用列表为空时不拼接 `not in []`。
- disabled chunk 数量超过安全阈值时，记录日志并返回明确错误，避免构造超长 Milvus 表达式后静默漏过滤。

路线 A 成立时不需要这一步。

### 任务 1：验证 Milvus 启停更新能力

状态：已完成，当前环境选择路线 B。

目标：确定路线 A 或路线 B。

步骤：

1. 在可丢弃测试 collection 上创建 auto_id 主键和 `enabled` 字段。
2. 插入一条 chunk，记录 `chunk_id`。
3. 尝试用 `MilvusClient.upsert` 更新同一 `chunk_id` 的 `enabled=false`。
4. 查询该 `chunk_id`，确认：
   - `chunk_id` 没变。
   - `enabled` 已变更。
   - content、metadata、dense/learned sparse/BM25 字段没有丢失。
5. 将验证结论写入阶段 6 实现记录或数据字典变更说明。

验收重点：

- 不允许用删除重插作为“通过”标准。
- 验证失败时必须走路线 B，不继续写有风险的 Milvus upsert 逻辑。

验证结果：

- 临时 collection 成功创建并清理，无遗留 `stage6_upsert_probe_*` collection。
- 普通 `upsert` 局部更新失败，错误类型为 `DataNotMatchException`，原因是缺少 `document_id` 等非 nullable 字段。
- `partial_update=True` 在 auto_id 主键 collection 上会生成新的 `chunk_id`。极简验证中，原 `chunk_id=467551067585611553` 更新后按原 ID 查询为 0 条，按 `document_id` 查询到 1 条新记录，新 `chunk_id=467551067585611554`，`enabled=false`。
- 该行为会破坏 Trace、Citation、人工标注和阶段 8 评测弱标签对旧 `chunk_id` 的关联，因此不能用于阶段 6 启停。
- 结论：阶段 6 后续任务按路线 B 实现。

## 验收标准

- 可以通过 API 按 document 查看当前版本 chunk。
- 可以禁用解析错误、页眉页脚、乱码、内容过期和人工误判等 chunk。
- 禁用后查询不再召回该 chunk。
- 启用后该 chunk 可以重新参与查询召回。
- 用户不能查看或操作其他用户私有文档下的 chunk。
- shared/public chunk 第一版只开放可见读取，非 owner 启停返回明确错误。
- chunk 原始记录保留，`chunk_id` 不因启停改变。
- 每次启停都有可审计事件，包含操作人、时间、原因、document_id、chunk_id、index_version。
- Retrieval Trace 能展示候选 chunk 的 enabled 状态、召回 Action 来源、是否进入 rerank、是否成为最终引用。
- Trace 和审计记录不保存模型私有思维链，不保存不必要的完整 chunk 正文副本。
- 阶段 8 数据构建工具可以通过 repository 读取 chunk 启停历史。
- 禁用记录只作为弱质量信号，不能未经复核直接作为 GRPO reward。
- `docs/数据字典.md` 在实现完成后同步新增集合、字段、API 和边界。
