# 阶段 7：管理 API 优先补齐

## 背景与目标

阶段 4 已经把导入对象升级为 `dataset -> document -> chunk` 的管理模型，阶段 5 已经把查询链路升级为 `Planner -> Action -> Observation -> Trace -> Citation` 的可解释闭环，阶段 6 已经补齐了按 document 查看 chunk、chunk 详情、启停和启停审计。

阶段 7 不先做复杂管理页面，先把后端管理 API 补齐。这里的 API 是“前端、测试脚本和后续离线评测都可以稳定调用的 HTTP 接口契约”，不是临时调试入口。

本阶段目标：

- 补齐 Dataset 管理能力：创建、列表、详情、owner、visibility 和 members。
- 收紧 Document 管理能力：列表排序、失败记录清理、owner/visibility 管理、任务状态安全回退。
- 扩展 Chunk 管理能力：跨 document 筛选、批量启停、shared/public 的最终启停权限策略。
- 补齐 Conversation 管理能力：聊天历史按 `user_id + session_id` 隔离，支持当前用户会话列表、详情和隐藏/删除。
- 补齐 Retrieval Test 管理能力：用 API 运行、展示、重放规则 Planner 检索过程，并保存结构化反馈。
- 补齐 Planner 管理能力：查询当前线上 Planner 模式、策略版本、规则配置摘要和已注册实现。
- 补齐 Trace 与反馈读取能力：只返回结构化决策和结果，不保存或对外返回模型私有思维链。

术语边界：

- `Dataset`：知识库容器。用于限定一组 document/chunk 的管理范围。
- `Document`：上传后的文档对象。它是长期元数据对象，不等同于一次导入任务。
- `Chunk`：文档切片。它是检索和引用的最小本地证据单元。
- `Conversation`：聊天会话和消息历史。`session_id` 只表示一个会话，不能代替用户身份。
- `Retrieval Test`：检索测试运行入口。它用于面试演示、调试和阶段 8 数据构建，不等同于真实聊天。
- `Planner`：查询规划器。它只输出下一步受约束 Action，不直接访问 Milvus、Mongo、Web 或生成最终答案。
- `Trace`：一次查询执行的结构化追踪记录。它保存 Action、Observation、候选摘要、引用和配置版本，不保存模型私有思维链。
- `Feedback`：人工反馈。它是给 Trace 标注期望主体、期望 Action、期望 chunk、答案要点和行为判断的结构化记录。

- 不做线上加载 `api/local_base/sft/grpo` 模型。阶段 7 只注册可识别的 Planner 实现名称，不执行训练模型推理。
- 不做阶段 8 的完整评测集构建、Reward 计算和训练数据拆分。

- 不保存模型私有思维链，不通过 Trace/Feedback API 对外返回隐藏推理文本。
- 不做旧生产数据在线迁移、双写灰度或复杂回滚。本项目当前仍按测试数据可重建的边界实施。

## 核心设计决策

### 1. Dataset 是外层权限边界，Document/Chunk 是内层证据边界

查询请求带 `dataset_ids` 时，阶段 7 必须先校验当前用户是否能访问这些 Dataset。只有通过 Dataset 访问校验后，才允许进入 LangGraph。

Document 和 Chunk 的 `visibility` 仍然继续表达文档/切片自己的可见范围。也就是说：

```text
Dataset 可访问
    AND Document/Chunk 可访问
        -> 才允许查询、列表、详情、启停或引用
```

Dataset 是第一道门；Document/Chunk 是第二道门。不能只依赖 Milvus chunk 过滤表达式来补 Dataset 权限，否则用户传入自己无权访问的 `dataset_id` 时，系统很难解释是空结果还是权限不足。

### 2. Dataset members 采用轻量角色，不引入完整 RBAC

新增 `dataset_members` 集合。第一版角色只保留三档：

| 角色 | 中文含义 | 允许动作 |
|---|---|---|
| `viewer` | 查看者 | 查询 dataset、查看可见 document/chunk、查看自己的 Trace。 |
| `editor` | 编辑者 | viewer 能力 + 上传、删除、重建、chunk 启停。 |
| `admin` | 管理员 | editor 能力 + 修改 dataset 元数据、管理 members。 |

Dataset 自身的 `owner_user_id` 永远拥有 admin 能力。owner 可以转移，但转移必须显式调用 API，不能通过普通成员更新隐式发生。

本阶段不实现更细的“只读某几个 document”“只能启停不能删除”等权限。

### 3. shared/public 的读权限和写权限分开

第一版策略：

| visibility | 读取/查询 | 上传/删除/重建/启停/修改 |
|---|---|---|
| `private` | owner 或 dataset member | owner、dataset `editor/admin` |
| `shared` | owner 或 dataset member | owner、dataset `editor/admin` |
| `public` | 任意当前用户可读 | owner、dataset `editor/admin` |

说明：

- `public` 只代表“可读”，不代表任何用户都可以修改。
- `shared` 在阶段 7 后应逐步收紧为显式 members，而不是继续把同一 `tenant_id` 下所有人都当作可编辑用户。
- 为兼容阶段 5/6 的测试数据，实施时可以保留一个过渡配置 `DATASET_SHARED_TENANT_READ_FALLBACK=false`。默认关闭，只有本地排查旧数据时手动开启。
- 启停 public/shared chunk 时，非 owner 只有在 dataset 中具备 `editor/admin` 时才允许操作。

### 4. Document owner/visibility 变更必须和 chunk 访问字段一致

当前 Milvus chunk 中已经保存：

```text
owner_user_id
tenant_id
visibility
dataset_id
document_id
index_version
```

阶段 6 已验证 auto_id 主键 collection 不能安全局部 `upsert` 保持 `chunk_id`。因此阶段 7 不允许只改 Mongo document 元数据而不处理 Milvus chunk，否则查询过滤会继续使用旧 owner/visibility，形成“列表看到已修改、查询仍按旧权限召回”的错乱。

Document access 更新采用保守策略：

- 对 `failed/uploaded` 且没有成功入库 chunk 的 document，可以只更新 Mongo。
- 对 `completed` document，修改 `owner_user_id` 或 `visibility` 必须触发 access sync：
  - 第一版推荐直接创建 `rebuild_index` 任务，按新的 owner/visibility 重建 chunk。
  - 重建会产生新的 `index_version` 和新 chunk 版本，旧 Trace/Feedback 继续通过旧 `document_id + chunk_id + index_version` 保持可解释。
  - API 响应必须明确返回 `requires_rebuild` 或新建的 `task_id`，不能让调用方误以为权限已即时同步到 Milvus。

### 5. Conversation 使用 `user_id + session_id`，不再只信 session_id

`session_id` 可以由前端生成，不具备权限含义。阶段 7 后：

- 写入 `chat_message` 时必须保存 `user_id`。
- 查询历史消息必须同时匹配 `user_id` 和 `session_id`。
- 当前用户会话列表按 `user_id` 聚合。
- 删除/隐藏会话只影响当前用户自己的消息。
- 旧的不含 `user_id` 的消息默认不返回给任何用户，避免把历史脏数据错误归属给当前用户。

### 6. Retrieval Test 不写聊天历史，但必须写 Trace

Retrieval Test 是调试和评测入口，不等同于真实聊天：

- 不写入 `chat_message`。
- 必须创建 `retrieval_traces`，并标记 `execution_source=retrieval_test`。
- 允许指定固定测试用户、dataset、检索配置和 `planner_mode=rule`。
- 第一版只允许线上已实现的 `rule` Planner 执行真实检索。
- 未注册或未启用的 Planner 模式必须显式报错，不得静默切换回 `rule`。

### 7. Trace 读取和反馈只保存结构化结果

Trace API 可以返回：

- `trace_id`
- 用户、dataset、session 快照
- 主体识别结果
- Planner Action Trace
- Observation 摘要
- 召回 chunk ID、document ID、index version、rerank 分数
- 最终 Citation
- 耗时、token 用量、成本估算和配置快照

Trace API 不返回：

- 模型私有思维链。
- 完整 chunk 正文。
- 原始答案 Prompt。
- 密钥、环境变量、异常堆栈。

Feedback API 只写人工标注结果，例如期望主体、期望 Action、期望 chunk、答案要点和是否应该追问/拒答/调用 Web。

## 数据契约

### 扩展 Mongo 集合：datasets

当前已有 `datasets` 集合。阶段 7 补充字段：

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `dataset_id` | string | 知识库业务 ID | 已有字段，Mongo 唯一索引。 |
| `name` | string | 知识库名称 | 展示和管理使用。 |
| `description` | string | 知识库说明 | 可为空。 |
| `owner_user_id` | string | dataset 所属用户 | owner 永远拥有 admin 能力。默认 demo dataset 可写系统 owner。 |
| `tenant_id` | string | 租户 ID | 当前默认 `tenant_default`。 |
| `visibility` | enum | `private/shared/public` | 控制 dataset 外层读取边界。 |
| `status` | enum | `active/deleted` | 删除第一版使用软删除。 |
| `created_by_user_id` | string | 创建人 | 记录最初创建者，owner 转移后不变。 |
| `created_at` | ISO datetime string | 创建时间 | UTC ISO 字符串。 |
| `updated_at` | ISO datetime string | 更新时间 | 元数据变化时更新。 |
| `deleted_at` | ISO datetime string | 删除时间 | 未删除为空。 |

建议索引：

```text
unique(dataset_id)
(owner_user_id, updated_at desc)
(tenant_id, visibility, updated_at desc)
(status, updated_at desc)
```

默认 dataset 补齐策略：

- `dataset_default_equipment_ops` 继续保留。
- 如果旧记录缺少 `owner_user_id/tenant_id/visibility/status`，`ensure_default_dataset` 补齐默认值。
- 默认 dataset 可作为公共 demo 容器，但用户上传 document 仍默认 `private`，避免“公共 dataset”自动公开用户私有导入。

### 新增 Mongo 集合：dataset_members

一条记录表示一个用户在某个 dataset 中的成员关系。

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `member_id` | string | 成员关系 ID | UUID，Mongo 唯一索引。 |
| `dataset_id` | string | 所属知识库 ID | 关联 `datasets.dataset_id`。 |
| `user_id` | string | 成员用户 ID | 与请求头 `X-User-Id` 同一类值。 |
| `role` | enum | `viewer/editor/admin` | 轻量权限角色，不是完整 RBAC。 |
| `added_by_user_id` | string | 添加人 | 必须是 owner 或 admin。 |
| `created_at` | ISO datetime string | 创建时间 | UTC ISO 字符串。 |
| `updated_at` | ISO datetime string | 更新时间 | 修改角色时更新。 |
| `removed_at` | ISO datetime string | 移除时间 | 第一版软删除，未移除为空。 |

建议索引：

```text
unique(dataset_id, user_id, removed_at)
(user_id, role, updated_at desc)
(dataset_id, role, updated_at desc)
```

约束：

- Dataset owner 不需要也不应该依赖 members 记录来获得权限。
- 不能移除 owner 的隐式 admin 权限。
- `user_id` 为空、role 非枚举值、dataset 不存在时 API 返回 422 或 404。

### 扩展 Mongo 集合：documents

阶段 7 建议补充字段：

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `record_kind` | enum | `active/history` | 同名失败记录折叠时用于展示。可由查询实时计算，也可落库。 |
| `history_group_key` | string | 历史分组 key | 建议用 `owner_user_id + dataset_id + normalized_file_name`。 |
| `superseded_by_document_id` | string | 被哪个新 document 替代 | 修复后重新导入成功时，旧失败记录可标记为历史。 |
| `hidden_at` | ISO datetime string | 用户清理失败记录时间 | 用于列表隐藏，不代表物理删除。 |
| `access_sync_status` | enum | `none/pending/processing/completed/failed` | owner/visibility 变更需要重建时使用。 |
| `access_sync_task_id` | string | 权限同步任务 ID | 指向 `tasks.task_id`。 |

说明：

- 如果只通过查询实时计算历史分组，可以先不落 `record_kind/superseded_by_document_id`，但 API 响应必须有等价字段，保证前端不自己猜。
- 清理失败记录优先使用 `hidden_at` 或 `status=deleted` 的软删除方式，不做物理删除。

### 扩展 Mongo 集合：tasks

新增任务类型：

| 枚举值 | 中文含义 | 典型来源 |
|---|---|---|
| `import` | 普通导入任务 | `POST /upload`。 |
| `rebuild_index` | 重建索引任务 | `POST /documents/{document_id}/rebuild`。 |
| `access_sync` | 权限字段同步任务 | Document owner/visibility 变更后重建 chunk 权限字段。第一版可复用 rebuild 实现。 |

约束：

- `/status/{task_id}` 返回内存状态时必须校验 `_persistent_task_metadata[task_id].owner_user_id == 当前用户`。
- `_persistent_task_metadata` 不存在时返回 404，不能把无归属的内存任务暴露出去。

### 扩展 Mongo 集合：chat_message

新增字段：

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `user_id` | string | 消息所属用户 | 来自 `X-User-Id`；聊天历史权限主键。 |
| `session_id` | string | 会话 ID | 只在当前用户内唯一，不具备权限含义。 |
| `hidden_at` | ISO datetime string | 用户隐藏/删除时间 | 列表默认排除。 |
| `conversation_title` | string | 会话标题 | 第一版可用首条用户消息截断生成，也可为空。 |
| `updated_at` | ISO datetime string | 更新时间 | 新消息写入时更新。 |

建议索引：

```text
(user_id, session_id, ts desc)
(user_id, hidden_at, updated_at desc)
(trace_id)
```

旧数据处理：

- 旧消息缺少 `user_id` 时，默认不返回。
- 不做把旧消息猜测归属到当前用户的迁移。
- 本地开发如需清理旧历史，可单独写脚本，不放进线上 API 默认流程。

### 扩展 Mongo 集合：retrieval_traces

阶段 7 建议补充字段：

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `execution_source` | enum | `chat/retrieval_test/replay` | 区分真实聊天、检索测试和重放。 |
| `replay_of_trace_id` | string \| null | 重放来源 Trace | 非 replay 为空。 |
| `config_match_status` | enum | `match/mismatch/unknown` | 重放时记录配置是否与原 Trace 一致。 |
| `corpus_match_status` | enum | `match/mismatch/unknown` | 重放时记录语料、document index version 和 enabled 快照是否一致。 |

说明：

- 现有 Trace 已保存 `owner_user_id`、`dataset_ids`、`planner_steps`、`channel_hits`、`final_citations`、`retrieval_config_snapshot` 等核心字段。
- 阶段 7 的重点是增加读取、重放和反馈接口，不重写 Trace 结构。

### 新增 Mongo 集合：trace_feedbacks

一条记录表示一个用户对一次 Trace 的结构化反馈。

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `feedback_id` | string | 反馈 ID | UUID，Mongo 唯一索引。 |
| `trace_id` | string | 关联 Trace | 必填，必须存在且当前用户可见。 |
| `operator_user_id` | string | 标注人 | 来自 `X-User-Id`。 |
| `dataset_ids` | list[string] | Trace 涉及知识库快照 | 从 Trace 投影，便于阶段 8 分组。 |
| `expected_subject_ids` | list[string] | 期望主体 ID | 可为空，表示本次不评价主体。 |
| `expected_actions` | list[string] | 期望 Action 路径 | 例如 `["local_search", "answer"]`。 |
| `expected_chunks` | list[object] | 期望 chunk | 每项至少包含 `document_id/chunk_id/index_version`。 |
| `expected_answer_points` | list[string] | 期望答案要点 | 中文短句，不要求保存完整标准答案。 |
| `expected_behavior` | object | 是否应追问/拒答/调用 Web | 结构化布尔或枚举。 |
| `rating` | int | 人工评分 | 可选，建议 1-5。 |
| `notes` | string | 人工备注 | 可为空，最长建议 1000 字符。 |
| `created_at` | ISO datetime string | 创建时间 | UTC ISO 字符串。 |
| `updated_at` | ISO datetime string | 更新时间 | 修改反馈时更新。 |

建议索引：

```text
unique(feedback_id)
(trace_id, created_at desc)
(operator_user_id, created_at desc)
(dataset_ids, created_at desc)
```

边界：

- Feedback 是阶段 8 数据构建来源，不等于最终训练样本。
- `expected_chunks` 必须保存 `document_id + chunk_id + index_version`，避免重建索引后误套旧标注。

## API 设计

所有管理 API 默认要求 `X-User-Id`。缺失或空白返回 400。

统一错误边界：

| HTTP 状态 | 场景 |
|---|---|
| 400 | 缺少 `X-User-Id`、请求参数组合非法。 |
| 403 | 当前用户可知道资源存在，但无权执行该操作。 |
| 404 | 资源不存在，或为了不泄露私有资源而统一返回不存在。 |
| 409 | `expected_index_version`、owner/visibility 同步状态、会话状态等发生冲突。 |
| 422 | Pydantic schema 校验失败，例如枚举值不合法、列表为空。 |
| 500 | 基础设施或未预期程序错误。 |

响应核心字段：

约束：

```json
{
```

```http
X-User-Id: user_a
```

详情包括：

- dataset 基本信息。
- 当前用户角色。
- document 数量摘要。
- members 数量摘要。

### Document API

#### 1. 上传文档

保留现有接口：

```http
POST /upload
X-User-Id: user_a
Content-Type: multipart/form-data
```

阶段 7 增强：

- 校验当前用户对目标 `dataset_id` 有写权限。
- 支持可选 `visibility` 表单字段，默认 `private`。
- 如果目标 dataset 不存在或当前用户无权上传，返回 404 或 403。

可选新增一致化别名：

```http
POST /documents
```

该别名内部复用现有 upload service，不重新实现导入逻辑。

#### 2. 查询文档列表

```http
GET /documents?dataset_id=dataset_default_equipment_ops&status=all&fold_history=true&limit=50
X-User-Id: user_a
```

阶段 7 列表语义：

- 先校验 dataset 可见。
- 默认只返回当前用户在该 dataset 下可见的 document。
- 默认按 `created_at desc` 排序，最新导入记录在最上面。
- `fold_history=true` 时，同名失败记录折叠到最新有效记录下。
- 每条记录返回：
  - `record_kind=active/history`
  - `history_record_count`
  - `superseded_by_document_id`
  - `latest_task_id`
  - `index_version`
  - `owner_user_id`
  - `visibility`

同名失败记录判断建议：

```text
normalized_file_name = trim(lower(file_name))
group_key = owner_user_id + dataset_id + normalized_file_name
```

如果同一 group 中存在更晚的 `completed` document，则更早的 `failed` 记录默认标记为 `history`。

#### 3. 查询文档详情和状态

保留：

```http
GET /documents/{document_id}
GET /documents/{document_id}/tasks
GET /status/{task_id}
```

阶段 7 增强：

- document 详情使用 dataset + document 双层权限。
- task 历史只返回当前用户可见 document 的任务。
- `/status/{task_id}` Mongo 查不到或 Mongo 异常时，只允许回退注册过 owner 的内存导入任务。

`/status/{task_id}` 内存回退规则：

```text
metadata = get_persistent_task_metadata(task_id)
if metadata 不存在:
    return 404
if metadata.owner_user_id != 当前用户:
    return 404
return memory status
```

#### 4. 修改 document owner/visibility

```http
PATCH /documents/{document_id}/access
X-User-Id: user_a
Content-Type: application/json

{
  "owner_user_id": "user_b",
  "visibility": "shared",
  "expected_index_version": 3,
  "sync_mode": "rebuild"
}
```

响应示例：

```json
{
  "code": 200,
  "document_id": "doc_xxx",
  "index_version": 4,
  "owner_user_id": "user_b",
  "visibility": "shared",
  "access_sync_status": "pending",
  "task_id": "task_xxx",
  "requires_rebuild": true
}
```

约束：

- 当前用户必须是 document owner 或 dataset `admin/editor`。
- `expected_index_version` 不一致返回 409。
- `completed` document 修改 owner/visibility 必须同步 chunk 访问字段；第一版用 rebuild 实现。
- `failed` document 可以直接改 Mongo，但仍要写审计日志。

#### 5. 删除文档和重建索引

保留：

```http
DELETE /documents/{document_id}
POST /documents/{document_id}/rebuild
```

阶段 7 增强：

- 当前用户必须是 document owner 或 dataset `editor/admin`。
- public/shared document 非 owner 删除必须走 dataset 写权限，不因为可读就可删。
- 重建时继续生成新 `index_version`，并清理旧 chunk/MinIO 资源。

#### 6. 清理失败导入记录

```http
POST /documents/failed-records/cleanup
X-User-Id: user_a
Content-Type: application/json

{
  "dataset_id": "dataset_default_equipment_ops",
  "document_ids": ["doc_failed_1", "doc_failed_2"],
  "only_superseded": true,
  "dry_run": false
}
```

响应：

```json
{
  "code": 200,
  "matched_count": 2,
  "cleaned_count": 2,
  "items": [
    {
      "document_id": "doc_failed_1",
      "status": "deleted",
      "hidden_at": "2026-07-15T00:00:00+00:00"
    }
  ]
}
```

约束：

- 只清理当前用户可见且可操作的失败记录。
- `only_superseded=true` 时，只清理已经被后续成功导入替代的同名失败记录。
- 不清理 `processing/pending`。
- 如果失败记录已经产生 chunk，必须走文档删除 service，不能只隐藏 metadata。

### Chunk API

阶段 6 已有按 document 的基础接口，阶段 7 扩展如下。

#### 1. 跨 document 查询 chunk

```http
GET /chunks?dataset_id=dataset_default_equipment_ops&document_id=doc_xxx&enabled=all&visibility=shared&keyword=E021&limit=100
X-User-Id: user_a
```

用途：

- 管理端按 dataset、document、subject、enabled、visibility 搜索 chunk。
- 集中查看 disabled chunk。
- 给阶段 8 数据构建工具读取人工禁用样本。

约束：

- 查询不返回向量字段。
- 默认不返回完整正文，只返回 `content_preview`。
- 权限先查 dataset，再查 document/chunk visibility。
- `enabled=false` 按 `effective_enabled` 判断，也就是叠加 Mongo `chunk_status_overrides.manual_status` 后的最终查询状态。

#### 2. 批量启停 chunk

```http
PATCH /chunks/enabled
X-User-Id: user_editor
Content-Type: application/json

{
  "enabled": false,
  "reason_type": "header_footer",
  "reason_detail": "批量禁用重复页脚",
  "items": [
    {
      "document_id": "doc_xxx",
      "chunk_id": 1001,
      "expected_index_version": 3
    }
  ]
}
```

响应需要逐项返回成功、无变化、失败原因：

```json
{
  "code": 200,
  "changed_count": 1,
  "failed_count": 0,
  "items": [
    {
      "document_id": "doc_xxx",
      "chunk_id": 1001,
      "changed": true,
      "effective_enabled": false
    }
  ]
}
```

约束：

- 单次批量上限建议 100。
- 任一 item 无权限时，该 item 返回失败；默认不让整个批次全部回滚。
- `expected_index_version` 必填，避免旧页面批量误操作新版本 chunk。

#### 3. shared/public 启停权限

阶段 7 后 chunk 启停权限：

- private document：document owner 或 dataset `editor/admin`。
- shared document：document owner 或 dataset `editor/admin`。
- public document：document owner 或 dataset `editor/admin`。
- viewer 和普通 public 读者只能查看，不能启停。

### Conversation API

#### 1. 当前用户会话列表

```http
GET /conversations?limit=50
X-User-Id: user_a
```

返回：

```json
{
  "code": 200,
  "items": [
    {
      "session_id": "session_1",
      "title": "HAK 180 E021 报警怎么处理",
      "latest_message_preview": "E021 表示...",
      "message_count": 6,
      "latest_trace_id": "trace_xxx",
      "updated_at": "2026-07-15T00:00:00+00:00"
    }
  ]
}
```

实现建议：

- 通过 `chat_message` 按 `user_id + session_id` 聚合。
- 默认排除 `hidden_at` 非空记录。
- `title` 第一版可取首条 user 消息前 40 个字符。

#### 2. 当前用户某个会话详情

```http
GET /conversations/{session_id}?limit=50
X-User-Id: user_a
```

行为：

- 只返回 `user_id == 当前用户` 且 `session_id` 匹配的消息。
- 返回消息中的 `citations`、`trace_id`、`terminal_reason_code`。
- 不返回其他用户同名 session。

现有兼容路径：

```http
GET /history/{session_id}
DELETE /history/{session_id}
```

阶段 7 可保留这两个路径，但必须强制 `X-User-Id` 并改为按 `user_id + session_id`。

#### 3. 删除或隐藏当前用户会话

```http
DELETE /conversations/{session_id}
X-User-Id: user_a
```

第一版推荐软删除：

- 给当前用户该 session 的消息写 `hidden_at`。
- 不物理删除 Trace。
- 不影响其他用户同名 session。

#### 1. 运行一次检索测试

```http
POST /retrieval-tests/runs

Content-Type: application/json

{
```

字段说明：

```json
    "total_duration_ms": 0,

  }
}
```

注意：

- 返回的 `planner_steps` 必须来自 Trace 契约，不拼自由文本推理。

#### 2. 基于 trace_id 重放

```http
POST /retrieval-tests/traces/{trace_id}/replay
X-User-Id: user_a
Content-Type: application/json

{
  "planner_mode": "rule",
  "strict_config_match": true
}
```

行为：

- 读取原 Trace，校验当前用户可见。
- 对比原 Trace 的 dataset、document index version、retrieval config snapshot、policy version 和 enabled chunk 状态。
- 如果 `strict_config_match=true` 且不一致，返回 409。
- 如果允许不一致，响应必须明确 `config_match_status` 和 `corpus_match_status`，不能声称“完全重放”。


约束：

- 当前用户必须能读取 Trace。
- `expected_chunks` 必须校验目标 chunk 当前或历史版本能与 Trace dataset/document 关联。
- feedback 不修改原 Trace。

- `retrieval_test_service.py`：构造测试 State、执行查询图、读取 Trace 摘要。
- `planner_management_service.py`：输出当前 Planner 配置和注册表。
- `trace_feedback_service.py`：Trace 读取权限、反馈写入、反馈查询。

当前 `document_lifecycle_service.py` 和 `chunk_management_service.py` 继续保留，阶段 7 的新 service 复用它们，不做大搬家。

### API 路由归属

为了减少进程和端口调整，第一版保持当前两个 FastAPI app：

- `import_server.py`：Dataset、Document、Chunk 管理 API。
- `query_server.py`：Conversation、Retrieval Test、Planner、Trace/Feedback API。

暂不新增第三个 management server。后续如果前端需要统一管理端口，再考虑网关或 router 聚合。

## 查询链路改造

阶段 7 需要在 `/query` 和 Retrieval Test 入口前增加 Dataset 访问校验：

```text
HTTP request
  -> X-User-Id 校验
  -> dataset_ids schema 规范化
  -> Dataset access 校验
  -> create_query_default_state
  -> safe_create_running_trace
  -> LangGraph
```

规则：

- 如果所有 dataset 都无权访问，返回 404 或 403，不进入 LangGraph。
- 如果传入多个 dataset，其中部分无权访问，第一版返回 403，不静默丢弃无权 dataset。
- Trace 中仍保存原请求最终实际执行的 `dataset_ids`。
- Retrieval Test 入口也走同一套 dataset access 校验。

## 前端最小改动

阶段 7 不做复杂页面，但为了不破坏现有页面，需要做最小兼容：

- `chat.html` 查询历史接口改为带 `X-User-Id`。
- `history/{session_id}` 删除接口改为带 `X-User-Id`。
- `import.html` 文档列表可继续用 `/documents`，但要能展示 `record_kind/history_record_count`。
- 失败记录清理可以先不做按钮，通过 API 验收。
- Dataset members、Retrieval Test、Planner status、Trace feedback 第一版可以只通过 API 和测试脚本验证。

## 具体实施任务

### 任务 1：定义阶段 7 schema 和枚举

目标：先固定 API 契约，避免 endpoint、service、test 各写各的字段。

细分任务：

- 新增 Dataset schema。
- 新增 Document management schema。
- 新增 Conversation schema。
- 新增 Retrieval Test schema。
- 新增 Planner status schema。
- 新增 Trace feedback schema。
- 给关键字段写中文注释：
  - `visibility`：资源可见性，不等同于编辑权限。
  - `role`：成员角色，只是轻量管理角色，不是完整 RBAC。
  - `policy_version`：Planner 策略版本。
  - `retrieval_config_version`：检索配置版本。
  - `execution_source`：Trace 来源。
  - `expected_chunks`：人工期望引用的 chunk 版本身份。

验收重点：

- schema 单元测试覆盖 enum 合法值、非法值、空字段、extra 字段拒绝。
- 所有新增 schema 可以 `model_dump(mode="json")`。

### 任务 2：补齐 Dataset repository 和 members 集合

目标：让 Dataset 不再只是默认知识库占位，而是可管理资源。

细分任务：

- 扩展 `datasets` 索引和默认字段补齐。
- 新增 `dataset_members` 集合和索引。
- 实现创建、列表、详情、更新、软删除。
- 实现 member add/list/update/remove。
- 实现当前用户在 dataset 中的 effective role 计算。

验收重点：

- owner 不依赖 members 也能获得 admin。
- public dataset 对非 member 可读但不可写。
- shared/private dataset 非 member 不可读。
- 移除 member 后立即失去访问权限。

### 任务 3：统一访问控制 service

目标：避免 Dataset、Document、Chunk、Query、Retrieval Test 各自重复写权限判断。

细分任务：

- 新增 `access_control_service.py`。
- 提供方法：
  - `get_dataset_role(dataset_id, user_id)`
  - `require_dataset_read(dataset_id, user_id)`
  - `require_dataset_write(dataset_id, user_id)`
  - `can_read_document(document, user_id, dataset_role)`
  - `can_write_document(document, user_id, dataset_role)`
  - `can_operate_chunk(document, user_id, dataset_role)`
- 把 shared/public 启停策略放到这个 service。

验收重点：

- private/shared/public 读写矩阵有单元测试。
- public 读者不能启停 chunk。
- dataset editor 可以操作 shared/public chunk。

### 任务 4：实现 Dataset API

目标：通过 API 完成 Dataset 管理闭环。

细分任务：

- 在 `import_server.py` 增加 `/datasets` 路由。
- 接入 Dataset management service。
- 补充 API 测试：
  - 创建 dataset。
  - 当前用户列表可见 dataset。
  - 查询详情。
  - 修改 visibility。
  - owner 转移。
  - 添加/修改/删除 member。

验收重点：

- 无 `X-User-Id` 返回 400。
- 非 owner/admin 修改 settings 返回 403。
- 非 member 读取 private/shared 返回 404。

### 任务 5：收紧上传、查询和导入状态权限

目标：让已有入口遵守 Dataset 权限和安全内存回退策略。

细分任务：

- `POST /upload` 校验目标 dataset 写权限。
- `GET /documents` 校验 dataset read 权限。
- `GET /documents/{document_id}` 使用 dataset + document 双层权限。
- `GET /documents/{document_id}/tasks` 使用 document 可见性校验。
- `GET /status/{task_id}` 收紧内存回退策略。
- `/query` 入口校验所有 `dataset_ids` 可读。

验收重点：

- Mongo 异常时，无 persistent metadata 的 task 不返回内存状态。
- 用户 A 不能通过 task_id 查到用户 B 的导入状态。
- 用户无权访问 dataset 时，查询不会进入 LangGraph。

### 任务 6：文档列表排序、失败记录折叠和清理

目标：解决导入历史可用性问题，避免旧失败记录干扰成功导入。

细分任务：

- 文档列表默认按 `created_at desc`。
- 增加 `fold_history` 查询参数。
- 返回 `record_kind/history_record_count/superseded_by_document_id`。
- 新增失败记录清理 API。
- 清理时复用删除 service，避免残留 chunk/MinIO。

验收重点：

- 新导入记录总在列表上方。
- 同名旧失败记录默认不干扰最新成功记录。
- 只清理当前用户自己的失败记录。
- `processing/pending` 不能被清理。

### 任务 7：Document owner/visibility 管理和 access sync

目标：支持 document 轻量权限管理，同时保持 Mongo 与 Milvus chunk 权限字段一致。

细分任务：

- 新增 `PATCH /documents/{document_id}/access`。
- 对 completed document 创建 access sync/rebuild 任务。
- 对未成功入库 document 直接更新 Mongo。
- 响应中明确 `requires_rebuild`、`task_id`、`access_sync_status`。
- 补充任务类型 `access_sync`，或复用 `rebuild_index` 并在 document 字段记录原因。

验收重点：

- `expected_index_version` 冲突返回 409。
- 权限字段不同步时不宣称修改完成。
- 重建后新 chunk 使用新 owner/visibility。

### 任务 8：扩展 Chunk 管理 API

目标：在阶段 6 基础上补齐跨 document 管理和 shared/public 操作权限。

细分任务：

- 新增 `GET /chunks`。
- 新增 `PATCH /chunks/enabled` 批量接口。
- 接入 Dataset access role。
- 按 `effective_enabled` 做 enabled 筛选。
- 保持现有按 document chunk API 兼容。

验收重点：

- public 普通读者可以查看但不能启停。
- dataset editor 可以启停 shared/public chunk。
- 批量启停逐项返回成功/失败，不静默吞错。

### 任务 9：聊天历史增加 user_id 和 Conversation API

目标：用户只能看到自己的会话和消息历史。

细分任务：

## 验收标准

- 面试演示时可以通过 API 展示完整 RAG 管理闭环：
  - 创建/查看 dataset。
  - 上传 document。
  - 查看 document 状态。
  - 查看 chunk 并启停。
  - 查询并看到 Trace/Citation。
  - 用 Retrieval Test 展示规则 Planner 决策过程。
  - 给 Trace 写入人工反馈。
- 可以区分公共 demo 知识库和用户私有导入内容。
- 用户只能查看自己的聊天会话和消息历史。
- 用户不能查看或操作其他用户私有 document/chunk/task/trace。
- public/shared chunk 的启停操作受 dataset role 控制，不再只靠 document owner 或 tenant 粗放判断。
- Document owner/visibility 修改不会造成 Mongo 与 Milvus 查询权限不一致。
- Retrieval Test 可以完整展示并重放 `rule` Planner 的决策过程。
- replay 明确说明语料/索引版本和配置是否与原 Trace 一致。
- 人工反馈能与 Trace、document 版本和 chunk 版本稳定关联，为阶段 8 构建数据集提供来源。
- 前端页面可以后续基于这些 API 再补，不需要阶段 7 同时完成复杂管理台。
