## 关键术语边界

- `Planner`：规划器。它只根据当前 State 和 Observation 选择下一个 Action，不直接执行 Milvus、Web 或答案生成。
- `Action`：规划器可输出的固定动作，包括 `local_search`、`hyde_search`、`web_search`、`answer`、`ask_clarification`、`refuse`。
- `State`：一次轨迹的运行时状态。它会随 Action 改变，包含当前问题、主体、Action history、最近 Observation、累计候选和终止状态。每条 rollout 必须有独立 State。
- `Observation`：Action 执行后的可验证事实，例如候选数量、rerank 分数、命中标识、错误码和耗时。它不是模型推理过程。
- `Trace`：轨迹记录。它保存每步 Action、Observation、Citation、Reward 分项和终止原因，不保存私有思维链。
- `Citation`：最终回答引用的证据身份。本地 Citation 必须能追踪到 `document_id + chunk_id + index_version`。
- `Reward`：奖励/评分信号。阶段 9 中 GRPO 使用 `total_reward` 训练，但排查必须看 `format/retrieval/citation/answer/behavior/cost` 六路分项。
- `fallback`：证据不足后的升级或收口路线，例如 `local_search -> hyde_search`、`local_search -> web_search` 或 `local_search -> refuse`。
- `SFT`：监督微调。这里训练模型输出合法 `PlannerDecision`，重点是结构化格式、基本路由和停止时机。
- `GRPO`：强化学习优化方法。这里用于优化同一个 case 下多条 Planner 轨迹的相对好坏，不训练最终答案模型。
- `token log probability`：模型对目标 JSON token 的对数概率。GRPO 需要它计算新旧策略概率比，不能只保存整条路径分数。
- `reference model`：参考模型。GRPO 中通常是冻结的 SFT 模型，用来约束新策略不要偏离过快。
- `checkpoint`：训练检查点。至少保存模型、tokenizer、训练配置、数据 manifest、Reward profile、环境快照 ID 和随机种子。
- `policy version`：策略版本。每个 rule、SFT、GRPO、API 或 local base Planner 都必须写入稳定版本，方便 Trace 和评测复现。
- `held-out test`：隔离测试集。只用于最终对比，不参与权重调整、Prompt 调整、模型选择或训练数据筛选。

这里的 `anti_pattern_flags` 是反模式标记，例如：

- `unnecessary_hyde_wins`：不必要 HyDE 路线比分数更高。
- `unnecessary_web_wins`：乱搜 Web 反而高于本地正确回答。
- `premature_refuse_wins`：应该回答的 case 上直接拒答得分更高。
- `premature_answer_wins`：证据不足仍回答得分更高。
- `no_component_variance`：多条路线六路分项几乎没有方差，Reward 不能提供训练信号。

### 验收标准

- 生成真实 `reward_v1_1_baseline_dev.json`，且不是只跑 rule 的单一路线结果。
- 每个 dev case 至少有 6 条路线结果。
- 报告能展示六路分项的均值、方差、排序和扣分原因。
- `behavior + cost` 能明显区分正确路线、乱 Web、乱 HyDE、过早拒答和过早追问。
- `retrieval + citation` 若基本不变，报告明确说明它主要由固定 provider 或检索器决定。
- 不出现“乱搜索反而系统性得分更高”的情况；若出现，必须先调权重或修 scorer，不允许冻结。
- 冻结后的 `reward_v1_1_training_profile.json` 被 SFT/GRPO 配置引用。

route seed 继续复用 `PlannerEvalCase`，不要另造训练格式。需要新增的只是“期望执行路径”文件：

字段边界：

- `case_id`：关联 `PlannerEvalCase.case_id`。
- `path_id`：同一 case 下的路线 ID，用于多路线评测和导出。
- `action_path`：人工批准的目标 Action 序列，只能包含 `QueryAction` 闭集成员。
- `route_family`：路线家族，例如 `ask_clarification`、`hyde_fallback`、`web_search`、`refuse`、`multi_step_fallback`、`stop_when_enough`。
- `export_to_sft`：是否允许导出 SFT。Reward 校准用的负例路线应为 false。
- `review_status`：复核状态，非 `reviewed` 不进入正式 SFT。

### 关键样本设计

追问样本：

- 用户只说“这个报警怎么处理”，没有设备或报警码上下文。
- 用户给了相近报警码，但检索只找到另一个码，必须 `ask_clarification`。
- 用户问题缺少时间窗口或故障现象，无法判断当前状态。

HyDE fallback 样本：

- 本地初搜有候选但 `top_rerank_score` 低于阈值，且问题明显属于本地知识域。
- HyDE 后能命中 expected chunk，再进入 `answer`。
- `web_search` 应标为 forbidden，避免模型遇到低分就乱联网。

Web 样本：

- 问题明确要求今天、最新公告、公开召回、官网通知等实时信息。
- 本地知识库不应伪造最新结论。
- 如果 Web 被环境禁止，应改为 `refuse`，不能绕过 `web_search_allowed=false`。

拒答样本：

- 用户要求编造手册没有的参数。
- 用户无权限访问目标 dataset。
- 本地和 HyDE 都没有可靠证据，且问题不可通过追问解决。
- Web 禁止或不适合，必须 `refuse`。

多步 fallback 样本：

- `local_search` 空，允许 Web，Web 有可靠外部公开证据后回答。
- `local_search` 低分，HyDE 仍不足，Web 禁止，最终拒答。
- `local_search` 命中多个相互冲突证据，最终追问而不是硬答。

适时停止样本：

- 当前 20 条 curated Gold 继续保留为高置信 `local_search -> answer`。
- 新增样本中也要包含“本地证据充足时不继续 HyDE/Web”的负例验证，确保 Reward 不鼓励多搜。

## 任务 9.2：真实 ActionProvider（动作执行器）与最小 Replay（回放）

### 目标

把离线环境从“只回放 expected chunk（期望命中切片）”升级到“可调用真实检索服务”。这是 SFT（监督微调）后评测和 GRPO（组相对策略优化强化训练）的共同前置。

9.2 不把 Replay（回放）作为主路线。主路线是：GPU（显卡算力）服务器部署完整项目代码，本地怎么训，GPU 服务器就怎么训；真实检索、HyDE（假设式改写检索）和 Web（网页检索）都走同一套业务代码。

### 三层实现

第一优先：`MilvusActionProvider（Milvus 动作执行器）`

- 直接调用现有本地检索、HyDE（假设式改写检索）和 Web（网页检索）服务。
- 由 `OfflineState（离线运行状态）` 适配成 `QueryGraphState（查询图状态）`，让评测和训练复用真实业务检索代码。
- 默认启用 Mongo（文档数据库）里的人工禁用 chunk（知识切片）覆盖；测试或无 Mongo 环境可以显式关闭。
- 本地候选必须继续满足 `RetrievalCandidate（检索候选）` 契约，并由 `OfflineRagEnvironment（离线 RAG 环境）` 校验是否属于当前 `snapshot（快照）`。
- Web（网页检索）只能返回真实 URL（网页地址）候选，不能伪造本地 `document_id/chunk_id（文档 ID/切片 ID）`。

第二优先：`RecordingActionProvider（记录型动作执行器）`

- 包在真实 Provider（执行器）外层，不改变真实检索结果。
- 每次 `Action（动作）` 执行后，记录 `Observation（观察结果）`、候选身份、耗时、错误、`snapshot_id（快照 ID）`、检索配置版本和配置 hash。
- 记录文件是训练审计日志，不是主训练数据；默认截断候选正文，避免产生大量长期无用文本。
- 记录失败会在 `Trace（轨迹记录）` 中显式报错，避免训练时以为已经完成审计。

第三优先：最小 `ReplayActionProvider（回放动作执行器）`

- 只读取 `RecordingActionProvider（记录型动作执行器）` 写出的少量 JSONL（逐行 JSON）记录。
- 只用于 smoke test（冒烟测试）、regression test（回归测试）和单条异常轨迹复现。
- 不要求覆盖全部训练数据，也不阻塞真实 Provider（执行器）训练。
- 缺少某个 case/action/query（样本/动作/查询）时必须明确报错，不允许空候选静默通过。

- `MilvusActionProvider（Milvus 动作执行器）` 实现 `OfflineActionProvider（离线动作执行器）` 协议，并默认复用真实业务检索代码。
- `RecordingActionProvider（记录型动作执行器）` 能记录 `Observation（观察结果）`、候选、错误和版本边界。

- GPU（显卡算力）服务器运行时必须记录代码版本、`snapshot（快照）`、`config（配置）`、Provider（执行器）版本和 Web（网页检索）开关。

### 正式上云前置清单

在正式租用 GPU（显卡算力）服务器做 SFT（监督微调）前，本地还要先把“模型 Planner（规划器）替换链路”跑通。这里的目标不是在 Mac（苹果本地电脑）上训练模型，而是确认业务代码、模型服务协议、配置、日志和失败处理都已经准备好；否则上云后会把 GPU 时间浪费在工程接线问题上。

#### 1. 冻结第一版基础模型选择

阶段 9 第一版不直接使用 `Qwen3-14B（通义千问 3 14B）` 作为默认模型。推荐冻结为：

```text
首选：Qwen3.5-4B（通义千问 3.5 4B）
升级对照：Qwen3.5-9B（通义千问 3.5 9B）
备用上限：Qwen3-14B（通义千问 3 14B）
```

选择理由：

- Planner（规划器）只输出结构化 `PlannerDecision（规划器决策）`，不是生成最终长答案。
- 第一版更需要稳定的 JSON（结构化数据）输出、低成本多轮评测和快速失败定位，而不是最大参数量。
- `Qwen3.5-4B（通义千问 3.5 4B）` 更适合先验证 SFT（监督微调）闭环、HTTP（超文本传输协议）推理接入和 Reward（奖励函数）区分能力。
- 只有当 4B 出现明显结构化输出不稳、关键 Action（动作）边界混乱或 dev（开发验证集）明显输给 rule（规则规划器）时，才升级 `Qwen3.5-9B（通义千问 3.5 9B）`。

#### 2. 本地先跑通 PlannerClient（规划器客户端）

本地 Mac（苹果本地电脑）不需要下载完整 SFT（监督微调）后权重，也不需要本地训练。上云前至少要让业务代码支持：

```text
业务 RAG 服务
  -> PlannerClient（规划器客户端）
  -> HTTP endpoint（HTTP 调用地址）
  -> PlannerModelServer（规划器模型服务）
  -> PlannerDecision（规划器决策）
```

本地 smoke run（冒烟运行）可以用三种方式之一：

- `debug_memorized（调试记忆）` checkpoint（检查点）：继续验证 prompt（提示词）、codec（编解码器）和离线评测入口。
- `mock_http（模拟 HTTP）` 服务：返回固定 JSON（结构化数据），验证业务流程和网络协议。
- `Qwen3.5-4B 4bit（通义千问 3.5 4B 的 4 位量化版）` 本地模型服务：只验证推理接入，不验证正式质量。

本地验收标准：

- `PlannerClient（规划器客户端）` 能从环境变量读取 endpoint（调用地址）、model_id（模型身份）、timeout（超时时间）、max_new_tokens（最大生成 token 数）和 temperature（采样温度），并在 HTTP（超文本传输协议）请求里映射成 OpenAI-compatible（兼容 OpenAI）的 `max_tokens（最大生成 token 数）`。
- 模型返回内容必须经过 `decision_codec（决策编解码器）` 解析，非法 JSON（结构化数据）、未知字段、未知 Action（动作）和未知 reason_code（原因码）都要转成结构化错误。
- `enable_thinking=false（关闭思考模式）` 必须进入模型调用参数或 prompt（提示词）约束，Planner（规划器）不得输出 `<think>` 之类私有思考过程。
- `node_query_planner（查询规划节点）` 不能继续硬编码 `RuleBasedPlanner（规则规划器）`，必须能通过 registry（注册表）选择 `rule/local_base/sft/grpo（规则/未微调基础模型/监督微调模型/强化训练模型）`。
- `/planner/status（规划器状态接口）` 必须能显示当前 Planner（规划器）模式、policy_version（策略版本）、model_id（模型身份）、endpoint（调用地址）和不可用原因。

#### 3. 正式推理形态采用同机 HTTP（本机 HTTP）

上云后可以把完整项目部署在同一台 GPU（显卡算力）服务器上，但模型仍建议单独作为 `PlannerModelServer（规划器模型服务）` 运行：

```text
同一台 GPU 服务器
  ├─ 业务 RAG 服务
  ├─ PlannerModelServer（规划器模型服务，加载 Qwen3.5-4B SFT checkpoint）
  ├─ Mongo/Milvus/Web（文档库/向量库/网页检索）连接配置
  └─ evaluation/stage9（训练、评测和报告入口）
```

业务服务调用：

```text
http://127.0.0.1:<planner_port>/v1/chat/completions
```

不要把 `Qwen3.5-4B（通义千问 3.5 4B）` 直接加载进每个 `uvicorn worker（服务工作进程）`。即使 4B 比 14B 小，多 worker（多服务进程）重复加载也会造成显存和内存浪费；后面升级 9B 或 GRPO（组相对策略优化强化训练）时风险更明显。

#### 4. 补齐云端训练后端能力

当前 `transformers_causal_lm（transformers 因果语言模型）` 入口只证明云端同构训练入口存在，还不能直接视为高效正式训练后端。正式上云前需要补齐：

- `PEFT（参数高效微调）` 支持。
- `LoRA（低秩适配）` 和 `QLoRA（4 位量化低秩适配）` 配置。
- Qwen3.5 chat_template（聊天模板）适配。
- `enable_thinking=false（关闭思考模式）` 的训练和推理一致性。
- adapter（适配器）保存、加载、合并或导出策略。
- 训练 manifest（清单）记录 base_model_id（基础模型身份）、adapter_id（适配器身份）、quantization（量化方式）、torch/cuda/transformers/peft 版本。

推荐策略：

- RTX 5090（32GB 显存）：第一版使用 `Qwen3.5-4B + QLoRA（4 位量化低秩适配）`。
- A800 80GB（80GB 显存）：优先使用 `Qwen3.5-4B + LoRA（低秩适配）`，必要时对照 `Qwen3.5-9B + LoRA（低秩适配）`。
- 不做第一版 full fine-tuning（全参数微调）；当前数据量和阶段目标不值得承担成本。

`evaluation/stage9（阶段实验目录）` 只保留训练配置、数据、报告和一次性评测入口。


云端材料至少包含：

## 任务 9.5：GRPO 工程升级

### 进入条件

只有满足以下条件，才进入 GRPO：

- Reward v1.1 training profile 已冻结。
- SFT 数据路线覆盖达标。
- SFT checkpoint 可加载、可推理、可在 dev 上跑完离线评测。
- `local_base` 和 `sft` baseline 已完成。
- Replay 或真实 provider 至少有一个可用于多 rollout。
- 每条轨迹独立 State 已有测试覆盖。

### 目标

把 `evaluation/stage9/grpo_core_teaching.py` 的教学闭环升级为真实模型训练闭环。

需要替换：

- `FiniteActionPathPolicy`
- 手工路径概率
- 均匀 reference policy

需要新增：

- 模型采样。
- token 级 log probability。
- 冻结 reference model。
- checkpoint 保存与恢复。
- rollout 级 Trace/Reward 日志。

### 新增接口

```python
class PlannerPolicy:
    policy_version: str

    def sample_group(self, context, group_size: int) -> list[PlannerRolloutSample]:
        ...

    def log_prob(self, batch) -> torch.Tensor:
        ...

    def ref_log_prob(self, batch) -> torch.Tensor:
        ...
```

字段边界：

- `sample_group`：同一 case 下采样 G 条候选轨迹，返回模型输出 JSON、解析后的 `PlannerDecision`、token IDs 和采样时 old log probability。
- `log_prob`：当前模型对已采样输出 token 的 log probability，用于 GRPO ratio。
- `ref_log_prob`：冻结 reference model 对同一输出 token 的 log probability，用于 KL 约束。

### rollout 记录

每条 GRPO 轨迹保存为 JSONL：

```json
{
  "run_id": "stage9_grpo_...",
  "case_id": "example",
  "group_index": 0,
  "sample_index": 2,
  "snapshot_id": "stage85-env-20260721-v2",
  "policy_version": "planner-grpo-stage9-v0.1",
  "reference_policy_version": "planner-sft-stage9-v0.1",
  "action_path": ["local_search", "hyde_search", "answer"],
  "terminal_action": "answer",
  "terminal_reason_code": "hyde_evidence_sufficient",
  "reward": {
    "total_reward": 0.88,
    "components": {}
  },
  "old_log_prob": -1.23,
  "new_log_prob": -1.18,
  "ref_log_prob": -1.31,
  "advantage": 0.42,
  "termination": "completed",
  "errors": []
}
```

不保存：

- 私有思维链。
- 完整 chunk 正文。
- 答案 Prompt。
- 用户私有文档原文。

### GRPO Trainer 要点

- 每个 case 采样 `group_size=4` 或 `8` 条轨迹。
- 每条轨迹从 `env.reset(case)` 创建独立 State。
- 每一步用模型生成一个 `PlannerDecision`，由环境执行 Action。
- 终止后使用 `score_trajectory` 计算 Reward。
- 同一 case 组内计算 advantage。
- 使用 clipped objective 和 KL penalty。
- reference model 使用冻结 SFT checkpoint。
- 每 N step 保存 checkpoint 和 rollout 样本摘要。

### 验收标准

- GRPO smoke 能跑完至少 2 个 case、每个 case 4 条 rollout。
- rollout 日志包含 Action、Observation、Reward 六路分项和终止原因。
- old/new/ref log probability 维度和 token 对齐有测试覆盖。
- reference model 参数冻结。
- checkpoint 可恢复继续训练。
- 同一 batch 内不同 rollout 不共享可变 State。
