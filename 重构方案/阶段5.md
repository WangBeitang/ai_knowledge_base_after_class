# 阶段 5：查询链路重构

## 背景与目标

阶段 4 已经把 chunk 从“文件标题维度”升级为“document 维度”，并写入了：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
index_version
chunk_index
enabled
source_title
```

这些字段使查询侧具备了按知识库、用户、可见性和 chunk 状态过滤的基础。但当前查询链路仍有几个关键问题：

- 查询 API 和聊天页还没有传递 `X-User-Id`，`QueryGraphState` 也没有用户和 dataset 上下文。
- chunk 检索目前只按 `subject_id` 过滤，阶段 4 写入的权限字段和 `enabled` 尚未生效。
- LangGraph 在主体确认后固定并发执行普通检索、HyDE 和 Web Search；Web 不是 fallback，查询成本和行为都不可解释。
- 当前图没有统一 Planner 契约，后续接入 Model Planner/GRPO 时会被迫重写图和检索节点。
- 当前 `rrf_service` 只融合普通检索与 HyDE，底层 Milvus 检索仍固定为 dense + BGE-M3 learned sparse 两路 `WeightedRanker`。
- rerank 前的格式转换会丢失 `document_id`、`chunk_id`、`index_version` 等元数据，最终答案无法稳定返回引用来源。
- 查询过程只有节点进度，没有结构化 Action、Observation 和 Retrieval Trace，无法解释为什么调用 HyDE/Web，也无法稳定重放规则基线。
- 设备型号、报警码、SOP 编号、零件编号等精确标识目前主要依赖 embedding/learned sparse，自身没有查询侧提取、归一化和结构化过滤闭环。

阶段 5 的目标不是引入一个“会自由思考的 Agent”，而是把查询流程改造成一个可约束、可解释、可评测、可替换策略的执行环境：

```text
subject_confirm
    -> QueryPlanner 选择 Action
    -> 执行一个合法 Action
    -> 返回结构化 Observation
    -> QueryPlanner 根据新状态再决策
    -> answer / ask_clarification / refuse
```

本阶段需明确区分“单次动作分类”和“多步 Planner”：

- 单次动作分类只根据原始问题从固定 Action 中选一个，没有执行后的 Observation 和后续决策，使用 SFT 或普通分类即可学习。
- 本项目的 Planner 是多步策略：先选择检索动作，再观察召回数量、分数、精确标识命中和候选证据，然后决定回答、继续 HyDE/Web、追问或拒答。
- 阶段 9 的 GRPO 优化整条 Action Trace 的召回、引用、答案、步数和调用成本，而不是六个 Action 之间的单次分类准确率。

阶段 5 在该通用接口上只注入 `RuleBasedPlanner`；后续替换为 Model Planner 时不改检索和答案节点。

本阶段完成后，应满足：

- 查询只召回公共/共享内容和当前用户自己的私有内容。
- 默认先查本地知识库，HyDE 和 Web 只在规则满足时触发。
- Planner 决策只输出受约束的 Action、query 和 `reason_code`，不直接生成答案文本。
- 每一步都有结构化 Observation 和 Trace，固定输入、固定 Observation 和固定策略版本下能得到相同 Action Trace。
- answer 返回稳定的引用字段，能追踪到本地 document/chunk 或 Web URL。
- 可以公平比较 dense + learned sparse、dense + BM25、三路融合，并在本阶段内依据评测结果收口最终 Milvus schema。
- 阶段 9 替换 `QueryPlanner` 实现时，不需要修改检索、HyDE、Web、rerank 和答案生成节点。

## 当前实现基线

阶段 5 开始前，查询链路实际是：

```text
node_subject_name_confirm
    -> node_search_embedding ───────────────┐
    -> node_search_embedding_hyde ─────────┼-> node_rrf -> node_rerank -> node_answer_output
    -> node_web_search_mcp ─────────────────┘
```

需要以以下事实为改造起点：

- `QueryGraphState` 目前只有会话、问题、主体、召回结果和答案字段，没有用户、dataset、Planner、Observation、Trace 和 citation 契约。
- 主体候选不明确时，`subject_name_confirm_service` 直接写 `state["answer"]`；阶段 5 要改为输出主体确认结果，由 Planner 决定 `ask_clarification` 或 `refuse`。
- `chunk_retrieval_utils.build_subject_filter_expr` 只生成 `subject_id in [...]`。
- `embedding_search_service` 和 `hyde_search_service` 都调用固定的 dense + `sparse_vector` 请求。
- `milvus_utils.hybrid_search` 固定使用 `WeightedRanker`，还不能根据召回组合切换为 `RRFRanker`。
- `rerank_service.fuse_documents` 会把本地 chunk 转成只有 `title/text/url/type/score` 的结构，导致引用所需的 document/chunk 元数据丢失。
- `rrf_service.check_params` 在本地两路都为空时直接抛错，Planner 没有机会根据空召回选择 Web 或拒答。
- 查询 API、SSE 最终包和非流式响应都没有 `trace_id`、`citations`。
- 聊天页没有生成/复用 `kb_user_id`，查询请求也没有 `X-User-Id`。
- 当前依赖为 `pymilvus 2.6.10`，客户端已经具备 BM25 Function 和 `RRFRanker` 能力，但仍需先确认实际 Milvus Server 版本及 Analyzer 行为。

## 改造边界

### 本阶段要做

- 新增统一 `QueryPlanner` 接口、结构化 `PlannerDecision` 和确定性的 `RuleBasedPlanner`。
- 固化六个 Action：`local_search`、`hyde_search`、`web_search`、`answer`、`ask_clarification`、`refuse`。
- 改造 LangGraph，使其按 Planner 决策串行执行 Action 并回到 Planner。
- 增加最大步骤、合法 Action 转移、重复 Action 检查和安全收口。
- 查询入口补齐 `X-User-Id`、`dataset_ids` 和默认 tenant 上下文。
- 对所有本地检索通道统一执行 dataset、subject、enabled、visibility/owner 过滤。
- 增加设备运维精确标识提取、归一化、精确过滤和零命中降级策略。
- 将现有 `sparse_vector` 明确为 BGE-M3 learned sparse；临时增加 BM25 实验字段和 Function。
- 支持三种可切换的本地召回组合，并统一使用基于名次的 RRF 做通道融合。
- 把 Web Search 从默认并发路径改为规则 fallback。
- 保留候选 chunk 的完整元数据，生成结构化 citations。
- 新增 Retrieval Trace 持久化，记录结构化 Action、Observation、证据标识、版本和耗时。
- 补充阶段 5 专项评测、单元测试、图测试、API 测试和用户隔离测试。
- 评测后删除未保留通道的字段、索引、Function、配置和死代码，重新建 collection 并导入测试文档。
- 同步 `docs/数据字典.md`、根目录 `重构方案.md` 和阶段 5 评测结论。

### 本阶段不做

- 不实现 `ModelPlanner` 推理，不加载 Planner 模型，不执行 SFT/GRPO 训练。
- 不把 LLM 私有思维链、隐藏推理文本或模型 token 概率写入 Trace。
- 不做在线强化学习，不把用户反馈自动用于训练。
- 不做完整 Dataset 管理、成员管理、RBAC 或多租户后台；这些仍属于阶段 7。
- 不做聊天会话列表和完整的 `user_id + session_id` 历史管理；阶段 7 再收口。
- 不做 Trace 查询/重放/人工反馈管理 API；阶段 5 只落数据契约和内部持久化，阶段 7 再开放管理接口。
- 不做 chunk 列表、人工启停和编辑；阶段 6 实现。阶段 5 只在查询过滤中强制 `enabled == true`。
- 不做完整阶段 8 评测平台和大规模训练数据集；阶段 5 只建设决定检索 schema 所需的小型专项评测。
- 不迁移历史 Milvus 数据，不做双写、backfill、在线 schema 兼容或灰度迁移。
- 不把前端改造成复杂的 Planner 调试台，只补用户身份、引用展示和必要的 trace_id 展示。

## 核心设计决策

### 1. Planner 是纯决策层，不包含检索实现

`QueryPlanner` 实现只读取结构化 `PlannerContext`/Observation，返回 `PlannerDecision`。阶段 5 的具体实现是 `RuleBasedPlanner`。Planner 不能：

- 直接访问 Milvus、Mongo、Web 或 LLM。
- 直接生成最终答案文本。
- 修改检索结果。
- 输出自由文本推理过程。

检索和答案仍由现有 service/node 执行。阶段 9 只替换 Planner 实现。

### 2. Observation 只表达可验证事实

Observation 可以包含：

- 本次 Action 是否成功。
- 各通道召回数量。
- 去重后的候选数量。
- rerank 后数量与 top score。
- 命中的设备型号、报警码、SOP/零件编号。
- 可生成的引用数量和有限数量的候选证据摘要。
- 耗时、错误码和是否发生结构化过滤降级。

Observation 不包含“我认为”“我的分析过程”等自由文本思维链。

候选证据摘要是 Model Planner 判断“证据是否真正覆盖问题”的运行时输入，不能只给出数量和分数，否则后续策略只能学会阈值分支。运行时 Observation 可携带受长度限制的证据片段；持久化 Trace 默认只保存证据 ID、标题、分数、命中标识和摘要 hash，不复制大量私有 chunk 正文。

### 3. 规则 Planner 的稳定性以结构化输入为边界

`RuleBasedPlanner.plan(context)` 必须是纯函数：相同 policy/config、相同主体确认结果、相同 Observation、相同 Action history，必须返回相同 `PlannerDecision`。

线上完整查询仍可能受到主体识别 LLM、HyDE 文本、Web 内容和外部服务变化影响，因此“稳定重放”分两层验收：

- Planner 单元重放：直接输入固定 Observation，Action Trace 必须完全一致。
- 固定语料集成重放：固定模型配置、知识库快照、检索配置并禁用 Web，Action 和 `reason_code` 必须一致；最终答案措辞不要求逐字相同。

### 4. Web 是受控 fallback，不再默认并发

Web 仅在以下任一条件满足时允许调用：

- 规则识别到明显实时性词语，例如“最新、今天、当前、实时、刚发布、价格、政策更新”。
- 本地检索为空。
- 本地/HyDE 经过 rerank 后仍低于证据阈值。
- 本地检索执行失败且问题允许外部信息回答。

设备说明书、报警码、维护 SOP 等内部知识问题，不因为一次低分就无条件相信 Web；Web 失败或没有可靠结果时安全拒答。

### 5. `shared` 的阶段 5 语义必须显式限定

阶段 7 尚未实现 dataset members。阶段 5 暂时采用轻量语义：

```text
private -> 仅 owner 可检索
public  -> 所有当前查询用户可检索
shared  -> 同一 tenant 内可检索
```

当前 `tenant_id` 固定为 `tenant_default`，因此 `shared` 实际相当于当前租户内共享。阶段 7 引入成员关系后必须收紧，不能把本阶段表达式当作最终权限模型。

### 6. BM25 是对比实验，不预判胜负

阶段 5A 临时保留三路字段：

```text
dense_vector
learned_sparse_vector
bm25_sparse_vector
```

对比完成后进入阶段 5B schema 收口，只保留有证据支持的组合。若质量接近，优先保留维护成本更低、入库与查询链路更简单的方案。

## 目标调用链与状态机

### 目标 LangGraph

```text
START
  -> subject_confirm
  -> planner
       ├─ local_search
       │    -> local_retrieval -> rrf -> rerank -> observation -> planner
       ├─ hyde_search
       │    -> hyde_retrieval  -> rrf -> rerank -> observation -> planner
       ├─ web_search
       │    -> web_retrieval   -> rerank -> observation -> planner
       ├─ answer
       │    -> answer_output -> trace_finalize -> END
       ├─ ask_clarification
       │    -> terminal_response -> trace_finalize -> END
       └─ refuse
            -> terminal_response -> trace_finalize -> END
```

说明：

- `subject_confirm` 不再决定图终点，只输出主体确认状态、候选和提示文本。
- `planner` 只生成决策并校验合法性。
- `observation` 汇总刚执行 Action 的结构化结果，并追加 Action history。
- `local_search` 和 `hyde_search` 使用同一套权限过滤和召回组合。
- Web 结果不进入 Milvus 通道 RRF；它和已有本地候选一起进入统一 reranker。
- 任何执行异常都先写 Observation/Trace，再回到 Planner 做 fallback 或安全拒答；不允许无限重试。

### 合法 Action 转移

| 当前阶段/上一个 Action | 允许的下一个 Action |
|---|---|
| 主体确认完成 | `local_search`、`web_search`、`ask_clarification`、`refuse` |
| `local_search` 完成 | `answer`、`hyde_search`、`web_search`、`ask_clarification`、`refuse` |
| `hyde_search` 完成 | `answer`、`web_search`、`ask_clarification`、`refuse` |
| `web_search` 完成 | `answer`、`ask_clarification`、`refuse` |
| `answer` | 终止 |
| `ask_clarification` | 终止 |
| `refuse` | 终止 |

额外约束：

- 同一个检索 Action 一次查询最多执行一次。
- `answer`、`ask_clarification`、`refuse` 必须是终止 Action。
- 默认最大 Planner 决策步数为 4；配置必须进入 Trace。
- 超过最大步数、非法转移、未知 Action、Planner 异常都转成 `refuse`，`reason_code=SAFE_GUARD_TRIGGERED`。
- 阶段 9 的 Model Planner 输出非法时回退规则 Planner；阶段 5 先实现相同的校验入口和回退接口测试。

## 具体改造任务

### 1. 固化查询输入、身份和知识库范围

目标：让查询在进入图之前就拥有明确的用户、tenant 和 dataset 上下文。

细分任务：

- 查询 API 复用导入 API 的轻量身份规则，强制读取：

```http
X-User-Id: user_xxx
```

- 缺少或只有空白 `X-User-Id` 时返回 400，不自动合并到公共 `anonymous_user`。
- `QueryRequestParam` 增加可选 `dataset_ids: list[str]`。
- 未传 `dataset_ids` 时使用：

```text
["dataset_default_equipment_ops"]
```

- 对 `dataset_ids` 做去空、去重和数量上限校验；第一版最多 10 个。
- API 初始化 `QueryGraphState` 时写入：

```text
owner_user_id
tenant_id = "tenant_default"
dataset_ids
```

- 聊天页复用导入页相同的 `kb_user_id` localStorage key，所有 `/query` 请求带 `X-User-Id`。
- 阶段 5 不改造 `/history/{session_id}` 的完整用户隔离模型，但要在文档中明确这是阶段 7 的剩余边界；不得误写成已经完成聊天历史权限隔离。

验收重点：

- 用户 A、用户 B 发起相同 query 时，state 中 owner 不同。
- 缺失 header 的查询不会进入 LangGraph。
- 空 dataset 列表、重复 dataset 和超长列表有确定行为。

实现状态：已完成。

- 查询和导入 API 已复用同一个轻量 `X-User-Id` 解析函数；缺失或空白 header 返回 400，并且发生在创建 SSE 队列和调度查询图之前。
- `QueryRequestParam.dataset_ids` 已实现默认值、去空、保序去重和最多 10 个不同 dataset 的校验；显式空列表或全空白列表返回 422。
- `owner_user_id`、`tenant_id`、`dataset_ids` 已写入 `QueryGraphState`，同步和流式查询都显式传递相同上下文。
- 聊天页已复用 `kb_user_id` 并在 `/query` 请求中发送 `X-User-Id`。
- 本部分只固化查询输入上下文；Milvus visibility/owner/dataset 权限过滤仍属于后续任务，聊天历史的完整用户隔离仍属于阶段 7。

### 2. 新增 Planner、Action、Observation 和引用契约

目标：先固定稳定的业务协议，再改图和节点。

建议新增：

```text
app/rag/query/contracts.py
app/rag/query/planner.py
```

`contracts.py` 至少定义：

```python
class QueryAction(str, Enum):
    LOCAL_SEARCH = "local_search"
    HYDE_SEARCH = "hyde_search"
    WEB_SEARCH = "web_search"
    ANSWER = "answer"
    ASK_CLARIFICATION = "ask_clarification"
    REFUSE = "refuse"


class PlannerDecision(BaseModel):
    action: QueryAction
    query: str
    reason_code: str


class EvidenceSummary(BaseModel):
    document_id: str | None
    chunk_id: str | int | None
    title: str
    source_type: str
    rerank_score: float | None
    matched_identifiers: dict[str, list[str]]
    content_excerpt: str


class RetrievalObservation(BaseModel):
    action: QueryAction
    status: str
    channel_counts: dict[str, int]
    candidate_count: int
    reranked_count: int
    top_rerank_score: float | None
    matched_identifiers: dict[str, list[str]]
    citation_count: int
    evidence_summaries: list[EvidenceSummary]
    evidence_ambiguous: bool
    clarification_question: str | None
    duration_ms: int
    error_code: str | None
    used_structured_filter: bool
    filter_fallback: bool


class PlannerHistoryItem(BaseModel):
    step: int
    decision: PlannerDecision
    execution_status: str


class PlannerContext(BaseModel):
    original_query: str
    current_query: str
    subject_resolution_status: str
    subject_ids: list[str]
    subject_candidates: list[str]
    clarification_question: str | None
    query_identifiers: dict[str, list[str]]
    latest_observation: RetrievalObservation | None
    action_history: list[PlannerHistoryItem]
    planner_step: int
    max_steps: int
    allowed_actions: list[QueryAction]


class Citation(BaseModel):
    document_id: str | None
    chunk_id: str | int | None
    title: str
    source: str
    score: float
    source_type: str
```

`EvidenceSummary.content_excerpt` 只用于当前 Planner 决策的受限证据上下文，必须限制 top-N、单条长度和总长度。Trace 持久化层不得默认保存该正文片段，只保存可重放的证据标识与摘要 hash。

阶段 5 的 `evidence_ambiguous` 由可重放的结构化规则产生：例如候选证据属于多个互不兼容的设备型号/版本，且用户问题缺少可区分信息。低分或候选数量多不能单独判定为歧义；`clarification_question` 也必须由命中的差异字段确定性生成。

`PlannerDecision.reason_code` 第一版使用固定枚举或集中常量，至少覆盖：

```text
SUBJECT_AMBIGUOUS
SUBJECT_REQUIRED
SUBJECT_NOT_FOUND
REALTIME_QUERY
INITIAL_LOCAL_SEARCH
LOCAL_EVIDENCE_SUFFICIENT
LOCAL_EMPTY
LOCAL_LOW_SCORE

HYDE_STILL_INSUFFICIENT
WEB_EVIDENCE_AVAILABLE
WEB_EMPTY_OR_FAILED
EVIDENCE_AMBIGUOUS
ACTION_EXECUTION_ERROR
SAFE_GUARD_TRIGGERED
```

`QueryPlanner` 接口：

```python
class QueryPlanner(Protocol):
    policy_version: str

    def plan(self, context: PlannerContext) -> PlannerDecision:
        ...
```

第一版只实现：

```text
RuleBasedPlanner(policy_version="rule-v1")
```

- 所有 Planner 输出都能通过 Pydantic/Enum 校验。
- reason code 是机器可读枚举，不写自由文本分析。
- Planner 不依赖 Milvus、Mongo、LLM 或 HTTP。

### 4. 统一构建权限、主体和结构化标识过滤表达式

目标：所有本地召回通道使用同一份、可测试的 Milvus filter，不允许普通检索和 HyDE 各自拼接。

建议在 `chunk_retrieval_utils.py` 中新增：

```text
build_chunk_access_filter(...)
build_structured_identifier_filter(...)
build_chunk_retrieval_filter(...)
```

基础过滤逻辑：

```text
dataset_id in 当前 dataset_ids
AND subject_id in 已确认 subject_ids
AND enabled == true
AND (
    visibility == "public"
    OR (visibility == "shared" AND tenant_id == 当前 tenant_id)
    OR owner_user_id == 当前 user_id
)
```

要求：

- 所有字符串、列表都走统一 Milvus 转义函数。
- dataset、subject 为空时不能生成 `in []` 后静默全库搜索；调用方必须得到明确校验错误或 Planner Observation。
- 权限条件必须加完整括号，避免 `AND/OR` 优先级导致私有数据越权。
- 普通检索、HyDE、BM25、learned sparse 和 dense 请求必须复用完全相同的 expr。
- `enabled == true` 从阶段 5 起强制生效，即使阶段 6 尚无人工禁用入口。

用户隔离测试矩阵：

| 数据 | user_a | user_b |
|---|---:|---:|
| user_a private | 可召回 | 不可召回 |
| user_b private | 不可召回 | 可召回 |
| public | 可召回 | 可召回 |
| tenant_default shared | 可召回 | 可召回 |
| enabled=false | 不可召回 | 不可召回 |
| 其他 dataset | 不可召回 | 不可召回 |

### 5. 增加设备运维标识提取、归一化与两段式检索

目标：让设备型号、报警码、SOP 编号和零件编号不再只依赖 embedding 猜测。

建议新增：

```text
app/rag/query/query_identifier_service.py
```

第一版使用确定性规则，不引入额外 LLM：

- `equipment_model`：识别字母/数字组合及空格、连字符变体，例如 `HAK180`、`HAK-180`、`HAK 180`，归一为同一 canonical form。
- `alarm_code`：识别 `E021`、`E020` 等明确报警/故障码，统一大写和分隔符。
- `sop_code`：识别包含 `SOP` 前缀的编号；当前 chunk 没有独立 `sop_code` 字段时，先进入 `lexical_text` 精确词召回，不伪装成 `sop_type`。
- `part_number`：识别明确零件/备件编号；当前 chunk 没有独立 `part_number` 字段时，先进入 `lexical_text`，评测确认价值后再决定是否扩 schema。
- 中文部件名继续使用现有 `part_name`，同时参与 lexical text。

两段式检索：

```text
第一段：基础权限/subject filter + 可映射的精确结构化字段 filter
  -> 有结果：保留并显著优先
  -> 0 结果：记录 filter_fallback=true
第二段：只保留基础权限/subject filter，使用原始 query + normalized identifiers 做多通道召回
```

这样既能提高精确编号命中率，也避免导入侧结构化字段缺失时直接把正确文档过滤掉。

验收重点：

- `HAK180`、`HAK-180`、`HAK 180` 归一结果一致。
- `E021/E020` 能分别提取，不能合并为一个错误编号。
- 精确 filter 0 命中时会降级召回，并在 Observation/Trace 中可见。
- 每个标识提取规则都有正例、变体和误匹配反例测试。

### 6. 重构本地召回通道与 RRF 融合

目标：支持可切换召回组合，并区分“单次 Action 内通道融合”和“original/HyDE 两次 Action 结果融合”。

召回模式固定为：

```text

dense_bm25
dense_learned_sparse_bm25
```

阶段 5A 中：

- `MilvusGateway.create_requests` 改为按 `retrieval_mode` 创建 2 或 3 个 `AnnSearchRequest`。
- dense 请求输入 dense vector。
- learned sparse 请求输入 BGE-M3 sparse vector。
- BM25 请求输入原始文本 query，由 Milvus Function 使用与入库相同的 Analyzer 生成查询稀疏表示。

- 现有 `WeightedRanker` 仍可供标准主题/别名 collection 使用，不要为改 chunk 检索破坏阶段 2；chunk 检索显式选择 RRF。

- original local search 与 HyDE search 的候选按 `chunk_id` 去重。
- 使用通用 `fuse_ranked_chunk_lists` 做第二层 RRF，不能假设两路都非空。
- 单路、空路都返回结构化结果，不因某一路为空抛异常。
- 排名并列时使用稳定的 `chunk_id` 次级排序，保证固定输入下顺序稳定。

改造当前格式转换：

- 定义统一 `RetrievalCandidate` 形态。
- rerank 前后必须保留：

```text

dataset_id
index_version
chunk_index
title
source_title
content/text
source_type
retrieval_channels
retrieval_rank
retrieval_score
rerank_score
url
```

- Web 候选没有本地 ID 时，`document_id/chunk_id/index_version` 为 `None`，不能伪造本地标识。

验收重点：

- 三种模式生成正确数量和字段的 `AnnSearchRequest`。
- 三路原始分数量级不同不会被直接相加。
- local 或 HyDE 任一路为空仍能继续。
- rerank 后本地候选仍保留 `document_id/chunk_id`。

### 8. 实现确定性的 RuleBasedPlanner

目标：形成线上默认策略、阶段 8 baseline 和阶段 9 故障回退。

第一版规则顺序：

1. 主体存在候选歧义，或问题/历史中完全没有可用主体：`ask_clarification`。
2. 用户明确提到了主体但无法映射到知识库，且不是明显实时问题：`refuse`。
3. 问题明显要求实时信息：`web_search`。
4. 已确认本地主题且还未检索：`local_search`。
5. 最新 Observation 显示证据存在可由用户补充信息解决的歧义：`ask_clarification`。
6. local rerank 证据充分：`answer`。
7. local 有候选但证据不足，且未执行 HyDE：`hyde_search`。
8. local 为空，或 HyDE 后仍不足，且允许 Web：`web_search`。
9. Web 有可用候选：`answer`。
10. Web 为空/失败或问题不适合 Web：`refuse`。
11. 任意安全约束触发：`refuse`。

“证据充分”不能凭主观固定一个阈值：

- 先用阶段 5 专项评测集采集 reranker score 分布。
- 标注哪些 query 的候选足以回答、哪些应该追问/拒答。
- 在开发集上确定 `RERANK_EVIDENCE_THRESHOLD`，再冻结到 `retrieval_config_version`。
- held-out 小测试集只做验收，不用于反复调阈值。

实时性判断使用版本化关键词/正则规则；命中规则、规则版本和结果写入 Trace。

Planner 伪代码：

```text
plan(context):
    validate_step_and_transition()

    if subject_status in (ambiguous, no_mention):
        return ask_clarification
    if subject_status == not_found and not realtime:
        return refuse
    if realtime and web_search not executed:
        return web_search
    if local_search not executed:
        return local_search
    if latest_observation.evidence_ambiguous:
        return ask_clarification
    if evidence_is_sufficient:
        return answer
    if local_has_candidates and hyde_search not executed:
        return hyde_search
    if web_search not executed and web_is_allowed:
        return web_search
    return refuse
```

验收重点：

- RuleBasedPlanner 是无 I/O 的纯函数。
- 给定固定 Observation 序列能稳定生成完整 Action Trace。
- 不会出现 `local -> hyde -> web -> hyde` 循环。
- 最大步骤和非法转移都会安全结束。

## BM25 专项评测与 schema 决策门

### 评测集

阶段 5 建立一个小而真实、只用于检索 schema 选择的设备运维专项集，建议 24～40 条，至少覆盖：

| 类型 | 示例 | 重点 |
|---|---|---|
| 报警码 | `E021/E020 是什么故障` | 精确编号与多编号 |
| 设备型号 | `HAK180/HAK-180/HAK 180` | 变体归一化 |
| SOP 编号/类型 | `SOP-xxx 的停机步骤` | 词法命中与流程语义 |
| 零件编号 | `某备件编号如何更换` | 精确字面召回 |
| 中文部件名 | `急停按钮复位后仍报警` | 中文分词与语义 |
| 纯语义问题 | `设备运行时温度不稳定怎么排查` | dense 语义召回 |

每条至少标注：

```text
query_id
query
dataset_id
owner_user_id
expected_subject_id
expected_chunk_ids
expected_identifiers
should_answer
should_use_web
```

评测集分为开发集和小型 held-out 集。Analyzer、阈值和组合参数只在开发集调整，held-out 只用于最后确认，避免根据测试结果反复调参。

### 公平对比条件

三组实验必须保持：

```text
相同 collection 数据快照
相同 chunk
相同 query
相同 user/dataset/visibility/enabled 过滤
相同 per-channel top-k
相同 RRF k 和 fusion top-k
相同 reranker 与 rerank top-k
相同 expected chunk 标注
```

对比：

```text
dense + learned sparse
dense + BM25
dense + learned sparse + BM25
```

指标：

```text
recall@k
MRR
nDCG
引用命中率
平均/P95 召回延迟
索引大小
单文档入库耗时
```

### 决策规则

在运行 held-out 之前冻结判断规则，避免看到结果后主观选择：

- 某组合在至少两个核心质量指标上有稳定、实质提升，且其他核心指标没有明显回退，才认为有保留价值。
- 如果质量差距很小，选择字段更少、入库更快、运行依赖更少的组合。
- 精确编号类 query 的 recall 不能为了平均指标被牺牲；必须单独查看报警码、型号、SOP/零件编号子集。
- 三路只有在相对最佳双路仍有稳定增益时才保留，不能因为“技术更多”保留。
- 结论、原始结果、最终 schema 和删除项写入阶段 5 评测报告。

最终只能形成以下一种明确结论：

```text
A. 保留 dense + learned sparse，删除 BM25
B. 保留 dense + BM25，删除 learned sparse
C. 保留 dense + learned sparse + BM25
```

## 验收标准

### 功能验收

- 只用本地知识库可以稳定回答有充分证据的问题。

- `enabled=false` chunk 不会被任何本地通道召回。
- Web Search 不再默认并发；只有实时性、空召回、低质量召回或受控失败时触发。
- 主体歧义时追问，证据不足时拒答，不为了完成流程强行生成答案。

### Planner/Trace 验收

- 六个 Action 语义清楚且都由结构化 `PlannerDecision` 驱动。
- Action、Observation、Trace 都有 schema 校验。
- `PlannerContext` 明确包含问题、主体结果、最新 Observation、Action history、步数和合法 Action，Planner 不直接依赖 LangGraph 全量 state。
- 固定 Observation 和配置下，RuleBasedPlanner 能稳定重放相同 Action/`reason_code` 序列。
- 同一问题在不同 Observation 下可稳定生成 `local -> answer`、`local -> hyde -> answer` 等不同的合法轨迹；检索后发现证据歧义时可以追问。
- 超过最大步骤、重复 Action、非法 Action 或 Planner 异常时安全结束。
- Trace 能展示原始/改写问题、标准主题、每步决策、各通道命中、rerank、最终引用、耗时、错误、策略/模型/提示词版本、token 用量和分项成本。

## 风险与控制

### 风险 1：权限表达式括号错误导致越权

控制：过滤表达式只由一个 builder 生成；对完整字符串和真实 fake search expr 做专项测试，所有本地通道禁止自己拼权限条件。

### 风险 2：BM25 Analyzer 破坏设备编号

控制：先运行 Analyzer token 验证；lexical_text 同时写入 canonical 和常见变体；精确字段仍保留结构化过滤，不让 BM25 成为唯一编号能力。

### 风险 3：RRF 后分数不能直接作为证据阈值

控制：Planner 的证据阈值使用 BGE reranker 的归一化分数，不使用 RRF 分数；RRF 只负责候选排序融合。

### 风险 4：Graph 循环或重复调用昂贵工具

控制：合法转移表、已执行 Action 集合、最大步骤和单 Action 一次限制同时生效。

### 风险 5：Trace 写入影响查询可用性

控制：repository 懒加载；Trace 写失败记录日志但不改变权限和答案结果；图异常仍由入口尝试标记 failed。

### 风险 6：阶段 5 临时三路 schema 变成永久负担

控制：把“评测决策 + 删除失败通道 + 最终重建”列为阶段完成条件，没有完成 schema 收口就不能标记阶段 5 完成。

### 风险 7：shared 被误认为完整权限

控制：代码注释、数据字典和 Trace 明确 `shared` 是当前 tenant 内轻量语义；阶段 7 成员模型落地后必须替换。

## 明确假设

- 当前 Mongo/Milvus 仍是少量测试数据，可以删除受影响 collection 后重建。
- 实施 BM25 前会确认实际 Milvus Server 支持 BM25 Function、Analyzer 和三向量字段，不只依据 Python 客户端版本。

- 阶段 5 最终交付必须包含明确的检索组合结论；在没有评测结果前，方案不预判 BM25 或 learned sparse 谁胜出。
