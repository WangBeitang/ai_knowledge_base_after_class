# 阶段 9 离线评测失真问题与面试价值复盘

## 文档定位

本文单独复盘阶段 9 SFT v1 在 expanded dev（扩展开发集）评测中暴露的离线评测失真问题，
重点记录：

- 问题为什么出现；
- 为什么经过多轮数据审核仍然没有提前发现；
- 如何通过正式模型复评定位到运行时契约；
- 后续应该怎样修复；
- 面试时怎样准确表达这次工程经验。

这不是生产事故复盘，也不能表述为“修复了线上 Milvus（向量数据库）故障”。准确边界是：

> 在 9.4 前的离线模型选择阶段，发现快照动作执行器丢失了不同检索动作之间的结果差异，
> 导致部分 HyDE（假设式改写检索）路线被错误判定为模型失败。

本文使用的事实来自已经冻结的 SFT v1 checkpoint、25 条 reviewed balanced dev（已审核均衡
开发集）、云端运行日志和代码归因。heldout test（留出测试集）没有运行。

## 一、先说明系统中各角色

### 1. Planner（规划器）

Planner 是被训练和评测的决策模型。它读取当前 State（运行状态）和最新
Observation（观察结果），决定下一步 Action（动作）：

- `local_search`：本地知识库检索；
- `hyde_search`：生成假设性答案或扩展查询后再次检索；
- `web_search`：网页检索；
- `answer`：基于现有证据回答；
- `ask_clarification`：信息不足时追问；
- `refuse`：请求不安全或无法可靠完成时拒绝。

Planner 只负责选择动作，不直接访问 Milvus、Web 或 Mongo。

### 2. Provider（动作执行器/环境结果提供器）

Provider 接收 Planner 输出的 Action，执行或回放对应外部动作，然后返回
Observation。它不负责选择下一步动作，也不负责最终判分。

项目中有两类关键实现：

| 实现 | 中文角色 | 检索结果来源 | 适用目的 |
|---|---|---|---|
| `MilvusActionProvider` | 真实检索动作执行器 | 调用真实业务检索节点，由 Milvus 返回候选文本块及排名 | 真实检索探针、端到端集成验证 |
| `SnapshotExpectedChunkActionProvider` | 快照期望文本块动作执行器 | 不访问 Milvus，根据 case 的期望证据构造确定性候选 | 离线状态机、Reward 和模型决策回归 |

因此，真实业务运行时是 Milvus 决定召回哪些 chunk（文本块）；Provider 负责调用检索服务并把结果
转换成统一 Observation。只有离线快照 Provider 才会绕过 Milvus，自行构造候选。

### 3. Evaluator（评测器/裁判）

Evaluator 在一条轨迹结束后读取：

- case 允许的 Action path（动作路径）；
- Planner 实际执行的 Action path；
- 最终是回答、追问还是拒绝；
- 检索证据、引用、禁止动作和执行错误；
- Reward（奖励分数）各组成部分。

然后输出是否通过和失败原因。Evaluator 不执行检索，也不替 Planner 决策。

### 4. 一次评测的完整链路

```text
Case（评测题和判题契约）
-> Planner（规划器）选择 Action
-> Provider（动作执行器）执行或回放 Action
-> Environment（运行环境）写入 Observation
-> Planner 根据新 Observation 继续决策
-> Evaluator（评测器）对完整轨迹判分
```

只有 Case、Provider、Observation 和 Evaluator 四层语义一致，模型错误归因才成立。

## 二、原本想验证什么

HyDE 路线 case 的构题依据是：

```text
原始问题执行 local_search
-> 目标文本块没有进入 Top 5，证据不足
-> 执行 hyde_search，生成更接近文档表达的扩展查询
-> 目标文本块提升到 Rank 1
-> Planner 基于证据 answer
```

这些 case 不是凭空规定“必须走 HyDE”。构题时保存了：

- 原始用户问题；
- 来源文档、文本块身份和 SHA256；
- 期望答案要点；
- 原始检索与 HyDE 检索的探针结论；
- 可接受路线 `local_search -> hyde_search -> answer`；
- 独立审核结果和跨 split（数据划分）泄漏检查。

因此，问题文本、来源证据和“为什么需要 HyDE”的检索依据总体仍然有效。

## 三、实际发生了什么

9.3.16 为了让不同 checkpoint 看到完全相同的环境，明确使用：

```text
EXPANDED_DEV_PROVIDER=snapshot_expected_chunks
```

这意味着本次正式模型推理没有连接真实 Milvus，而是使用离线快照动作执行器。

当前 `SnapshotExpectedChunkActionProvider` 的简化逻辑是：

```text
local_search
-> 返回 case.expected_chunks

hyde_search
-> 仍返回 case.expected_chunks
```

候选还被构造成：

```text
retrieval_score=0.95
rerank_score=0.95
content=expected_answer_points
```

模型第一次执行 `local_search` 后看到的已经是高分目标证据和答案要点。实际 5 条路线为：

```text
4 条：local_search -> answer
1 条：local_search -> refuse
```

5 条都没有进入 `hyde_search`。其中 4 条直接回答符合模型实际看到的高分 Observation；另一条
涉及高电流测量安全边界，模型在首次检索后选择拒绝。Evaluator 随后按冻结路线检查：

```text
期望：local_search -> hyde_search -> answer
实际：local_search 后直接 answer 或 refuse
结果：wrong_action_path
```

最终 5 条 HyDE case 全部被记为失败，但这 5 条不能据此归因为“模型不会使用 HyDE”。

## 四、根因不是 Milvus，而是离线环境信息损失

### 1. 离线快照只保存了最终正确证据

现有 case 能说明“最终答案依赖哪个 chunk”，却没有形成统一的逐 Action Observation：

```text
local_search_observation
hyde_search_observation
web_search_observation
```

最终正确证据被保留了，但“第一次为什么不足、第二次怎样改善”的过程信息没有进入正式回放契约。

### 2. local search 和 HyDE 被压缩成同一种返回

快照 Provider 对 `local_search` 和 `hyde_search` 复用了同一个候选构造函数，只修改
retrieval channel（检索通道）标记，没有保留真实候选集合和排名差异。

这相当于把：

```text
原始检索未命中
HyDE 检索后命中
```

压缩成：

```text
两次检索都直接返回标准答案
```

### 3. 原本用于链路验证的简化实现被用于路线质量准入

快照 Provider 最初的合理目标是：

- 不依赖 Milvus 和 Web；
- 确定性验证 Planner 状态机；
- 验证 Reward、Citation（引用）和数据导出契约；
- 让单元测试和离线 smoke（冒烟测试）稳定复现。

它能够证明“评测管线可执行”，但不能自然证明“多条检索路线的前置条件真实”。9.3.16 将其用于
HyDE、安全拒绝等多路线模型准入时，原有简化边界被突破。

### 4. Evaluator 的严格路径判断放大了矛盾

HyDE 路线能力测试严格要求完整 Action path，本身并没有错；否则无法证明模型是否会在证据不足时
升级到 HyDE。

问题是 Provider 已经把证据提前给足，Evaluator 却仍按“证据不足”的路线判分。严格判分将上游
Observation 错误放大为 5 条模型失败。

## 五、为什么多轮审核没有发现

此前多轮审核主要验证：

- 问题是否来自真实文档；
- 答案是否能追溯到来源 chunk；
- 来源、版本和 SHA256 是否正确；
- 原始检索与 HyDE 后排名改善是否有探针依据；
- case 是否重复或泄漏到 train/dev/test；
- 路线标签和用户意图是否合理。

这些属于静态 Case 审核。审核包没有真正启动：

```text
Planner
-> SnapshotExpectedChunkActionProvider
-> Offline Environment
-> Evaluator
```

也没有检查“同一 case 在每个 Action 下到底返回什么 Observation”。

因此，审核并非没有价值，而是覆盖了数据与标签层，没有覆盖运行时回放契约层。9.3.16 是第一次让
正式 checkpoint、离线 Provider 和严格 Evaluator 在完整 25 条均衡开发集上联合运行，问题才被
暴露。

## 六、问题是怎样被发现的

发现过程不是先猜代码，而是从结果逐层缩小范围：

1. 正式 SFT v1 在 25 条 balanced dev 上得到 8/25，五路线宏平均为 0.32。
2. 按路线桶查看，HyDE 为 0/5；4 条为 `local_search -> answer`，1 条安全边界问题为
   `local_search -> refuse`，共同点是都没有进入 `hyde_search`。
3. 运行中没有格式错误、执行失败或禁止动作，说明不是模型服务异常。
4. 检查逐步 Observation，发现第一次 local search 已出现目标 chunk、0.95 高分和答案要点。
5. 回到 case 检索探针，确认原始问题本应未进 Top 5，HyDE 后才提升到 Rank 1。
6. 继续追踪 Provider 代码，确认 local search 和 HyDE 都调用同一批 `expected_chunks`。
7. 最终将 5 条 HyDE 归因为 evaluator false negative（评测器误判），而不是模型错误。

这个过程体现了一个重要工程原则：

> 评测失败不能直接归因于模型，必须沿 Case、Provider、Observation、Planner 和 Evaluator
> 的完整数据流逐层核查。

## 七、为什么这是一个有价值的错误

### 1. 它发生在 heldout 和 9.4 之前

问题在 balanced dev 阶段被发现，没有运行密封 heldout test，也没有使用错误结论进入 9.4。
门禁发挥了作用。

### 2. 它暴露的是抽象边界，不是单个 if 错误

真正问题不是把一个分数从 0.95 改成 0.20，而是：

- 离线环境应该冻结哪些事实；
- Provider 接口怎样保留真实检索语义；
- 模型错误和环境错误如何区分；
- 确定性回放与真实端到端验证怎样分层。

这些是可迁移到其他 Agent、RAG 和强化学习项目的工程经验。

### 3. 它避免了错误补训练数据

如果直接把 5 条失败当成模型能力不足，就会根据受污染的评测结果补 HyDE 训练样本。模型可能被
训练成“看到高质量答案仍继续搜索”，既增加成本，也破坏及时停止能力。

### 4. 它没有推翻已有数据建设

文档来源、问题、答案、哈希、泄漏检查和真实检索探针都能继续使用。需要重建的是逐 Action
Observation 回放层，而不是推翻全部 case。

## 八、后续修复方案

### 1. 冻结真实的逐 Action Observation

先使用 `MilvusActionProvider`（真实检索动作执行器）执行并记录：

```text
local_search:
  query
  Top K chunks
  retrieval/rerank score
  index_version
  retrieval config

hyde_search:
  hypothetical query
  Top K chunks
  retrieval/rerank score
  index_version
  retrieval config
```

安全拒绝 case 还必须保存真实手册警告证据，不能因 `should_answer=false` 返回空候选。

### 2. 正式模型对比使用可审计回放

模型选择阶段使用 `ReplayActionProvider`（检索结果回放执行器）原样回放已记录 Observation，
而不是重新访问不断变化的 Milvus，也不再根据标准答案临时构造候选。

这样可以同时保证：

- 结果确实来源于真实检索；
- 所有 checkpoint 看到相同环境；
- local search 与 HyDE 的结果不会混淆；
- 回放记录能通过 snapshot_id、index_version 和 SHA256 审计。

### 3. 分开两类评测

`route capability test`（路线能力测试）：

- 构造第一次本地检索确实不足的环境；
- 严格检查模型是否进入 HyDE；
- 用于证明特定路线能力。

`policy quality test`（策略质量测试）：

- 允许多条安全、正确的可接受路线；
- 比较答案、证据、引用、成本和延迟；
- 允许更短且同样正确的路线获得更高 Reward。

不能用一套“唯一固定路径”同时承担这两种目标。

### 4. 增加运行时契约测试

至少增加以下回归测试：

- HyDE case 的首次 local search 不包含目标 chunk 或明确低于证据阈值；
- HyDE 后目标 chunk 的排名和冻结探针一致；
- 安全拒绝 case 的 local search 能返回手册警告；
- 回放记录的 case_id、Action、query、snapshot_id 和 index_version 一致；
- Provider 不允许用 `should_answer`直接决定是否返回检索证据；
- Evaluator 报告分别标注模型错误、Provider 错误和不可归因结果。

### 5. 当前落地状态

9.3.18 已完成本地代码实现：

- 保留 `MilvusActionProvider`（真实检索执行器）和
  `SnapshotExpectedChunkActionProvider`（快照冒烟执行器）的原有职责，不把快照执行器改造成
  另一套伪 Milvus。
- 新增 expanded dev 真实动作录制入口，只录制 `acceptable_action_paths`（可接受动作路径）
  实际需要的 local/HyDE/Web 动作。Web-only 或直接追问样本不能为了补记录而放宽主体和权限
  范围；完整标准查询集合共 32 条动作记录。
- 新增回放契约校验器，拒绝非真实 Milvus 来源、缺动作、快照或配置漂移、HyDE 目标提前进入
  local Top 5，以及安全警告未进入 local Top 5。
- 模型评测入口已支持严格 `ReplayActionProvider`；缺少精确
  `case_id + Action + query` 记录时明确失败，不静默改用标准答案候选。

2026-07-30 已在本地生成 32 条真实记录，Mongo、Milvus、BGE-M3、HyDE LLM 和 Web MCP
均连通，Provider error 为 0。记录 SHA256 为
`37c6888e0c3c462d7bf3e0128e94c9a304b40d47dfa9ce98a168ea8a4dcb9644`。

但路线契约只通过 `5/10`：HyDE 为 `2/5`，安全拒绝为 `3/5`。这说明“替换失真的离线
Provider”只是第一步；真实召回又暴露出 3 条 HyDE 与 2 条安全拒绝 case 的路线前提不成立。
当前必须保留 `ok=false`，不能把这些记录直接用于模型准入，也不能为了通过门禁伪造候选或修改
分数。

## 九、修复完成的验收标准

- 5 条 HyDE 均能证明“首次检索不足、HyDE 后改善”。
- 5 条安全拒绝均能看到支持拒绝的来源证据。
- Observation 来自真实 Provider 记录或其不可变回放，不再根据最终标签临时构造。
- 同一回放输入在重复运行中 hash（哈希）一致。
- Reward v1.1 的正确轨迹仍稳定高于错误轨迹。
- 保持 SFT v1 checkpoint、25 条 dev 和 Reward 不变重新评测，校正真实模型失败数量。
- 修复前后的报告同时保留，不能覆盖历史失败证据。

## 十、面试价值

### 1. 面试官真正会关注什么

这次经历的价值不在于“我跑了一个 SFT”，而在于能说明：

- 知道如何隔离模型能力和检索系统能力；
- 能识别 mock（模拟实现）或 replay（回放）失真；
- 不会把所有离线失败都归因于模型；
- 能沿多组件数据流完成失败归因；
- 会使用版本、快照、哈希和 heldout 门禁保证评测可信；
- 不会为了让指标通过而调低门槛或污染训练数据。

### 2. 30 秒面试表达

> 我在做 RAG Planner 的 SFT 评测时，发现 HyDE 路线 5 条全部失败，但模型实际都在第一次
> 本地检索后终止，4 条直接回答、1 条因安全边界拒绝。我没有马上补训练数据，而是沿
> Case、Provider、Observation 和
> Evaluator 逐层排查。最后发现离线 Snapshot Provider 为了确定性，直接把最终目标 chunk
> 同时返回给 local search 和 HyDE，丢失了真实 Milvus 中“原始检索未命中、HyDE 后命中”
> 的差异，造成评测器误判。后续方案是先记录真实 Milvus 的逐 Action Observation，再用
> 不可变 Replay Provider 做 checkpoint 对比，同时把路线能力评测和综合策略评测分开。

### 3. 2 分钟面试表达

> 项目中 Planner 会根据检索结果在 local search、HyDE、Web、回答、追问和拒绝之间决策。
> 为了让不同 checkpoint 的评测可重复，我们没有让模型选择阶段每次都访问动态 Milvus，而是
> 使用离线 Snapshot Provider。第一版 Provider 只保存最终正确 chunk，并让 local search 和
> HyDE 都返回同一批高分候选。
>
> 在 25 条均衡开发集的正式复评中，HyDE 桶是 0/5。模型都在 local search 后终止，
> 其中 4 条直接回答、1 条因安全边界拒绝，表面看像是不会 HyDE。但我检查逐步 Observation
> 后发现，它第一次检索就已经看到了目标
> chunk、0.95 分和答案要点。继续核对真实检索探针，确认原始查询本应未进 Top 5，HyDE 后
> 才到 Rank 1。因此问题不在 Milvus，也不能直接归因模型，而是离线回放丢失了逐 Action
> 语义，严格 Evaluator 又把上游环境错误放大成了模型失败。
>
> 我们没有修改 Reward 或降低门槛，也没有把 dev case 加进训练集，而是保留原始失败产物，
> 计划用真实 Milvus Provider 先记录每个 Action 的 Observation，再用带 snapshot_id、
> index_version 和哈希的 Replay Provider 做确定性模型比较；同时单独保留真实端到端检索
> 探针。这个问题让我认识到，评测可信度不仅取决于数据和模型，还取决于环境模拟是否忠实。

### 4. 常见追问

**为什么不直接一直使用真实 Milvus？**

真实 Milvus 适合端到端集成验证，但索引、语料、embedding 和 rerank 配置可能变化。模型选择需要
相同输入才能做公平归因，所以推荐“真实记录 + 不可变回放”，而不是每次动态检索。

**为什么不直接让 Evaluator 接受 `local_search -> answer`？**

如果目标是验证 HyDE 路线能力，第一次检索已经给足答案就无法验证该能力。应先修复环境，让
HyDE 的触发条件真实成立；综合策略评测再允许正确且低成本的替代路线。

**为什么审核没有发现？**

审核覆盖了来源、答案、路线依据、哈希和泄漏，没有执行完整 Provider/Observation 运行链。后续
必须把运行时契约测试加入数据冻结门禁。

**这次失败是否证明 SFT v1 其实可以通过？**

不能。即使把有争议的 HyDE 和安全拒绝两桶都按满分计算，五路线宏平均最好为 0.72，仍低于
0.80 门槛；Web 为 0/5 也低于单桶门槛。SFT v1 不进入 9.4 的决定仍然有效，只是 17 条失败
不能全部算成模型错误。

## 十一、不能夸大的边界

面试时不要说：

- “修复了线上 Milvus 召回事故”；
- “证明 SFT v1 已经具备 HyDE 能力”；
- “离线评测已经等价于真实线上环境”；
- “5 条 HyDE 都是模型正确”。

可以准确地说：

- 在正式 checkpoint 的离线均衡开发集评测中发现环境回放失真；
- 通过逐轨迹和代码链定位到 Provider/Observation 契约；
- 阻止了错误补训练数据和错误调整 Reward；
- 建立了“真实记录、不可变回放、端到端探针分层”的修复方案；
- 修复后的复评尚未完成，因此不提前宣称模型能力提升。
