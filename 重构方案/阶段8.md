# 阶段 8：评测与 Demo 数据

## 背景与目标

阶段 5 已经把查询链路改造成 `Planner -> Action -> Observation -> Trace -> Citation` 的闭环，阶段 6 补齐了 chunk 启停和审计，阶段 7 补齐了 Dataset、Document、Conversation、Retrieval Test、Trace 和 Feedback 的管理 API。

阶段 8 的任务不是训练模型，而是把这些能力整理成一个可复现的离线评测系统。只有先能稳定回答“当前系统好在哪里、差在哪里、和什么 baseline 比较”，阶段 9 的 SFT/GRPO 才有意义。

本阶段目标：

- 准备 10-20 条高质量设备运维 Demo 回归样本，用于面试展示和快速冒烟。
- 构建规模更大的 Planner 训练候选池，覆盖真实问题、文档约束合成问题和人工改写问题。
- 明确区分公共 demo 知识库评测和用户私有文档评测。
- 固化 train/dev/test 拆分，held-out test 不参与调参、Reward 权重选择、Prompt 选择、模型选择或训练轨迹挑选。
- 固化可重放的离线 RAG Environment，能执行指定 Action 序列并产出 Observation、Trace 和 Reward 明细。
- 建立 `RuleBasedPlanner`、顶级 API Planner、本地开源零样本 Planner 三类 baseline。
- 定义阶段 9 训练要使用的 Reward v1 契约。
- 从高质量规则轨迹、通过筛选的 API 轨迹和人工标注中导出 SFT 数据。
- 输出可复现评测报告，作为面试 Demo 和阶段 9 对照基线。

术语边界：

- `Demo 回归集`：少量高质量展示样本，用于面试演示和快速回归，不进入 GRPO 训练。
- `Planner 训练候选池`：规模更大的问题与轨迹候选来源，经过 Reward 或人工复核后才能导出 SFT/训练数据。
- `held-out test`：最终保留测试集，中文可以理解为“隔离考试集”。它不能参与任何规则、权重、Prompt 或模型选择。
- `Environment`：离线执行环境。它接收 State 和 Action，执行本地检索、HyDE、Web 或终止动作，返回 Observation 和 Trace。
- `State`：一次查询的运行时状态快照，包含用户、dataset、主体、当前 Action history、检索配置和当前 Observation。
- `Action`：Planner 允许输出的固定动作，例如 `local_search`、`hyde_search`、`web_search`、`answer`、`ask_clarification`、`refuse`。
- `Observation`：Action 执行后的可验证事实，例如候选数量、rerank 分数、命中标识、引用数量、耗时和错误码。
- `Trace`：一次查询的结构化追踪记录，用于复盘 Action、Observation、引用、配置、成本和终态，不保存模型私有思维链。
- `Reward`：奖励函数。它把一条轨迹按格式、检索、引用、答案、行为和成本拆分评分，阶段 9 用它判断训练方向。
- `baseline`：基线方案。用于证明新 Planner 是否真正优于当前规则、强 API 参考和本地零样本起点。
- `SFT`：监督微调。这里用于学习结构化输出、基本路由和合法状态转移，不等同于 GRPO。
- `reward hacking`：模型钻奖励规则空子，例如为了提高检索分不断调用 HyDE/Web 或伪造引用。因此 Reward 必须保存分项。

## 核心设计决策

### 1. Demo 回归集和训练候选池必须物理分开

Demo 回归集服务面试展示和快速回归，不服务训练。

推荐文件边界：

```text
evaluation/stage8/cases/demo_regression_cases.jsonl
evaluation/stage8/cases/planner_cases.jsonl
evaluation/stage8/cases/split_manifest.json
```

`demo_regression_cases.jsonl` 只能用于：

- 面试演示。
- 每次重构后的冒烟检查。
- 说明系统能围绕设备手册、报警码、维护 SOP 展示。

它不能用于：

- SFT 训练。
- GRPO 训练。
- API teacher 轨迹筛选。
- Prompt 选择。
- Reward 权重调节。

如果某条 Demo 问题也需要出现在训练候选池，必须改写为不同问题，并设置相同 `leakage_group_id`，让拆分工具强制它们不跨训练和测试边界。

### 2. 评测样本使用文件化契约，Trace/Feedback 只是来源证据

阶段 7 的 `retrieval_traces` 和 `trace_feedbacks` 是高质量数据来源，但不应直接当最终评测集。

原因：

- Trace 是一次运行结果，可能受当时配置和语料状态影响。
- Feedback 是人工标注来源，可能不完整。
- 训练和评测需要稳定 split、版本、样本 ID 和来源说明。

阶段 8 应新增文件化样本，作为评测真相来源：

```text
evaluation/stage8/cases/planner_cases.jsonl
```

Trace/Feedback 的作用是帮助生成候选样本。最终进入 JSONL 前必须经过 schema 校验，关键样本需要人工复核。

### 3. split 必须按泄漏组和来源文档隔离

单纯随机切分 query 不够。设备运维问题里，同一文档、同一报警码、同一 SOP 的改写问题很容易泄漏。

阶段 8 拆分规则：

- 同一个 `leakage_group_id` 必须只出现在一个 split。
- 同一组 query 改写、口语变体、错别字变体必须只出现在一个 split。
- 能按文档隔离时，优先把同一 `source_document_id` 放入同一 split。
- 如果文档太少导致无法完全按文档隔离，必须在 `split_manifest.json` 中记录例外原因。
- `test` 只做最终评测，不参与 dev 调整。
- `demo_regression` 是独立用途，不算 train/dev/test。

推荐 split：

| split | 中文用途 | 是否可用于调参 | 是否可用于训练 |
|---|---|---|---|
| `train` | 训练候选 | 可以用于 SFT/阶段 9 训练 | 可以 |
| `dev` | 开发验证 | 可以用于规则、Reward 权重、Prompt 和模型候选选择 | 不直接作为最终报告 |
| `test` | 隔离测试 | 不可以 | 不可以 |
| `demo_regression` | 面试展示和快速回归 | 不可以 | 不可以 |

### 4. Environment 必须读取快照，而不是读取当前线上漂移状态

阶段 8 的离线评测要证明可复现。只记录 `retrieval_config_version` 不够，还要记录实际快照。

环境快照至少包含：

- dataset 列表。
- document 列表。
- 每个 document 的 `index_version`。
- 每个 document 的 chunk 数量。
- 当前 enabled chunk 快照。
- 当前 `chunk_status_overrides` 中的 disabled chunk。
- 检索配置快照。
- Planner 策略版本。
- reranker 配置。
- 答案模型配置。
- Web fallback 开关。
- 评测固定用户。

离线 Environment 执行时必须优先使用快照中的状态。当前 Mongo 或 Milvus 状态和快照不一致时，默认报错或标记 `corpus_match_status=mismatch`，不能静默继续当作同一评测。

### 5. Reward 必须是分项结果，不只保存总分

阶段 9 最容易出现的问题是 Reward 看起来变高，但实际行为变坏。例如：

- 多次调用 HyDE/Web 换取略高召回。
- 对本应拒答的问题硬答。
- 引用了非期望 chunk。
- 输出格式合法但 Action 路径不合理。

因此每条轨迹必须保存：

- `R_format`
- `R_retrieval`
- `R_citation`
- `R_answer`
- `R_behavior`
- `R_cost`
- `total_reward`
- 每个分项的证据明细和扣分原因。

阶段 8 先定义 Reward v1，权重只允许在 dev 上确定。确定后写入 `reward_version`，并在 test 评测中冻结使用。

### 6. API teacher 只是候选来源，不是标准答案

顶级 API Planner 可以作为强能力参考和 teacher 候选，但不能直接把它的轨迹当训练标签。

进入 SFT 数据需要满足至少一个条件：

- 轨迹通过 Environment Reward 阈值。
- 人工复核通过。
- 与规则轨迹或人工期望路径一致。

不能进入 SFT 的情况：

- Reward 低。
- 格式非法。
- 引用无效。
- 对本应追问或拒答的问题直接回答。
- 使用了 held-out test 样本。
- 使用了 Demo 回归样本。

### 7. 本地 Planner 模型先验证兼容性，再冻结 checkpoint

阶段 8 不锁死具体训练 checkpoint。

候选策略：

- 首选候选：`Qwen3.5-4B`，优先验证小模型训练和本地部署性价比。
- 升级对照：`Qwen3.5-9B`，仅当 4B 结构化输出和基本路由明显不足时再评估。

阶段 8 要冻结的是“兼容性证据”，不是训练结果：

- `model_id`
- `revision`
- `tokenizer`
- `chat_template`
- 量化配置
- 是否使用非思考模式
- 结构化输出解析成功率
- 单条推理延迟
- 显存/内存占用

这些信息必须写入 baseline 结果，阶段 9 才能公平比较 SFT/GRPO 的提升和部署成本。

## 数据契约

### 评测样本：PlannerEvalCase

`planner_cases.jsonl` 每行一条 JSON。

建议字段：

| 字段 | 类型/形态 | 含义 | 边界 |
|---|---|---|---|
| `case_id` | string | 样本稳定 ID | 全局唯一，不能复用。 |
| `case_group` | enum string | 样本分组 | `core/colloquial/private_doc/realtime/refusal/clarification/demo`。 |
| `split` | enum string | 数据用途 | `train/dev/test/demo_regression`。 |
| `leakage_group_id` | string | 泄漏隔离组 | 同组样本不能跨 split。 |
| `query` | string | 用户原始问题 | 评测入口原样使用。 |
| `query_variants` | list[string] | 同义改写候选 | 只用于构建数据，不默认全部评测。 |
| `dataset_ids` | list[string] | 固定知识库范围 | 必须通过权限校验。 |
| `owner_user_id` | string | 固定测试用户 | 避免用户隔离导致召回范围漂移。 |
| `tenant_id` | string | 固定租户 | 当前通常为 `tenant_default`。 |
| `privacy_scope` | enum string | 数据范围 | `public_demo/private_user`。 |
| `source_document_ids` | list[string] | 来源文档 | 用于泄漏隔离和报告说明。 |
| `source_index_versions` | object | 文档索引版本 | key 为 document_id，value 为 index_version。 |
| `expected_subject_ids` | list[string] | 期望主题 ID | 稳定主键，不用展示名代替。 |
| `expected_subject_names` | list[string] | 期望主题名称 | 用于报告展示。 |
| `expected_chunks` | list[object] | 期望证据 chunk | 必须包含 document_id、chunk_id、index_version。 |
| `expected_answer_points` | list[string] | 期望答案要点 | 用于答案覆盖评估。 |
| `expected_behavior` | object | 期望行为 | 是否回答、拒答、追问、调用 Web。 |
| `acceptable_action_paths` | list[list[string]] | 可接受 Action 路径 | 允许多条合法路径。 |
| `expected_identifiers` | object | 期望结构化标识 | 例如设备型号、报警码、SOP 编号。 |
| `label_source` | enum string | 标注来源 | `manual/feedback/api_assisted/synthetic`。 |
| `human_review_status` | enum string | 人工复核状态 | `reviewed/pending/rejected`。 |
| `notes` | string | 备注 | 可为空，不参与评分。 |

`expected_chunks` 建议结构：

| 字段 | 类型/形态 | 含义 |
|---|---|---|
| `document_id` | string | 文档 ID |
| `chunk_id` | string/int | chunk ID |
| `index_version` | int | 文档索引版本 |
| `relevance` | enum string | `required/supporting/acceptable` |
| `answer_point_ids` | list[string] | 该 chunk 支撑的答案要点 |

## 离线 RAG Environment 设计

### 目标接口

阶段 8 推荐实现一个不依赖 FastAPI 的离线环境类：

```python
class OfflineRagEnvironment:
    def reset(self, case: PlannerEvalCase, snapshot: EnvironmentSnapshot) -> OfflineState:
        ...

    def step(self, state: OfflineState, decision: PlannerDecision) -> StepResult:
        ...

    def run_action_path(self, case: PlannerEvalCase, actions: list[PlannerDecision]) -> TrajectoryResult:
        ...

    def run_planner(self, case: PlannerEvalCase, planner: QueryPlanner) -> TrajectoryResult:
        ...
```

中文边界：

- `reset`：根据评测样本和快照创建初始 State。
- `step`：执行一个 PlannerDecision，并返回 Observation。
- `run_action_path`：用于执行外部传入的固定 Action 序列。
- `run_planner`：用于让 rule/api/local_base 自己逐步决策并执行。

### 初始 State 构造

Environment 必须从 case 和 snapshot 构造稳定 State：

- `session_id` 使用 `eval_{run_id}_{case_id}_{planner_mode}`。
- `owner_user_id` 使用 case 中固定用户。
- `tenant_id` 使用 case 中固定租户。
- `dataset_ids` 使用 case 中固定范围。
- `original_query` 使用 case 原始问题。
- `query_identifiers` 使用确定性提取结果，并与 case 标注对比。
- `subject_ids` 优先使用 case 的 `expected_subject_ids`，避免主体 LLM 波动污染 Planner 评测。
- `retrieval_mode` 使用 snapshot 中冻结模式。
- `retrieval_config_snapshot` 使用 snapshot 中冻结参数。
- `web_search_allowed` 使用 snapshot 或 case 的 Web 边界。
- `disabled_chunk_ids` 使用 snapshot，不读取当前 Mongo 漂移状态。
- `history_persistence_enabled=False`。
- `trace_persistence_enabled` 第一版可以写 JSON 文件；如写 Mongo，必须设置 `execution_source=evaluation`。

阶段 8 评测重点是 Planner 轨迹和检索/引用质量，不是主体识别 LLM 的鲁棒性。主体识别可以作为扩展子评测，但默认主评测应固定主体标注。

### Action 执行

Environment 支持六类 Action：

| Action | 执行方式 | 结果 |
|---|---|---|
| `local_search` | 调用现有本地检索、RRF、rerank、Observation 生成 | 返回本地候选 Observation |
| `hyde_search` | 调用 HyDE 检索、累计融合、rerank、Observation 生成 | 返回 HyDE 后 Observation |
| `web_search` | 按 case/snapshot 判断是否允许联网 | 返回 Web Observation 或受控失败 |
| `answer` | 调用答案生成或评测简化答案生成 | 返回答案、Citation 和终态 |
| `ask_clarification` | 生成追问终态 | 返回终态 |
| `refuse` | 生成拒答终态 | 返回终态 |

执行约束：

- 每次 step 都复制 State，不允许候选轨迹互相污染。
- 非法 Action 转移直接产生 `R_format=0` 或格式错误，不继续伪造结果。
- `web_search` 对 public demo 可以默认关闭，除非 case 标注 `should_call_web=true`。
- 如果 Web 真的执行，必须记录 provider、query、URL、耗时和失败原因。
- 不能把 Web 结果伪装成本地 chunk 引用。
- 不能保存模型私有思维链。

### 轨迹重放

阶段 7 的 replay API 目前只是在线重跑。阶段 8 要补完整离线重放：

- 输入：历史 `trace_id` 或显式 Action 序列。
- 校验：原 trace 的 `retrieval_config_snapshot` 是否和快照一致。
- 校验：原 trace 命中的 `document_id + chunk_id + index_version` 是否仍在快照内。
- 执行：按原 Action 序列逐步执行。
- 输出：
  - `config_match_status`
  - `corpus_match_status`
  - 新 trace 或 JSON trace 文件
  - Observation 差异
  - Reward 差异

如果配置或语料不一致，默认不把新结果纳入正式对比，只输出诊断报告。

## Reward v1 设计

### 总体结构

Reward v1 输出：

```json
{
  "reward_version": "reward-v1",
  "total_reward": 0.86,
  "sub_scores": {
    "R_format": 1.0,
    "R_retrieval": 0.9,
    "R_citation": 1.0,
    "R_answer": 0.8,
    "R_behavior": 1.0,
    "R_cost": 0.7
  },
  "weights": {
    "R_format": 0.15,
    "R_retrieval": 0.25,
    "R_citation": 0.20,
    "R_answer": 0.20,
    "R_behavior": 0.15,
    "R_cost": 0.05
  },
  "details": {}
}
```

权重原则：

- 第一版权重只在 dev 上确定。
- test 运行前必须冻结 `reward_version` 和权重。
- 如果某个 case 本身不应该回答，`R_answer` 应按拒答/追问场景调整，不因没有答案要点而误扣。
- `R_format` 是门槛项。格式非法或 Action 非法时，总分应强制上限，例如不超过 0.2。
- `R_cost` 不能权重过高，避免模型为了省成本不检索就拒答。

### R_format

评价 Planner 输出是否可执行。

检查项：

- 是否能通过 `PlannerDecision` schema 校验。
- `action` 是否属于六个固定 Action。
- `query` 是否非空。
- `reason_code` 是否属于已知枚举。
- Action 转移是否合法。
- 是否超过 `PLANNER_MAX_STEPS`。
- 本地引用是否伪造 document/chunk/dataset/index 身份。
- Web 引用是否伪造本地 chunk 身份。

扣分示例：

- JSON 解析失败：0。
- Action 未知：0。
- 少必要字段：0。
- 重复执行同一检索 Action：最多 0.5。
- 终止后继续输出 Action：最多 0.3。

### R_retrieval

评价检索是否命中期望证据。

指标：

- `recall@k`
- `MRR`
- `nDCG`
- 关键标识命中率
- `identifier_resolution_status` 是否符合标注

建议计算：

- 必需 chunk 命中权重大于 supporting chunk。
- 首个相关 chunk 越靠前，MRR 越高。
- expected identifiers 不匹配时，即使召回文本相似也要扣分。
- 本应追问的相近报警码场景，不能把相近码当命中。

### R_citation

评价最终引用是否有效。

检查项：

- 最终 citation 是否来自期望 chunk 或有效 supporting chunk。
- citation 是否携带 `document_id + chunk_id + index_version`。
- citation 是否来自当前 snapshot 的 enabled chunk。
- citation 是否越权引用私有文档。
- Web citation 是否包含真实 URL。

扣分示例：

- answer 使用了本地证据但没有 citation。
- citation 指向非当前 index_version。
- citation 指向 disabled chunk。
- citation 指向未授权 dataset。
- 引用了无关 chunk。

### R_answer

评价答案是否覆盖要点并保持事实一致。

第一版优先使用可复现规则：

- `expected_answer_points` 可以配置关键词、正则或人工短句。
- 对设备型号、报警码、SOP 编号做精确字符串校验。
- 对安全提醒、排查顺序、拒答措辞做可执行规则。

LLM Judge 只能作为补充：

- 必须记录 judge provider、model_id、prompt_version。
- judge 结果不能覆盖明确的引用/标识错误。
- judge 原因不能包含私有思维链。
- judge 只写分项，不替代总 Reward 规则。

特殊场景：

- `should_refuse=true` 时，答案越具体越应该扣分。
- `should_ask_clarification=true` 时，不应因没有答案要点而扣 `R_answer`，应主要看 `R_behavior`。
- `should_call_web=true` 时，如果本地资料没有实时信息，不能因为本地 chunk 未命中就简单判 0，要看 Web 引用和答案事实。

### R_behavior

评价 Planner 行为是否符合标注。

检查项：

- 是否应该回答。
- 是否应该拒答。
- 是否应该追问。
- 是否应该调用 Web。
- 是否调用了 forbidden actions。
- 实际 Action path 是否在 `acceptable_action_paths` 中。
- 终止原因码是否符合预期。

扣分示例：

- 本应拒答却回答：0。
- 本应追问却直接回答：0。
- 本地知识问题无必要 Web：扣分。
- 明显实时问题不调用 Web：扣分。
- 本地证据充分仍继续 HyDE/Web：扣分。

### R_cost

评价轨迹成本是否合理。

成本项：

- Planner 步数。
- HyDE 调用次数。
- Web 调用次数。
- Planner token。
- 答案 token。
- 总延迟。
- provider 计费估算。

原则：

- 成本只做轻权重惩罚。
- 对 `should_call_web=true` 的 case，Web 调用不算不必要成本。
- 对本地证据低分且 HyDE 合理补充的 case，HyDE 不应被重罚。
- 对重复 Action、无限接近上限的路径要明显扣分。

## baseline 设计

### RuleBasedPlanner baseline

当前线上默认策略，也是最低可用线。

### 顶级 API Planner baseline

强能力参考和 teacher 候选。

执行方式：

- 离线执行，不启用线上。
- API Planner 只输出结构化 `PlannerDecision`，不能直接调用工具。
- API Planner 不生成最终答案，答案仍由 Environment 的 answer Action 执行。
- 使用严格 JSON schema 或等价结构化输出。
- 记录 provider、model_id、model_revision、prompt_version、token、耗时和成本。

约束：

- 输出非法 Action 直接计入 `R_format` 扣分。
- 不能把 API 的自然语言解释写入 Trace 作为私有思维链。
- API teacher 轨迹不直接进入 SFT。
- 只有通过 Reward 阈值或人工复核的 train/dev 轨迹才能导出。
- test 和 demo 轨迹不得进入训练数据。

### 本地开源零样本 Planner baseline

评估本地模型在未训练状态下的起点。

执行方式：

- 使用候选本地模型进行结构化 Planner 输出。
- 第一版只做零样本，不做 SFT/GRPO。
- 支持非思考模式，避免输出大段不可用推理文本。
- 对输出做严格 schema 校验和错误记录。

需要记录：

- `model_id`
- `revision`
- `tokenizer`
- `chat_template`
- 量化配置
- 推理后端
- 推理设备
- 平均延迟
- P95 延迟
- 格式通过率
- Action 合法率
- Reward 分项

判断标准：

- 如果 4B 格式通过率、基本路由和延迟可接受，阶段 9 优先用 4B 做 SFT。
- 如果 4B 无法稳定输出结构化 Action，再用 9B 做对照。
- 不因为 9B 更大就默认选择 9B。选择依据必须来自阶段 8 评测。

## 建议实施顺序

第一步先做 `PlannerEvalCase` schema、模板样本和 split 校验。没有稳定数据契约，后面的 Environment、Reward 和 baseline 都会反复改。

第二步做 environment snapshot 和 `rule` baseline 一键运行。先证明当前规则系统在固定环境下可复现。

第三步做 Reward v1 和报告。先让评测结果可解释，再接 API/local baseline。

第四步接 API Planner 和本地零样本 Planner。它们都只能作为离线 baseline，不进入线上默认查询。

第五步做 SFT 导出。只有当 Reward 和人工复核边界清楚后，再把轨迹转成训练数据。

阶段 8 不追求“训练出模型”，只追求把训练前的地基做扎实：数据边界清楚、评测可复现、Reward 可解释、baseline 可对比。
