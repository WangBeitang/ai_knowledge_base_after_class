# 第一部分：查询输入、身份与知识库范围契约

阶段 5 第一部分的核心不是立刻实现 Planner、BM25 或查询权限过滤，而是先把一次查询的入口上下文固定下来：查询在进入 LangGraph 之前，必须明确知道“谁在查询、属于哪个 tenant、允许查询哪些 dataset”。

阶段核心判断是：

```text
查询链路只有先拥有稳定、显式的身份和知识库范围，后续权限过滤、Planner Trace、评测重放才有可信输入。
```

原来的查询入口是：

```text
POST /query
    -> 读取 query / session_id / is_stream
    -> 创建 QueryGraphState
    -> 同步执行查询图，或创建 SSE 队列后调度后台任务
    -> LangGraph 执行主体确认和检索
```

原来的 `QueryGraphState` 只知道：

```text
session_id
original_query
is_stream
```

它不知道：

```text
当前查询用户是谁
当前 tenant 是什么
本次查询目标 dataset 是哪些
```

这会带来几个实际问题：

- 阶段 4 已经把 `owner_user_id`、`tenant_id`、`visibility`、`dataset_id` 写入 Milvus chunk，但查询入口没有当前用户和知识库范围，后续无法构造可靠的权限过滤条件。
- 导入页已经要求 `X-User-Id`，查询页却没有携带相同身份，同一个匿名用户的“导入”和“查询”上下文没有对齐。
- 查询 API 没有 dataset 输入契约，后续如果直接在检索节点里临时决定默认知识库，不同节点可能出现不一致行为。
- 同步查询和流式后台查询走两条调用路径，如果上下文只在其中一条路径补充，最终会出现同一接口两种行为。
- 无身份请求原来可以进入查询图，等到后续实现私有文档过滤时，才临时回退到公共匿名用户会产生串数据风险。

改完后的入口是：

```text
POST /query
    -> 校验 X-User-Id
    -> 规范化 dataset_ids
    -> 缺少身份：直接返回 400，不创建 SSE 队列，不进入 LangGraph
    -> dataset 范围非法：直接返回 422，不进入 LangGraph
    -> 创建 QueryGraphState
       owner_user_id = 当前 X-User-Id
       tenant_id = tenant_default
       dataset_ids = 已规范化的知识库列表
    -> 同步执行或携带相同上下文调度流式后台任务
```

这一步没有改变当前检索算法，但把后续查询链路需要依赖的三个关键上下文变成了稳定契约。

## 1. 查询和导入开始使用同一套轻量身份入口

阶段 3.5 已经在导入 API 中使用：

```http
X-User-Id: user_xxx
```

阶段 5 第一部分没有在查询服务里再复制一套相似逻辑，而是新增共享的 HTTP 请求上下文解析函数：

```text
app/api/http/request_context.py
    -> get_current_user_id(request)
```

导入 API 和查询 API 现在都复用这个函数。

统一后的规则是：

```text
读取 X-User-Id
    -> 去除首尾空白
    -> 非空：作为当前 owner_user_id
    -> 缺失或全空白：返回 400
```

### 1.1 为什么不能自动回退 anonymous_user

看起来最省事的实现是：

```text
没有 X-User-Id
    -> owner_user_id = anonymous_user
```

但这种做法会把所有忘记传 header 的调用方合并成同一个用户。

在当前第一部分，它会掩盖请求构造错误；等后续查询过滤接入后，它还可能造成：

```text
用户 A 忘记传 header ─┐
                      ├-> 都被识别为 anonymous_user
用户 B 忘记传 header ─┘
```

所以当前选择是尽早失败：

```text
身份不明确
    -> HTTP 400
    -> 不进入查询图
```

这不是增加调用负担，而是让错误发生在最接近请求入口的位置，避免错误身份继续流入检索、Trace 和历史记录。

### 1.2 身份校验为什么必须早于 SSE 和后台任务

流式查询原来的路径是：

```text
POST /query
    -> create_sse_queue(session_id)
    -> BackgroundTasks.add_task(query_graph_invoke)
```

阶段 5 第一部分把身份校验放在这两个动作之前：

```text
POST /query
    -> get_current_user_id(request)
    -> 身份合法后，才创建 SSE 队列或调度后台任务
```

这样缺失身份的请求不会留下：

- 没有实际执行者的 SSE 队列。
- 已调度但缺少 owner 上下文的后台任务。
- 进入 `task_utils` 的伪查询状态。
- 无法解释归属的后续 Trace。

这个顺序体现的是入口校验边界：请求上下文不完整时，不产生任何查询执行副作用。

### 1.3 X-User-Id 仍然不是生产级鉴权

当前 `X-User-Id` 是浏览器生成并主动发送的轻量用户标识。

它能解决的是：

```text
当前匿名用户在导入和查询过程中使用同一个 owner 标识
```

它不能解决：

- 用户是否真的拥有这个 ID。
- 调用方是否伪造其他用户 ID。
- 登录、注册、密码、JWT。
- 管理员角色、RBAC、组织权限。
- 可信的服务端身份认证。

所以准确表述是：

```text
阶段 5 第一部分固化了轻量用户上下文，没有实现生产级身份安全。
```

## 2. dataset_ids 成为明确的查询输入契约

`QueryRequestParam` 原来只有：

```text
query
session_id
is_stream
```

阶段 5 第一部分新增：

```text
dataset_ids: list[str]
```

这个字段表示：

```text
调用方希望本次查询限定在哪些知识库范围内执行
```

它不是查询结果，也不是系统自动识别出来的 dataset，更不是完整权限判断结果。

### 2.1 不传 dataset_ids 时使用默认知识库

为了保持当前单知识库 Demo 的调用方式不变，字段省略时使用：

```text
["dataset_default_equipment_ops"]
```

也就是原有前端不需要立刻增加知识库选择控件，现有查询请求仍然可以工作。

这里使用 `default_factory` 创建默认列表，避免不同请求共享同一个可变 list。

### 2.2 显式空列表为什么不回退默认值

当前对“字段省略”和“显式传空”做了区分：

```text
未传 dataset_ids
    -> 调用方没有指定范围
    -> 使用默认知识库

dataset_ids = []
    -> 调用方明确传入了一个空范围
    -> 返回 422
```

如果把显式空列表也自动改成默认知识库，会掩盖前端或调用方的状态错误。

更重要的是，在后续权限过滤阶段，“空范围”不应该被偷偷扩大成“默认范围”。因此当前选择是让调用方修正请求，而不是在后端猜测意图。

全空白列表也按空范围处理：

```text
["", "   ", "\n"]
    -> 去空后没有有效 dataset
    -> 返回 422
```

### 2.3 去空、保序去重和数量上限

`dataset_ids` 的规范化顺序是：

```text
去除每个 ID 首尾空白
    -> 丢弃空字符串
    -> 按第一次出现顺序去重
    -> 校验不同 dataset 数量不超过 10
```

例如：

```text
[" dataset_b ", "dataset_a", "dataset_b", ""]
```

规范化后是：

```text
["dataset_b", "dataset_a"]
```

采用保序去重，而不是转成无序 set 后直接返回，原因是：

- API 返回和日志更容易复现。
- 后续 Trace 中的请求上下文顺序稳定。
- 测试可以准确断言输入经过了什么转换。
- 不会因为集合遍历顺序让相同请求产生不必要差异。

第一版最多允许 10 个不同 dataset。这个限制不是性能优化结论，而是给后续 Milvus 过滤表达式和 Planner 输入设置明确上界，避免单次查询携带无限增长的知识库列表。

### 2.4 dataset_ids 不等于多知识库自动路由

新增 `dataset_ids` 后，调用方可以显式提供查询范围，但当前尚未实现：

- 根据用户问题自动判断应该查哪个 dataset。
- 校验当前用户是否是某个 dataset 的成员。
- Dataset 管理 API。
- Planner 在多个 dataset 之间自主选择。
- 根据 dataset 优先级动态扩展或缩小范围。

因此不能把这一部分表述成“已经实现多知识库查询系统”。

更准确的说法是：

```text
查询入口已经能够接收并规范化显式 dataset 范围，真正使用该范围过滤召回结果属于后续任务。
```

## 3. QueryGraphState 补齐跨节点查询上下文

阶段 5 第一部分在 `QueryGraphState` 中新增：

```text
owner_user_id: str
tenant_id: str
dataset_ids: list[str]
```

三个字段分别表示：

| 字段 | 当前含义 | 来源 | 后续用途 |
|---|---|---|---|
| `owner_user_id` | 当前轻量查询用户 | `X-User-Id` | owner/visibility 检索过滤、Trace 归属 |
| `tenant_id` | 当前租户上下文 | 默认 `tenant_default` | shared 范围和后续租户过滤 |
| `dataset_ids` | 本次目标知识库范围 | `QueryRequestParam` | Milvus dataset 过滤、评测重放 |

### 3.1 为什么要在 API 入口写入 state

另一种做法是等到检索节点执行时，再从 HTTP Request、环境变量或 Mongo 临时获取这些值。

当前没有这样做，原因是 LangGraph 节点应该依赖明确的 state 输入，而不是隐式依赖已经离开调用边界的 HTTP 对象。

现在的数据流是：

```text
HTTP Request
    -> 校验 owner_user_id
QueryRequestParam
    -> 规范化 dataset_ids
共享默认配置
    -> tenant_default

三者在 query_graph_invoke 汇合
    -> create_query_default_state(...)
    -> QueryGraphState
    -> 后续所有节点读取同一份查询上下文
```

这样后续新增权限过滤或 Planner 时，不需要让每个节点重复解析请求。

### 3.2 同步和流式查询使用相同契约

查询 API 当前有两条执行路径：

```text
is_stream = false
    -> 当前请求直接调用 query_graph_invoke

is_stream = true
    -> BackgroundTasks 调用 query_graph_invoke
```

阶段 5 第一部分在两条路径中都显式传递：

```text
owner_user_id
dataset_ids
```

`query_graph_invoke` 再统一补入：

```text
tenant_id = tenant_default
```

这使同步和流式只在“如何交付结果”上不同，不会在“本次查询属于谁、查哪些知识库”上产生分叉。

### 3.3 dataset_ids 在写入 state 时再次复制

Pydantic 已经为请求创建了独立 list，`query_graph_invoke` 写入 state 时仍然执行一次复制：

```text
dataset_ids = list(dataset_ids)
```

这样后台任务和调用方不会意外共享同一个可变对象。

同时，`query_graph_default_state` 中的 `dataset_ids` 默认值也和其他 list/dict 状态一样通过深拷贝创建，避免不同查询之间互相污染。

这个细节的价值不在于当前代码会主动修改 dataset 列表，而在于提前保证 state 的隔离语义，为后续 Planner 多步执行和 Trace 重放减少隐蔽状态污染。

### 3.4 tenant_default 只是当前上下文默认值

当前查询 state 固定写入：

```text
tenant_id = "tenant_default"
```

这是为了与阶段 3.5/4 已经写入 document 和 chunk 的默认 tenant 对齐。

它不表示当前已经完成：

- 多租户识别。
- tenant 成员管理。
- tenant 级鉴权。
- tenant 之间的查询隔离验收。

当前价值只是让查询 state 不再缺失 tenant 维度。后续如果真实登录身份能够提供 tenant，入口可以替换默认值，而不需要推翻 state 契约。

## 4. 导入和查询共享知识库默认值

阶段 5 第一部分把下面默认值集中到共享配置：

```text
DEFAULT_DATASET_ID = "dataset_default_equipment_ops"
DEFAULT_TENANT_ID = "tenant_default"
DEFAULT_VISIBILITY = "private"
```

原来这些值主要定义在导入元数据 repository 中。查询入口如果继续复制字符串，会出现：

```text
导入默认写入 dataset A
查询默认读取 dataset B
```

这种问题不会在类型检查阶段暴露，却会表现成“文档导入成功但查询不到”。

重构后：

```text
导入 repository ─┐
                 ├-> knowledge_base_config.py
查询 schema/API ─┘
```

共享默认值不是新增业务能力，但它让导入和查询对 dataset/tenant/visibility 的基础语义保持一致，也避免查询层为了读取常量去依赖导入持久化 repository。

## 5. 聊天页开始传递稳定用户上下文

后端强制要求 `X-User-Id` 后，现有聊天页也必须同步升级，否则所有浏览器查询都会直接返回 400。

阶段 5 第一部分在聊天页复用导入页相同的 localStorage key：

```text
USER_ID_STORAGE_KEY = "kb_user_id"
```

页面初始化逻辑是：

```text
读取 localStorage.kb_user_id
    -> 已存在：继续复用
    -> 不存在：生成 user_xxx
    -> 写回 localStorage
```

`POST /query` 现在携带：

```http
Content-Type: application/json
X-User-Id: currentUserId
```

这让一次浏览器查询从只有 session 上下文：

```text
session_id = 这次对话是谁
```

扩展为同时拥有：

```text
user_id = 当前匿名用户是谁
session_id = 当前对话会话是谁
```

两者不能混为一谈：

| 字段 | 表示什么 | 当前用途 |
|---|---|---|
| `owner_user_id` | 用户归属 | 进入 QueryGraphState，为后续文档可见范围过滤准备 |
| `session_id` | 一次对话会话 | 历史消息、SSE 和查询任务进度 |

### 5.1 localStorage 的同源边界

复用相同 key 能保证同一 origin 下的导入页和查询页使用相同用户标识。

但浏览器 localStorage 按 origin 隔离，origin 包含协议、主机和端口。因此本地如果分别通过：

```text
http://127.0.0.1:8000/html
http://127.0.0.1:8001/html
```

访问导入页和查询页，即使 key 都叫 `kb_user_id`，两个端口也不会自动共享值。

当前可通过同源反向代理，或在联调时手动固定相同 `kb_user_id` 解决。阶段 5 第一部分没有为了这个开发环境问题引入登录系统或跨域身份同步协议。

## 6. 和原有逻辑的区别

| 对比项 | 重构前 | 阶段 5 第一部分后 |
|---|---|---|
| 查询身份 | `/query` 不读取用户身份 | 强制读取并规范化 `X-User-Id` |
| 缺失身份 | 仍可进入查询图 | 返回 400，不创建 SSE、不执行图 |
| dataset 输入 | 没有显式查询范围 | `dataset_ids` 成为请求契约 |
| 默认知识库 | 后续节点只能自行猜测或硬编码 | API schema 统一使用默认设备运维知识库 |
| 空 dataset | 没有定义 | 显式空/全空白返回 422 |
| 重复 dataset | 没有定义 | 去空后保序去重 |
| dataset 数量 | 没有上限 | 最多 10 个不同 dataset |
| 查询 state | 只有 session/query/stream 等查询字段 | 新增 owner/tenant/dataset 上下文 |
| 同步与流式 | 都没有身份/dataset 上下文 | 两条路径显式传递同一上下文 |
| 前端请求 | 只发送 JSON body | `/query` 同时发送 `X-User-Id` |
| 默认值来源 | 主要由导入 repository 定义 | 导入与查询共享知识库默认配置 |

这一部分不是替换 LangGraph、`session_id` 或现有检索节点，而是在它们之前补齐请求上下文层。

## 7. 关键取舍和边界

阶段 5 第一部分已经完成：

- 查询和导入 API 复用同一个 `get_current_user_id`。
- `/query` 缺失或空白 `X-User-Id` 返回 400。
- 身份校验发生在 SSE 队列和查询图执行之前。
- `QueryRequestParam` 新增并规范化 `dataset_ids`。
- `QueryGraphState` 新增 `owner_user_id`、`tenant_id`、`dataset_ids`。
- 同步和流式查询都传递相同上下文。
- 聊天页生成或复用 `kb_user_id`，查询请求携带 header。
- 导入和查询共享 dataset/tenant/visibility 默认值。

阶段 5 第一部分没有完成：

- 没有把 `owner_user_id`、`tenant_id`、`dataset_ids` 拼入 Milvus filter。
- 没有实现 `visibility=public/shared` 或 owner 私有文档过滤。
- 没有实现 `enabled=true` 过滤。
- 没有实现 `QueryPlanner`、Action、Observation 或 Retrieval Trace。
- 没有把 Web Search 改成 fallback。
- 没有实现 BM25 对比实验。
- 没有实现答案 citations。
- 没有实现 dataset 成员校验或自动路由。
- 没有改造 `/history/{session_id}` 的完整用户隔离。
- 没有把 `X-User-Id` 升级为可信鉴权。

这里最容易出现的过度解读是：

```text
QueryGraphState 已经有 owner_user_id
    ≠ 查询已经不会召回其他用户私有文档
```

当前只能确认：

```text
用户 A、用户 B 发起相同 query 时，进入图的 owner_user_id 不同。
```

真正阻止跨用户召回，必须在阶段 5 后续任务中让所有本地检索通道复用同一份 dataset/subject/enabled/visibility/owner 过滤表达式，并完成 user_a/user_b 的召回隔离测试。

## 8. 本部分的实际提升

这次重构没有直接提升召回率，也没有减少模型 token。它的价值是把查询链路从“只有问题和会话”升级为“拥有稳定执行上下文”。

具体提升：

- 无身份请求会在 HTTP 边界失败，不再进入查询图产生副作用。
- 导入和查询开始使用同一套轻量 owner 语义。
- dataset 范围有了默认、空值、去重和数量上限等确定行为。
- 同步和流式查询不会因调用路径不同而丢失用户或知识库上下文。
- 后续检索节点可以直接从 state 获取 owner、tenant、dataset，不需要读取 HTTP Request 或重复解析。
- 后续 Trace 可以记录明确的查询归属和知识库范围。
- 阶段 8 固定评测环境时，可以把 `owner_user_id + dataset_ids` 一起作为可重放输入。
- 真实身份接入后，可以替换入口身份来源而保留现有 state 字段和下游节点契约。

一句话总结：

```text
阶段 5 第一部分没有开始“选择检索动作”，而是先让后续每一次动作都知道自己代表谁、在哪个租户、允许面对哪些知识库。
```

```text
tests/test_query_api_stage5.py
tests/test_query_frontend_stage5.py
```

同时扩展：

```text
tests/test_state_defaults.py
```

关键覆盖包括：

- 显式空列表、全空白列表返回 422。
- 11 个不同 dataset 返回 422，正好 10 个允许。
- 缺失或空白 `X-User-Id` 返回 400。
- 流式缺失身份时不创建 SSE 队列，也不调用查询图。
- 非法 dataset 范围不会进入查询图。
- header 首尾空白会被去除。
- 同步路径传递规范化后的 owner/dataset。
- 流式后台路径传递 owner 和默认 dataset。
- 用户 A、用户 B 发起相同 query 时，state 中的 owner 不同。
- `dataset_ids` 默认值和查询 state 之间保持深拷贝隔离。
- 聊天页复用 `kb_user_id` 并发送 `X-User-Id`。
- 共享身份解析和知识库默认值没有破坏既有导入 API、repository 和图编译行为。

## 10. 后续阶段为什么依赖这次重构

后续检索权限过滤需要：

```text
owner_user_id
tenant_id
dataset_ids
```

后续 RuleBasedPlanner 和 Retrieval Trace 需要：

```text
明确的初始查询上下文
固定的知识库范围
可追踪的用户归属
同步/流式一致的 state
```

阶段 8 的离线评测和阶段 9 的模型 Planner rollout 也必须知道轨迹是在什么用户和 dataset 环境中产生的。否则同一个 query 的召回候选可能因为权限范围不同而变化，Reward 和对比结果就不可复现。

因此这部分的依赖价值是：

```text
先固定查询环境的输入边界
    -> 再实现权限过滤
    -> 再让 Planner 基于结构化 Observation 决策
    -> 最后才有可比较、可重放的轨迹和策略优化基础
```
