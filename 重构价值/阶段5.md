# 第一部分：查询输入、身份与知识库范围契约

阶段 5 第一部分的核心不是立刻实现 Planner、BM25 或查询权限过滤，而是先把一次查询的入口上下文固定下来：查询在进入 LangGraph 之前，必须明确知道“谁在查询、属于哪个 tenant、允许查询哪些 dataset”。

阶段核心判断是：

```text
查询链路只有先拥有稳定、显式的身份和知识库范围，后续权限过滤、Planner Trace、评测重放才有可信输入。
```

原来的查询入口是：

```text
POST /query
    -> 读取 query / session_id / is_stream
    -> 创建 QueryGraphState
    -> 同步执行查询图，或创建 SSE 队列后调度后台任务
    -> LangGraph 执行主体确认和检索
```

原来的 `QueryGraphState` 只知道：

```text
session_id
original_query
is_stream
```

它不知道：

```text
当前查询用户是谁
当前 tenant 是什么
本次查询目标 dataset 是哪些
```

这会带来几个实际问题：

- 阶段 4 已经把 `owner_user_id`、`tenant_id`、`visibility`、`dataset_id` 写入 Milvus chunk，但查询入口没有当前用户和知识库范围，后续无法构造可靠的权限过滤条件。
- 导入页已经要求 `X-User-Id`，查询页却没有携带相同身份，同一个匿名用户的“导入”和“查询”上下文没有对齐。
- 查询 API 没有 dataset 输入契约，后续如果直接在检索节点里临时决定默认知识库，不同节点可能出现不一致行为。
- 同步查询和流式后台查询走两条调用路径，如果上下文只在其中一条路径补充，最终会出现同一接口两种行为。
- 无身份请求原来可以进入查询图，等到后续实现私有文档过滤时，才临时回退到公共匿名用户会产生串数据风险。

改完后的入口是：

```text
POST /query
    -> 校验 X-User-Id
    -> 规范化 dataset_ids
    -> 缺少身份：直接返回 400，不创建 SSE 队列，不进入 LangGraph
    -> dataset 范围非法：直接返回 422，不进入 LangGraph
    -> 创建 QueryGraphState
       owner_user_id = 当前 X-User-Id
       tenant_id = tenant_default
       dataset_ids = 已规范化的知识库列表
    -> 同步执行或携带相同上下文调度流式后台任务
```

这一步没有改变当前检索算法，但把后续查询链路需要依赖的三个关键上下文变成了稳定契约。

## 1. 查询和导入开始使用同一套轻量身份入口

阶段 3.5 已经在导入 API 中使用：

```http
X-User-Id: user_xxx
```

阶段 5 第一部分没有在查询服务里再复制一套相似逻辑，而是新增共享的 HTTP 请求上下文解析函数：

```text
app/api/http/request_context.py
    -> get_current_user_id(request)
```

导入 API 和查询 API 现在都复用这个函数。

统一后的规则是：

```text
读取 X-User-Id
    -> 去除首尾空白
    -> 非空：作为当前 owner_user_id
    -> 缺失或全空白：返回 400
```

### 1.1 为什么不能自动回退 anonymous_user

看起来最省事的实现是：

```text
没有 X-User-Id
    -> owner_user_id = anonymous_user
```

但这种做法会把所有忘记传 header 的调用方合并成同一个用户。

在当前第一部分，它会掩盖请求构造错误；等后续查询过滤接入后，它还可能造成：

```text
用户 A 忘记传 header ─┐
                      ├-> 都被识别为 anonymous_user
用户 B 忘记传 header ─┘
```

所以当前选择是尽早失败：

```text
身份不明确
    -> HTTP 400
    -> 不进入查询图
```

这不是增加调用负担，而是让错误发生在最接近请求入口的位置，避免错误身份继续流入检索、Trace 和历史记录。

### 1.2 身份校验为什么必须早于 SSE 和后台任务

流式查询原来的路径是：

```text
POST /query
    -> create_sse_queue(session_id)
    -> BackgroundTasks.add_task(query_graph_invoke)
```

阶段 5 第一部分把身份校验放在这两个动作之前：

```text
POST /query
    -> get_current_user_id(request)
    -> 身份合法后，才创建 SSE 队列或调度后台任务
```

这样缺失身份的请求不会留下：

- 没有实际执行者的 SSE 队列。
- 已调度但缺少 owner 上下文的后台任务。
- 进入 `task_utils` 的伪查询状态。
- 无法解释归属的后续 Trace。

这个顺序体现的是入口校验边界：请求上下文不完整时，不产生任何查询执行副作用。

### 1.3 X-User-Id 仍然不是生产级鉴权

当前 `X-User-Id` 是浏览器生成并主动发送的轻量用户标识。

它能解决的是：

```text
当前匿名用户在导入和查询过程中使用同一个 owner 标识
```

它不能解决：

- 用户是否真的拥有这个 ID。
- 调用方是否伪造其他用户 ID。
- 登录、注册、密码、JWT。
- 管理员角色、RBAC、组织权限。
- 可信的服务端身份认证。

所以准确表述是：

```text
阶段 5 第一部分固化了轻量用户上下文，没有实现生产级身份安全。
```

## 2. dataset_ids 成为明确的查询输入契约

`QueryRequestParam` 原来只有：

```text
query
session_id
is_stream
```

阶段 5 第一部分新增：

```text
dataset_ids: list[str]
```

这个字段表示：

```text
调用方希望本次查询限定在哪些知识库范围内执行
```

它不是查询结果，也不是系统自动识别出来的 dataset，更不是完整权限判断结果。

### 2.1 不传 dataset_ids 时使用默认知识库

为了保持当前单知识库 Demo 的调用方式不变，字段省略时使用：

```text
["dataset_default_equipment_ops"]
```

也就是原有前端不需要立刻增加知识库选择控件，现有查询请求仍然可以工作。

这里使用 `default_factory` 创建默认列表，避免不同请求共享同一个可变 list。

### 2.2 显式空列表为什么不回退默认值

当前对“字段省略”和“显式传空”做了区分：

```text
未传 dataset_ids
    -> 调用方没有指定范围
    -> 使用默认知识库

dataset_ids = []
    -> 调用方明确传入了一个空范围
    -> 返回 422
```

如果把显式空列表也自动改成默认知识库，会掩盖前端或调用方的状态错误。

更重要的是，在后续权限过滤阶段，“空范围”不应该被偷偷扩大成“默认范围”。因此当前选择是让调用方修正请求，而不是在后端猜测意图。

全空白列表也按空范围处理：

```text
["", "   ", "\n"]
    -> 去空后没有有效 dataset
    -> 返回 422
```

### 2.3 去空、保序去重和数量上限

`dataset_ids` 的规范化顺序是：

```text
去除每个 ID 首尾空白
    -> 丢弃空字符串
    -> 按第一次出现顺序去重
    -> 校验不同 dataset 数量不超过 10
```

例如：

```text
[" dataset_b ", "dataset_a", "dataset_b", ""]
```

规范化后是：

```text
["dataset_b", "dataset_a"]
```

采用保序去重，而不是转成无序 set 后直接返回，原因是：

- API 返回和日志更容易复现。
- 后续 Trace 中的请求上下文顺序稳定。
- 测试可以准确断言输入经过了什么转换。
- 不会因为集合遍历顺序让相同请求产生不必要差异。

第一版最多允许 10 个不同 dataset。这个限制不是性能优化结论，而是给后续 Milvus 过滤表达式和 Planner 输入设置明确上界，避免单次查询携带无限增长的知识库列表。

### 2.4 dataset_ids 不等于多知识库自动路由

新增 `dataset_ids` 后，调用方可以显式提供查询范围，但当前尚未实现：

- 根据用户问题自动判断应该查哪个 dataset。
- 校验当前用户是否是某个 dataset 的成员。
- Dataset 管理 API。
- Planner 在多个 dataset 之间自主选择。
- 根据 dataset 优先级动态扩展或缩小范围。

因此不能把这一部分表述成“已经实现多知识库查询系统”。

更准确的说法是：

```text
查询入口已经能够接收并规范化显式 dataset 范围，真正使用该范围过滤召回结果属于后续任务。
```

## 3. QueryGraphState 补齐跨节点查询上下文

阶段 5 第一部分在 `QueryGraphState` 中新增：

```text
owner_user_id: str
tenant_id: str
dataset_ids: list[str]
```

三个字段分别表示：

| 字段 | 当前含义 | 来源 | 后续用途 |
|---|---|---|---|
| `owner_user_id` | 当前轻量查询用户 | `X-User-Id` | owner/visibility 检索过滤、Trace 归属 |
| `tenant_id` | 当前租户上下文 | 默认 `tenant_default` | shared 范围和后续租户过滤 |
| `dataset_ids` | 本次目标知识库范围 | `QueryRequestParam` | Milvus dataset 过滤、评测重放 |

### 3.1 为什么要在 API 入口写入 state

另一种做法是等到检索节点执行时，再从 HTTP Request、环境变量或 Mongo 临时获取这些值。

当前没有这样做，原因是 LangGraph 节点应该依赖明确的 state 输入，而不是隐式依赖已经离开调用边界的 HTTP 对象。

现在的数据流是：

```text
HTTP Request
    -> 校验 owner_user_id
QueryRequestParam
    -> 规范化 dataset_ids
共享默认配置
    -> tenant_default

三者在 query_graph_invoke 汇合
    -> create_query_default_state(...)
    -> QueryGraphState
    -> 后续所有节点读取同一份查询上下文
```

这样后续新增权限过滤或 Planner 时，不需要让每个节点重复解析请求。

### 3.2 同步和流式查询使用相同契约

查询 API 当前有两条执行路径：

```text
is_stream = false
    -> 当前请求直接调用 query_graph_invoke

is_stream = true
    -> BackgroundTasks 调用 query_graph_invoke
```

阶段 5 第一部分在两条路径中都显式传递：

```text
owner_user_id
dataset_ids
```

`query_graph_invoke` 再统一补入：

```text
tenant_id = tenant_default
```

这使同步和流式只在“如何交付结果”上不同，不会在“本次查询属于谁、查哪些知识库”上产生分叉。

### 3.3 dataset_ids 在写入 state 时再次复制

Pydantic 已经为请求创建了独立 list，`query_graph_invoke` 写入 state 时仍然执行一次复制：

```text
dataset_ids = list(dataset_ids)
```

这样后台任务和调用方不会意外共享同一个可变对象。

同时，`query_graph_default_state` 中的 `dataset_ids` 默认值也和其他 list/dict 状态一样通过深拷贝创建，避免不同查询之间互相污染。

这个细节的价值不在于当前代码会主动修改 dataset 列表，而在于提前保证 state 的隔离语义，为后续 Planner 多步执行和 Trace 重放减少隐蔽状态污染。

### 3.4 tenant_default 只是当前上下文默认值

当前查询 state 固定写入：

```text
tenant_id = "tenant_default"
```

这是为了与阶段 3.5/4 已经写入 document 和 chunk 的默认 tenant 对齐。

它不表示当前已经完成：

- 多租户识别。
- tenant 成员管理。
- tenant 级鉴权。
- tenant 之间的查询隔离验收。

当前价值只是让查询 state 不再缺失 tenant 维度。后续如果真实登录身份能够提供 tenant，入口可以替换默认值，而不需要推翻 state 契约。

## 4. 导入和查询共享知识库默认值

阶段 5 第一部分把下面默认值集中到共享配置：

```text
DEFAULT_DATASET_ID = "dataset_default_equipment_ops"
DEFAULT_TENANT_ID = "tenant_default"
DEFAULT_VISIBILITY = "private"
```

原来这些值主要定义在导入元数据 repository 中。查询入口如果继续复制字符串，会出现：

```text
导入默认写入 dataset A
查询默认读取 dataset B
```

这种问题不会在类型检查阶段暴露，却会表现成“文档导入成功但查询不到”。

重构后：

```text
导入 repository ─┐
                 ├-> knowledge_base_config.py
查询 schema/API ─┘
```

共享默认值不是新增业务能力，但它让导入和查询对 dataset/tenant/visibility 的基础语义保持一致，也避免查询层为了读取常量去依赖导入持久化 repository。

## 5. 聊天页开始传递稳定用户上下文

后端强制要求 `X-User-Id` 后，现有聊天页也必须同步升级，否则所有浏览器查询都会直接返回 400。

阶段 5 第一部分在聊天页复用导入页相同的 localStorage key：

```text
USER_ID_STORAGE_KEY = "kb_user_id"
```

页面初始化逻辑是：

```text
读取 localStorage.kb_user_id
    -> 已存在：继续复用
    -> 不存在：生成 user_xxx
    -> 写回 localStorage
```

`POST /query` 现在携带：

```http
Content-Type: application/json
X-User-Id: currentUserId
```

这让一次浏览器查询从只有 session 上下文：

```text
session_id = 这次对话是谁
```

扩展为同时拥有：

```text
user_id = 当前匿名用户是谁
session_id = 当前对话会话是谁
```

两者不能混为一谈：

| 字段 | 表示什么 | 当前用途 |
|---|---|---|
| `owner_user_id` | 用户归属 | 进入 QueryGraphState，为后续文档可见范围过滤准备 |
| `session_id` | 一次对话会话 | 历史消息、SSE 和查询任务进度 |

### 5.1 localStorage 的同源边界

复用相同 key 能保证同一 origin 下的导入页和查询页使用相同用户标识。

但浏览器 localStorage 按 origin 隔离，origin 包含协议、主机和端口。因此本地如果分别通过：

```text
http://127.0.0.1:8000/html
http://127.0.0.1:8001/html
```

访问导入页和查询页，即使 key 都叫 `kb_user_id`，两个端口也不会自动共享值。

当前可通过同源反向代理，或在联调时手动固定相同 `kb_user_id` 解决。阶段 5 第一部分没有为了这个开发环境问题引入登录系统或跨域身份同步协议。

## 6. 和原有逻辑的区别

| 对比项 | 重构前 | 阶段 5 第一部分后 |
|---|---|---|
| 查询身份 | `/query` 不读取用户身份 | 强制读取并规范化 `X-User-Id` |
| 缺失身份 | 仍可进入查询图 | 返回 400，不创建 SSE、不执行图 |
| dataset 输入 | 没有显式查询范围 | `dataset_ids` 成为请求契约 |
| 默认知识库 | 后续节点只能自行猜测或硬编码 | API schema 统一使用默认设备运维知识库 |
| 空 dataset | 没有定义 | 显式空/全空白返回 422 |
| 重复 dataset | 没有定义 | 去空后保序去重 |
| dataset 数量 | 没有上限 | 最多 10 个不同 dataset |
| 查询 state | 只有 session/query/stream 等查询字段 | 新增 owner/tenant/dataset 上下文 |
| 同步与流式 | 都没有身份/dataset 上下文 | 两条路径显式传递同一上下文 |
| 前端请求 | 只发送 JSON body | `/query` 同时发送 `X-User-Id` |
| 默认值来源 | 主要由导入 repository 定义 | 导入与查询共享知识库默认配置 |

这一部分不是替换 LangGraph、`session_id` 或现有检索节点，而是在它们之前补齐请求上下文层。

## 7. 关键取舍和边界

阶段 5 第一部分已经完成：

- 查询和导入 API 复用同一个 `get_current_user_id`。
- `/query` 缺失或空白 `X-User-Id` 返回 400。
- 身份校验发生在 SSE 队列和查询图执行之前。
- `QueryRequestParam` 新增并规范化 `dataset_ids`。
- `QueryGraphState` 新增 `owner_user_id`、`tenant_id`、`dataset_ids`。
- 同步和流式查询都传递相同上下文。
- 聊天页生成或复用 `kb_user_id`，查询请求携带 header。
- 导入和查询共享 dataset/tenant/visibility 默认值。

阶段 5 第一部分没有完成：

- 没有把 `owner_user_id`、`tenant_id`、`dataset_ids` 拼入 Milvus filter。
- 没有实现 `visibility=public/shared` 或 owner 私有文档过滤。
- 没有实现 `enabled=true` 过滤。
- 没有实现 `QueryPlanner`、Action、Observation 或 Retrieval Trace。
- 没有把 Web Search 改成 fallback。
- 没有实现 BM25 对比实验。
- 没有实现答案 citations。
- 没有实现 dataset 成员校验或自动路由。
- 没有改造 `/history/{session_id}` 的完整用户隔离。
- 没有把 `X-User-Id` 升级为可信鉴权。

这里最容易出现的过度解读是：

```text
QueryGraphState 已经有 owner_user_id
    ≠ 查询已经不会召回其他用户私有文档
```

当前只能确认：

```text
用户 A、用户 B 发起相同 query 时，进入图的 owner_user_id 不同。
```

真正阻止跨用户召回，必须在阶段 5 后续任务中让所有本地检索通道复用同一份 dataset/subject/enabled/visibility/owner 过滤表达式，并完成 user_a/user_b 的召回隔离测试。

## 8. 本部分的实际提升

这次重构没有直接提升召回率，也没有减少模型 token。它的价值是把查询链路从“只有问题和会话”升级为“拥有稳定执行上下文”。

具体提升：

- 无身份请求会在 HTTP 边界失败，不再进入查询图产生副作用。
- 导入和查询开始使用同一套轻量 owner 语义。
- dataset 范围有了默认、空值、去重和数量上限等确定行为。
- 同步和流式查询不会因调用路径不同而丢失用户或知识库上下文。
- 后续检索节点可以直接从 state 获取 owner、tenant、dataset，不需要读取 HTTP Request 或重复解析。
- 后续 Trace 可以记录明确的查询归属和知识库范围。
- 阶段 8 固定评测环境时，可以把 `owner_user_id + dataset_ids` 一起作为可重放输入。
- 真实身份接入后，可以替换入口身份来源而保留现有 state 字段和下游节点契约。

一句话总结：

```text
阶段 5 第一部分没有开始“选择检索动作”，而是先让后续每一次动作都知道自己代表谁、在哪个租户、允许面对哪些知识库。
```

同时扩展：

- 缺失或空白 `X-User-Id` 返回 400。
- 流式缺失身份时不创建 SSE 队列，也不调用查询图。
- 非法 dataset 范围不会进入查询图。
- header 首尾空白会被去除。
- 同步路径传递规范化后的 owner/dataset。
- 流式后台路径传递 owner 和默认 dataset。
- 用户 A、用户 B 发起相同 query 时，state 中的 owner 不同。
- `dataset_ids` 默认值和查询 state 之间保持深拷贝隔离。
- 聊天页复用 `kb_user_id` 并发送 `X-User-Id`。
- 共享身份解析和知识库默认值没有破坏既有导入 API、repository 和图编译行为。

专项验证结果：


## 10. 后续阶段为什么依赖这次重构

后续检索权限过滤需要：

```text
owner_user_id
tenant_id
dataset_ids
```

后续 RuleBasedPlanner 和 Retrieval Trace 需要：

```text
明确的初始查询上下文
固定的知识库范围
可追踪的用户归属
同步/流式一致的 state
```

阶段 8 的离线评测和阶段 9 的模型 Planner rollout 也必须知道轨迹是在什么用户和 dataset 环境中产生的。否则同一个 query 的召回候选可能因为权限范围不同而变化，Reward 和对比结果就不可复现。

因此这部分的依赖价值是：

```text
先固定查询环境的输入边界
    -> 再实现权限过滤
    -> 再让 Planner 基于结构化 Observation 决策
```


# 第二部分：Planner、Action、Observation 与引用契约

阶段 5 第二部分没有直接修改 LangGraph 路由，而是先把 Planner 与执行环境之间要交换的数据定义成稳定、可校验的业务协议。

阶段核心判断是：

```text
先固定 Planner 的输入、输出、动作、观察和引用契约，再实现规则策略和图路由。
```

如果不先定义契约，后续很容易变成：

```text
Planner 返回任意 dict
    -> 节点靠字符串猜 action
    -> reason code 散落在 if/else 中
    -> Observation 混入完整 chunk 和自由文本分析
    -> Rule Planner 与 Model Planner 各用一套格式
    -> Trace、评测和训练数据无法稳定复用
```

第二部分改完后，协议关系变成：

```text
PlannerContext
    -> QueryPlanner.plan(context)
    -> PlannerDecision
       action: QueryAction
       query: str
       reason_code: PlannerReasonCode

执行 Action
    -> RetrievalObservation
       结构化数量、分数、证据、耗时和错误

最终 answer 证据
    -> Citation
       本地 document/chunk 或 Web URL
```

这些对象目前还是独立契约，尚未接入 `QueryGraphState` 和 LangGraph。它们解决的是“后续节点之间按照什么协议通信”，而不是提前实现完整 Planner 流程。

## 1. QueryAction 把路由动作从魔法字符串升级为枚举

阶段 5 固定的 Action 是：

```text
local_search
hyde_search
web_search
answer
ask_clarification
refuse
```

如果直接在各处写字符串：

```python
if action == "local_serach":
    ...
```

拼写错误只有运行到该分支时才会暴露，而且错误值还可能先进入 state、Mongo Trace 或 API。

现在使用 Python 标准库 Enum：

```python
class QueryAction(str, Enum):
    LOCAL_SEARCH = "local_search"
    HYDE_SEARCH = "hyde_search"
    WEB_SEARCH = "web_search"
    ANSWER = "answer"
    ASK_CLARIFICATION = "ask_clarification"
    REFUSE = "refuse"
```

它和 Java Enum 的核心作用一致：

| 能力 | Java | 当前 Python 实现 |
|---|---|---|
| 类型成员 | `QueryAction.LOCAL_SEARCH` | `QueryAction.LOCAL_SEARCH` |
| 稳定外部值 | 自定义字段或方法 | `.value == "local_search"` |
| 从外部值解析 | `valueOf` 或自定义方法 | `QueryAction("local_search")` |
| 非法值 | 抛异常 | Enum/Pydantic 校验失败 |

这里继承 `str, Enum`，而不是只继承 `Enum`，是因为 Action 后续要进入：

- Pydantic JSON。
- LangGraph State。
- Mongo Retrieval Trace。
- API 调试响应。
- 阶段 8 评测数据。
- 阶段 9 Planner 训练样本。

代码内部使用 Enum 成员避免魔法字符串，对外持久化使用稳定的小写 value。

## 2. PlannerReasonCode 固化“为什么做这个动作”

`PlannerDecision` 不只需要告诉环境下一步执行什么，还要告诉 Trace 和评测系统命中了哪条规则。

第二部分新增固定 `PlannerReasonCode`，覆盖：

```text
subject_ambiguous
subject_required
subject_not_found
identifier_confirmation_required
identifier_not_found
realtime_query
initial_local_search
local_evidence_sufficient
local_empty
local_low_score
hyde_evidence_sufficient
hyde_still_insufficient
web_evidence_available
web_empty_or_failed
evidence_ambiguous
action_execution_error
safe_guard_triggered
```

reason code 的价值是让同一个 Action 可以区分不同原因。

例如同样执行 `web_search`，原因可能是：

```text
realtime_query
local_empty
hyde_still_insufficient
```

如果只记录 Action，后续只能知道“调用了 Web”，不知道为什么调用。

固定 reason code 后，可以在 Trace 和评测中统计：

- 有多少 Web 调用来自实时性规则。
- 有多少来自本地空召回。
- 有多少来自 HyDE 后仍证据不足。
- 有多少追问来自“只找到不同编号候选”或“完全未找到用户编号”。
- 哪些查询触发了安全兜底。
- 规则 Planner 和未来 Model Planner 的行为差异。

### 2.1 reason code 不是思维链

reason code 表达的是：

```text
命中了哪条可重放、可验证的决策规则
```

它不表达：

```text
模型内部是如何一步步思考的
```

因此当前允许：

```text
LOCAL_LOW_SCORE
```

不允许把下面内容塞进 reason code：

```text
“我仔细分析了用户问题，认为本地结果可能不够好，所以想继续搜索……”
```

这个边界既减少隐私和存储风险，也让 reason code 可以稳定进入统计、回归和训练数据。

## 3. PlannerDecision 成为 Planner 的唯一业务输出

`PlannerDecision` 定义为：

```text
action
query
reason_code
```

三者职责分别是：

| 字段 | 表示什么 | 不表示什么 |
|---|---|---|
| `action` | 下一步执行哪个固定动作 | 不是具体节点执行结果 |
| `query` | 该 Action 实际使用的查询文本 | 不是最终答案 |
| `reason_code` | 命中的机器可读规则 | 不是自由文本推理 |

Pydantic 会把合法字符串解析成 Enum：

```python
PlannerDecision(
    action="local_search",
    query="HAK 180 如何开机？",
    reason_code="initial_local_search",
)
```

序列化为 JSON 模式后仍是稳定字符串：

```json
{
  "action": "local_search",
  "query": "HAK 180 如何开机？",
  "reason_code": "initial_local_search"
}
```

非法 Action、非法 reason code、空白 query 和未知额外字段都会在契约边界被拒绝。

### 3.1 为什么所有契约都禁止额外字段

Pydantic 默认可能忽略模型未声明的字段。对于 Planner 协议，这种宽松行为会掩盖拼写错误。

例如：

```text
reason_code 写成 reason
```

或者未来模型输出：

```text
private_thought
chain_of_thought
```

当前公共基类统一配置：

```text
extra = forbid
str_strip_whitespace = true
validate_assignment = true
```

这意味着：

- 未声明字段直接报错。
- 必填字符串先去除首尾空白。
- 模型创建后修改字段也继续校验。

契约层选择严格失败，而不是静默吞掉错误。

## 4. QueryPlanner 使用 Protocol，而不是绑定具体父类

第二部分新增：

```python
class QueryPlanner(Protocol):
    policy_version: str

    def plan(self, context: PlannerContext) -> PlannerDecision:
        ...
```

Python `Protocol` 表达的是结构化接口：实现类不要求显式继承 `QueryPlanner`，只要提供相同属性和方法，就能被视为符合接口。

后续可以分别实现：

```text
RuleBasedPlanner
    policy_version = rule-v1
    plan(context) -> PlannerDecision

ModelPlanner
    policy_version = model-xxx
    plan(context) -> PlannerDecision
```

LangGraph 和 Action 执行节点只依赖：

```text
QueryPlanner
```

而不依赖：

- 规则 if/else 的具体文件。
- 某个 LLM SDK。
- GRPO 训练框架。
- Milvus 或 Mongo 客户端。

### 4.1 QueryPlanner 为什么不能访问外部 I/O

当前接口明确要求 `plan` 只读取 `PlannerContext` 并返回 `PlannerDecision`。

它不能在内部直接：

- 查询 Milvus。
- 访问 Mongo。
- 读取 FastAPI Request。
- 调用 Web Search。
- 执行检索节点。

未来 ModelPlanner 可以调用模型完成策略推理，但工具执行仍然属于环境节点；模型不能伪造已经执行过的 Observation。

这样才能形成清楚的交互边界：

```text
Planner 选择 Action
    -> Environment 执行 Action
    -> Environment 返回 Observation
    -> Planner 再决策
```

### 4.2 当前为什么没有放一个空 RuleBasedPlanner

第二部分已经定义稳定版本常量：

```text
rule-v1
```

但没有为了“看起来完成”创建一个 `plan()` 永远抛 `NotImplementedError` 的 `RuleBasedPlanner`。

具体规则包括：

- 主体歧义时追问。
- 初始本地检索。
- 本地高分时回答。
- 本地低分时 HyDE。
- 本地/HyDE 不足时 Web fallback。
- 最大步数和非法转移安全拒答。

这些属于阶段 5 后续规则策略任务。当前先让接口稳定，再实现完整纯函数规则，避免出现一个名字已经存在但行为不可用的假实现。

## 5. RetrievalObservation 只记录可验证事实

`RetrievalObservation` 表达一个检索 Action 执行后，环境返回给 Planner 的结果。

它记录：

```text
action
status
channel_counts
candidate_count
reranked_count
top_rerank_score
requested_identifiers
matched_identifiers
identifier_resolution_status
suggested_identifiers
citation_count
evidence_summaries
evidence_ambiguous
clarification_question
duration_ms
error_code
used_structured_filter
filter_fallback
```

这些字段可以回答：

- 哪个 Action 刚刚执行。
- dense/learned sparse/BM25 各召回多少。
- 去重后有多少候选。
- rerank 后保留多少结果。
- top rerank 分数是多少。
- 是否命中型号、报警码等精确标识。
- 命中的是用户原编号、metadata 漏填后的同编号，还是不同编号纠错候选。
- 哪些候选编号必须等待用户确认。
- 是否有足够引用候选。
- 是否发生结构化 filter 降级。
- 执行耗时和标准错误码是什么。

它不保存：

- Planner 私有思维过程。
- LLM 隐藏推理文本。
- “我认为证据不错”之类自由文本判断。
- 无限制的完整 chunk 正文。

### 5.1 Observation 状态也是关闭枚举

一个 Action 的执行状态限定为：

```text
success
empty
failed
```

并且契约会检查字段关系：

- `reranked_count` 不能大于 `candidate_count`。
- `citation_count` 不能大于 `reranked_count`。
- 有 rerank 结果时必须有 `top_rerank_score`。
- 没有 rerank 结果时 top score 必须为空。
- `empty` 不能携带候选、rerank 或证据摘要。
- `failed` 必须有机器可读 `error_code`。
- 非 failed Observation 不能混入错误码。
- 没有先使用结构化过滤，不能声称发生 filter fallback。
- 非 `not_applicable` 状态必须携带本次 Action 使用的 `requested_identifiers` 快照。
- `exact_match` 和 `fallback_exact_match` 必须携带实际 `matched_identifiers`，并覆盖所有请求编号。
- `fallback_exact_match` 必须记录 `filter_fallback=true`。
- `suggestion_required` 必须携带 `suggested_identifiers` 和追问文本，并且 `citation_count=0`。
- `not_found` 不能伪造任何 `matched_identifiers`，但必须给出核对编号的追问。

这些校验避免 Planner 收到自相矛盾的环境状态。

### 5.2 编号确认不是向量相似度判断

讨论 `E020` 与 `E021` 的纠错边界后，契约新增 `IdentifierResolutionStatus`：

```text
not_applicable
exact_match
fallback_exact_match
suggestion_required
not_found
```

三类标识数据必须分开：

```text
PlannerContext.query_identifiers
    = 用户问题中实际出现并归一化的编号

RetrievalObservation.requested_identifiers
    = 本次检索 Action 实际使用的用户编号快照

RetrievalObservation.matched_identifiers
    = 召回证据中实际出现的编号

RetrievalObservation.suggested_identifiers
    = 系统建议用户确认的不同编号候选
```

例如用户输入 `E020`，宽松召回只找到 `E021`：

```text
query_identifiers = {"alarm_code": ["E020"]}
requested_identifiers = {"alarm_code": ["E020"]}
matched_identifiers = {"alarm_code": ["E021"]}
identifier_resolution_status = suggestion_required
suggested_identifiers = {"alarm_code": ["E021"]}
citation_count = 0
```

即使 E021 的向量分数和 rerank 分数很高，也只能触发 `ask_clarification`。Observation 会直接校验 exact/fallback 的 `matched_identifiers` 必须覆盖 `requested_identifiers`，因此 E020 请求不能伪装成 E021 精确命中。如果 metadata 没填，但宽松召回的正文仍明确包含 `E020`，才可以标记 `fallback_exact_match` 并继续作为同编号答案证据。

## 6. EvidenceSummary 限制 Planner 可见正文

部分 Planner 决策不能只依赖一个 top score。

例如两个候选分数都很高，但分别属于：

```text
HAK 180
HAK 180 Pro
```

用户问题又没有说明版本。这时需要看少量受限证据摘要，判断是否应该追问。

因此 `EvidenceSummary` 保存：

```text
document_id
chunk_id
title
source_type
rerank_score
matched_identifiers
content_excerpt
```

但正文范围被明确限制：

```text
最多 5 条摘要
单条最多 500 字符
总计最多 2000 字符
```

这个限制有三个价值：

- 防止多步 Planner Context 越积越大。
- 控制后续 Model Planner token 成本。
- 避免 Trace 无意保存大量私有文档正文。

当前 `content_excerpt` 只属于运行时 Context。后续 Trace 持久化默认只保存 document/chunk 标识、分数、命中字段和摘要 hash，不能直接把正文片段完整落库。

### 6.1 evidence_ambiguous 必须对应可解释追问

当前契约要求：

```text
evidence_ambiguous = true
    -> clarification_question 必须非空

evidence_ambiguous = false
    -> clarification_question 必须为空
```

这避免节点只打一个“有歧义”标记，却不给 Planner 可执行的追问内容。

但契约只校验字段一致性，不负责判定歧义。后续必须由可重放规则判断，例如候选属于多个互不兼容型号且用户缺少区分信息；低分或候选数量多不能单独等同于歧义。

## 7. PlannerContext 固化每一步决策输入

`PlannerContext` 汇总一次 `plan()` 调用需要的结构化状态：

```text
original_query
current_query
subject_resolution_status
subject_ids
subject_candidates
clarification_question
query_identifiers
latest_observation
action_history
planner_step
max_steps
allowed_actions
```

它把决策所需信息分成几类：

| 类别 | 字段 | 作用 |
|---|---|---|
| 问题 | original/current query | 区分用户原话和当前执行查询 |
| 主体 | status/ids/candidates | 决定直接检索、追问或拒答 |
| 标识 | query_identifiers | 传递设备型号、报警码等结构化结果 |
| 最新环境结果 | latest_observation | 决定回答、继续检索或 fallback |
| 历史 | action_history | 防止重复动作和循环 |
| 安全约束 | step/max_steps/allowed_actions | 限制步骤和合法路由 |

`subject_resolution_status` 也使用关闭枚举：

```text
confirmed
ambiguous
not_found
no_mention
```

`allowed_actions` 至少包含一个 Action，并且不能重复，避免路由白名单自身存在歧义。

### 7.1 PlannerHistoryItem 记录的是已执行步骤

`PlannerHistoryItem` 当前包含：

```text
step
decision
execution_status
```

`step` 从 1 开始，执行终态限定为：

```text
completed
failed
```

未执行的 Decision 不应提前写入 history。后续完整 Trace 会继续记录 input/output Observation 和耗时，但当前 history 契约先解决 Planner 判断“已经做过哪些动作、执行是否失败”的最小需求。

## 8. Citation 把引用与答案文本分开

`Citation` 定义：

```text
document_id
chunk_id
title
source
score
source_type
```

当前来源类型限定为：

```text
local
web
```

本地引用必须包含：

```text
document_id
chunk_id
```

Web 引用的两个本地 ID 必须为空，`source` 保存 URL。

这个约束防止：

- 本地引用丢失 chunk 追踪能力。
- Web 结果伪造本地 document/chunk ID。
- 最终答案把来源只写成无法解析的自然语言。

Citation 由代码根据最终 reranked evidence 生成，不要求答案模型输出 JSON。这样答案措辞可以变化，但引用 ID 和分数仍然可验证。

需要注意：当前只完成 Citation 模型，`answer_service`、API、SSE 和聊天页还没有实际输出 citations；这属于阶段 5 后续引用链路任务。

## 9. 和原有逻辑的区别

| 对比项 | 重构前 | 阶段 5 第二部分后 |
|---|---|---|
| Action | 没有统一 Planner Action | 六个固定 `QueryAction` |
| 决策原因 | 没有统一 reason code | 17 个机器可读 `PlannerReasonCode` |

| 非法字段 | dict 可能静默携带任意内容 | Pydantic 禁止额外字段并校验一致性 |

第二部分没有替换现有检索节点，而是为后续重构定义一层稳定协议。

# 第三部分：扩展 QueryGraphState，并守住 partial state 边界

阶段 5 第三部分把第二部分定义的 Planner、Observation 和 Citation 契约放进 `QueryGraphState`，让一次查询从进入 LangGraph 开始就拥有完整、明确的跨节点数据位置。

这一部分仍然没有实现 Planner 决策和新图路由。它解决的是：后续 Planner 接入时，字段放在哪里、由谁写入、默认值代表什么、哪些信息只在运行时存在，以及节点怎样避免覆盖彼此状态。

一句话目标：

```text
先把查询运行时 State 变成可解释的数据协议，再让 Planner 和 Action 节点写入真实内容。
```

## 1. 为什么不能等 Planner 接图时再随手加字段

如果一边写 Planner 路由，一边临时往 State 中塞字段，容易出现下面的问题：

```text
同一概念出现多个名字
    -> planner_result / decision / current_action 混用

字段只写 dict
    -> 拼错字段名也可能静默运行

空值没有语义
    -> 不知道是“尚未执行”还是“执行后没有结果”

节点返回完整 State
    -> 并发分支把彼此的新结果覆盖成旧值

session_id 当 trace_id
    -> 同一会话多次查询无法区分
```

第三部分先固定这些边界，后续 `RuleBasedPlanner` 只需要填充已经定义好的位置，不需要再次修改整张 State。

## 2. QueryGraphState 是运行时状态，不是持久化模型

`State` 的中文含义是“状态”。`QueryGraphState` 表示一次查询在 LangGraph 各节点之间传递的运行时数据。

它和 Mongo Trace 的区别是：

```text
QueryGraphState
    -> 服务内存中的当前执行状态
    -> 可以包含下一节点马上要用的临时对象
    -> 查询结束后不会自动保存

Trace
    -> 从 State 和节点事件中选择必要字段形成的持久化记录
    -> 用于排错、评测和轨迹重放
    -> 不应默认保存模型私有思维链或大段证据正文
```

因此，把字段加入 `QueryGraphState` 只表示“运行时可以承载它”，不表示它已经进入 Mongo，也不表示对应业务已经执行。

## 3. 新增字段按职责分组

### 3.1 请求和执行身份

| 字段 | 中文理解 | 当前行为 |
|---|---|---|
| `trace_id` | 单次查询执行追踪 ID | 每次真实查询生成独立 UUID；同一会话连续查询也不复用。 |
| `query_started_at` | 查询开始时间 | 写入带 UTC 时区的 ISO 8601 字符串，便于计算耗时和跨时区排序。 |

`session_id` 和 `trace_id` 最容易混淆：

```text
session_id = 一段聊天会话
trace_id   = 这段会话中的某一次查询执行
```

一个 `session_id` 可以对应多个 `trace_id`。如果直接把 session 当作 trace，后续两次相同问题的 Action、Observation 和耗时会混在一起。

### 3.2 主体确认和结构化标识

| 字段 | 中文理解 | 默认值的准确含义 |
|---|---|---|
| `subject_resolution_status` | 主体确认状态 | `None` 表示旧主体节点尚未产出新契约，不等于 `NOT_FOUND`。 |
| `subject_candidates` | 候选标准主题 | 空列表表示当前没有候选。 |
| `clarification_question` | 可返回给用户的追问 | `None` 表示没有生成追问。 |
| `query_identifiers` | 用户问题中实际出现的结构化标识 | 空字典；后续保存设备型号、报警码、SOP/零件编号等，不能被系统纠错候选覆盖。 |

这里直接使用 `SubjectResolutionStatus` 枚举，而不是自由字符串。这样 `confirmed`、`ambiguous`、`not_found` 和 `no_mention` 的含义是关闭集合，后续 Planner 不需要猜测拼写。

### 3.3 Planner 字段

`Planner` 可以理解为“查询策略规划器”。它根据当前结构化上下文选择下一步 Action。

| 字段 | 中文理解 | 当前边界 |
|---|---|---|
| `planner_step` | 当前决策步数 | 默认 0；Planner 尚未接图，所以当前不会递增。 |
| `policy_version` | 策略版本 | 默认空字符串；不能提前写 `rule-v1`，否则会错误声称规则策略已执行。 |
| `current_planner_decision` | 最近一次决策 | 类型是 `PlannerDecision \| None`，不是裸 dict。 |
| `planner_action_history` | 已执行动作历史 | 只保存已经执行完成或失败的 `PlannerHistoryItem`。 |
| `planner_type` | 规划器类型 | 后续填写 `rule` 或 `model`；当前为空。 |
| `planner_runtime_metadata` | Planner 运行元数据 | 后续保存模型、Prompt 版本、token、耗时和成本，不保存思维链。 |

`runtime metadata` 的中文含义是“运行元数据”，即描述一次运行环境和成本的数据，而不是业务答案本身。

### 3.4 Observation 和检索配置

`Observation` 的中文含义是“观察结果”。它记录 Action 执行后环境真正发生了什么，只包含可验证事实。

| 字段 | 中文理解 | 当前边界 |
|---|---|---|
| `retrieval_observation` | 最近一次检索观察 | 类型是 `RetrievalObservation \| None`；第五部分普通本地检索已生成编号确认结果，其他 Action 后续补齐。 |
| `retrieval_mode` | 召回组合模式 | 后续标记 dense、learned sparse、BM25 的实际组合。 |
| `retrieval_config_version` | 检索配置版本 | 后续关联 top-k、RRF、rerank 阈值等配置快照。 |
| `retrieval_channel_results` | 各召回通道原始结果 | 按通道名保存候选，默认空字典。 |

这里特意不在第三部分提前填一个看起来合理的 `retrieval_mode`。State 中的空字符串表示“当前旧检索链路还没有完成模式化标记”，比写入无法验证的默认模式更诚实。

### 3.5 引用、终止原因和答案模型元数据

| 字段 | 中文理解 | 当前边界 |
|---|---|---|
| `citations` | 结构化引用 | 类型是 `list[Citation]`；当前答案链路尚未生成。 |
| `terminal_reason_code` | 最终终止原因码 | 类型是 `PlannerReasonCode \| None`；当前主图尚未写入。 |
| `answer_runtime_metadata` | 答案模型运行元数据 | 与 Planner 元数据分开，便于分别统计成本。 |

`Citation` 的中文含义是“引用”。它不是答案里随手写的一段来源文字，而是可以追踪到本地 document/chunk 或外部 URL 的结构化对象。

## 4. 为什么使用强类型契约，而不是继续写 dict

第三部分直接复用第二部分模型：

```text
current_planner_decision -> PlannerDecision
planner_action_history   -> PlannerHistoryItem
retrieval_observation    -> RetrievalObservation
citations                -> Citation
terminal_reason_code     -> PlannerReasonCode
```

价值是：

- IDE 能提示字段，不需要背诵英文 key。
- 拼错 Action、reason code 或契约字段时，可以在边界尽早发现。
- State、Trace、API、评测和训练轨迹可以复用同一套业务含义。
- 后续 Model Planner 不能随意改变字段结构。

需要注意：`QueryGraphState` 本身是 `TypedDict`。`TypedDict` 主要做静态类型提示，不会像 Pydantic 一样自动校验每次字典写入。因此关键的 Decision、Observation 和 Citation 仍使用 Pydantic 模型承担运行时校验。

## 5. partial state 是什么，为什么必须保持

`partial state` 的中文含义是“局部状态”。一个节点只返回自己负责修改的字段，LangGraph 再把这些字段合并到主 State。

例如普通检索节点只返回：

```python
{
    "embedding_chunks": result_state.get("embedding_chunks")
}
```

而不是：

```python
return result_state
```

当前查询图有普通检索、HyDE 和 Web 等并发或可分支节点。每个节点拿到的是执行开始时的 State 视图。如果它们把完整字典原样返回，就可能发生：

```text
普通检索完成，写入 embedding_chunks
HyDE 随后返回自己收到的旧完整 State
    -> 旧 State 中没有新的 embedding_chunks
    -> 普通检索结果被覆盖
```

第三部分对七个查询节点建立精确返回字段测试：

- 主体确认节点只返回主体、改写、历史和当前兼容答案字段。
- 普通检索只返回 `embedding_chunks`。
- HyDE 只返回 `hyde_embedding_chunks`。
- Web 只返回 `web_search_docs`。
- RRF 只返回 `rrf_chunks`。
- rerank 只返回 `reranked_docs`。
- 答案节点只返回 `answer` 和 `image_urls`。

即使底层 service 为兼容旧实现返回一份完整字典，LangGraph node 也只投影自己负责的字段。

## 6. 可变默认值为什么必须深拷贝

Python 的 list 和 dict 是可变对象。如果所有查询共享同一份默认容器，就可能出现用户 A 的 Action history 或 Citation 出现在用户 B 的 State 中。

当前工厂函数每次都执行 `deepcopy`，中文是“深拷贝”：不仅复制最外层字典，还复制内部嵌套的 list/dict。

测试覆盖了：

- `dataset_ids`、主体候选和历史列表互不共享。
- `query_identifiers` 内部列表互不共享。
- `planner_runtime_metadata` 嵌套字典互不共享。
- `retrieval_channel_results` 内部候选列表和候选字典互不共享。
- Action history、Citation 和答案元数据互不共享。
- 评测或轨迹分支使用 `copy_query_state` 后，修改副本不会污染原 State。

这为阶段 8 的评测重放和阶段 9 的多个 rollout 分支建立了必要的状态隔离。

## 7. 为什么旧召回字段暂时保留

当前固定查询图仍实际读写：

```text
embedding_chunks
hyde_embedding_chunks
web_search_docs
rrf_chunks
reranked_docs
```

任务 3 如果直接删除这些字段，现有检索、融合、重排和答案节点会立即失效。因此第三部分保留它们，并逐字段注明当前读写方和未来收口方向。

这属于“运行时代码分步切换”，不是 Milvus 数据迁移：

- 不为新旧 State 做双写。
- 不增加长期兼容适配器。
- 不考虑 Milvus 历史 backfill。
- 后续统一召回结构接管后，一次性重命名、归并或删除旧字段。
- Milvus schema 调整仍可直接删测试 collection、重建并重新导入少量测试文档。

## 8. 日志为什么优先使用 trace_id

查询日志原来主要回退到 `task_id` 或 `session_id`。第三部分让日志优先读取 `trace_id`：

```text
trace_id -> task_id -> session_id -> "-"
```

这样同一聊天会话中的两次查询可以分别检索完整日志。旧调用方还没有 `trace_id` 时仍可回退，不会因为 State 扩展立刻破坏导入链路或旧单元测试。

# 第四部分：统一权限、主体和结构化标识过滤表达式

阶段 5 第四部分为所有本地召回通道增加同一个“检索门卫”。普通检索和 HyDE 不再只按 `subject_id` 查询，而是同时受到知识库范围、chunk 启用状态和用户可见性约束。

一句话目标：

```text
无论使用 dense、learned sparse、HyDE 还是后续 BM25，允许参与召回的数据范围必须完全相同。
```

## 1. 改造前的问题

改造前普通检索和 HyDE 分别调用：

```text
build_subject_filter_expr(subject_ids)
```

最终表达式只有：

```text
subject_id in ["subject_hak_180"]
```

虽然 `QueryGraphState` 已经有 `owner_user_id`、`tenant_id` 和 `dataset_ids`，chunk 也已经保存 `visibility` 与 `enabled`，但这些字段没有真正进入查询条件。

这会产生三个实际问题：

- 同一 subject 下可能召回本次未选择的其他 dataset 数据。
- user_a 可能召回 user_b 的 private chunk。
- 将来阶段 6 禁用 chunk 后，查询仍可能召回 `enabled=false` 的内容。

此外，普通检索和 HyDE 各自调用主体过滤函数。如果后续只修改其中一条链路，就可能出现权限规则不一致。

## 2. 改造后的统一调用链

```text
QueryGraphState
    -> build_chunk_retrieval_filter_from_state
    -> build_chunk_access_filter
    -> subject_id 条件
    -> build_structured_identifier_filter（可选）
    -> 最终 Milvus expr
    -> dense / learned sparse / HyDE 共享
```

`expr` 是 expression 的缩写，中文是“表达式”。在这里它相当于 SQL 的 `WHERE` 条件，决定哪些 Milvus entity 有资格参加向量相似度计算。

## 3. access filter 解决“当前用户能看什么”

`access` 的中文含义是“访问权限”。`build_chunk_access_filter` 输出三类约束：

```text
dataset_id in 当前 dataset_ids
AND enabled == true
AND (
    visibility == "public"
    OR (visibility == "shared" AND tenant_id == 当前 tenant_id)
    OR owner_user_id == 当前用户
)
```

逐项理解：

- `dataset_id`：只允许查询请求明确选择的知识库。
- `enabled`：只允许当前启用的 chunk 参与召回。
- `public`：所有用户可见。
- `shared`：只允许同一 tenant 的用户查看。
- `owner_user_id`：私有数据只允许所属用户本人查看。

最关键的是可见性三个 `OR` 分支外层括号。如果写成：

```text
dataset 条件 AND enabled 条件 AND public
OR shared
OR owner
```

数据库可能按运算优先级理解为：只对 public 应用 dataset/enabled 条件，而 shared 或 owner 分支绕过前面的限制。当前实现强制把整个可见性规则放进括号，再和 dataset、enabled 使用 `AND` 连接。

## 4. 空范围为什么必须失败

`dataset_ids` 和 `subject_ids` 都是本地检索的安全边界。

当前实现明确禁止：

```text
dataset_id in []
subject_id in []
```

也禁止为了让流程继续而直接删除这两个条件。原因是：空范围本来表示上游输入不完整，如果静默去掉条件，就可能从“没有合法范围”退化成“搜索整个 collection”。

现在缺少 dataset、subject、owner 或 tenant 时，会在下面两项操作之前抛出中文 `ValueError`：

- 调用 embedding 模型生成向量。
- 向 Milvus 发送检索请求。

这既减少无效模型调用，也确保异常输入不会接触数据库。

## 5. 所有动态字符串统一转义

filter 中的 dataset、subject、用户、tenant 和设备标识都可能包含引号、反斜杠或换行。如果直接使用字符串拼接，可能导致表达式解析失败，甚至改变原有条件结构。

当前统一流程是：

```text
去除首尾空白
    -> 保序去重
    -> 转义反斜杠和双引号
    -> 把换行、回车、制表符转换为空格
    -> 生成 Milvus 字符串字面量
```

同时明确拒绝把单个字符串误传给列表参数。因为 Python 中字符串本身可以迭代，如果不校验：

```python
dataset_ids = "dataset_ops"
```

可能被错误拆成：

```text
["d", "a", "t", "a", ...]
```

这种错误生成的 expr 在语法上可能仍然合法，因此必须在构建器边界提前拒绝。

## 6. structured identifier filter 当前做了什么

`structured identifier` 的中文含义是“结构化标识”。它表示设备型号、报警码、部件等可以直接匹配 schema 字段的信息。

第四部分只允许当前 chunk schema 已存在的六个字段：

| 字段 | 中文含义 |
|---|---|
| `equipment_model` | 设备型号 |
| `alarm_code` | 报警码/故障码 |
| `part_name` | 部件名称 |
| `sop_type` | SOP 类型 |
| `safety_level` | 安全等级 |
| `maintenance_stage` | 维护阶段 |

字段名使用固定白名单，不能把 `query_identifiers` 中任意 key 直接拼进 expr。未知字段会明确失败，既避免表达式注入，也避免查询不存在的 Milvus 字段。

需要特别说明：

```text
sop_type 已存在
    ≠ SOP 编号字段已经存在

part_name 已存在
    ≠ 零件编号字段已经存在
```

SOP 编号、零件编号等字段必须等后续 schema 正式确定后再加入。第四部分没有为了提前覆盖需求而虚构字段名。

同一字段的多个值使用 `in`，不同字段使用 `AND`：

```text
equipment_model in ["HAK 180", "HAK 180 Pro"]
AND alarm_code in ["E021"]
```

字段输出顺序固定，不依赖字典插入顺序，保证相同输入可以生成完全相同的表达式，便于测试和后续 Trace 重放。

## 7. 为什么当前真实查询通常还没有结构化条件

第三部分已经在 State 中增加 `query_identifiers`，第四部分已经能够把它安全转换成过滤条件。

但任务 5 的设备型号、报警码、SOP/零件编号提取和归一化还没有实现，所以当前真实查询中：

```text
query_identifiers = {}
```

这是准确的阶段边界：

```text
支持消费结构化标识
    ≠ 已经能够从用户问题自动提取结构化标识
```

因此第四部分当前实际生效的是 dataset、subject、enabled 和权限过滤；结构化标识过滤等待任务 5 提供输入。

任务 5 接入后，当前 `build_chunk_retrieval_filter` 继续承担第一段精确过滤；第二段通过不传结构化标识条件复用同一权限边界。第四部分的 filter 构建器不负责判断“E020 是否应该纠正为 E021”，该判断由后续编号解析和 Observation 契约完成。宽松召回得到不同编号时只能写入 `suggested_identifiers`，不能进入答案 Citation。

## 8. 普通检索、HyDE 和两个向量通道如何保持一致

普通检索和 HyDE 都调用：

```text
build_chunk_retrieval_filter_from_state(state)
```

两者只在向量化文本上不同：

- 普通检索使用改写后的 query。
- HyDE 使用 query 与假设答案组成的增强文本。

它们允许访问的数据范围完全相同。

当前 Milvus hybrid search 又包含两个底层请求：

- `dense_vector`：稠密语义向量。
- `sparse_vector`：BGE-M3 learned sparse，即学习式稀疏向量。

共享 expr 会同时传入这两个 `AnnSearchRequest`。因此不是只在外层看起来统一，而是两个实际 Milvus 向量通道都受到同一权限过滤。

第四部分交付时 BM25 尚未实现；第七部分加入后继续复用同一个构建器，没有创建 BM25 专用权限拼接逻辑。

# 第五部分：设备运维标识提取、归一化与两段式检索

阶段 5 第五部分解决的是编号类问题中“语义相近不等于业务相同”的风险。E020 和 E021 在文本、embedding 甚至上下文上都可能很接近，但它们仍是两个不同报警码；系统不能因为 E021 分数更高，就假装用户输入的 E020 已经被纠正。

一句话目标：

```text
相同编号可以成为证据；相近但不同的编号只能成为待用户确认的候选。
```

## 1. 改造前的问题

改造前普通检索直接把改写后的自然语言问题送入 dense + learned sparse 混合搜索。设备型号、报警码、SOP 编号和零件编号没有统一提取结果，也没有“用户原编号、实际命中编号、建议编号”三个独立位置。

这会产生两类相反错误：

- metadata 存在 E020，但 query 写成 `E-020`，格式差异降低精确命中能力。
- 当前库只有 E021 时，向量相似度可能召回 E021；若直接回答，就把不同编号当成了同一故障。

## 2. 查询入口先保存用户真正输入了什么

新增 `app/rag/query/query_identifier_service.py`，使用确定性规则提取：

| 字段 | 中文含义 | 第一版规则与边界 |
|---|---|---|
| `equipment_model` | 设备型号 | 至少两个字母加至少两位数字；`HAK180`、`HAK-180`、`HAK 180` 统一成 `HAK 180`。 |
| `alarm_code` | 报警码/故障码 | 识别 E 加 3～4 位数字；E020、E021 分别保留，不合并。 |
| `sop_code` | SOP 编号 | 必须显式带 SOP 前缀，普通单词“SOP”不算具体编号。 |
| `part_number` | 零件/备件编号 | 必须带“零件编号、备件号、料号、P/N、part number”等上下文，避免把任意字母数字串武断分类。 |

提取发生在创建 `QueryGraphState` 时，来源始终是 `original_query`。这很重要：主体改写可能根据历史补充设备名，但补充内容不应伪装成用户本轮亲自输入的编号。

`query_identifiers` 始终保存用户请求快照，例如：

```python
{"alarm_code": ["E020"]}
```

即使后续只找到 E021，也不能覆盖成：

```python
{"alarm_code": ["E021"]}
```

E021 只能进入 `RetrievalObservation.suggested_identifiers`。

## 3. 为什么 SOP 编号和零件编号没有直接拼 filter

当前 chunk schema 有 `sop_type` 和 `part_name`，但没有独立 `sop_code` 和 `part_number`：

```text
sop_type 是“开机/点检/维修”等流程类型，不是 SOP-001
part_name 是“传感器/急停按钮”等部件名称，不是 AB-123
```

因此第五部分把 `sop_code/part_number` 定义成 lexical-only identifier，中文可理解为“当前只进入检索文本和正文核验的标识”。它们会被追加到规范化检索 query，但不会生成不存在的 Milvus 字段条件。

当前 learned sparse 可以提供一定字面召回能力；正式 `lexical_text`、BM25 和独立 schema 字段仍需要后续评测后决定。本部分没有用名称相近的旧字段冒充新字段。

## 4. 两段式检索如何工作

```text
用户 query + query_identifiers
    -> 第一段：基础权限/subject + 可映射结构化编号 filter
        -> 完整同码命中：exact_match
        -> 没有完整覆盖：filter_fallback=true
    -> 第二段：只删除结构化编号条件
        -> 正文仍找到同一编号：fallback_exact_match
        -> 只找到相近不同编号：suggestion_required
        -> 没有可靠候选：not_found
```

两段复用同一次 embedding 结果，避免精确过滤零命中时重复调用 embedding 服务。第二段只放宽编号条件，始终保留：

- 当前 `dataset_ids`；
- 已确认 `subject_ids`；
- `enabled == true`；
- public、同 tenant shared、当前 owner 的可见性规则。

因此 fallback 是“在同一安全范围内扩大编号召回”，不是全库搜索。

## 5. metadata 漏填为什么仍能继续回答

若第一段因为 `alarm_code` metadata 为空而零命中，第二段召回的正文仍明确出现 E020，则状态为：

```text
identifier_resolution_status = fallback_exact_match
requested_identifiers = {alarm_code: [E020]}
matched_identifiers = {alarm_code: [E020]}
filter_fallback = true
```

这说明编号身份仍由相同文本 E020 证明，只是导入 metadata 可能漏填。这类 chunk 可以继续进入 RRF、rerank 和后续答案证据。

## 6. 相近编号如何生成候选

编号候选优先来自带完整基础 filter 的 Milvus metadata 查询，以及第二段已经召回的有权限 chunk。候选排序使用：

- 编号格式必须同类，例如报警码必须都是 E 加数字；
- 编辑距离越小越优先；
- 合法记录中出现频次越高越优先；
- 最后使用稳定字典序，保证相同输入可重放。

若用户同时写了设备型号和报警码，候选记录还必须在同一条记录上兼容其他已确认类型。例如 HAK 180 的 E020 不能用 HAK 200 的 E021 作为纠错候选。缺少其他类型 metadata 时也不默认兼容，宁可追问或返回未找到。

embedding 只负责帮助召回含相关自然语言上下文的 chunk，不参与“E020 是否等于 E021”的身份判定。

## 7. 当前固定查询图的安全保护

真正的 Planner 路由尚未接入。为了在分步实施期间也满足“不同编号不得回答”，第五部分增加三层临时保护：

- RRF 在终止型编号 Observation 且本地候选为空时安全返回空列表。
- rerank 发现 `suggestion_required/not_found` 后直接跳过，不给候选打证据分。
- 答案出口只交付 Observation 的确定性追问，清空 `citations` 和 `image_urls`，不调用答案 LLM。

答案出口同时写入：

```text
suggestion_required -> IDENTIFIER_CONFIRMATION_REQUIRED
not_found           -> IDENTIFIER_NOT_FOUND
```

这里仍会经过 `node_answer_output`，只是为了复用 SSE/同步结果交付和聊天历史保存，不代表执行了 Planner 的 `answer` Action。后续 Planner 接图后会由 `ask_clarification` 更早路由，出口保护保留为最后一道防线。

## 8. Observation 已落地到什么程度

普通本地检索现在会生成强类型 `RetrievalObservation`，已经包含：

- 用户请求编号快照；
- 实际同码命中；
- `exact_match/fallback_exact_match/suggestion_required/not_found`；
- 建议候选和追问；
- 是否使用结构化 filter、是否发生 fallback；
- 候选数量、通道数量和本次检索耗时。

HyDE 当前仍复用相同权限和结构化过滤，但不会并行覆盖第二份 `retrieval_observation`。其他 Action 的完整 Observation、rerank 分数、EvidenceSummary 和 Trace 持久化仍是后续任务，本部分没有把运行时 State 误写成已经可查询的 Trace 系统。

# 第六部分：可切换召回、跨 Action RRF 与统一候选

阶段 5 第六部分把“检索结果能用”进一步改造成“不同召回通道、不同检索 Action 和 Web 结果能够用同一套候选协议公平融合，并且来源身份不会在 rerank 时丢失”。

一句话目标：

```text
每个 Action 保留自己的原始排名；所有已执行 Action 一次性融合；候选从召回到答案始终带着真实身份证明。
```

## 1. 改造前的问题

改造前存在三个相互关联的问题：

- chunk hybrid search 固定使用 `WeightedRanker(0.9, 0.1)`，只支持 dense + BGE-M3 sparse，不能切换 BM25，也会尝试直接组合不同量级的原始分数。
- RRF 只接受 ordinary/HyDE 两个本地列表，Web 在 rerank 服务中另行追加；无法表达 original + Web、仅 Web 或 original + HyDE + Web。
- rerank 前把本地候选转换成只有 `title/text/type/score` 的临时字典，`document_id/chunk_id/dataset_id/index_version` 会丢失，最终无法可靠生成 Citation。

## 2. 三种 RetrievalMode

`RetrievalMode` 中文是“单次本地检索的召回组合模式”，固定为：

```text
dense_learned_sparse
dense_bm25
dense_learned_sparse_bm25
```

`MilvusGateway.create_requests` 现在按模式创建 2 或 3 个 `AnnSearchRequest`：

- dense 输入稠密向量，使用 `dense_vector + COSINE`；
- learned sparse 输入 BGE-M3 稀疏向量，当前使用 `sparse_vector + IP`；
- BM25 直接输入查询文本，目标字段是后续 Milvus Function 产生的 `bm25_sparse_vector`。

所有请求复用同一个权限/subject/编号 expr 和相同 per-channel top-k。

当前默认仍是：

```text
dense_learned_sparse
```

第六部分交付时只有 BM25 请求能力，`bm25_sparse_vector`、`lexical_text` 和 Function 尚未在 collection 中建立；第七部分现已补齐物理 schema，但默认模式仍等待固定评测结论。

## 3. 为什么 chunk 改用 RRFRanker

dense、learned sparse、BM25 的原始分数不在同一量纲，不能直接相加。第六部分让 chunk hybrid search 显式使用：

```text
RRFRanker(k=60)
```

RRF 只根据各通道名次投票，解决分数量级差异。标准主题和别名 collection 仍保留历史 `WeightedRanker`，没有为了改 chunk 检索破坏阶段 2 已稳定的主体确认链路。

## 4. RetrievalCandidate 统一了什么

`RetrievalCandidate` 中文是“统一候选证据”。普通本地、HyDE 和 Web 在产生候选时就转换成这一契约，关键字段包括：

```text
document_id / chunk_id / dataset_id
index_version / chunk_index
title / source_title / content
source_type
retrieval_channels
retrieval_rank / retrieval_score
rerank_score
url
```

同时继续保留设备型号、报警码、部件名称、SOP 类型、安全等级和维护阶段，避免第五部分的同码判断经过 RRF 后失去 metadata。

身份规则是强校验：

```text
local：必须有 document_id、chunk_id、dataset_id、index_version、chunk_index
web：必须有真实 URL，本地身份字段必须全部为 None
```

因此 Web 结果无法为了复用本地逻辑伪造 `chunk_id`，本地结果也不能在缺失来源时静默进入 rerank。

## 5. retrieval_channels 的含义

`RetrievalChannel` 同时记录本地 Action 启用的模式通道和跨 Action 来源：

```text
dense
learned_sparse
bm25
original
hyde
web
```

例如同一个 chunk 分别出现在普通 Action 和 HyDE Action 的 Milvus 合并结果中，两次
Action 启用的模式通道并集可能是：

```python
"retrieval_channels": ["dense", "learned_sparse", "original", "hyde"]
```

这比旧 `type="milvus"` 更可解释，但边界必须明确：Milvus `hybrid_search` 当前只返回内部 RRF 后的统一列表，不返回单个 chunk 在 dense/learned sparse/BM25 各自的原始命中。因此前三个值表示 Action 启用了哪些通道，不证明该 chunk 逐条命中全部通道；`original/hyde/web` Action 来源是确定事实。若后续 Trace 必须展示逐通道命中，需要改为保存每个请求的独立结果，不能从当前合并响应反推。

## 6. 外层 RRF 不再固定两路

新增 `fuse_ranked_candidate_lists`，输入是当前所有实际存在的 Action 原始排名列表：

```text
[original]
[original, hyde]
[original, web]
[original, hyde, web]
[web]
```

它每次都从原始列表重新计算：

```text
sum(1 / (k + rank))
```

不会把上一轮 original + HyDE 的 RRF 输出再拿来和 Web 套一层 RRF。这样最终分数不依赖 Action 到达顺序，也不会因为某个列表先融合而获得隐式权重。

去重规则按来源区分：

- 本地使用 `chunk_id`；
- Web 使用移除锚点、统一 scheme/host 的规范化 URL；
- 同一 Action 内重复候选只投一票；
- 同一候选跨 Action 出现时合并通道集合。

分数并列时使用稳定身份键排序，所以相同输入的结果可重放。

## 7. Web 如何进入统一链路

Web 搜索页现在会立即转成 `RetrievalCandidate`：

```text
source_type = web
retrieval_channels = [web]
document_id/chunk_id/dataset_id/index_version/chunk_index = None
url = 真实网页 URL
content = 搜索摘要
```

缺少 URL 或摘要的页面直接丢弃，不伪造本地身份，也不把空正文送入 reranker。

Web 不进入第一层 Milvus 通道 RRF，但会作为独立 Action 排名列表进入第二层外部 RRF，然后和本地候选一起统一 rerank。明显实时问题未来可以只有 Web 候选，因此答案前置校验不再强制 Web-only 结果伪造本地标准主题。

## 8. rerank 后元数据不再丢失

rerank 服务不再执行：

```text
本地 -> {title, text, type, score}
Web  -> {title, text, type, score}
```

它直接验证累计 `RetrievalCandidate`，使用统一 `content` 构造模型输入，只写入 `rerank_score`，其他字段原样保留。排序并列时再次使用本地 chunk/Web URL 稳定身份键。

`retrieval_score` 和 `rerank_score` 的职责也被明确分开：

- `retrieval_score`：RRF 排名融合分，只负责候选顺序；
- `rerank_score`：统一 reranker 相关性分，后续 Planner 的证据阈值读取它。

## 9. 当前阶段边界

第六部分完成的是“模式、候选、融合、rerank 执行环境”，还没有提前实现 Planner 路由：

- 当前 LangGraph 仍在主体确认后并发执行 ordinary、HyDE、Web；
- 目前 RRF 根据 State 中实际非空的三个 Action 字段融合；
- 任务 9 改成闭环 Planner 后，未执行 Action 不写候选列表，本轮函数可以直接复用；
- “执行过但结果为空”的 Action 仍需要后续完整 Observation/Action history 记录；
- BM25 物理 schema、Analyzer 和 Function 属于第七部分。

这保证代码能力向前推进，但文档没有把闭环 Planner 或 BM25 collection 误写成已经完成。

## 10. 测试覆盖

第六部分专项测试覆盖：

- 三种模式分别创建正确的 2/2/3 个请求。

# 第七部分：BM25 实验 schema、lexical_text 与编号词法召回

阶段 5 第七部分把第六部分已经定义好的 BM25“请求能力”真正接到了 chunk collection 的物理 schema 上。核心目的不是提前断言 BM25 一定优于 learned sparse，而是让两者可以在同一批 chunk、同一权限 filter、同一 top-k 和 rerank 配置下做公平实验。

## 1. 改造前的问题

改造前 chunk 只有：

```text
dense_vector
sparse_vector
```

其中 `sparse_vector` 实际是 BGE-M3 生成的 learned sparse（学习式稀疏向量），但字段名没有表达来源。第六部分虽然可以创建 BM25 查询请求，collection 中却没有 BM25 文本源、Function 和输出字段，包含 BM25 的模式不能真实运行。

另一个问题是设备编号对分隔符非常敏感：

```text
HAK180
HAK-180
HAK 180
```

它们表示同一个设备型号，但普通分词器可能产生不同 token。相反，`E020` 和 `E021` 虽然字面非常接近，却是两个不同报警码，系统不能用相似度静默纠正。

## 2. 新 schema 明确区分两种稀疏通道

chunk collection 现在使用：

```text
dense_vector
learned_sparse_vector
lexical_text
bm25_sparse_vector
```

逐字段含义：

- `dense_vector`：稠密语义向量，负责自然语言语义相近召回。
- `learned_sparse_vector`：BGE-M3 模型生成的学习式稀疏向量，索引 metric 为 `IP`。
- `lexical_text`：BM25 的原始词法文本，由应用按确定规则生成并写入。
- `bm25_sparse_vector`：Milvus BM25 Function 的输出，索引 metric 为 `BM25`，应用禁止写入。

标准主题和别名 collection 仍保留它们原有的 `sparse_vector`。这次只修改 chunk schema，因为实验对象是 chunk 召回；没有把“字段改名”机械扩散到不相关 collection。

## 3. lexical_text 如何生成

`lexical` 的中文含义是“词法/字面”。它按固定顺序拼接：

```text
standard_subject_name
equipment_model
alarm_code
part_name
sop_type
safety_level
maintenance_stage
source_title
title
parent_title
content
```

固定顺序的价值是：同一个 chunk 重复导入时会得到相同输入，后续评测和 Trace 才可重放。

拼接后还会追加技术编号的常见分隔符变体，例如：

```text
HAK180 HAK-180 HAK 180
E021 E-021 E 021
```

这里的“变体”只表达同一编号的不同写法，不做相近编号纠错。正文同时出现 E020 和 E021 时，两组变体都会独立保留，绝不会合并。

如果 lexical_text 极端超长，只截断 BM25 输入副本，不修改原始 `content`；编号变体优先保留。

## 4. Analyzer 为什么必须真实验证

Analyzer（文本分析器）负责把文本切成 BM25 使用的 token（词元）。当前配置为：

```text
tokenizer: jieba
filters: cnalphanumonly + lowercase
```

- `jieba` 负责连续中文分词；
- `cnalphanumonly` 去除标点 token，同时保留汉字、拉丁字母和数字；
- `lowercase` 统一设备编号大小写。

仅检查 Python 配置对象不足以证明服务端真实分词正确。因此创建空 collection 前，代码会调用 Milvus `run_analyzer`，要求结果至少包含：

```text
hak180
e021
中文 token
```

缺少任何一类都会中止建库，避免导入完成后才发现 BM25 无法搜索设备编号。当前连接的 Milvus 已实际返回 `hak180`、`e021`、`报警`、`温度传感器` 等 token。

## 5. BM25 Function 的数据所有权

完整入库链路现在是：

```text
应用：生成 dense_vector + learned_sparse_vector
应用：构造并写入 lexical_text
Milvus：Analyzer 对 lexical_text 分词
Milvus：BM25 Function 生成 bm25_sparse_vector
Milvus：维护词频、文档频率和平均文档长度等 collection 统计
```

应用如果自行计算或写入 `bm25_sparse_vector`，就可能与 Milvus 查询时使用的 Analyzer 和 collection 统计不一致。因此入库边界会直接拒绝：

- 旧字段 `sparse_vector`；
- 应用传入的 `bm25_sparse_vector`。

## 6. 为什么不做旧 schema 兼容

当前 Milvus 只有少量可丢弃测试数据，用户已确认可以删库。因此本部分没有加入 backfill（历史回填）、双写或在线迁移逻辑。

如果发现已有 chunk collection 缺少 `learned_sparse_vector`、`lexical_text` 或 `bm25_sparse_vector`，代码会明确报错并要求删除 collection 后重新导入。这样比静默把新代码跑在旧 schema 上更安全，也不会为一次性测试数据留下长期兼容债务。

## 7. 当前能力边界

第七部分完成后，三种模式都已有物理 schema 和请求能力：

```text
dense + learned sparse
dense + BM25
dense + learned sparse + BM25
```

但默认仍是 `dense_learned_sparse`。这不是说 BM25 没有价值，而是因为真正的选择必须依赖固定评测集的 Recall@K、MRR、nDCG、引用命中率、延迟、索引大小和入库耗时。阶段 5A 负责让三种方案可比较，阶段 5B 才根据证据删除失败方案并收口最终 schema。

## 9. 本部分的实际提升

| 对比项 | 改造前 | 第七部分后 |
|---|---|---|
| learned sparse 字段语义 | `sparse_vector` 来源不清 | `learned_sparse_vector` 明确由 BGE-M3 生成 |

