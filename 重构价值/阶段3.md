# 第一部分：文档任务元数据闭环

阶段 3 的核心不是让导入链路“跑得更快”，而是把原来一次性的导入流程，升级成可管理、可追踪、可排查的文档任务闭环。

原来的逻辑是：

```text
upload -> 生成 task_id -> 保存文件 -> 后台跑 LangGraph -> task_utils 内存记录进度 -> 写入 Milvus
```

这个流程能完成导入，但管理能力比较弱：

- `task_utils` 是进程内字典，服务重启后状态会丢失。
- 系统没有明确的 `document` 概念，只知道“这次上传了一个文件”。
- `task_id` 更像一次执行流水号，不适合用户作为历史记录入口。
- 失败时主要依赖日志排查，不方便通过 API 看到失败节点和错误信息。
- Milvus 里的 chunk 是检索数据，不适合承担文档管理状态。
- Mongo 原来主要存 `chat_message`，服务的是对话历史，不管理导入文档和任务。

阶段 3 改完后，导入链路变成：

```text
upload -> 创建 dataset/document/task 元数据 -> 保存文件 -> 后台跑 LangGraph -> 节点推进时更新 task/document -> 写入 Milvus -> document/task 状态完成
```

也就是在“导入执行”之外，补了一层 Mongo 管理元数据。

## 1. 新增三类管理对象

### dataset：知识库容器

`dataset` 表示知识库容器。

当前阶段先提供一个默认知识库：

```text
dataset_id = dataset_default_equipment_ops
name = 设备运维知识库
```

它的价值是把后续的 document、task、chunk 都挂到一个明确的知识库下面。

这一步不是为了当前就做复杂多知识库管理，而是为后续能力留好入口：

- 阶段 5 查询时可以按 `dataset_id` 过滤。
- 阶段 7 可以扩展 Dataset 管理 API。
- 后续如果出现“设备运维知识库”“售后维修知识库”“产品说明书知识库”，结构上可以自然扩展。

### document：文档长期对象

`document` 表示上传进系统的一份文档，是用户找历史记录的主要入口。

它记录：

- `document_id`
- `dataset_id`
- `latest_task_id`
- 文件名
- 文件路径
- 工作目录
- 文档整体状态 `status`
- 解析状态 `parse_status`
- 索引状态 `index_status`
- `chunk_count`
- `subject_id`
- `standard_subject_name`
- `failed_node`
- `error_message`

这里要区分 document 和 Milvus chunk：

- document 是文档管理对象。
- chunk 是向量检索对象。

Milvus chunk 解决“能不能搜到内容”，document 解决“这个文档现在是什么状态、是否解析成功、是否索引成功、失败在哪里”。

### task：一次异步执行记录

`task` 表示一次异步任务执行。

当前阶段主要是：

```text
task_type = import
```

它记录：

- `task_id`
- `document_id`
- `dataset_id`
- `task_type`
- `status`
- `running_nodes`
- `done_nodes`
- `failed_node`
- `error_message`

一个 document 应该可以关联多个 task。

例如同一份 `HAK180说明书.pdf`：

| 操作 | document_id | task_id | task_type |
|---|---|---|---|
| 第一次导入 | doc_001 | task_001 | import |
| 重新解析 | doc_001 | task_002 | parse |
| 重建索引 | doc_001 | task_003 | rebuild_index |
| 删除文档 | doc_001 | task_004 | delete |

所以 document 中只保存 `latest_task_id`，历史任务通过 `document_id` 去 tasks 表反查。

这样比把所有任务状态直接塞进 document 更清晰：

- document 负责描述“这份文档当前是什么状态”。
- task 负责描述“某一次执行具体跑到了哪里”。

## 2. 和原有数据的区别

阶段 3 新增的三张 Mongo 表不是替代原来的数据，而是补齐缺失的管理元数据层。

| 原有数据 | 作用 | 不适合承担的问题 |
|---|---|---|
| `chat_message` | 存聊天历史 | 不管理导入文档和任务 |
| Milvus `standard_subjects` | 存标准主题 | 是知识体系，不是文档状态 |
| Milvus `subject_aliases` | 存主题别名 | 是主体识别索引，不是任务状态 |
| Milvus `chunks` | 存可检索切片 | 是向量检索数据，不适合做文档管理 |
| `task_utils` 内存字典 | 存当前任务进度 | 重启丢失，只适合即时展示 |

重构后职责更清楚：

- Mongo `datasets/documents/tasks`：负责知识库、文档、任务管理。
- Milvus：负责向量检索和主题识别索引。
- Mongo `chat_message`：负责用户对话历史。
- `task_utils`：负责当前进程内的即时进度和 SSE 推送。

## 3. 服务重启后的真实含义

“服务重启后还能查历史任务”不是断点续传，也不是自动恢复执行。

更准确的说法是：

```text
服务重启后，可以通过 document 列表找回文档，并查看最近一次 task 的历史状态、失败节点和错误信息。
```

原因是 `task_id` 本身不适合作为用户找历史记录的入口。

`task_id` 是一次任务执行 ID，更像流水号。用户重启服务后不一定记得上一次的 `task_id`。

更合理的查询路径是：

```text
GET /documents
    -> 通过文件名、上传时间、状态找到 document

GET /documents/{document_id}
    -> 查看文档当前状态和 latest_task_id

GET /documents/{document_id}/tasks
    -> 查看这份文档的历史任务记录

GET /status/{task_id}
    -> 已知 task_id 时，查看某一次任务执行细节
```

因此阶段 3 实现的是“状态可追溯”，不是“任务可恢复执行”。

如果服务在任务执行过程中重启，后台线程已经结束，当前 LangGraph 调用栈也不存在了。Mongo 中保留的是上次执行到哪里、完成了哪些节点、失败或中断在哪个节点，但不会自动从这个节点继续跑。

真正的断点续跑需要额外设计：

- 每个节点的输入和输出都能持久化。
- 每个节点都要幂等。
- 中间文件路径稳定。
- Milvus、MinIO 等外部副作用要能重复执行且不产生脏数据。
- 任务调度器能把 `processing` 状态识别成 `interrupted` 或 `retrying`。
- 重试时要处理 `retry_of_task_id`、新旧 task 关系、chunk 版本等问题。

这已经超出阶段 3。

当前项目的正确取舍是：

```text
先做状态持久化 + 失败可见 + 文档可找回。
后续再做重新导入、重建索引、删除文档。
暂时不做严格断点续跑。
```

这个取舍更符合当前项目规模。Mongo 数据少，都是测试数据，可以删库重建；导入任务也不是大规模分布式队列。现在做完整断点续跑，成本明显高于收益。

## 4. 懒加载 Mongo 的价值

阶段 3 新增的 `import_metadata_repository.py` 保持懒加载。

也就是：

```text
模块 import 时不连接 Mongo
服务启动时不强制连接 Mongo
第一次上传、查询 document、查询 task 时才初始化 MongoClient 和索引
```

这样做的原因是阶段 0 已经明确要求：不要让外部服务在启动阶段把基础测试和 graph compile 卡死。

懒加载带来的好处：

- Mongo 临时不可用时，不影响导入图、查询图 compile。
- 单元测试可以 monkeypatch repository，不需要真实 Mongo。
- 服务启动更稳。
- 只有真正使用导入元数据能力时，才承担 Mongo 连接成本。

当前聊天历史 Mongo 工具也是类似思路：`mongo_history_utils.py` 里全局实例默认是 `None`，只有调用 `save_chat_message`、`get_recent_messages` 等函数时才会真正初始化。

## 5. 本阶段实际提升

阶段 3 的提升可以概括为：从“能跑导入流程”，升级为“能管理导入流程”。

具体提升：

- 上传后可以查 document 状态。
- 可以通过 document 列表找回历史文档，而不是依赖用户记住 `task_id`。
- 可以看到解析状态、索引状态、chunk 数量。
- 可以看到最近一次任务和历史任务。
- 失败时可以通过 API 看到失败节点和错误信息。
- `task_utils` 不再是唯一状态源，服务重启后仍保留历史状态。
- document 和 task 分开后，为后续重建索引、删除文档、多次任务历史打好基础。

一句话总结：

```text
Milvus 负责检索，chat_message 负责对话，dataset/document/task 负责管理。
```

阶段 3 补齐的是 RAG 系统从“脚本式导入”走向“管理型知识库”的关键一层。

# 第二部分：扩展导入状态契约

这一部分关注的是导入 state 和 `/upload` API 的契约变化：一次导入任务现在不只要知道“任务是谁”，还要知道“处理哪份文档、归属哪个知识库”。

## 1. task_id 不是新增字段

这里要注意，`task_id` 不是阶段 3 新增的。原来的 `/upload` 已经会生成 `task_id`，它表示一次导入任务执行。

原来 `task_id` 已经用于：

- 后台导入图追踪一次执行。
- `task_utils` 记录 running/done 节点。
- 日志里作为追踪 ID。
- `/status/{task_id}` 查询进度。

阶段 3 没有推翻这个机制，而是继续沿用它。

## 2. 真正新增的是 document_id 和 dataset_id

阶段 3 在 `ImportGraphState` 中新增：

- `document_id`：表示被处理的长期文档对象。
- `dataset_id`：表示这份文档和这次任务所属的知识库容器。

因此导入 state 现在更准确地表达为：

```text
task_id      已有：这一次导入任务
document_id  新增：这份文档
dataset_id   新增：所属知识库
```

这个变化的价值是让导入链路中的每个节点都能知道自己正在处理哪份 document，以及这份 document 属于哪个 dataset。这样节点推进时就能同步更新 document/task 元数据，而不是只更新进程内的 `task_utils`。

## 3. /upload 的职责边界

原来的 `/upload` 做的是：

```text
生成 task_id -> 保存文件 -> 启动后台导入
```

阶段 3 后，`/upload` 变成：

```text
沿用原 task_id 生成逻辑
生成 document_id
解析导入目标 dataset_id
创建 document/task 元数据
把 task_id/document_id/dataset_id 写入导入 state
启动后台导入
```

这里有一个重要边界：导入流程不应该把“创建知识库”和“上传文档”混在一起。

当前单知识库版本里，`POST /upload` 不传 `dataset_id` 时，会使用并确保默认 dataset 存在。这个设计是为了让现有 Demo 和单知识库流程保持简单。

但如果后续变成多知识库，上传文件时应该指定一个已经存在的 `dataset_id`，而不是每次上传都创建新的 dataset。也就是说：

```text
不传 dataset_id
    -> 使用 dataset_default_equipment_ops，并确保默认 dataset 存在

传入已有 dataset_id
    -> document/task 归属到这个 dataset

传入不存在的 dataset_id
    -> 拒绝导入，提示先创建 dataset
```

这样做可以避免一个常见问题：用户每上传一次文件，系统就误创建一个知识库，最后 dataset 变成一堆无意义的上传批次。

所以阶段 3 里的 dataset 仍然是管理容器，不负责判断用户问题属于哪个知识库，也不负责自动创建多知识库。多知识库创建应该放到后续 Dataset 管理 API，例如：

```text
POST /datasets
POST /upload 携带 dataset_id
```

## 4. 这部分的实际提升

扩展导入状态契约后，导入链路的上下文更完整：

- `task_id` 继续表示一次执行，不破坏原有任务追踪。
- `document_id` 让任务可以稳定关联到长期文档对象。
- `dataset_id` 让文档和任务归属到明确知识库。
- 上传时可以不传 `dataset_id` 走默认知识库，也可以指定已有 `dataset_id` 归属到目标知识库。
- 未知 dataset 会被拒绝，避免上传流程误创建知识库。

这部分不是复杂功能，但它把后续多知识库、文档列表、任务历史、重建索引的关系提前理清了。
