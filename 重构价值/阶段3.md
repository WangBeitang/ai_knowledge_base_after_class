# 第一部分：文档任务元数据闭环

阶段 3 的核心不是让导入链路“跑得更快”，而是把原来一次性的导入流程，升级成可管理、可追踪、可排查的文档任务闭环。

原来的逻辑是：

```text
upload -> 生成 task_id -> 保存文件 -> 后台跑 LangGraph -> task_utils 内存记录进度 -> 写入 Milvus
```

这个流程能完成导入，但管理能力比较弱：

- `task_utils` 是进程内字典，服务重启后状态会丢失。
- 系统没有明确的 `document` 概念，只知道“这次上传了一个文件”。
- `task_id` 更像一次执行流水号，不适合用户作为历史记录入口。
- 失败时主要依赖日志排查，不方便通过 API 看到失败节点和错误信息。
- Milvus 里的 chunk 是检索数据，不适合承担文档管理状态。
- Mongo 原来主要存 `chat_message`，服务的是对话历史，不管理导入文档和任务。

阶段 3 改完后，导入链路变成：

```text
upload -> 创建 dataset/document/task 元数据 -> 保存文件 -> 后台跑 LangGraph -> 节点推进时更新 task/document -> 写入 Milvus -> document/task 状态完成
```

也就是在“导入执行”之外，补了一层 Mongo 管理元数据。

## 1. 新增三类管理对象

### dataset：知识库容器

`dataset` 表示知识库容器。

当前阶段先提供一个默认知识库：

```text
dataset_id = dataset_default_equipment_ops
name = 设备运维知识库
```

它的价值是把后续的 document、task、chunk 都挂到一个明确的知识库下面。

这一步不是为了当前就做复杂多知识库管理，而是为后续能力留好入口：

- 阶段 5 查询时可以按 `dataset_id` 过滤。
- 阶段 7 可以扩展 Dataset 管理 API。
- 后续如果出现“设备运维知识库”“售后维修知识库”“产品说明书知识库”，结构上可以自然扩展。

### document：文档长期对象

`document` 表示上传进系统的一份文档，是用户找历史记录的主要入口。

它记录：

- `document_id`
- `dataset_id`
- `latest_task_id`
- 文件名
- 文件路径
- 工作目录
- 文档整体状态 `status`
- 解析状态 `parse_status`
- 索引状态 `index_status`
- `chunk_count`
- `subject_id`
- `standard_subject_name`
- `failed_node`
- `error_message`

这里要区分 document 和 Milvus chunk：

- document 是文档管理对象。
- chunk 是向量检索对象。

Milvus chunk 解决“能不能搜到内容”，document 解决“这个文档现在是什么状态、是否解析成功、是否索引成功、失败在哪里”。

### task：一次异步执行记录

`task` 表示一次异步任务执行。

当前阶段主要是：

```text
task_type = import
```

它记录：

- `task_id`
- `document_id`
- `dataset_id`
- `task_type`
- `status`
- `running_nodes`
- `done_nodes`
- `failed_node`
- `error_message`

一个 document 应该可以关联多个 task。

例如同一份 `HAK180说明书.pdf`：

| 操作 | document_id | task_id | task_type |
|---|---|---|---|
| 第一次导入 | doc_001 | task_001 | import |
| 重新解析 | doc_001 | task_002 | parse |
| 重建索引 | doc_001 | task_003 | rebuild_index |
| 删除文档 | doc_001 | task_004 | delete |

所以 document 中只保存 `latest_task_id`，历史任务通过 `document_id` 去 tasks 表反查。

这样比把所有任务状态直接塞进 document 更清晰：

- document 负责描述“这份文档当前是什么状态”。
- task 负责描述“某一次执行具体跑到了哪里”。

## 2. 和原有数据的区别

阶段 3 新增的三张 Mongo 表不是替代原来的数据，而是补齐缺失的管理元数据层。

| 原有数据 | 作用 | 不适合承担的问题 |
|---|---|---|
| `chat_message` | 存聊天历史 | 不管理导入文档和任务 |
| Milvus `standard_subjects` | 存标准主题 | 是知识体系，不是文档状态 |
| Milvus `subject_aliases` | 存主题别名 | 是主体识别索引，不是任务状态 |
| Milvus `chunks` | 存可检索切片 | 是向量检索数据，不适合做文档管理 |
| `task_utils` 内存字典 | 存当前任务进度 | 重启丢失，只适合即时展示 |

重构后职责更清楚：

- Mongo `datasets/documents/tasks`：负责知识库、文档、任务管理。
- Milvus：负责向量检索和主题识别索引。
- Mongo `chat_message`：负责用户对话历史。
- `task_utils`：负责当前进程内的即时进度和 SSE 推送。

## 3. 服务重启后的真实含义

“服务重启后还能查历史任务”不是断点续传，也不是自动恢复执行。

更准确的说法是：

```text
服务重启后，可以通过 document 列表找回文档，并查看最近一次 task 的历史状态、失败节点和错误信息。
```

原因是 `task_id` 本身不适合作为用户找历史记录的入口。

`task_id` 是一次任务执行 ID，更像流水号。用户重启服务后不一定记得上一次的 `task_id`。

更合理的查询路径是：

```text
GET /documents
    -> 通过文件名、上传时间、状态找到 document

GET /documents/{document_id}
    -> 查看文档当前状态和 latest_task_id

GET /documents/{document_id}/tasks
    -> 查看这份文档的历史任务记录

GET /status/{task_id}
    -> 已知 task_id 时，查看某一次任务执行细节
```

因此阶段 3 实现的是“状态可追溯”，不是“任务可恢复执行”。

如果服务在任务执行过程中重启，后台线程已经结束，当前 LangGraph 调用栈也不存在了。Mongo 中保留的是上次执行到哪里、完成了哪些节点、失败或中断在哪个节点，但不会自动从这个节点继续跑。

后续补充改造进一步解决了“后台线程已经消失，但 Mongo 永远停在处理中”的假状态。导入服务进入 FastAPI lifespan 启动阶段时，会幂等检查所有 `pending/processing` task：

```text
旧 task 已不是 document.latest_task_id
    -> 只收口旧 task，不覆盖新 document

document 与索引已经 completed
    -> 说明最终节点已经提交，只是 task 终态漏写
    -> 把 task 修复为 completed

其他遗留 task
    -> status = failed
    -> error_code = import_service_restarted
    -> running_nodes = []，done_nodes 保留
    -> 有明确 running node 时更新对应 parse/index 阶段
    -> 没有 running node 时不猜测失败阶段
```

这里的“收口”是把不可能继续执行的假处理中状态改成真实终态，方便用户重新上传或重建索引；它仍然不是从断点自动续跑。

前端也按同一事实来源展示状态：新上传卡片每 2 秒轮询 task；“我的导入记录”在存在 `uploaded/processing` document 时，用唯一的 `setTimeout` 链每 2 秒刷新 document 列表。HTTP 错误或网络断开只表示“暂时无法确认”，页面保留最后一次成功状态并继续重试，不自行把任务改成失败。服务恢复后，前端最终展示的是上述启动收口写入 Mongo 的真实终态；`error_code=import_service_restarted` 的专用提示优先于根据 `failed_node` 推测 PDF 或 Milvus 故障。

对应回归测试覆盖：pending/processing 收口、重复执行幂等、旧 task 与最新 document 隔离、已完成 document 的 task 终态修复、解析/索引/无运行节点三种阶段归因、Mongo 不可用时启动不被阻断、API `error_code` 投影，以及前端单定时器、HTTP 状态检查和断线提示。

真正的断点续跑需要额外设计：

- 每个节点的输入和输出都能持久化。
- 每个节点都要幂等。
- 中间文件路径稳定。
- Milvus、MinIO 等外部副作用要能重复执行且不产生脏数据。
- 任务调度器能把 `processing` 状态识别成 `interrupted` 或 `retrying`。
- 重试时要处理 `retry_of_task_id`、新旧 task 关系、chunk 版本等问题。

这已经超出阶段 3。

当前项目的正确取舍是：

```text
先做状态持久化 + 失败可见 + 文档可找回。
后续再做重新导入、重建索引、删除文档。
暂时不做严格断点续跑。
```

这个取舍更符合当前项目规模。Mongo 数据少，都是测试数据，可以删库重建；导入任务也不是大规模分布式队列。现在做完整断点续跑，成本明显高于收益。

## 4. 懒加载 Mongo 的价值

阶段 3 新增的 `import_metadata_repository.py` 保持懒加载。

也就是：

```text
模块 import 时不连接 Mongo
FastAPI lifespan 启动时尝试连接 Mongo，执行遗留任务收口
Mongo 不可用时只记录日志，不阻止 HTTP 服务启动
后续第一次仓储访问仍可再次懒初始化 MongoClient 和索引
```

这样做的原因是阶段 0 已经明确要求：不要在模块导入阶段产生外部连接副作用；同时，进程内后台任务在服务重启后确实需要一个明确的生命周期钩子把持久状态收口。lifespan 把这两件事分开了。

这一边界带来的好处：

- Mongo 临时不可用时，不影响导入图、查询图 compile。
- 单元测试可以 monkeypatch repository，不需要真实 Mongo。
- 启动收口连接失败时会留下明确日志，但不会阻止 HTTP 服务提供其他能力。
- Mongo 连接发生在明确的运行期生命周期中，不会因单纯 import 模块而提前建立。

当前聊天历史 Mongo 工具也是类似思路：`mongo_history_utils.py` 里全局实例默认是 `None`，只有调用 `save_chat_message`、`get_recent_messages` 等函数时才会真正初始化。

## 5. 本阶段实际提升

阶段 3 的提升可以概括为：从“能跑导入流程”，升级为“能管理导入流程”。

具体提升：

- 上传后可以查 document 状态。
- 可以通过 document 列表找回历史文档，而不是依赖用户记住 `task_id`。
- 可以看到解析状态、索引状态、chunk 数量。
- 可以看到最近一次任务和历史任务。
- 失败时可以通过 API 看到失败节点和错误信息。
- `task_utils` 不再是唯一状态源，服务重启后仍保留历史状态。
- document 和 task 分开后，为后续重建索引、删除文档、多次任务历史打好基础。

一句话总结：

```text
Milvus 负责检索，chat_message 负责对话，dataset/document/task 负责管理。
```

阶段 3 补齐的是 RAG 系统从“脚本式导入”走向“管理型知识库”的关键一层。

# 第二部分：扩展导入状态契约

这一部分关注的是导入 state 和 `/upload` API 的契约变化：一次导入任务现在不只要知道“任务是谁”，还要知道“处理哪份文档、归属哪个知识库”。

## 1. task_id 不是新增字段

这里要注意，`task_id` 不是阶段 3 新增的。原来的 `/upload` 已经会生成 `task_id`，它表示一次导入任务执行。

原来 `task_id` 已经用于：

- 后台导入图追踪一次执行。
- `task_utils` 记录 running/done 节点。
- 日志里作为追踪 ID。
- `/status/{task_id}` 查询进度。

阶段 3 没有推翻这个机制，而是继续沿用它。

## 2. 真正新增的是 document_id 和 dataset_id

阶段 3 在 `ImportGraphState` 中新增：

- `document_id`：表示被处理的长期文档对象。
- `dataset_id`：表示这份文档和这次任务所属的知识库容器。

因此导入 state 现在更准确地表达为：

```text
task_id      已有：这一次导入任务
document_id  新增：这份文档
dataset_id   新增：所属知识库
```

这个变化的价值是让导入链路中的每个节点都能知道自己正在处理哪份 document，以及这份 document 属于哪个 dataset。这样节点推进时就能同步更新 document/task 元数据，而不是只更新进程内的 `task_utils`。

## 3. /upload 的职责边界

原来的 `/upload` 做的是：

```text
生成 task_id -> 保存文件 -> 启动后台导入
```

阶段 3 后，`/upload` 变成：

```text
沿用原 task_id 生成逻辑
生成 document_id
解析导入目标 dataset_id
创建 document/task 元数据
把 task_id/document_id/dataset_id 写入导入 state
启动后台导入
```

这里有一个重要边界：导入流程不应该把“创建知识库”和“上传文档”混在一起。

当前单知识库版本里，`POST /upload` 不传 `dataset_id` 时，会使用并确保默认 dataset 存在。这个设计是为了让现有 Demo 和单知识库流程保持简单。

但如果后续变成多知识库，上传文件时应该指定一个已经存在的 `dataset_id`，而不是每次上传都创建新的 dataset。也就是说：

```text
不传 dataset_id
    -> 使用 dataset_default_equipment_ops，并确保默认 dataset 存在

传入已有 dataset_id
    -> document/task 归属到这个 dataset

传入不存在的 dataset_id
    -> 拒绝导入，提示先创建 dataset
```

这样做可以避免一个常见问题：用户每上传一次文件，系统就误创建一个知识库，最后 dataset 变成一堆无意义的上传批次。

所以阶段 3 里的 dataset 仍然是管理容器，不负责判断用户问题属于哪个知识库，也不负责自动创建多知识库。多知识库创建应该放到后续 Dataset 管理 API，例如：

```text
POST /datasets
POST /upload 携带 dataset_id
```

## 4. 这部分的实际提升

扩展导入状态契约后，导入链路的上下文更完整：

- `task_id` 继续表示一次执行，不破坏原有任务追踪。
- `document_id` 让任务可以稳定关联到长期文档对象。
- `dataset_id` 让文档和任务归属到明确知识库。
- 上传时可以不传 `dataset_id` 走默认知识库，也可以指定已有 `dataset_id` 归属到目标知识库。
- 未知 dataset 会被拒绝，避免上传流程误创建知识库。

这部分不是复杂功能，但它把后续多知识库、文档列表、任务历史、重建索引的关系提前理清了。

# 第三部分：导入状态推进与关键元数据回写

这一部分关注的是导入流程运行中的状态推进：阶段 3 没有另起一套新的任务进度系统，而是在保留 `task_utils` 即时状态的基础上，把已注册导入任务的节点进度和关键 document 结果同步写入 Mongo。

原来的逻辑是：

```text
导入节点开始 -> add_running_task -> task_utils 内存 running_list
导入节点完成 -> add_done_task -> task_utils 内存 done_list
前端轮询 /status/{task_id} -> 读取内存状态
```

这个逻辑对“当前进程内的实时展示”是够用的，但它有几个明显问题：

- `running_list`、`done_list` 只在内存里，服务重启后丢失。
- `task_utils` 同时被导入链路和查询链路使用，不能简单地把所有 task/session 都写进导入任务表。
- 节点执行结果主要停留在 LangGraph state、日志或 Milvus 里，document 列表看不到 `chunk_count`、主题信息和索引完成状态。
- 失败时虽然能从当前 running 节点推断失败位置，但如果不落库，用户事后仍然很难通过 API 排查。

改完后的逻辑是：

```text
POST /upload
    -> 创建 document/task 元数据
    -> register_persistent_task(task_id, document_id, dataset_id)

导入节点开始
    -> add_running_task
    -> task_utils 内存更新
    -> 已注册导入任务同步 tasks.running_nodes / tasks.done_nodes

导入节点完成
    -> add_done_task
    -> task_utils 内存更新
    -> 已注册导入任务同步 tasks.running_nodes / tasks.done_nodes

关键节点产出结果
    -> 回写 documents.chunk_count / subject_id / standard_subject_name / index_status 等管理字段
```

## 1. task_utils 仍然负责即时进度

阶段 3 没有替换 `task_utils`。

`task_utils` 仍然负责：

- 当前进程内的 `running_list`。
- 当前进程内的 `done_list`。
- 当前任务状态 `status`。
- SSE 或轮询时需要的即时展示数据。

保留它的原因是：前端进度条和 SSE 更关心“当前这一刻跑到哪里”，内存状态读写简单、成本低，也不需要每一次展示都直接依赖 Mongo。

但阶段 3 增加了一个判断：只有调用过 `register_persistent_task(task_id, document_id, dataset_id)` 的导入任务，才会把进度快照同步到 Mongo。

这个边界很重要。查询链路也会复用 `task_utils`，例如 `node_subject_name_confirm`、`node_search_embedding`、`node_answer_output` 这些 query 节点也会产生临时进度。如果不做注册判断，Mongo 的 `tasks` 表就会混入大量不属于文件导入的查询 session。

所以新的职责关系是：

| 场景 | task_utils 内存 | Mongo tasks |
|---|---|---|
| 已注册的导入任务 | 写入 | 写入 |
| 未注册的查询 session | 写入 | 不写入 |
| 临时调试 task | 写入 | 不写入 |

这说明阶段 3 做的是“导入任务状态持久化”，不是把 `task_utils` 改造成全局任务中心。

## 2. running/done 同步的是快照，不是事件日志

每个导入节点仍然继续调用现有的：

```text
add_running_task(task_id, node_name)
add_done_task(task_id, node_name)
```

区别是：对已注册的导入任务，`task_utils` 会在内存状态变化后，把当前完整快照同步到 Mongo：

- `running_nodes`
- `done_nodes`

这里保存的是“当前状态快照”，不是完整事件流。

也就是说，Mongo 里能回答：

```text
这个 task 当前有哪些节点正在运行？
这个 task 已经完成了哪些节点？
这个 task 最后失败在哪个节点？
```

但它不负责回答：

```text
每个节点几点开始？
每个节点耗时多少？
每个节点重试了几次？
每一次状态变化的历史记录是什么？
```

这些更像任务审计日志或调度系统能力，不属于阶段 3 的范围。阶段 3 先把当前进度和失败定位持久化，已经能覆盖文档管理和问题排查的主要需求。

## 3. document 回写的是用户关心的管理结果

`tasks` 记录的是“一次执行跑到哪里”，而 `documents` 记录的是“这份文档现在是什么状态”。

所以阶段 3 不只同步 task 节点进度，还在关键导入节点额外回写 document 元数据。

当前落地的回写点是：

| 节点 | 回写到 document 的字段 | 价值 |
|---|---|---|
| `node_entry` | `status=processing`、`parse_status=processing`、`file_title` | 文档进入处理态，并记录后续 chunk/Milvus 使用的文件标题 |
| `node_pdf_to_md` | `md_path` | PDF 转 Markdown 后，文档状态里能定位解析产物 |
| `node_md_img` | `parse_status=completed`、`md_path` | Markdown 和图片处理完成后，解析阶段有明确完成态 |
| `node_document_split` | `chunk_count`、`index_status=processing` | 切分完成后，文档列表可以看到切片数量，并知道进入索引阶段 |
| `node_subject_name_recognition` | `subject_id`、`standard_subject_name` | 文档能关联到阶段 2 的标准主题体系 |
| `node_import_milvus` | `status=completed`、`index_status=completed`、`chunk_count` | Milvus 入库完成后，文档整体和索引状态闭环 |

这几个字段的价值不是给 LangGraph 下一步计算用，而是给“文档管理视角”用。

例如用户打开文档列表时，不需要知道 LangGraph state 的内部结构，也不需要去 Milvus 里查 chunk，就能看到：

- 文档是否还在解析。
- 文档是否已经完成索引。
- 这份文档切成了多少个 chunk。
- 这份文档被识别成哪个标准主题。
- 如果失败，失败落在解析阶段还是索引阶段。

这就是 document 和 task 分开的意义：task 面向执行过程，document 面向用户管理入口。

## 4. 失败处理按节点归因到解析阶段或索引阶段

后台导入在 `invoke_graph` 中统一收口异常。

失败时流程是：

```text
LangGraph 节点抛异常
    -> get_last_running_task_node_name(task_id)
    -> update_task_status(task_id, failed)
    -> safe_mark_import_failed(task_id, failed_node, error_message)
```

`safe_mark_import_failed` 会同时更新 task 和 document：

- task 写入 `status=failed`、`failed_node`、`error_message`。
- document 写入 `status=failed`、`failed_node`、`error_message`。
- 如果失败节点属于解析阶段，写 `parse_status=failed`。
- 如果失败节点属于主体识别、向量化、Milvus 入库等后续阶段，写 `index_status=failed`。

这个设计让失败排查更直接。

原来只能从日志里判断“哪里失败了”。现在 API 可以直接表达：

```text
这份文档整体失败了
失败节点是 node_import_milvus
错误信息是 Milvus 入库失败
解析阶段已完成
索引阶段失败
```

这比单一的 `status=failed` 更有价值，因为解析失败和索引失败的处理方式不同：解析失败通常要看文件、MinerU 或 Markdown 图片处理；索引失败通常要看主体识别、Embedding、Milvus 连接或 schema。

## 5. 关键取舍和边界

这一部分容易被误解成“已经做了完整任务恢复”，需要明确边界。

阶段 3 已经做了：

- 已注册导入任务的 running/done 快照落 Mongo。
- 普通查询 session 不写入导入任务表。
- document 关键管理字段随节点推进回写。
- 导入失败时记录 `failed_node` 和 `error_message`。
- 解析阶段失败和索引阶段失败分开记录。

阶段 3 没有做：

- 不记录每个节点的完整事件流水。
- 不记录每个节点的开始时间、结束时间和耗时。
- 不做服务重启后的自动恢复执行。
- 不做节点级重试调度。
- 不保证 document/task 更新和 Milvus 入库之间具备分布式事务。
- 不改变 Milvus chunk 的幂等策略；当前仍然按 `file_title` 清理旧 chunk 后插入。

这里还有一个实现上的现实边界：`safe_update_document`、`safe_update_task_nodes`、`safe_mark_import_failed` 这类函数会捕获异常并写日志，避免 Mongo 写入失败直接打断导入节点主流程。这个取舍更适合当前阶段，因为阶段 3 的目标是补齐管理元数据，而不是让 Mongo 成为每个节点继续执行的强事务前置条件。

## 6. 本阶段实际提升

这部分重构后的实际提升是：导入链路从“只知道当前进程里跑到哪”，变成“任务进度和文档结果都能被管理接口看见”。

具体来说：

- `/status/{task_id}` 可以优先读 Mongo 中的任务进度，内存不存在时仍能查到历史状态。
- `/documents/{document_id}` 可以展示文档的解析状态、索引状态、chunk 数量和主题信息。
- 失败后不用只翻日志，可以从 task/document 里看到失败节点和错误信息。
- `task_utils` 仍然能服务前端即时进度，不需要把前端展示逻辑重写一遍。
- 已注册导入任务和普通查询 session 被区分开，避免状态表被无关 session 污染。

面试或项目复盘时，这一部分可以这样表达：

```text
我没有把内存进度工具直接废掉，而是保留它的实时展示职责；
同时通过任务注册机制，只把真正的导入任务同步到 Mongo；
再在切分、主体识别、Milvus 入库这些关键节点回写 document 管理字段。
这样既兼容原来的进度展示，又让文档状态具备可追溯和可排查能力。
```

验证结果：当前全量回归已通过 `uv run python -m pytest -q`，结果为 `289 passed`。

# 第四部分：导入 API 状态查询契约

这一部分关注的是阶段 3 对外 API 的变化：导入接口不再只返回一个临时 `task_id`，状态查询也不再只看当前进程内的进度，而是把 document、dataset、失败信息和时间戳一起纳入接口契约。

原来的 API 逻辑更偏“任务进度查询”：

```text
POST /upload
    -> 返回 task_ids

GET /status/{task_id}
    -> 从 task_utils 内存读取 status / done_list / running_list
```

这个逻辑能支撑前端展示当前上传任务的进度，但它有几个问题：

- 上传响应里只有 `task_id`，用户很难把一次导入和长期 document 对象关联起来。
- `/status/{task_id}` 依赖内存状态，服务重启后无法优先返回持久化任务记录。
- 状态响应缺少 `document_id`、`dataset_id`，不方便从任务跳转到文档详情或知识库维度。
- 失败时只有整体状态，不方便通过 API 看到 `failed_node` 和 `error_message`。
- 没有独立的文档状态查询入口，文档列表和任务状态之间缺少稳定衔接。

阶段 3 改完后，API 逻辑变成：

```text
POST /upload
    -> 创建 document/task 元数据
    -> 返回 task_ids + document_ids + dataset_id

GET /status/{task_id}
    -> 优先从 Mongo tasks 读取持久化任务状态
    -> 没有持久化记录或 Mongo 查询失败时，回退 task_utils 内存状态

GET /documents/{document_id}
    -> 从 Mongo documents 查询文档整体状态
```

## 1. UploadSchema 从任务入口扩展成文档入口

原来的 `UploadSchema` 只需要表达“上传成功，并且后台任务 ID 是什么”。

阶段 3 增加了：

- `dataset_id`
- `document_ids`

也就是上传响应现在同时告诉前端两件事：

```text
task_ids     用来查看这一次异步导入任务的进度
document_ids 用来查看这份长期文档对象的状态
dataset_id   用来说明这份文档归属哪个知识库容器
```

这个变化的价值是让前端或调用方不再只围绕 `task_id` 运转。

`task_id` 适合短期进度展示；`document_id` 才适合作为后续文档详情、任务历史、重建索引、删除文档等能力的入口。

## 2. TaskStatusSchema 补齐持久化任务上下文

阶段 3 的 `TaskStatusSchema` 在原有字段上继续保留：

- `status`
- `done_list`
- `running_list`

这是为了兼容现有 `import.html` 的进度展示，不让前端因为状态源变化而重写进度条。

同时新增：

- `document_id`
- `dataset_id`
- `failed_node`
- `error_message`
- `created_at`
- `updated_at`

这些字段让 `/status/{task_id}` 不只回答“当前跑到哪”，还能回答：

```text
这个 task 属于哪份 document？
这个 task 属于哪个 dataset？
如果失败，失败在哪个节点？
错误信息是什么？
这条任务记录是什么时候创建、什么时候更新的？
```

这里的设计重点是：状态接口不只是给进度条用，也要能服务问题排查和历史记录查看。

## 3. /status/{task_id} 优先读 Mongo，再回退内存

阶段 3 没有直接删除内存状态查询，而是调整了读取优先级：

```text
优先读取 Mongo tasks
    -> 找到 task 记录，返回持久化状态

Mongo 查询失败或没有持久化记录
    -> 回退 task_utils 内存状态
```

这样做有两个价值。

第一，服务重启或导入结束后，如果 Mongo 里有 task 记录，`/status/{task_id}` 仍然可以返回历史任务状态、失败节点和错误信息。

第二，兼容还没有注册持久化元数据的临时任务或旧调用路径。只要 `task_utils` 内存里还有状态，接口仍然能返回原来的 `done_list` 和 `running_list`。

这个设计不是“双写一定强一致”。更准确地说，它是一个兼容过渡策略：

- 对阶段 3 的导入任务，Mongo 是长期状态源。
- 对未持久化任务，内存仍是临时状态源。
- Mongo 不可用时，接口尽量回退到已有内存状态，而不是直接让前端进度查询失败。

## 4. 新增文档状态查询入口

阶段 3 新增：

```text
GET /documents/{document_id}
```

它返回的是 document 视角的状态，而不是 task 视角的状态。

核心字段包括：

- `document_id`
- `dataset_id`
- `latest_task_id`
- `file_name`
- `file_path`
- `local_dir`
- `status`
- `parse_status`
- `index_status`
- `chunk_count`
- `subject_id`
- `standard_subject_name`
- `md_path`
- `failed_node`
- `error_message`
- `created_at`
- `updated_at`

这个接口的价值是把“文档当前情况”从任务执行细节里拆出来。

用户或前端可以直接问：

```text
这份文档是否解析完成？
这份文档是否索引完成？
这份文档切出了多少个 chunk？
这份文档识别成哪个标准主题？
最近一次任务是哪一个？
如果失败，失败节点和错误信息是什么？
```

如果 `document_id` 不存在，接口返回 404。这个边界比返回空对象更清晰，因为调用方可以明确知道：这是一个无效文档 ID，而不是一份状态为空的文档。

## 5. 和前端/历史查询路径的关系

阶段 3 后，导入状态查询路径变成两条：

```text
实时任务进度：
POST /upload -> task_ids -> GET /status/{task_id}

文档管理状态：
POST /upload -> document_ids -> GET /documents/{document_id}
```

这两条路径服务的对象不同：

| API | 面向对象 | 主要用途 |
|---|---|---|
| `GET /status/{task_id}` | 一次任务执行 | 进度展示、失败节点、任务历史状态 |
| `GET /documents/{document_id}` | 一份长期文档 | 文档详情、解析/索引状态、主题信息、后续管理入口 |

这样设计后，前端不需要把 `task_id` 当成所有管理能力的唯一入口。上传刚完成时可以用 `task_id` 看进度；服务重启后或用户查看历史时，更适合从 document 列表或 `document_id` 进入。

## 6. 关键取舍和边界

阶段 3 已经做了：

- 上传响应返回 `document_ids` 和 `dataset_id`。
- 任务状态响应返回 document/dataset 上下文、失败节点、错误信息和时间戳。
- `/status/{task_id}` 优先读 Mongo，失败时回退内存。
- 新增 `GET /documents/{document_id}` 查询文档状态。
- 文档不存在时返回 404。

阶段 3 没有做：

- 不做完整 Dataset 管理 API。
- 不做多知识库自动路由。
- 不做文档删除 API。
- 不做重建索引 API。
- 不把 `/documents/{document_id}` 设计成 chunk 明细查询接口。
- 不保证前端已经完整消费所有新增字段；当前重点是先稳定后端契约。

这部分的边界是：API 只是把阶段 3 的 document/task 元数据暴露出来，方便状态查询和后续管理能力接入；它还不是完整的知识库后台管理系统。

测试覆盖：

# 第五部分：导入失败处理与阶段归因

这一部分关注的是导入链路失败时怎么落状态：阶段 3 不只是把任务标成 `failed`，还会记录失败节点、错误信息，并把失败归因到解析阶段或索引阶段。

原来的失败处理更偏日志排查：

```text
后台导入异常
    -> 写日志
    -> 内存 task 状态可能变成 failed
    -> 具体失败节点和 document 阶段状态不稳定
```

这个逻辑的问题是：

- 用户或前端只能看到整体失败，很难知道失败发生在哪个节点。
- 解析失败和索引失败混在一起，排查方向不清晰。
- 如果只依赖日志，服务重启或日志滚动后，历史失败原因不容易找回。
- task/document 没有统一失败收口，任务状态和文档状态可能表达不一致。

阶段 3 改完后，失败收口变成：

```text
后台导入异常
    -> 根据当前 running 节点推断 failed_node
    -> task.status = failed
    -> task.failed_node / task.error_message 落库
    -> document.status = failed
    -> document.failed_node / document.error_message 落库
    -> 按 failed_node 判断 parse_status 或 index_status
```

## 1. 后台异常用当前 running 节点定位失败点

导入主流程在 `invoke_graph` 中统一执行 LangGraph。

当后台导入异常时，异常收口逻辑会先调用：

```text
get_last_running_task_node_name(task_id)
```

也就是从 `task_utils` 当前 running 节点列表里取最后一个节点，作为本次失败的 `failed_node`。

这个设计的价值是：节点本身仍然只需要在开始时调用 `add_running_task`，完成时调用 `add_done_task`；异常收口不需要每个节点都写一遍 try/except。只要节点进入 running 状态，后台统一收口就能知道大致失败位置。

例如 Milvus 入库阶段失败时，状态会表达为：

```text
failed_node = node_import_milvus
error_message = Milvus 入库失败
```

这比只返回 `status=failed` 更有排查价值。

## 2. task 和 document 同步进入 failed

失败时会同时更新两层状态：

| 对象 | 更新内容 | 含义 |
|---|---|---|
| task | `status=failed` | 这一次异步执行失败 |
| task | `running_nodes=[]` | 失败后不再保留“仍在运行”的节点 |
| task | `failed_node` | 本次执行失败节点 |
| task | `error_message` | 本次执行错误信息 |
| document | `status=failed` | 这份文档当前导入结果失败 |
| document | `failed_node` | 最近一次失败节点 |
| document | `error_message` | 最近一次失败原因 |

这里的职责边界仍然是：

- task 记录“一次执行为什么失败”。
- document 记录“这份文档当前处于失败状态，失败在哪里”。

两者都要写，是因为用户可能从不同入口查状态：

```text
GET /status/{task_id}
    -> 看某一次任务执行失败在哪里

GET /documents/{document_id}
    -> 看这份文档当前为什么不可用
```

## 3. 解析失败和索引失败分开记录

阶段 3 把失败阶段分成两类。

解析阶段节点包括：

- `upload_file`
- `node_entry`
- `node_pdf_to_md`
- `node_md_img`

这些节点失败时，document 写：

```text
parse_status = failed
```

索引阶段节点包括：

- `node_subject_name_recognition`
- `node_bge_embedding`
- `node_import_milvus`

这些节点失败时，document 写：

```text
index_status = failed
```

这样区分后，排查方向更明确。

解析阶段失败通常要看：

- 上传文件是否保存成功。
- 文件类型是否支持。
- PDF 转 Markdown 是否失败。
- Markdown 图片处理是否失败。

索引阶段失败通常要看：

- 主体识别和标准主题入库是否失败。
- Embedding 服务是否可用。
- Milvus collection、schema、连接或插入是否失败。

这也是 `parse_status` 和 `index_status` 分开的实际价值：它不是为了多加字段，而是为了让失败问题能被快速归类。

## 4. 上传保存失败也纳入同一套失败模型

`upload_file` 是解析阶段的一部分。

上传接口在保存文件失败时，会：

```text
update_task_status(task_id, failed)
safe_mark_import_failed(task_id, "upload_file", error_message)
```

所以即使失败发生在 LangGraph 启动前，也会进入同一套 task/document 失败记录：

- task 写 `status=failed`。
- task 写 `failed_node=upload_file`。
- document 写 `status=failed`。
- document 写 `parse_status=failed`。
- task/document 都写入 `error_message`。

这让“上传保存失败”和“图节点执行失败”在状态模型上保持一致。

## 5. 关键取舍和边界

阶段 3 已经做了：

- 后台导入异常时，根据当前 running 节点记录 `failed_node`。
- task/document 同步写入 `failed`。
- task/document 同步写入 `error_message`。
- 解析阶段失败写 `parse_status=failed`。
- 主体识别、向量化、Milvus 入库失败写 `index_status=failed`。
- task 失败后清空 `running_nodes`，避免历史状态看起来仍在运行。

阶段 3 没有做：

- 不做节点级自动重试。
- 不做失败后自动恢复执行。
- 不做失败事件流水审计。
- 不记录每个节点的耗时和异常堆栈到 Mongo。
- 不在 Mongo 和 Milvus 之间做分布式事务。

还有一个实现边界要明确：`failed_node` 依赖节点先进入 running 状态。如果异常发生在某个节点调用 `add_running_task` 之前，`failed_node` 可能为空。当前导入节点都按“开始时 add_running_task、完成时 add_done_task”的模式推进，因此正常节点异常可以被定位到当前 running 节点。

## 6. 测试覆盖
