# 第一部分：把“能跑”升级为“能证明效果”的评测地基

阶段 8 的核心不是训练模型，而是补齐训练前最容易被忽略的一层能力：

```text
同一个问题、同一份语料快照、同一套 Planner 配置、同一个 Reward 版本下，
系统能不能稳定复现轨迹，并解释好在哪里、差在哪里、和谁比。
```

阶段 5 已经把线上查询链路改成：

```text
Planner -> Action -> Observation -> Planner -> terminal Action -> Citation
```

阶段 6 补齐了 chunk 启停审计，阶段 7 补齐了 Dataset、Document、Conversation、Trace 和 Feedback 的管理能力。

但是在阶段 8 之前，这些能力仍然主要服务“线上能查询”和“人工能看 Trace”。它们还不能直接回答后续训练前必须回答的问题：

- 评测样本在哪里，格式是否固定。
- 哪些问题可以作为 Demo，哪些问题可以作为训练候选。
- train/dev/test 是否真的隔离。
- 评测时使用的是哪一版 document、index version 和 enabled chunk。
- 同一个初始 State 下，不同 Planner 轨迹是否能公平对比。
- Reward 到底奖励了什么，是否只保存一个总分。
- API teacher 或本地模型轨迹能不能直接进入训练。
- 阶段 9 的 SFT/GRPO 是在什么基线上证明增益。

原来的链路更像：

```text
真实查询或 Retrieval Test
    -> 线上图实时访问当前 Mongo/Milvus/Web 配置
    -> 生成 Trace
    -> 人工查看或反馈
```

这个链路能支撑线上查询，但不适合直接做训练前评测。因为当前环境一旦变化，Trace 的含义也会跟着变化。

阶段 8 改完后的主链路是：

```text
PlannerEvalCase
    -> EnvironmentSnapshot
    -> OfflineRagEnvironment
    -> Planner baseline / 指定 Action path
    -> Trace / Observation / Reward
    -> baseline report / SFT export
```

这一层的价值是把“线上能力”转换成“可复现实验证据”。阶段 9 再做 SFT 或 GRPO 时，不需要临时补评测系统，也不会只能用主观感觉判断训练有没有提升。

## 1. 阶段 8 解决的不是效果提升，而是效果证明

阶段 8 当前并没有重新优化 Milvus 召回，也没有训练新模型。

它解决的是评测可信度问题：

```text
阶段 5 证明：三路检索 C 在真实检索评测中效果最好。
阶段 8 证明：后续 Planner 轨迹、Reward、SFT 数据导出能在固定环境里复现和比较。
```

这两个结论不能混在一起。

阶段 5 的报告里，真实检索核心集四轮结果是：

```text
C：dense + learned sparse + BM25
核心集 Recall@K = 1.0000
核心集引用命中率 = 1.0000
```

阶段 8 当前的 `snapshot_expected_chunks` provider 则是离线自检工具。它根据标注的 expected chunk 构造候选，用来验证管线闭环，不代表真实 Milvus 再次提升了召回。

这条边界很重要。否则阶段 8 很容易被误解成：

```text
又做了一轮检索优化
```

实际应该表达为：

```text
阶段 8 把检索、Planner、Reward 和训练数据导出之间的评测地基搭好了。
```

## 2. 和原有 Trace/Feedback 的关系

阶段 7 已经有 `retrieval_traces` 和 `trace_feedbacks`。

但是 Trace 和 Feedback 只是数据来源，不是最终评测真相。

原因是：

- Trace 是某一次运行结果，会受到当时配置、语料和用户权限影响。
- Feedback 是人工反馈来源，可能只标了局部期望。
- 训练和评测需要固定 split、版本、样本 ID 和标注字段。

所以阶段 8 新增文件化样本：

```text
evaluation/stage8/cases/planner_cases.jsonl
evaluation/stage8/cases/demo_regression_cases.jsonl
evaluation/stage8/cases/split_manifest.json
```

它们把 Trace/Feedback 里分散的线索整理成可校验、可复用、可对比的评测契约。

## 3. 本部分实际提升

阶段 8 第一部分带来的提升是：

- 从“看起来能跑”变成“能固定环境复跑”。
- 从“某条 Trace 结果不错”变成“同一批 case 可以对多个 Planner 公平比较”。
- 从“训练数据靠人工挑”变成“先过 schema、split、Reward 和复核边界”。
- 从“阶段 9 直接上 GRPO”变成“先有 rule baseline、SFT 数据和 held-out test 评测基线”。

面试里可以这样表达：

```text
我没有直接把强化学习 Trainer 接进线上查询链路，而是先做阶段 8 的离线评测层。
它把 case、环境快照、Planner 轨迹、Reward 分项和训练数据导出固定下来。
这样阶段 9 训练出来的模型到底有没有提升，不靠主观演示，而是能在同一套 held-out 数据和 snapshot 上对比。
```

# 第二部分：文件化样本契约与 train/dev/test 边界

阶段 8 的第二个价值是把评测数据从“散落在 Trace、Feedback 和口头约定里”，升级成了明确的文件化契约。

原来的数据来源是：

```text
真实查询 Trace
Retrieval Test 运行
人工反馈
阶段 5 检索样本
设备手册里的典型问题
```

这些来源都有价值，但如果直接混在一起用于训练，会出现几个问题：

- Demo 样本可能被训练集污染，展示时看起来效果很好，但不代表泛化。
- test 样本可能被用来调 Prompt、挑 Reward 权重或选择模型。
- 同一问题的改写可能同时出现在 train 和 test。
- 私有文档样本如果没有复核，可能越过隐私边界。
- API teacher 轨迹如果不筛选，可能把错误路径教给本地模型。

阶段 8 改完后的样本边界是：

```text
planner_cases.jsonl
    -> train/dev/test 候选池
    -> 阶段 9 训练和评测来源

demo_regression_cases.jsonl
    -> 面试展示和快速回归
    -> 不进入 SFT/GRPO 训练

split_manifest.json
    -> 固定 case_id 与 leakage_group_id 的 split 归属
    -> 防止同源样本跨 split 泄漏
```

当前实际数据规模是：

```text
planner_cases.jsonl：53 条
  train = 11
  dev = 7
  test = 35

demo_regression_cases.jsonl：12 条
  demo_regression = 12
```

Planner 候选池覆盖了：

```text
core
colloquial
clarification
refusal
realtime
private_doc
```

## 1. PlannerEvalCase 的价值

`PlannerEvalCase` 是阶段 8 的核心样本对象。

它不是普通问答样本，而是 Planner 评测样本。它同时记录：

- 用户问题。
- 所属 dataset。
- 固定测试用户和 tenant。
- 来源 document 和 index version。
- 期望 subject。
- 期望 chunk。
- 期望答案要点。
- 期望行为，例如回答、拒答、追问或 Web。
- 可接受 Action 路径。
- 标识期望，例如设备型号、报警码、部件名。
- 标签来源和人工复核状态。

这比普通 QA 数据多了很多字段，但这些字段都不是装饰。它们让阶段 9 可以训练 Planner，而不是只训练一个会背答案的模型。

例如一个回答型问题，不只要知道最终答案，还要知道：

```text
应该先 local_search
应该命中哪个 chunk
最终引用是否来自这个 chunk
是否不应该调用 Web
是否允许先 HyDE 再回答
```

这就是 Planner 训练和普通问答微调的区别。

## 2. Demo 回归集和训练候选池物理分开

Demo 回归集的作用是展示和冒烟，不是训练。

如果把 Demo 样本直接加入训练，就会让后续演示失去说服力。模型可能只是见过这些问题，并不能证明 Planner 策略真的变好。

阶段 8 的设计是：

```text
Demo 回归集
    -> 固定 10-20 条
    -> 面试展示、快速回归
    -> 不进入训练导出

Planner 候选池
    -> 显著大于 Demo
    -> train/dev/test 拆分
    -> 经过 Reward 和复核后再导出训练
```

当前 Demo 回归集 12 条，围绕设备手册、报警码、维护 SOP 和口语问法展示，不混入 SFT/GRPO。

## 3. leakage_group_id 防止同源样本泄漏

`leakage_group_id` 的中文含义是“泄漏分组 ID”。

它解决的是一个很实际的问题：

```text
同一个问题的正式问法进了 train，
同一个问题的口语改写进了 test，
最后 test 指标看起来很好，但其实模型见过同源信息。
```

阶段 8 的 schema 校验会拒绝同一个 `leakage_group_id` 跨 split。

这使得数据拆分不只是文件名上的 train/test，而是有防泄漏规则约束。

## 4. 本部分实际提升

这一部分的提升是：

- Demo、训练候选、held-out test 的边界清晰。
- 每条回答型样本都有 expected chunk 和答案要点。
- 拒答、追问、Web 实时类样本有行为标注，不会被误当成普通问答。
- 私有文档样本通过 `privacy_scope` 和 `human_review_status` 控制，不会未经复核直接导出训练。
- 后续扩充公开制造业数据时，可以先进入候选池，而不是直接混入训练。

面试里可以这样表达：

```text
阶段 8 我没有只做一个 demo_cases.json，而是把 Demo 回归集和 Planner 训练候选池分开。
每条样本都记录 expected chunk、期望行为、可接受 Action 路径和 leakage_group_id。
这样后续 SFT/GRPO 不是拿测试集调出来的，也不会把展示样本混进训练。
```

# 第三部分：EnvironmentSnapshot 固定语料和配置版本

阶段 8 的第三个价值是补齐环境快照。

没有环境快照时，离线评测看起来是在跑同一批问题，实际可能不是同一批环境。

原来的问题是：

```text
今天的 document/index version
今天的 enabled chunk
今天的 retrieval_config
今天的 Planner policy
今天的 disabled override
```

这些都会随着项目继续开发而变化。

如果没有快照，后续看到某个模型分数变化时，很难判断原因：

- 是 Planner 变好了。
- 是检索配置变了。
- 是 chunk 被禁用了。
- 是文档重建导致 chunk_id 变了。
- 是测试用户能看的 dataset 范围变了。

阶段 8 新增：

```text
evaluation/stage8/snapshots/environment_snapshot.json
evaluation/stage8/build_environment_snapshot.py
```

快照固定了：

- dataset。
- document。
- index version。
- enabled chunk。
- disabled chunk。
- retrieval config version。
- retrieval config snapshot。
- planner registry。
- 固定测试用户。
- 输入文件 hash。

当前快照 ID 是：

```text
stage8-env-20260715-v1
```

## 1. index_version 为什么必须进入快照

`chunk_id` 不是孤立身份。

更可靠的 chunk 身份是：

```text
document_id + chunk_id + index_version
```

如果只记录 `chunk_id`，文档重建后可能出现同一个业务问题对应不同 chunk 版本。旧标注就可能被错误套到新语料上。

阶段 8 的快照构建会校验 case 引用的 document、chunk 和 index version 是否存在。引用旧 `index_version` 时会给出明确错误。

这让评测失败尽早发生在数据准备阶段，而不是阶段 9 训练跑到一半才发现标注漂移。

## 2. enabled/disabled chunk 为什么也要固定

阶段 6 已经支持 chunk 启停。

如果阶段 8 离线环境每次都读取当前 Mongo 里的 disabled 覆盖，就会出现：

```text
同一个 case
昨天评测能命中
今天因为人工禁用某个 chunk 导致无法命中
```

这不一定是 Planner 退化，而是语料环境变了。

所以阶段 8 的设计是：

```text
离线评测只读取 snapshot 里的 enabled/disabled 状态。
当前 Mongo 的后续漂移不自动影响这次评测。
```

如果需要更新语料，就生成新的 snapshot ID，而不是悄悄改变旧评测口径。

## 3. planner_registry 的价值

阶段 8 要比较：

```text
rule
api
local_base
```

但当前第一版只真正执行 `rule`。

如果 `api` 和 `local_base` 没有配置，最差的做法是生成假结果，或者把缺失结果当作 0 分。

阶段 8 的做法是把 planner 可用性写入 snapshot 和输出摘要：

```text
api：skipped，原因是阶段 7 只注册名称，不加载 API Planner
local_base：skipped，原因是阶段 8 离线评测预留
```

这样报告不会误导读者，也给阶段 9 接入真实模型留下稳定位置。

## 4. 本部分实际提升

这一部分的提升是：

- 评测不再依赖当前数据库的即时状态。
- case 引用旧文档版本或不存在 chunk 时能明确失败。
- 同一个 snapshot 可以复用在 rule、SFT、GRPO 前后对比。
- `api/local_base` 没配置时诚实跳过，不伪造 baseline。
- 阶段 9 前可以冻结 snapshot，避免训练前后比较口径漂移。

面试里可以这样表达：

```text
我把离线评测的语料和配置做成 EnvironmentSnapshot。
它固定 dataset、document、index version、enabled chunk、检索配置和 planner registry。
这样模型训练前后对比时，能确认变化来自 Planner 或模型本身，而不是语料或配置漂移。
```

# 第四部分：OfflineRagEnvironment 把 Planner 轨迹变成可复现执行

阶段 8 的第四个价值是实现离线 `Environment`。

这里的 `Environment` 可以理解为强化学习里的环境：

```text
Planner 给出 Action
Environment 执行 Action
Environment 返回 Observation
Planner 再根据 Observation 决定下一步
```

在阶段 8 之前，真实查询图也能做到类似闭环，但它依赖线上图、当前 Mongo/Milvus/Web 和真实聊天路径。

这不适合训练前评测。

阶段 8 新增：

```text
app/rag/evaluation/offline_environment.py
```

它提供：

```text
reset(case, snapshot)
step(state, decision)
run_action_path(case, actions)
run_planner(case, planner)
to_json_trace()
```

## 1. 为什么不能直接复用线上查询图做训练评测

线上查询图的职责是服务用户请求。

它会处理：

- HTTP 请求。
- SSE。
- 聊天历史。
- 当前用户上下文。
- 当前 Mongo/Milvus 状态。
- 真实 Trace 持久化。

训练评测需要的是：

- 固定初始 State。
- 同一个 case 可运行多条轨迹。
- 不写聊天历史。
- 不被当前数据库漂移影响。
- 可以注入不同 ActionProvider。
- 可以把非法路径标成结构化错误。

所以阶段 8 没有把 GRPO Trainer 或离线评测脚本塞进线上 FastAPI，也没有让训练逻辑直接调用真实查询 API。

它单独抽出离线环境，服务评测和训练数据生成。

## 2. State 会随着 Action 变化，Environment 不是不变的

这里容易误解。

固定 `EnvironmentSnapshot` 不等于每一步 State 都一样。

真实执行是：

```text
S0：query、dataset、snapshot、空 action_history
A0：local_search
S1：增加 local_search Observation 和 retrieved chunks
A1：answer
S2：增加 final_answer、citation、terminal_action
```

不变的是外部环境边界：

```text
同一份语料快照
同一套检索配置
同一批 enabled/disabled chunk
```

变化的是轨迹状态：

```text
action_history
latest_observation
retrieved_candidates
citations
terminal_action
errors
```

这正好符合 Planner 训练需要。模型每一步都根据新的 Observation 决策，但多个 Planner 之间看到的是同一份外部环境。

## 3. ActionProvider 的价值

`OfflineRagEnvironment` 不直接写死 Milvus 或 Web。

它通过 `OfflineActionProvider` 注入 Action 执行能力：

```text
local_search(state, decision)
hyde_search(state, decision)
web_search(state, decision)
```

当前第一版使用：

```text
snapshot_expected_chunks
```

它根据 case.expected_chunks 构造可复现候选。

这个 provider 的边界是：

```text
验证离线评测闭环，不代表真实 Milvus 召回质量。
```

后续要接真实 Milvus provider 时，不需要重写 runner 和 Reward 主流程，只要替换 provider。

## 4. 非法 Action 路径变成可解释错误

Planner 模型很可能输出非法路径。

例如：

```text
第一步直接 hyde_search
已经 answer 后继续 local_search
重复执行 local_search
没有证据却 answer
```

阶段 8 的离线环境会把这些情况标记为结构化错误，而不是让脚本崩掉或静默吞掉。

这对阶段 9 很重要。因为训练早期的本地模型可能经常格式错、路径错、终态错。评测环境必须能收集这些失败轨迹，Reward 才能正确惩罚。

## 5. 本部分实际提升

这一部分的提升是：

- 同一个 case 可以对多条轨迹公平评分。
- 规则 Planner、API Planner、本地 Planner、后续 SFT/GRPO Planner 可以共用执行环境。
- 不写聊天历史，不污染线上用户数据。
- 非法 Action 被明确标记，便于训练和排查。
- 后续 GRPO 的 rollout 阶段有了环境接口基础。

面试里可以这样表达：

```text
我把线上查询图里的 Planner 思路抽成了离线 Environment。
它不直接连线上聊天路径，而是在固定 snapshot 下执行 Action，返回 Observation 和 Trace。
这样强化学习里的 rollout 可以复用同一套环境，模型每一步的 State 会更新，但外部语料和配置保持公平一致。
```

# 第五部分：Reward v1 从“一个分数”拆成可解释评分体系

阶段 8 的第五个价值是实现 Reward v1。

如果后续要做 GRPO，Reward 不能只是一个模糊总分。

否则模型很容易学会钻空子：

- 为了提高检索命中，不断调用 HyDE 或 Web。
- 为了引用命中，引用一堆无关 chunk。
- 为了避免错答，所有问题都拒答。
- 为了格式通过，输出看似合法但路径完全不符合业务。
- 伪造不存在的工具结果或引用。

阶段 8 新增：

```text
app/rag/evaluation/metrics.py
app/rag/evaluation/reward.py
```

Reward v1 分成六个分项：

```text
R_format
R_retrieval
R_citation
R_answer
R_behavior
R_cost
```

## 1. metrics 和 reward 的职责区别

`metrics.py` 更像“基础打分规则库”。

它负责计算：

- chunk key 统一。
- recall@k。
- MRR。
- nDCG。
- citation hit rate。
- answer point coverage。
- action path 对比。

`reward.py` 更像“实际奖励流程”。

它负责：

- 从 case 和 trajectory 里取输入。
- 调用 metrics。
- 按 RewardConfig 加权。
- 生成每个 component 的 score、weight、weighted_score、details、reasons。
- 处理格式非法总分上限。
- 输出可 JSON 序列化的 `TrajectoryReward`。

可以简单理解为：

```text
metrics：怎么算某个指标。
reward：怎么把一条完整轨迹评成训练可用奖励。
```

## 2. 为什么必须统一 chunk 身份

不同来源里的 chunk 可能长得不一样：

```text
ExpectedChunk：document_id + chunk_id + index_version
RetrievalCandidate：document_id + chunk_id + index_version
Citation：document_id + chunk_id + index_version
```

Reward 不能只比较 chunk_id。因为同一个 chunk_id 如果缺少 document 和 index version，就可能在重建索引后失去稳定含义。

所以阶段 8 先统一成：

```text
ChunkKey = document_id + chunk_id + index_version
```

再计算 recall、citation 和排序指标。

这使得：

- local_search 和 hyde_search 返回同一证据时不会重复刷高检索分。
- 重复命中同一 chunk 只算一次证据质量。
- 但是否多调用了 HyDE/Web 仍然由 `behavior` 和 `cost` 分项惩罚。

也就是说，去重不会抹掉“多余 HyDE”这件事，因为 Action 路径仍然完整保存。

## 3. 二值相关性为什么当前够用

当前 recall、MRR、nDCG 第一版使用二值相关性：

```text
命中 expected chunk = 1
没命中 = 0
```

这不是说所有证据永远同等重要，而是阶段 8 第一版的重点是：

```text
先保证能稳定命中人工标注证据，并能比较轨迹。
```

`required/supporting/acceptable` 已经在样本 schema 里保留了证据强度，后续可以扩展成加权 nDCG。

当前先用二值相关性的价值是：

- 实现简单、可复现、容易人工检查。
- 不会因为证据强度权重没调好导致 Reward 难解释。
- 对当前设备手册问答，最重要的是先别漏掉期望 chunk。

这属于阶段 8 的保守设计，不是指标能力的终点。

## 4. 不应该回答的 case 不能因为没有答案要点被误扣

拒答、追问、Web 实时问题通常没有 expected chunk 和答案要点。

如果 Reward 简单地说“没有 expected chunk 就检索 0 分，没有答案要点就 answer 0 分”，就会错罚正确拒答或正确追问。

阶段 8 的 Reward 明确处理：

```text
非回答型样本
    -> retrieval 可标记 not_applicable
    -> citation 可标记 not_applicable
    -> answer 不因没有答案要点误扣
    -> 重点看 terminal behavior 是否符合 expected_behavior
```

这让 Reward 能覆盖真实业务场景，而不是只会评普通问答。

## 5. 本部分实际提升

这一部分的提升是：

- Reward 结果不是黑盒总分，能看到每个分项和扣分原因。
- 格式非法有总分上限，防止模型靠其他分项掩盖 schema 错误。
- 检索、引用、答案、行为、成本分开，便于定位问题。
- 不必要 HyDE/Web 会扣成本和行为分，减少 reward hacking。
- Reward 输出可 JSON 序列化，能进入报告和阶段 9 训练。

面试里可以这样表达：

```text
我没有把 GRPO 的奖励写成一个不可解释的总分，而是拆成格式、检索、引用、答案、行为和成本。
每个分项都有 details 和 reasons。
这样模型如果通过多调用 Web 或伪造引用刷分，可以从 Reward 分项里直接看出来。
```

# 第六部分：baseline runner 让 Planner 对比有固定裁判

阶段 8 的第六个价值是实现 baseline runner。

`baseline runner` 可以理解为“基线评测跑批器”。

它不训练模型，也不计算 GRPO 的组内 advantage。它只做一件事：

```text
固定 case、snapshot、reward_version，
让一个或多个 Planner 跑完离线轨迹，
输出每个 Planner 的配置、用量、Reward 和逐 case 结果。
```

阶段 8 新增：

```text
app/rag/evaluation/baseline_runner.py
evaluation/stage8/run_planner_eval.py
```

支持命令：

```bash
uv run python evaluation/stage8/run_planner_eval.py \
  --cases evaluation/stage8/cases/planner_cases.jsonl \
  --snapshot evaluation/stage8/snapshots/environment_snapshot.json \
  --split dev \
  --planners rule,api,local_base \
  --reward-version reward-v1 \
  --output evaluation/stage8/results/planner_eval_dev.json
```

## 1. rule 是当前可执行下限基线

`RuleBasedPlanner` 当前能真实执行。

它的价值不是模型能力强，而是：

- 确定性。
- 可复现。
- 线上已有回退策略。
- 适合作为阶段 9 的最低可用 baseline。

当前 dev 结果是：

```text
split = dev
case_count = 7
planner = rule
failed = 0
average_reward = 0.8389
```

train 结果是：

```text
split = train
case_count = 11
planner = rule
failed = 0
average_reward = 0.7956
```

Demo 回归结果是：

```text
split = demo_regression
case_count = 12
planner = rule
failed = 0
average_reward = 0.8000
```

这些结果给阶段 9 一个清晰起点：

```text
SFT/GRPO 至少要在同一 snapshot 和 held-out test 上证明优于 rule。
```

## 2. api 和 local_base 跳过不是失败，而是诚实记录边界

阶段 8 的报告里，`api` 和 `local_base` 当前是 skipped。

这不是实现失败，而是因为它们还没有配置可执行 provider 或本地模型。

输出中保留原因：

```text
api：阶段 7 只注册名称，不加载 API Planner
local_base：阶段 8 离线评测预留
```

这样做比伪造结果更有价值。

因为阶段 9 接入 API Planner、本地零样本 Planner、SFT Planner、GRPO Planner 时，可以复用同一 runner 和同一输出结构。

## 3. 评测报告把结果变成可展示材料

阶段 8 新增：

```text
evaluation/stage8/generate_eval_report.py
evaluation/stage8/reports/阶段8评测报告.md
```

报告包含：

- 阶段 5 A/B/C 真实检索质量对照。
- 阶段 8 `snapshot_expected_chunks` 离线管线自检。
- `rule/api/local_base` baseline 对比。
- Demo 回归结果。
- Reward 分项。
- SFT 导出统计。
- 阶段 9 前置结论。

这使得评测产物不仅是 JSON，还能直接用于面试展示和阶段复盘。

## 4. 本部分实际提升

这一部分的提升是：

- 一键评测命令可以跑 `rule`。
- 每个 planner 都有状态、配置、用量和 Reward。
- 未配置的 planner 被明确标记 skipped，不伪造结果。
- 报告能解释为什么阶段 9 可以进入 SFT，但不能提前宣称 GRPO 增益。
- 后续新增 SFT/GRPO Planner 时，有固定对照框架。

面试里可以这样表达：

```text
我给 Planner 做了 baseline runner。
它在同一批 case、同一个 snapshot 和同一个 Reward 版本下跑 rule、API 或本地 Planner。
现在 API 和 local_base 没配置会明确 skipped，不造假。
后续 SFT/GRPO 模型接进来后，可以直接和 rule 在同一套 held-out 环境里比较。
```

# 第七部分：SFT 数据导出把高质量轨迹变成训练样本

阶段 8 的第七个价值是实现 SFT 数据导出。

阶段 9 不应该直接拿所有轨迹训练。

原因是：

- 有些轨迹 Reward 低。
- 有些轨迹格式非法。
- 有些轨迹终态行为不符合标注。
- API teacher 可能也会错。
- 私有文档样本必须经过人工复核。
- test/demo 样本不能进入训练。

阶段 8 新增：

```text
app/rag/evaluation/sft_exporter.py
evaluation/stage8/export_sft_data.py
evaluation/stage8/results/sft_planner_train.jsonl
evaluation/stage8/results/sft_manifest.json
```

## 1. 导出的是单步 PlannerDecision，不是完整答案

SFT 数据导出的目标不是让模型背手册正文。

它导出的是：

```text
在当前 State 和 Observation 下，
Planner 应该输出哪个结构化 Action。
```

一条轨迹会拆成多条单步样本。

例如：

```text
local_search -> answer
```

会拆成：

```text
样本 1：初始 State -> target_decision = local_search
样本 2：local_search Observation 后的 State -> target_decision = answer
```

这和阶段 9 的目标一致：先让本地 Planner 学会结构化输出、基本路由和合法状态转移。

## 2. 导出过滤是训练数据闸门

阶段 8 的导出规则包括：

```text
test/demo split 永不导出
格式非法轨迹不导出
执行错误或无效引用轨迹不导出
API teacher 轨迹必须达到 Reward 阈值
私有文档样本默认必须 human_review_status=reviewed
不导出完整 chunk 正文、答案 Prompt 或模型私有思维链
```

当前导出结果是：

```text
exported_trajectory_count = 9
sample_count = 17
source_counts = {"rule": 17}
filter_counts = {
  "private_case_not_reviewed": 1,
  "terminal_behavior_mismatch": 1
}
```

这说明阶段 8 已经不是把所有轨迹直接喂给模型，而是有了明确筛选边界。

## 3. sft_manifest 的价值

`sft_manifest.json` 是训练数据清单。

它记录：

- 来源 run_id。
- snapshot_id。
- reward_version。
- reward_threshold。
- allowed_splits。
- exported_case_count。
- exported_trajectory_count。
- sample_count。
- source_counts。
- review_status_counts。
- filter_counts。
- excluded_payloads。

它的价值是防止阶段 9 只看到一个 JSONL，却不知道这些数据从哪里来、为什么能训练、哪些被过滤掉。

训练失败或效果异常时，可以先看 manifest，而不是盲目翻 JSONL。

## 4. 本部分实际提升

这一部分的提升是：

- SFT 训练数据从评测结果中自动筛选，不靠手工复制。
- test/demo 样本有硬边界，不会进入训练。
- 低 Reward API teacher 轨迹不会污染训练。
- 私有文档样本未复核不会进入训练。
- 导出字段不含完整 chunk 正文和私有思维链，训练数据边界更清楚。

面试里可以这样表达：

```text
我把 Planner 轨迹导出成单步 SFT 样本，而不是直接训练最终答案。
导出前会检查 split、Reward、格式、引用、隐私复核和来源比例。
这样阶段 9 的 SFT 是在干净的轨迹上学习结构化决策，不会把 test/demo 或低质量 teacher 轨迹混进去。
```

# 第八部分：阶段 8 对阶段 9 的真实价值和当前边界

阶段 8 最重要的价值，是让阶段 9 的 SFT/GRPO 不再是“为了用了强化学习而强化学习”。

阶段 9 现在可以基于阶段 8 做：

```text
固定 case
固定 snapshot
固定 Reward 版本
固定 baseline runner
固定 SFT 导出 manifest
固定 report
```

然后比较：

```text
rule baseline
SFT Planner
GRPO Planner
```

这才是一个完整训练实验应该有的形态。

## 1. 阶段 8 当前已经完成的能力

已落地能力包括：

- `PlannerEvalCase` 等样本 schema。
- Demo 回归集和 Planner 候选池。
- train/dev/test/demo 边界和 `split_manifest`。
- `EnvironmentSnapshot` 构建和 case 引用校验。
- `OfflineRagEnvironment`。
- Reward v1。
- baseline runner。
- SFT 导出器。
- 评测报告生成脚本。
- 数据字典和测试同步。

验证结果已达到：

```text
阶段 8 定向测试：35 passed
一键 rule 评测：dev 7 条，failed = 0，avg_reward = 0.8389
全量回归：404 passed
```

## 2. 阶段 8 当前明确没有完成的能力

阶段 8 没有完成，也不应该宣称完成：

- 没有训练 SFT 模型。
- 没有执行 GRPO 训练。
- 没有把 GRPO Trainer 接进线上查询图。
- 没有启用 API Planner 在线服务。
- 没有启用本地模型 Planner 在线服务。
- 当前 `snapshot_expected_chunks` 不代表真实 Milvus/Web provider 质量。
- 当前 Reward v1 第一版使用二值相关性，不是最终加权证据排序模型。
- 当前 SFT 数据量只够验证流程，不代表最终训练数据规模已经充分。

这几条边界必须保留。它们不是缺点，而是阶段设计的诚实边界。

## 3. 为什么阶段 8 后可以进入阶段 9

阶段 9 可以进入 SFT 的原因是：

- 已经有 SFT 数据导出格式。
- 已经有训练样本 manifest。
- 已经有 Reward 分项。
- 已经有 baseline runner。
- 已经有固定 snapshot。
- 已经有 Demo 和 held-out test 边界。

但是阶段 9 不应该一上来就宣称 GRPO 有收益。

更稳妥的路线是：

```text
先用 SFT 学结构化输出和合法路由
再用同一 runner 对比 rule 和 SFT
如果 SFT 具备稳定输出能力，再进入 GRPO
GRPO 结果必须在同一 held-out test 和 Reward 版本下比较
```

## 4. 后续制造业数据扩充为什么应该放在阶段 8.5 或阶段 9 前

当前阶段 8 的数据足够验证评测闭环，但不代表最终训练数据已经充足。

制造业公开数据扩充应该单独做流水线：

```text
公开文档采集
切 chunk
生成候选问题
人工复核
标注 expected chunk
拆 train/dev/test
防泄漏
进入候选池
Reward 过滤
再决定是否导出 SFT/GRPO
```

不应该让新数据直接混进训练。

阶段 8 当前的价值是先把“数据应该怎样进入训练”的闸门建好。后续扩数据时只要遵守这个闸门，就不会重新回到人工散乱维护数据的状态。

## 5. 面试复盘表达

可以这样总结阶段 8：

```text
阶段 8 我没有直接训练模型，而是先做训练前评测地基。

我把样本定义成 PlannerEvalCase，里面不仅有问题和答案要点，还有 expected chunk、
期望行为、可接受 Action 路径和 leakage_group_id。

然后用 EnvironmentSnapshot 固定 dataset、document、index version、enabled chunk 和检索配置，
用 OfflineRagEnvironment 在这个快照下执行 Planner Action。

Reward v1 拆成格式、检索、引用、答案、行为和成本六个分项，每个分项都有 details 和扣分原因。

最后用 baseline runner 跑 rule/api/local_base 对照，用 SFT exporter 只导出高质量、非 test/demo、
非私有未复核的轨迹。

所以阶段 9 做 SFT/GRPO 时，不是凭感觉判断效果，而是能在同一 held-out 数据、同一 snapshot
和同一 Reward 版本下和 rule baseline 对比。
```

如果面试官问“为什么不直接上 GRPO”，可以回答：

```text
因为 GRPO 的关键不是 Trainer 代码，而是 rollout 环境、Reward 和评测边界是否可信。
如果没有固定 case、snapshot、Reward 和 baseline，训练出来分数变高也很难判断是真的模型变好，
还是数据泄漏、环境漂移或 reward hacking。
所以我先做阶段 8，把训练前的实验地基补齐。
```

如果面试官问“阶段 8 是否已经证明模型变强”，要直接回答：

```text
没有。阶段 8 证明的是评测和数据导出闭环可复现。
模型是否变强，要等阶段 9 接入 SFT/GRPO 后，在同一 held-out test 上和 rule baseline 比较。
```
