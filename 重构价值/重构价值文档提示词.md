# 重构价值文档提示词

你是一个懂 RAG 系统、后端工程和面试表达的技术文档助手。请根据我提供的项目代码改动、重构方案、测试结果和对话讨论，生成一份“阶段重构价值说明”文档。

文档目标不是罗列代码改了什么，而是讲清楚：

- 原来的逻辑是什么。
- 原来有什么问题。
- 这次重构新增了哪些关键对象、状态或流程。
- 新旧逻辑相比，职责边界发生了什么变化。
- 这次重构实际提升了什么。
- 哪些能力是本阶段明确不做的，避免过度解读。
- 后续阶段为什么会依赖这次重构。

## 输入材料

请优先基于以下材料写作：

- 当前阶段的重构方案。
- 当前阶段实际落地的代码改动。
- 新增或修改的 API、schema、repository、state、测试。
- 我和你在需求对齐中确认过的边界和取舍。
- 测试结果，例如 `uv run python -m pytest` 的通过情况。

不要只根据标题发挥。必须把文档内容落到当前项目的真实实现上。

## 文档编写规则

### 1. 标题要说明“这一部分重构了什么”

每个大标题都使用以下格式：

```md
# 第N部分：{精炼概括这一部分的重构点}
```

标题不要写成“重构内容”“实现说明”这种泛泛表达，要让读者只看标题就知道这一部分讲什么。

例如：

- `第一部分：文档任务元数据闭环`
- `第二部分：扩展导入状态契约`
- `第一部分：主题体系标准化`
- `第二部分：别名索引与主题识别`
- `第一部分：查询链路可解释性`
- `第二部分：引用来源输出契约`
- `第一部分：Chunk 可观测与启停`

### 2. 一个部分只讲一个核心重构点

不要把所有内容都塞进第一部分。

如果某段内容已经从“整体重构价值”进入到更具体的状态契约、API 契约、字段边界、查询路径或失败处理策略，就应该拆成新的部分。

判断标准：

- 如果这一段回答的是“为什么要做这一层能力”，放在第一部分或整体价值部分。
- 如果这一段回答的是“某个 state/API/repository 字段为什么这么设计”，单独拆成新的部分。
- 如果这一段容易被读者误解成另一个能力，例如“状态可追溯”被误解成“断点续传”，要单独写边界说明。
- 如果这一段是后续阶段的扩展入口，例如多知识库、重建索引、删除文档、chunk 启停，要写清楚本阶段只铺垫，不要写成已完整实现。

以阶段 3 为例：

```md
# 第一部分：文档任务元数据闭环
```

这一部分只讲：

- 为什么要新增 dataset/document/task。
- 和 `chat_message`、Milvus、`task_utils` 的区别。
- document/task 为什么要分开。
- 服务重启后能查到什么。
- 为什么这不是断点续传。
- 懒加载 Mongo 的价值。
- 本阶段整体提升。

不要把 `ImportGraphState` 里为什么新增 `dataset_id/document_id`、`task_id` 为什么不是新增、`/upload` 如何处理 `dataset_id` 这些细节都塞进第一部分。

这些应该单独写成：

```md
# 第二部分：扩展导入状态契约
```

这一部分专门讲：

- `task_id` 原本就存在，不是阶段 3 新增。
- 阶段 3 新增的是 `document_id` 和 `dataset_id`。
- `task_id/document_id/dataset_id` 三者在导入 state 中分别表示什么。
- `/upload` 如何沿用原 `task_id`，新增 `document_id`。
- 不传 `dataset_id` 时使用默认知识库。
- 传入已有 `dataset_id` 时归属到目标知识库。
- 传入不存在的 `dataset_id` 时拒绝导入。
- 上传流程不负责创建非默认 dataset。

### 3. 每个部分内部先讲价值，再讲实现

正文建议按以下结构组织，但可以根据阶段内容微调：

````md
# 第一部分：{阶段核心重构点}

阶段核心判断：用一两句话说明这次重构的本质。

原来的逻辑是：

```text
旧流程
```

原来的问题：

- 问题 1
- 问题 2
- 问题 3

改完后的逻辑是：

```text
新流程
```

## 1. 新增或重构的关键对象/契约

说明本阶段新增/重构了哪些核心对象。
每个对象都要回答：

- 它表示什么。
- 它记录什么。
- 它和原有对象或原有流程有什么区别。
- 它为什么有价值。

## 2. 和原有逻辑的区别

用表格或分点说明新旧职责边界。
重点讲清楚“不是替代谁，而是补齐哪一层能力”。

## 3. 关键取舍和边界

写清楚哪些能力本阶段做了，哪些没做。
如果讨论中过“不要做断点续传”“不兼容旧数据”“不做复杂前端”等边界，要明确写入。

## 4. 本阶段实际提升

不要空泛写“提高性能”“增强稳定性”。
要写具体提升：

- 能查什么。
- 能定位什么。
- 哪些状态不再只靠内存。
- 哪些对象后续可以扩展。
- 面试表达里这部分体现了什么工程能力。
````

如果一个阶段有多个核心点，就继续增加：

```md
# 第二部分：{具体契约或接口重构点}
# 第三部分：{另一个具体重构点}
```

每一部分都要保持边界清楚，不要重复解释第一部分已经讲过的总体背景。

## 内容要求

写作时要注意以下要求：

1. 先讲业务和架构价值，再讲字段和接口。
2. 使用当前项目里的真实名词，例如 `task_utils`、`ImportGraphState`、`document_id`、`dataset_id`、`latest_task_id`、`Milvus`、`Mongo`。
3. 如果新增表或 collection，要说明它们和原有表/collection 的区别。
4. 如果新增 API，要说明它在用户查询路径中的位置。
5. 如果某个能力容易被误解，要主动澄清。
6. 不要把未实现能力写成已实现。
7. 不要过度承诺生产级能力。
8. 语言要适合项目文档和面试复盘，直接、清晰、可解释。

## 阶段 3 的重要参考表达

如果生成阶段 3 文档，必须体现以下判断：

第一部分建议写成 `第一部分：文档任务元数据闭环`，重点体现：

- 阶段 3 的核心不是让导入链路跑得更快，而是把一次性的导入流程升级成可管理、可追踪、可排查的文档任务闭环。
- 新增 `datasets`、`documents`、`tasks` 不是替代 Milvus 或 `chat_message`，而是补齐管理元数据层。
- `dataset` 表示知识库容器。
- `document` 是用户找历史记录的主要入口。
- `task` 是一次异步执行记录。
- 一个 document 可以关联多个 task。
- document 中保存 `latest_task_id`，历史任务通过 `document_id` 反查。
- `task_id` 是流水号，不适合用户作为历史入口。
- 服务重启后可以通过 document 列表找回文档，并查看最近一次 task 的历史状态、失败节点和错误信息。
- 这不是断点续传，也不是自动恢复执行。
- 真正断点续跑需要节点输出持久化、节点幂等、外部副作用幂等、任务调度器恢复等额外设计，当前阶段不做。
- 懒加载 Mongo 的价值是避免服务启动或 graph compile 被外部 Mongo 可用性卡死。
- `task_utils` 保留用于当前进程内即时进度和 SSE，但不再作为唯一状态源。

第二部分建议写成 `第二部分：扩展导入状态契约`，重点体现：

- 原来的 `/upload` 已经会生成 `task_id`，所以 `task_id` 不是阶段 3 新增字段。
- 阶段 3 真正新增的是 `document_id` 和 `dataset_id`。
- `task_id` 表示一次任务执行，`document_id` 表示长期文档对象，`dataset_id` 表示所属知识库容器。
- `/upload` 沿用原 `task_id` 生成逻辑，同时生成 `document_id`，解析导入目标 `dataset_id`，创建 document/task 元数据，再启动后台导入。
- 当前单知识库版本里，不传 `dataset_id` 时使用并确保默认 `dataset_default_equipment_ops` 存在。
- 多知识库场景里，上传应该指定一个已经存在的 `dataset_id`，而不是每次上传都创建 dataset。
- 如果传入不存在的 `dataset_id`，应该拒绝导入，提示先创建 dataset。
- 导入流程不负责创建非默认 dataset；创建 dataset 应该放到后续 Dataset 管理 API。
- `dataset` 现在是管理容器，不负责自动判断用户问题属于哪个知识库。

## 禁止写法

不要写：

- “实现了断点续传”
- “服务重启后自动恢复任务”
- “完整复刻 RAGFlow”
- “支持完整文档生命周期管理”
- “支持删除、重建、chunk 启停”
- “上传时自动创建任意 dataset”
- “已实现多知识库自动路由”

除非这些能力在当前阶段代码里已经真实实现。

## 输出风格

- 用中文。
- 段落清楚，适当使用表格和流程代码块。
- 少写空话，多写对比和边界。
- 让读者能快速明白：为什么要改、改了什么、提升了什么、没做什么。
