# 阶段 4 重构价值

## 一、任务 1：固化 document/index 元数据契约

### 1. Document 级索引生命周期元数据契约

阶段 4 当前已经落地的第一步，不是直接改 Milvus 入库逻辑，也不是立刻实现删除文档和重建索引 API，而是先把 document 需要表达的索引生命周期元数据补齐。

阶段核心判断是：

```text
document 不只要记录“上传和导入状态”，还要能记录“这份文档当前对应哪一版检索索引产物”。
```

这里的 `index_version` 指的是 document 级检索索引产物版本：

```text
原始文档 -> 解析 -> 切分 -> 向量化 -> 写入 Milvus 后形成的 chunk/vector 数据版本
```

它不是 Milvus 的 HNSW 或稀疏倒排物理索引版本，也不是文档内容版本。

原来的逻辑是：

```text
POST /upload
    -> 创建 document/task
    -> document 记录上传、解析、索引状态
    -> 导入图写入 Milvus
```

这个逻辑已经能表达文档是否导入成功，但还不能表达后续阶段需要的几个问题：

- 这份 document 当前对应第几版索引产物。
- 这份 document 如果后续被删除，删除时间应该落在哪里。
- 这份 document 的图片、MinerU 解析产物应该挂在哪里。
- 重建索引时，如何复用原 `document_id`，同时产生新的任务记录。
- API 返回 document 详情时，前端是否能看到这些生命周期字段。

改完后的逻辑是：

```text
POST /upload
    -> 创建 document/task
    -> document 默认 index_version=1
    -> document 预留删除时间、图片前缀、解析产物路径字段
    -> ImportGraphState 携带 index_version
    -> UploadSchema / DocumentStatusSchema 对外返回 index_version 等字段
```

#### 1.1 document 新增索引生命周期字段

阶段 4 第一部分在 `documents` 中新增了几个字段：

| 字段 | 含义 | 当前价值 |
|---|---|---|
| `index_version` | document 级检索索引产物版本 | 首次导入为 `1`，后续重建索引时递增 |
| `deleted_at` | 文档删除时间 | 字段已落地，后续删除流程写入 |
| `image_prefix` | document 在 MinIO 中的图片对象前缀 | 字段已落地，后续图片增强流程写入 |
| `parse_result_zip_path` | MinerU 解析结果 zip 本地路径 | 字段已落地，后续 PDF 解析流程写入 |
| `parse_result_dir` | MinerU 解析结果解压目录 | 字段已落地，后续 PDF 解析流程写入 |

这几个字段的价值不是为了让当前导入流程立刻更复杂，而是把后续“可删、可重建、可追踪”的数据落点先定下来。

原来 document 主要表达：

```text
这份文档是否上传、解析、索引成功
```

现在 document 进一步能表达：

```text
这份文档当前对应哪一版索引产物
这份文档后续删除时在哪里记录删除时间
这份文档后续图片和解析产物应该挂靠在哪里
```

这样后续阶段就不需要临时把这些信息散落在 task、state、MinIO 路径或 Milvus chunk 里。

#### 1.2 index_version 为什么挂在 document 上

`index_version` 挂在 `documents` 上，是因为它描述的是“这份 document 当前有效的检索索引产物版本”。

它和几个相近概念的边界是：

| 概念 | 表示什么 | 是否当前字段 |
|---|---|---|
| `document_id` | 这份文档是谁 | 是 |
| `document_version` | 文档内容改到了第几版 | 不是 |
| `index_version` | 这份文档生成的 chunk/vector 索引产物第几版 | 是 |
| Milvus 物理索引版本 | HNSW、SPARSE_INVERTED_INDEX 等底层索引结构版本 | 不是 |

当前阶段的设计是：

```text
普通上传
    -> 创建新的 document_id
    -> index_version = 1

重建索引
    -> 复用原 document_id
    -> 创建新的 task
    -> index_version + 1
```

这个设计避免了两个混淆：

- 重新上传新文件不是重建索引，它应该创建新的 document。
- 重建索引不代表源文档内容变了，它代表这份文档重新生成了一版检索数据。

因此 `index_version` 是合适的命名。它挂在 document 上，语义就是 document 的当前索引产物版本。

### 2. 导入 State 与 API 契约补齐

这一部分关注的是 `index_version` 不只存在 Mongo 里，还要贯穿导入图启动和 API 返回。

原来的 `ImportGraphState` 已经有：

```text
task_id
dataset_id
document_id
owner_user_id
tenant_id
visibility
```

阶段 4 第一部分新增：

```text
index_version
```

这样导入图启动时，state 能完整表达：

```text
这一次 task
处理哪一份 document
属于哪个 dataset
属于哪个 owner
当前 document 对应第几版索引产物
```

#### 2.1 ImportGraphState 的价值

`ImportGraphState.index_version` 当前还没有参与 Milvus chunk 入库，这是刻意的阶段边界。

它现在的价值是先把导入图上下文补齐：

```text
API / repository 决定 index_version
    -> invoke_graph 写入 ImportGraphState
    -> 后续 index 节点可以直接从 state 读取
```

后续真正改造 chunk 入库时，就可以把 `index_version` 和下面字段一起写入 Milvus：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
index_version
chunk_index
enabled
source_title
```

这比到 Milvus 入库阶段再临时查 Mongo 更清楚：导入图的业务上下文在入口处就已经确定。

#### 2.2 API 返回字段的价值

阶段 4 第一部分扩展了几个 schema：

| Schema | 新增字段 | 价值 |
|---|---|---|
| `UploadSchema` | `index_version` | 上传后前端能知道这份新 document 的初始索引版本 |
| `DocumentStatusSchema` | `index_version`、`deleted_at`、`image_prefix`、`parse_result_zip_path`、`parse_result_dir` | 文档详情能展示索引版本和后续生命周期字段 |
| `TaskStatusSchema` | `task_type` | 状态查询能区分普通导入任务和后续重建索引任务 |

这让 API 不再只表达“任务是否完成”，而是开始表达“document 的生命周期状态”。

当前已经可以通过文档详情看到：

```text
document_id
latest_task_id
index_version
parse_status
index_status
chunk_count
subject_id
standard_subject_name
deleted_at
image_prefix
parse_result_zip_path
parse_result_dir
```

这些字段为后续前端展示“文档详情、删除状态、重建版本、解析产物位置”提供了稳定契约。

#### 2.3 和阶段 3/3.5 的衔接

阶段 3 解决的是：

```text
document/task 元数据闭环
```

阶段 3.5 解决的是：

```text
document/task 归属于 owner_user_id
```

阶段 4 第一部分继续往前推进：

```text
document 能表达索引生命周期
```

这三步是递进关系：

| 阶段 | 解决的问题 |
|---|---|
| 阶段 3 | 系统能记录 document/task 状态 |
| 阶段 3.5 | 当前用户只能看到自己的 document/task |
| 阶段 4 第一部分 | document 能记录索引版本、删除时间和导入产物位置 |

这一步之后，后续删除文档、重建索引、chunk 权限过滤都有了统一的 document 入口。

### 3. 重建索引任务类型与 Repository 边界

阶段 4 第一部分还新增了 repository 级能力：

```text
create_rebuild_task_metadata(...)
```

它还没有接到 HTTP API 上，当前是为后续：

```http
POST /documents/{document_id}/rebuild
```

预留的元数据创建能力。

这个方法做的不是“执行重建索引”，而是只负责创建重建索引所需的 Mongo 元数据。

#### 3.1 task_type 是持久任务类型，不是临时状态

阶段 4 新增：

```text
TASK_TYPE_REBUILD_INDEX = "rebuild_index"
```

它表示这条 task 是一次“重建索引任务”。

它不是运行状态。

真正的运行状态仍然是：

```text
status = pending / processing / completed / failed
```

因此一次重建索引任务的生命周期应该是：

```text
task_type = rebuild_index
status = pending

task_type = rebuild_index
status = processing

task_type = rebuild_index
status = completed
```

失败时也是：

```text
task_type = rebuild_index
status = failed
failed_node = ...
error_message = ...
```

这个区分很重要：`task_type` 让历史任务可解释，`status` 表达任务当前或最终状态。

#### 3.2 重建索引复用 document，新建 task

`create_rebuild_task_metadata` 的核心逻辑是：

```text
按 document_id + owner_user_id 查 document
    -> document 不存在，拒绝
    -> document 已删除，拒绝
    -> document 存在且未删除，创建 rebuild_index task
    -> latest_task_id 指向新 task
    -> index_version + 1
```

这个方法体现了阶段 4 的一个关键边界：

```text
document 是长期对象
task 是一次执行记录
```

重建索引不应该创建新的 document，因为它处理的是同一份文档。

但它必须创建新的 task，因为这是一次新的异步执行。

所以正确关系是：

| 操作 | document_id | task_id | index_version |
|---|---|---|---|
| 首次导入 | 新建 | 新建 | 1 |
| 重建索引 | 复用 | 新建 | +1 |
| 重新上传 | 新建 | 新建 | 1 |

#### 3.3 已删除文档不能在 repository 层自动转上传

讨论中确认过一个边界：如果 document 已经删除，`create_rebuild_task_metadata` 不应该自动转到重新上传流程。

原因是 repository 层只负责 Mongo 元数据，不掌握上传所需的文件流和请求上下文。

重新上传需要：

```text
UploadFile 文件流
保存文件到 output 目录
创建新的 document_id
创建新的 task_id
启动导入图
```

这些属于 API/service 层能力，不属于 repository 层能力。

所以当前设计是：

```text
deleted document:
    rebuild -> 拒绝，提示不能重建
    upload  -> 用户重新上传，创建新 document
```

这个判断主要是兜底防线。正常产品流程中，已删除 document 不应该展示“重建索引”入口；即使有人绕过前端或使用旧页面缓存直接调用，repository 也不会让 deleted document 被悄悄复活。

如果未来要做“恢复已删除文档”，也应该单独设计：

```http
POST /documents/{document_id}/restore
```

而不是让 rebuild 顺手恢复删除状态。

#### 3.4 本任务实际提升

阶段 4 第一部分的提升不是“已经完整实现删除和重建索引闭环”，而是把这些能力需要的元数据边界先落稳。

具体提升：

- 新 document 默认有 `index_version=1`。
- document 详情可以看到当前索引版本。
- 导入图 state 已经携带 `index_version`，后续 Milvus chunk 入库可以直接使用。
- document 预留了删除时间、图片前缀、解析产物路径字段。
- task 状态响应能返回 `task_type`。
- repository 已经能为未删除 document 创建 `rebuild_index` task，并递增 `index_version`。
- deleted document 被 repository 层兜底拒绝重建，避免后续误复活。

这一步让阶段 4 后续任务可以沿着清晰边界继续推进：

```text
先有 document/index 元数据契约
再做图片和解析产物挂靠
再做 chunk 元数据入库
再做 document_id 幂等
最后补删除和重建 API
```

### 4. 当前边界、测试与后续依赖

这一部分容易被误解成“阶段 4 已经全部完成”，需要明确边界。

当前阶段 4 已经落地的是：

- `documents.index_version`
- `documents.deleted_at`
- `documents.image_prefix`
- `documents.parse_result_zip_path`
- `documents.parse_result_dir`
- `ImportGraphState.index_version`
- `UploadSchema.index_version`
- `DocumentStatusSchema` 生命周期字段
- `TaskStatusSchema.task_type`
- `TASK_TYPE_REBUILD_INDEX`
- repository 级 `create_rebuild_task_metadata`

当前阶段 4 还没有落地的是：

- 没有实现 `DELETE /documents/{document_id}`。
- 没有实现 `POST /documents/{document_id}/rebuild`。
- 没有把 `index_version` 写入 Milvus chunk。
- 没有把 chunk 幂等从 `file_title` 改成 `document_id`。
- 没有把 MinIO 图片前缀改成 document 维度。
- 没有写入 `parse_result_zip_path`、`parse_result_dir` 的真实解析产物路径。
- 没有改变查询召回过滤逻辑。

当前阶段的正确表述是：

```text
阶段 4 的第一部分已经补齐 document/index 元数据契约；
删除、重建索引 API、Milvus chunk schema 和 document_id 幂等仍在后续任务中实现。
```

#### 4.1 测试覆盖

本次改动补了几类测试。

Repository 测试覆盖：

- 创建 document 时默认写入 `index_version=1`。
- 创建 document 时写入 `deleted_at`、`image_prefix`、`parse_result_zip_path`、`parse_result_dir` 默认值。
- 创建 rebuild task 时复用原 document。
- 创建 rebuild task 时 `index_version + 1`。
- rebuild task 的 `task_type=rebuild_index`。
- document 不存在时拒绝创建 rebuild task。
- document 已删除时拒绝创建 rebuild task。

API/schema 测试覆盖：

- `UploadSchema` 返回 `index_version`。
- `TaskStatusSchema` 返回 `task_type`。
- `DocumentStatusSchema` 返回索引版本和生命周期字段。
- `POST /upload` 创建普通 document 时返回 `index_version=1`。
- `invoke_graph` 启动时把 `index_version` 写入 `ImportGraphState`。

State 测试覆盖：

- `ImportGraphState` 默认字段包含 `index_version`。
- 默认 `index_version=0`，实际上传创建 document 后再写入 `1`。

当前全量回归结果：

```text
uv run python -m pytest
75 passed
```

#### 4.2 后续任务为什么依赖这次重构

后续阶段 4 的其它任务都会依赖这次契约。

图片和解析产物挂靠依赖：

```text
documents.image_prefix
documents.parse_result_zip_path
documents.parse_result_dir
```

chunk 元数据入库依赖：

```text
ImportGraphState.index_version
documents.index_version
```

document_id 幂等和重建索引依赖：

```text
document_id
index_version
task_type=rebuild_index
latest_task_id
```

删除文档依赖：

```text
deleted_at
STATUS_DELETED
repository 层对 deleted document 的兜底判断
```

阶段 5 查询权限过滤也会间接依赖这一层，因为 chunk 后续要写入：

```text
dataset_id
document_id

visibility

```

如果 document 级索引版本和生命周期字段不先定义清楚，后续 chunk 入库、删除、重建、查询过滤都会缺少统一的上游契约。

#### 4.3 面试复盘表达

这部分可以这样概括：

```text
阶段 4 我没有一上来直接改 Milvus 入库或做删除 API，而是先补齐 document 级索引生命周期契约。
原来 document 只能表达上传、解析、索引是否完成；
现在 document 可以表达当前索引产物版本、删除时间、图片前缀和解析产物位置。
同时 ImportGraphState 和 API schema 都带上 index_version，后续 chunk 入库可以直接使用。
我还在 repository 层补了 rebuild_index task 的元数据创建能力，明确重建索引复用 document、新建 task、递增 index_version。
deleted document 不允许在 repository 层自动转上传，这只是兜底防线；重新上传应该走 API/service 层的 upload 流程。
```

这体现的工程价值是：

- 先定清楚生命周期模型，再改具体副作用。
- 把 document 和 task 的职责继续拆清楚。
- 把重建索引建模为任务类型，而不是运行状态。
- 不在 repository 层混入上传业务流程。
- 明确哪些字段已经落地，哪些删除、Milvus 幂等、查询过滤能力还没做。

这一步不花哨，但它让后续阶段 4 的删除、重建、chunk 元数据和阶段 5 的查询过滤都能沿着同一套 document 契约继续推进。
