# 阶段 4 重构价值

## 一、任务 1：固化 document/index 元数据契约

### 1. Document 级索引生命周期元数据契约

阶段 4 当前已经落地的第一步，不是直接改 Milvus 入库逻辑，也不是立刻实现删除文档和重建索引 API，而是先把 document 需要表达的索引生命周期元数据补齐。

阶段核心判断是：

```text
document 不只要记录“上传和导入状态”，还要能记录“这份文档当前对应哪一版检索索引产物”。
```

这里的 `index_version` 指的是 document 级检索索引产物版本：

```text
原始文档 -> 解析 -> 切分 -> 向量化 -> 写入 Milvus 后形成的 chunk/vector 数据版本
```

它不是 Milvus 的 HNSW 或稀疏倒排物理索引版本，也不是文档内容版本。

原来的逻辑是：

```text
POST /upload
    -> 创建 document/task
    -> document 记录上传、解析、索引状态
    -> 导入图写入 Milvus
```

这个逻辑已经能表达文档是否导入成功，但还不能表达后续阶段需要的几个问题：

- 这份 document 当前对应第几版索引产物。
- 这份 document 如果后续被删除，删除时间应该落在哪里。
- 这份 document 的图片、MinerU 解析产物应该挂在哪里。
- 重建索引时，如何复用原 `document_id`，同时产生新的任务记录。
- API 返回 document 详情时，前端是否能看到这些生命周期字段。

改完后的逻辑是：

```text
POST /upload
    -> 创建 document/task
    -> document 默认 index_version=1
    -> document 预留删除时间、图片前缀、解析产物路径字段
    -> ImportGraphState 携带 index_version
    -> UploadSchema / DocumentStatusSchema 对外返回 index_version 等字段
```

#### 1.1 document 新增索引生命周期字段

阶段 4 第一部分在 `documents` 中新增了几个字段：

| 字段 | 含义 | 当前价值 |
|---|---|---|
| `index_version` | document 级检索索引产物版本 | 首次导入为 `1`，后续重建索引时递增 |
| `deleted_at` | 文档删除时间 | 字段已落地，后续删除流程写入 |
| `image_prefix` | document 在 MinIO 中的图片对象前缀 | 字段已落地，后续图片增强流程写入 |
| `parse_result_zip_path` | MinerU 解析结果 zip 本地路径 | 字段已落地，后续 PDF 解析流程写入 |
| `parse_result_dir` | MinerU 解析结果解压目录 | 字段已落地，后续 PDF 解析流程写入 |

这几个字段的价值不是为了让当前导入流程立刻更复杂，而是把后续“可删、可重建、可追踪”的数据落点先定下来。

原来 document 主要表达：

```text
这份文档是否上传、解析、索引成功
```

现在 document 进一步能表达：

```text
这份文档当前对应哪一版索引产物
这份文档后续删除时在哪里记录删除时间
这份文档后续图片和解析产物应该挂靠在哪里
```

这样后续阶段就不需要临时把这些信息散落在 task、state、MinIO 路径或 Milvus chunk 里。

#### 1.2 index_version 为什么挂在 document 上

`index_version` 挂在 `documents` 上，是因为它描述的是“这份 document 当前有效的检索索引产物版本”。

它和几个相近概念的边界是：

| 概念 | 表示什么 | 是否当前字段 |
|---|---|---|
| `document_id` | 这份文档是谁 | 是 |
| `document_version` | 文档内容改到了第几版 | 不是 |
| `index_version` | 这份文档生成的 chunk/vector 索引产物第几版 | 是 |
| Milvus 物理索引版本 | HNSW、SPARSE_INVERTED_INDEX 等底层索引结构版本 | 不是 |

当前阶段的设计是：

```text
普通上传
    -> 创建新的 document_id
    -> index_version = 1

重建索引
    -> 复用原 document_id
    -> 创建新的 task
    -> index_version + 1
```

这个设计避免了两个混淆：

- 重新上传新文件不是重建索引，它应该创建新的 document。
- 重建索引不代表源文档内容变了，它代表这份文档重新生成了一版检索数据。

因此 `index_version` 是合适的命名。它挂在 document 上，语义就是 document 的当前索引产物版本。

### 3. 重建索引任务类型与 Repository 边界

阶段 4 第一部分还新增了 repository 级能力：

```text
create_rebuild_task_metadata(...)
```

它还没有接到 HTTP API 上，当前是为后续：

```http
POST /documents/{document_id}/rebuild
```

预留的元数据创建能力。

这个方法做的不是“执行重建索引”，而是只负责创建重建索引所需的 Mongo 元数据。

#### 3.1 task_type 是持久任务类型，不是临时状态

阶段 4 新增：

```text
TASK_TYPE_REBUILD_INDEX = "rebuild_index"
```

它表示这条 task 是一次“重建索引任务”。

它不是运行状态。

真正的运行状态仍然是：

```text
status = pending / processing / completed / failed
```

因此一次重建索引任务的生命周期应该是：

```text
task_type = rebuild_index
status = pending

task_type = rebuild_index
status = processing

task_type = rebuild_index
status = completed
```

失败时也是：

```text
task_type = rebuild_index
status = failed
failed_node = ...
error_message = ...
```

这个区分很重要：`task_type` 让历史任务可解释，`status` 表达任务当前或最终状态。

#### 3.2 重建索引复用 document，新建 task

`create_rebuild_task_metadata` 的核心逻辑是：

```text
按 document_id + owner_user_id 查 document
    -> document 不存在，拒绝
    -> document 已删除，拒绝
    -> document 存在且未删除，创建 rebuild_index task
    -> latest_task_id 指向新 task
    -> index_version + 1
```

这个方法体现了阶段 4 的一个关键边界：

```text
document 是长期对象
task 是一次执行记录
```

重建索引不应该创建新的 document，因为它处理的是同一份文档。

但它必须创建新的 task，因为这是一次新的异步执行。

所以正确关系是：

| 操作 | document_id | task_id | index_version |
|---|---|---|---|
| 首次导入 | 新建 | 新建 | 1 |
| 重建索引 | 复用 | 新建 | +1 |
| 重新上传 | 新建 | 新建 | 1 |

#### 3.3 已删除文档不能在 repository 层自动转上传

讨论中确认过一个边界：如果 document 已经删除，`create_rebuild_task_metadata` 不应该自动转到重新上传流程。

原因是 repository 层只负责 Mongo 元数据，不掌握上传所需的文件流和请求上下文。

重新上传需要：

```text
UploadFile 文件流
保存文件到 output 目录
创建新的 document_id
创建新的 task_id
启动导入图
```

这些属于 API/service 层能力，不属于 repository 层能力。

所以当前设计是：

```text
deleted document:
    rebuild -> 拒绝，提示不能重建
    upload  -> 用户重新上传，创建新 document
```

这个判断主要是兜底防线。正常产品流程中，已删除 document 不应该展示“重建索引”入口；即使有人绕过前端或使用旧页面缓存直接调用，repository 也不会让 deleted document 被悄悄复活。

如果未来要做“恢复已删除文档”，也应该单独设计：

```http
POST /documents/{document_id}/restore
```

而不是让 rebuild 顺手恢复删除状态。

#### 3.4 本任务实际提升

阶段 4 第一部分的提升不是“已经完整实现删除和重建索引闭环”，而是把这些能力需要的元数据边界先落稳。

具体提升：

- 新 document 默认有 `index_version=1`。
- document 详情可以看到当前索引版本。
- 导入图 state 已经携带 `index_version`，Milvus chunk 入库已直接使用。
- document 预留了删除时间、图片前缀、解析产物路径字段。
- task 状态响应能返回 `task_type`。
- repository 已经能为未删除 document 创建 `rebuild_index` task，并递增 `index_version`。

这一步让阶段 4 后续任务可以沿着清晰边界继续推进：

## 二、任务 2：记录 PDF/MinerU 与图片增强产物

第二部分解决的是导入产物归属问题：Markdown、MinerU zip、解压目录和 MinIO 图片都必须明确属于某个 document，而不能继续依赖文件名推断归属。

原来的逻辑是：

```text
PDF 文件名
    -> MinerU 生成 Markdown 和 images 目录
    -> 图片以前缀 md_path.stem 上传 MinIO
    -> document 只知道最终 md_path
```

这里有两个问题：

- 用户 A 和用户 B 上传同名文件时，图片前缀可能相同，存在互相覆盖或清理的风险。
- MinerU 的 zip 和解压目录虽然存在于本地，但 document 没有记录，后续排查、删除和重建时无法稳定定位产物。

改完后的逻辑是：

```text
PDF 解析
    -> state 写入 md_path / parse_result_zip_path / parse_result_dir
    -> node_pdf_to_md 回写 documents

图片增强
    -> 使用 document_id 构建 image_prefix
    -> 只清理当前 document 前缀下的旧图片
    -> 上传并替换 Markdown 图片 URL
    -> node_md_img 回写 image_prefix 和增强后的 md_path
```

### 1. MinerU 解析产物成为可追踪数据

`download_and_extract_markdown` 不再只返回 Markdown 路径，而是同时返回：

| 返回值 | 含义 | document 落点 |
|---|---|---|
| `md_path` | 最终选中的 Markdown 文件 | `documents.md_path` |
| `parse_result_zip_path` | MinerU 下载结果 zip | `documents.parse_result_zip_path` |
| `parse_result_dir` | zip 解压目录 | `documents.parse_result_dir` |

`parse_pdf_to_markdown` 先把三个路径写入 `ImportGraphState`，`node_pdf_to_md` 再通过 repository 回写 document，并把 `parse_status` 标记为 completed。

这里继续遵守节点返回 partial state 的约定。节点只向图返回后续流程需要的 `md_path` 和 `md_content`；用于长期追踪的 zip、解压目录通过 repository 写入 Mongo，不要求所有后续节点携带这些字段。

工程价值是：

- document 详情可以定位完整解析产物，不需要从文件名猜目录。
- 后续删除 document 时，可以按元数据清理 zip 和解压目录。
- 重建失败时，可以明确知道使用了哪一份解析产物，排查链路更完整。

### 2. 图片资源从文件名维度升级为 document 维度

图片前缀原来依赖 Markdown 文件 stem，同名文件容易得到相同前缀。现在统一通过：

```text
minio_gateway.build_image_prefix(document_id)
```

生成类似：

```text
kb-images/{document_id}
```

图片增强时的资源边界变成：

```text
当前 document
    -> 只列出 image_prefix 下的旧对象
    -> 只删除 image_prefix 下的旧对象
    -> 新图片仍上传到同一 image_prefix
```

因此：

- 不同 document 即使 `file_title` 完全相同，也不会共享图片前缀。
- 同一 document 重跑图片增强时，可以清理并替换自己的旧图片。
- 图片 URL 仍写回 Markdown，后续 chunk `content` 可以继续保留图片说明和访问地址。

### 3. 无图片文档继续正常导入

图片增强不是所有文档都具备的强制步骤。纯 Markdown 文件、没有图片的 PDF、MinerU 未生成 images 目录的文件，都应该继续进入切分和 Milvus 入库。

当前处理规则是：

```text
images 目录不存在 -> 跳过图片增强
images 目录为空 -> 跳过图片增强
没有被 Markdown 引用的可处理图片 -> 跳过图片增强
存在有效图片 -> 要求 document_id，并执行 document 维度上传
```

`document_id` 只在确实需要管理图片资源时强制校验，避免无图片文档被无意义阻断。

### 4. 第二部分的重构价值

第二部分把“解析过程产生了一些文件”升级为“document 拥有一组可定位、可清理、可重建的导入产物”。

一句话总结：

```text
文件名只负责展示；document_id 才负责资源归属。
```

当前边界也需要明确：

- 已记录产物位置，但删除 API 还没有真正执行本地文件和 MinIO 对象清理。
- 已实现同一 document 前缀内的图片替换，但完整重建索引入口仍在后续任务。
- Markdown 直接导入没有 MinerU zip 和解压目录，对应字段为空是正常状态。

面试复盘可以这样表达：

```text
阶段 4 第二部分把 MinerU 解析产物和图片资源都挂到了 document 上。
PDF 解析后会记录 Markdown、zip 和解压目录；图片上传不再使用文件名 stem，而是使用 document_id 构建 MinIO 前缀。
这样同名文件不会互相覆盖，同一 document 重跑时也只替换自己的资源，同时无图片文档仍能正常进入后续入库流程。
```

## 三、任务 3：重构 chunk 元数据与 Milvus schema

第三部分解决的是 chunk 的业务身份问题。原来的 chunk 主要依赖 `file_title` 表达来源，能用于展示，但不能稳定回答它属于哪个 document、哪个用户、哪个知识库和哪一版索引产物。

原来的模型是：

```text
chunk
    -> file_title
    -> subject 元数据
    -> content / vector
```

这个模型存在几个限制：

- 同名文件无法作为稳定业务标识。
- 无法按 document 精确删除或重建 chunk。
- chunk 没有 owner 和 visibility，阶段 5 无法追加可靠的权限过滤。
- 没有 `index_version` 和 `chunk_index`，难以追踪版本和 document 内顺序。

改完后的模型是：

```text
document/task state
    -> 入库前统一补齐 document/user/visibility/version 元数据
    -> 按最终顺序生成 chunk_index
    -> 写入 Milvus
    -> 检索结果继续透传这些字段
```

### 1. Milvus chunk schema 显式增加 document 维度字段

第三部分新增字段如下：

| 字段 | 来源/默认值 | 当前价值 |
|---|---|---|
| `dataset_id` | state | 标识所属知识库，为多知识库过滤提供条件 |
| `document_id` | state | chunk 的稳定 document 归属和幂等业务键 |
| `owner_user_id` | state | 标识文档所有者，为私有文档过滤提供条件 |
| `tenant_id` | state，为空默认 `tenant_default` | 预留租户隔离维度 |
| `visibility` | state，为空默认 `private` | 预留 private/shared/public 可见性规则 |
| `index_version` | state | 标识当前 chunk 属于 document 的哪版索引产物 |
| `chunk_index` | 最终 chunks 顺序，从 `0` 递增 | 稳定表达 document 内切片顺序 |
| `enabled` | 默认 `true` | 为后续 chunk 启停和查询过滤预留 |
| `source_title` | 当前 `file_title` | 独立承担来源标题展示语义 |

已有的正文、标题、主题领域字段和向量字段全部保留。`file_title` 也继续保留，但只负责展示和兼容，不再承担业务身份职责。

### 2. 元数据在入库边界统一补齐

第三部分没有让每个切分节点分别维护这些横切字段，而是在 `index_service` 写入 Milvus 前统一调用元数据标准化逻辑。

数据流是：

```text
ImportGraphState
    -> dataset_id / document_id / owner_user_id
    -> tenant_id / visibility / index_version

最终 chunks
    -> 按列表顺序生成 chunk_index
    -> enabled=true
    -> source_title=file_title

normalize chunk metadata
    -> insert Milvus
```

这样做的价值是：

- 切分逻辑只关心正文和标题，不需要知道用户、租户和权限模型。
- 所有入库 chunk 使用同一套默认值和必填校验，不会因上游节点不同而字段缺失。
- `chunk_index` 基于最终入库顺序生成，不受中间切分步骤影响。
- state 已经在导入入口确定业务上下文，入库时无需再次查询 Mongo。

`dataset_id`、`document_id`、`owner_user_id` 是必填业务字段，缺失时直接拒绝入库；`tenant_id`、`visibility` 和初始 `index_version` 则使用 repository 已定义的默认契约。

### 3. file_title 退出幂等条件

`file_title` 不适合作为幂等键，因为不同用户、不同 document 完全可能上传同名文件。

旧逻辑：

```text
delete chunks where file_title == 当前文件标题
```

新逻辑：

```text
delete chunks where document_id == 当前 document_id
```

这项切换是第三部分“`file_title` 只保留展示用途”的必要落地，同时也是第四部分 document 维度幂等入库的基础步骤。

它解决了两个直接问题：

- 不同用户上传同名文件时，不会删除对方 document 的 chunk。
- 同一 document 重跑时，可以准确替换自己的旧 chunk。

需要注意：第四部分还包含完整的 document 索引状态回写和重建流程，本次只完成了第三部分所必需的删除条件切换，不能把第四部分整体视为已完成。

### 4. 检索返回元数据，为阶段 5 建立接口基础

只把字段写进 Milvus 还不够，查询链路还必须能取回这些字段。因此 `CHUNK_OUTPUT_FIELDS` 和检索结果格式化逻辑也同步增加了第三部分字段。

当前检索结果已经可以携带：

```text
dataset_id
document_id
owner_user_id
tenant_id
visibility
index_version
chunk_index
enabled
source_title
```

这不代表阶段 5 权限过滤已经实现。当前只是让查询层拿得到这些数据；阶段 5 仍需要在 Milvus 查询表达式中加入 dataset、owner、visibility、enabled 等过滤条件。

### 5. 第三部分的重构价值

第三部分把 chunk 从“某个标题下的一段文本”升级为“某个 document、某个用户、某个索引版本下的一条可管理检索数据”。

核心价值包括：

- 业务身份从不稳定的文件标题切换为稳定的 `document_id`。
- document、用户、可见性和版本信息贯穿到最末端的检索数据。
- `chunk_index` 为引用排序、问题定位和后续 chunk 管理提供稳定序号。
- `enabled` 为后续软停用单个 chunk 留出扩展点。
- 阶段 5 可以直接基于已落地字段追加权限过滤，不需要再次重建 schema。

当前边界是：

- Milvus 测试集合需要删除重建，当前不做旧 schema 在线兼容。
- 阶段 5 查询权限表达式尚未实现。
- document 删除和重建 API 尚未完成。
- 当前删除旧 chunk 后再插入；重建失败时如何完整更新 document/task 状态，仍由第四部分继续收口。

面试复盘可以这样表达：

```text
阶段 4 第三部分把 Milvus chunk 从文件标题维度升级到了 document 维度。
我在 schema 中补齐 dataset、document、owner、visibility、index_version、chunk_index 等字段，并在入库边界统一从 state 回填，避免切分节点重复处理横切元数据。
同时幂等删除从 file_title 切换为 document_id，并让查询结果透传这些字段。
这样同名文件不会互相影响，chunk 可以追踪到具体 document 和索引版本，也为下一阶段的用户权限过滤准备好了稳定数据基础。
```
