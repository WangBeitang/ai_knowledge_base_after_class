# 第一部分：用户维度导入历史隔离

阶段 3.5 的核心不是做一套完整登录权限系统，而是在阶段 3 已经完成 `document/task` 元数据闭环的基础上，补上轻量用户归属维度。

阶段 3 之后，系统已经能记录导入文档和任务状态，但这些状态仍然是“系统维度”的。也就是说，所有用户理论上都在看同一套 document/task 记录。

原来的逻辑是：

```text
用户上传文件
    -> /upload 生成 task_id/document_id
    -> Mongo documents/tasks 记录导入状态
    -> /documents 或 /status 查询状态
    -> 查询时不区分当前用户
```

这个逻辑能支撑文档状态追踪，但对前端用户来说还有明显问题：

- 用户刷新页面后，如果没有“我的导入记录”，仍然很难找回刚才上传或失败的文档。
- 所有用户共享同一份 document/task 列表时，用户 A 和用户 B 的导入历史会串在一起。
- 失败节点和错误信息已经落库，但如果没有用户隔离，用户可能看到别人的失败信息。
- `task_id` 如果能被猜到，`/status/{task_id}` 可能暴露其他用户的实时任务进度。
- 后续阶段 4/5 做 chunk 管理和查询召回隔离时，如果 document/task 还没有用户归属，会出现权限模型断层。

阶段 3.5 改完后的逻辑是：

```text
前端首次访问导入页
    -> localStorage 生成并保存 kb_user_id

前端调用导入相关 API
    -> 请求头携带 X-User-Id

后端接收请求
    -> get_current_user_id(request) 解析当前用户
    -> 创建 document/task 时写 owner_user_id
    -> 查询 document/task/status 时按 owner_user_id 过滤

前端页面加载或刷新
    -> GET /documents
    -> 只展示当前用户自己的导入历史
```

这一阶段的关键判断是：

```text
先让“我的导入历史”和“我的任务状态”不串用户；
不把它升级成完整认证、授权、多租户系统。
```

## 1. 轻量用户归属而不是完整账号系统

阶段 3.5 使用的用户身份来源是前端匿名 ID：

```text
localStorage.getItem("kb_user_id")
    -> 如果存在，继续复用
    -> 如果不存在，生成 user_xxx
    -> 写回 localStorage
```

后续导入相关请求统一携带：

```http
X-User-Id: user_xxx
```

后端通过 `get_current_user_id(request)` 读取这个 header。如果缺少 `X-User-Id`，直接返回 400：

```text
缺少 X-User-Id 请求头
```

这里没有采用 `anonymous_user` 兜底，原因是：如果所有未带 header 的请求都被归到同一个匿名用户，多个真实用户仍然会混在同一个历史列表里，反而掩盖了隔离问题。

这个设计的价值是把“当前用户是谁”显式传入导入链路，而不是继续让 document/task 停留在系统全局维度。

但它不是生产级身份认证：

- `kb_user_id` 来自浏览器 `localStorage`，不是服务端签发身份。
- `X-User-Id` 可以被调用方伪造。
- 它只能解决当前开发阶段的导入历史归属问题。
- 后续接入正式登录时，应把 `X-User-Id` 替换成 JWT `sub` 或服务端认证后的用户 ID。

所以阶段 3.5 的正确定位是：

```text
轻量用户归属字段落地，不是完整安全认证系统。
```

## 2. owner_user_id 成为 document/task 的归属边界

阶段 3.5 在导入元数据中新增并使用：

```text
owner_user_id
tenant_id
visibility
```

其中 `owner_user_id` 是当前阶段真正参与过滤的字段。

`tenant_id` 和 `visibility` 当前使用默认值：

```text
tenant_id = tenant_default
visibility = private
```

它们的价值是为后续阶段预留扩展入口，而不是在阶段 3.5 就实现完整租户和共享权限。

document 现在表达的是：

```text
这份文档属于哪个用户
这份文档属于哪个 dataset
这份文档当前是否 private/shared/public
这份文档的解析、索引、失败状态是什么
```

task 现在表达的是：

```text
这一次异步导入任务属于哪个用户
这一次任务处理哪份 document
这一次任务属于哪个 dataset
这一次任务执行到哪里、是否失败
```

这让阶段 3 的 `document/task` 元数据闭环从“系统维度”升级成“用户维度”：

| 对象 | 阶段 3 | 阶段 3.5 |
|---|---|---|
| document | 记录文档状态 | 记录文档状态，并标记 `owner_user_id` |
| task | 记录任务状态 | 记录任务状态，并标记 `owner_user_id` |
| dataset | 默认知识库容器 | 继续保留，不做 dataset 成员权限 |
| query recall | 按原逻辑检索 | 不做用户隔离，留到阶段 5 |

这里的重点是：阶段 3.5 隔离的是导入历史和任务状态，不隔离查询召回结果。

原因是当前 Milvus chunk 还没有稳定写入 `owner_user_id`、`visibility`、`document_id` 等字段。如果现在强行在查询链路做用户过滤，要么过滤不可靠，要么破坏现有公共 demo 知识库测试。

## 3. 和 session_id 的边界

阶段 3.5 没有复用聊天中的 `session_id` 做导入历史隔离。

原因是 `user_id` 和 `session_id` 表达的不是同一个问题：

| 字段 | 表示什么 | 适合做什么 |
|---|---|---|
| `user_id` / `owner_user_id` | 用户或匿名用户归属 | 我的文档、我的导入历史、后续权限范围 |
| `session_id` | 一次对话会话 | 当前多轮问答上下文、一次聊天历史 |

导入历史属于“用户资产”，不能只挂在某一次聊天会话下面。用户刷新页面、关闭会话或新开聊天后，仍然应该能看到自己的导入记录。

所以阶段 3.5 的选择是：

```text
导入历史：按 owner_user_id 隔离
聊天上下文：仍按 session_id 处理
聊天历史升级到 user_id + session_id：留到阶段 7
```

这个边界避免了把导入管理和对话管理提前揉在一起。

## 4. 本阶段实际提升

阶段 3.5 的提升可以概括为：从“系统有导入历史”，升级为“用户有自己的导入历史”。

具体提升：

- 用户刷新导入页后，可以看到当前 `kb_user_id` 对应的历史导入记录。
- 用户 A 和用户 B 的 document/task 查询互相隔离。
- 上传时 document/task 会写入 `owner_user_id`，后续权限模型有稳定归属字段。
- 缺少 `X-User-Id` 的请求会明确失败，避免把多个用户混到同一个匿名历史里。
- 状态接口避免在 owner 不匹配时回退内存状态，降低 `task_id` 猜测带来的串扰风险。
- `tenant_id`、`visibility` 预留了后续多租户、共享、公开文档的扩展空间。

一句话总结：

```text
阶段 3 让文档任务可管理；
阶段 3.5 让文档任务归属于当前用户。
```

# 第二部分：Repository 与导入状态契约升级

这一部分关注的是后端元数据层的变化：`ImportMetadataRepository` 不再只管理全局 document/task，而是把 owner 作为创建和查询的基础条件。

原来的 repository 逻辑是：

```text
create_import_metadata(dataset_id, document_id, task_id, file_name, ...)
    -> 创建 document
    -> 创建 task

get_document(document_id)
list_documents(dataset_id, status, keyword, limit)
get_task(task_id)
list_tasks(document_id, limit)
```

这个逻辑缺少用户维度。只要知道 `document_id` 或 `task_id`，就有机会查到其他用户的状态。

阶段 3.5 后，repository 契约变成：

```text
create_import_metadata(
    dataset_id,
    document_id,
    task_id,
    owner_user_id,
    tenant_id = tenant_default,
    visibility = private,
    ...
)

get_document(document_id, owner_user_id)
list_documents(dataset_id, owner_user_id, status, keyword, limit)
get_task(task_id, owner_user_id)
list_tasks(document_id, owner_user_id, limit)
```

也就是说，owner 不再是一个可选展示字段，而是查询条件的一部分。

## 1. document/task 创建时写入归属字段

`create_import_metadata` 创建 document 时写入：

```text
owner_user_id
tenant_id
visibility
```

创建 task 时写入：

```text
owner_user_id
tenant_id
```

这让 document 和 task 在数据层具备明确归属。

其中 document 多了 `visibility`，因为后续查询召回和文档管理会区分：

```text
private  只属于 owner
shared   对特定成员或范围可见
public   对所有用户可见
```

当前阶段只落 `private` 默认值，不实现 shared/public 行为。

## 2. 查询时把 owner 作为过滤条件

阶段 3.5 的 repository 查询不再只按 ID 查，而是按 ID + owner 查。

例如：

```text
get_document(document_id, owner_user_id)
    -> documents.find_one({
        document_id,
        owner_user_id
    })

get_task(task_id, owner_user_id)
    -> tasks.find_one({
        task_id,
        owner_user_id
    })
```

列表查询也是同样原则：

```text
list_documents
    -> owner_user_id + dataset_id + status/keyword/limit

list_tasks
    -> owner_user_id + document_id/dataset_id/status/limit
```

这个设计的价值是：记录不存在和记录存在但不属于当前用户，对 repository 来说都返回空结果。HTTP 层再统一表现为 404。

这样可以避免暴露类似信息：

```text
这个 document_id 存在，但不属于你
```

在权限系统里，这类信息也属于不该轻易暴露的资源存在性信息。

## 3. 索引也按用户维度补齐

阶段 3.5 给 Mongo documents/tasks 增加了 owner 相关索引：

```text
documents:
  (owner_user_id, dataset_id, updated_at)
  (owner_user_id, document_id)
  (owner_user_id, status)

tasks:
  (owner_user_id, task_id)
  (owner_user_id, document_id, created_at)
```

这说明用户维度不是只在应用层临时过滤，而是被纳入常用查询路径。

导入页加载“我的导入记录”时，核心查询就是：

```text
owner_user_id + dataset_id + updated_at
```

某个文档查看任务历史时，核心查询就是：

```text
owner_user_id + document_id + created_at
```

这些索引让阶段 3.5 的访问路径和数据结构保持一致。

## 4. ImportGraphState 同步预留用户上下文

阶段 3.5 也扩展了 `ImportGraphState`：

```text
owner_user_id
tenant_id
visibility
```

这一步的价值不是让每个节点都直接做权限判断，而是让导入图的上下文完整表达：

```text
当前任务处理哪份 document
属于哪个 dataset
属于哪个用户
当前可见性是什么
```

后续阶段 4 做 chunk 入库时，可以从 state 中把这些字段写入 Milvus chunk：

```text
owner_user_id
tenant_id
visibility
dataset_id
document_id
```

这样阶段 5 才能在查询召回时做：

```text
visibility=public/shared 或 owner_user_id=当前用户
```

也就是说，阶段 3.5 不是直接改变查询召回，而是把后续查询隔离需要的上游归属字段先接到导入状态里。

## 5. 关键取舍和边界

阶段 3.5 在 repository 和 state 层已经做了：

- document/task 创建时写入 `owner_user_id`。
- document/task 创建时写入默认 `tenant_id`。
- document 创建时写入默认 `visibility=private`。
- document/task 查询方法增加 owner 过滤。
- Mongo 增加 owner 维度索引。
- `ImportGraphState` 增加 `owner_user_id`、`tenant_id`、`visibility`。

阶段 3.5 没有做：

- 不迁移旧数据。
- 不兼容没有 `owner_user_id` 的历史 document/task。
- 不做 dataset owner/members。
- 不做组织或租户后台。
- 不做 shared/public 的真实授权逻辑。
- 不改造 Milvus 历史 chunk。
- 不在查询召回阶段使用 owner 过滤。

当前项目 Mongo 和 Milvus 都是少量测试数据，所以阶段 3.5 选择不做历史数据回写。这个取舍很重要：当前阶段目标是把正确结构落地，而不是为测试数据做复杂兼容层。

# 第三部分：导入 API 与状态查询隔离

这一部分关注对外 API 的变化：导入相关接口现在都必须知道“当前用户是谁”，并且按用户过滤 document/task/status。

原来的 API 查询路径是：

```text
POST /upload
    -> 创建 document/task
    -> 返回 task_id/document_id

GET /documents
    -> 返回系统中的 document 列表

GET /documents/{document_id}
    -> 返回指定 document

GET /documents/{document_id}/tasks
    -> 返回指定 document 的 task 列表

GET /status/{task_id}
    -> 返回指定 task 状态
```

阶段 3.5 后，这些接口都变成“当前用户视角”：

```text
POST /upload
    -> 必须携带 X-User-Id
    -> 创建属于当前用户的 document/task

GET /documents
    -> 必须携带 X-User-Id
    -> 只返回当前用户 document

GET /documents/{document_id}
    -> 必须携带 X-User-Id
    -> 只允许查看当前用户 document

GET /documents/{document_id}/tasks
    -> 必须携带 X-User-Id
    -> 只返回当前用户在这份 document 下的 tasks

GET /status/{task_id}
    -> 必须携带 X-User-Id
    -> 只允许查看当前用户 task
```

## 1. /upload 写入 owner 并返回 owner

`POST /upload` 的处理流程现在是：

```text
1. get_current_user_id(request)
2. 生成 task_id
3. 生成 document_id
4. create_import_metadata 写入 owner_user_id/tenant_id/visibility
5. register_persistent_task(task_id, document_id, dataset_id, owner_user_id)
6. 保存文件
7. 后台 invoke_graph 传入 owner_user_id/tenant_id/visibility
8. 返回 task_ids/document_ids/dataset_id/owner_user_id
```

上传响应里的 `owner_user_id` 不是前端必须依赖的字段，因为前端本来就知道自己的 `currentUserId`。但把它返回出来有调试价值：

- 可以确认后端实际解析到哪个用户。
- 测试可以验证 owner 是否正确传入 metadata 和后台 graph。
- 排查跨用户数据时更直观。

## 2. /documents 成为“我的导入记录”数据源

阶段 3.5 中，`GET /documents` 的意义从“系统文档列表”变成“当前用户导入历史列表”。

接口仍然支持阶段 3 已有筛选：

```text
dataset_id
status
keyword
limit
```

但无论这些筛选条件怎么传，底层都会带上：

```text
owner_user_id = 当前 X-User-Id
```

这让前端刷新页面后可以直接调用：

```text
GET /documents
X-User-Id: user_xxx
```

并展示当前用户自己的历史导入记录。

## 3. /documents/{document_id} 对 owner 不匹配返回 404

`GET /documents/{document_id}` 现在按：

```text
document_id + owner_user_id
```

查询。

如果 document 不存在，返回 404。

如果 document 存在但属于其他用户，也返回 404。

这个行为避免暴露资源存在性。对调用方来说，下面两种情况表现一致：

```text
document_id 不存在
document_id 存在但不属于当前用户
```

这符合阶段 3.5 的轻量隔离目标。

## 4. /documents/{document_id}/tasks 按 owner 过滤任务

文档任务列表现在按：

```text
owner_user_id + document_id
```

过滤。

这样即使出现不同用户传入相同或可猜的 document_id，接口也只会返回当前用户自己的 task 列表。

更严格的做法是先查 document 是否属于当前用户，再查 tasks。当前实现直接在 `list_tasks` 层按 `owner_user_id + document_id` 过滤，也能达到阶段 3.5 的隔离目标。

## 5. /status/{task_id} 收紧内存回退边界

`/status/{task_id}` 是阶段 3.5 最需要注意的接口。

阶段 3 里它会优先读 Mongo，失败时回退 `task_utils` 内存状态。这个回退对兼容实时进度有价值，但在用户隔离场景下有风险：

```text
如果 Mongo 查不到当前用户 task，
但内存里正好有同名 task_id，
就可能把别人的实时进度返回出去。
```

阶段 3.5 收紧后的逻辑是：

```text
GET /status/{task_id}
    -> 读取 X-User-Id
    -> get_task(task_id, owner_user_id)

如果找到 task
    -> 返回 Mongo 任务状态

如果 Mongo 查询异常
    -> 回退内存状态
    -> 如果该 task 是已注册持久化任务，并且 owner 不匹配，返回 404

如果 Mongo 正常但查不到当前用户 task
    -> 不回退内存
    -> 返回 404
```

这个边界很关键。

它保留了 Mongo 不可用时的兼容能力，但避免了“Mongo 正常查不到 owner task，却从内存泄漏其他用户 task”的问题。

## 6. 关键取舍和边界

阶段 3.5 的 API 层已经做了：

- 导入相关 API 统一要求 `X-User-Id`。
- 缺少 `X-User-Id` 返回 400。
- 上传时写入并返回 `owner_user_id`。
- `/documents` 只返回当前用户文档。
- `/documents/{document_id}` 对不存在或 owner 不匹配统一 404。
- `/documents/{document_id}/tasks` 按 owner 过滤。
- `/status/{task_id}` 正常查不到当前用户 task 时返回 404，不再回退内存。

阶段 3.5 没有做：

- 不做 JWT 鉴权。
- 不做账号密码登录。
- 不做管理员绕过权限。
- 不做 RBAC。
- 不做 dataset 成员授权。
- 不对查询问答 API 加用户过滤。

这个边界保证阶段 3.5 不会被误解成完整权限系统。它只是把导入历史和状态查询先按用户隔离。

# 第四部分：前端“我的导入记录”与失败提示友好化

这一部分关注前端体验变化：阶段 3 已经让后端能记录文档状态，阶段 3.5 让用户刷新页面后真正看得到自己的历史导入记录，并且把失败原因用更友好的方式展示出来。

原来的导入页逻辑是：

```text
用户选择文件
    -> POST /upload
    -> 拿 task_id
    -> 轮询 /status/{task_id}
    -> 当前页面显示进度

刷新页面
    -> 当前页面状态丢失
    -> 不主动加载历史 document
```

这个逻辑的问题是：

- 刷新页面后，用户看不到之前上传过什么。
- 后端虽然已经有 document 列表，但前端没有使用。
- 失败时前端只显示“失败”，不解释失败发生在什么阶段。
- 后端返回的 `failed_node` 是技术节点名，直接展示给普通用户不够友好。

阶段 3.5 后，导入页变成：

```text
页面初始化
    -> 生成或读取 kb_user_id
    -> 调用 GET /documents
    -> 渲染“我的导入记录”

用户上传文件
    -> POST /upload 携带 X-User-Id
    -> 当前上传区显示实时进度
    -> 完成或失败后刷新历史记录

用户查看历史记录
    -> 看到文件名、上传时间、状态、解析状态、索引状态、chunk 数量
    -> 失败时看到友好失败摘要
    -> 展开详情后看到 failed_node/error_message/task_id/document_id 等技术信息
```

## 1. 前端稳定生成 kb_user_id

导入页现在使用：

```text
USER_ID_STORAGE_KEY = "kb_user_id"
```

初始化逻辑是：

```text
const existingUserId = localStorage.getItem(USER_ID_STORAGE_KEY)
if (existingUserId) return existingUserId

const userId = createUserId()
localStorage.setItem(USER_ID_STORAGE_KEY, userId)
return userId
```

后续请求统一通过 `userHeaders()` 添加：

```http
X-User-Id: currentUserId
```

这保证同一个浏览器在不清空 localStorage 的情况下，刷新页面后仍然是同一个匿名用户。

测试时也可以手动把 `kb_user_id` 固定成：

```text
user_a
user_b
user_demo
```

这样可以复现用户隔离行为。

## 2. 页面加载时调用 GET /documents

导入页新增 `loadDocumentHistory()`：

```text
fetch(`${API_BASE}/documents`, {
    headers: userHeaders(),
})
```

接口返回后调用：

```text
renderDocumentHistory(data.items || [])
```

这样页面第一次打开或刷新时，会直接展示当前用户自己的导入历史。

这一步把阶段 3 的后端 document 元数据真正接到了用户界面上。否则 document/task 虽然已经落库，但用户仍然感知不到“历史可找回”。

## 3. 历史列表展示的是 document 视角

历史记录不是直接展示 task 流水，而是展示 document 状态。

每条历史记录展示：

- 文件名。
- 上传时间。
- 文档整体状态。
- 解析状态。
- 索引状态。
- chunk 数量。
- 友好失败摘要。
- 查看详情。

详情里保留技术字段：

- `document_id`
- `latest_task_id`
- `dataset_id`
- `subject_id`
- `standard_subject_name`
- `md_path`
- `failed_node`
- `error_message`

这延续了阶段 3 的职责边界：

```text
document 是用户找历史记录的入口；
task 是一次异步执行记录。
```

所以前端“我的导入记录”应该以 document 为主，而不是要求用户记住 task_id。

## 4. 当前上传任务和历史记录分开展示

导入页现在分成两块：

```text
activeFileList
    -> 当前页面刚上传、还在轮询的任务

fileList
    -> GET /documents 返回的历史导入记录
```

上传中的任务继续显示实时进度和日志；任务完成或失败后，会刷新历史列表，并把当前上传条目移除。

这样做避免了两个问题：

- 上传中的实时进度和历史 document 列表混在一起。
- 同一个文件完成后，在页面上同时出现“实时任务条目”和“历史记录条目”。

## 5. 失败信息分成用户提示和技术详情

阶段 3 后端已经能返回：

```text
failed_node
error_message
```

但 `node_import_milvus`、`node_bge_embedding` 这类节点名对普通用户不友好。

阶段 3.5 在前端增加 `FAILED_NODE_MESSAGES` 映射：

| failed_node | 用户提示 |
|---|---|
| `upload_file` | 文件保存失败，请重新上传 |
| `node_entry` | 文件类型不支持或文件信息读取失败 |
| `node_pdf_to_md` | PDF 解析失败，请检查文件是否损坏或格式是否支持 |
| `node_md_img` | Markdown 图片处理失败 |
| `node_subject_name_recognition` | 文档主题识别失败 |
| `node_bge_embedding` | 文档向量化失败，请稍后重试 |
| `node_import_milvus` | 文档索引入库失败，请稍后重试 |
| 空或未知 | 导入失败，请稍后重试或联系管理员 |

这样前端主提示面向用户：

```text
文档索引入库失败，请稍后重试
```

详情区仍然保留技术信息：

```text
failed_node: node_import_milvus
error_message: Milvus 入库失败
task_id: ...
document_id: ...
```

这个设计同时满足两类人：

- 普通用户知道下一步该重试、换文件或联系管理员。
- 开发人员仍然能从详情里看到具体节点和错误信息。

## 6. 关键取舍和边界

阶段 3.5 前端已经做了：

- 稳定生成并复用 `kb_user_id`。
- 所有导入 API 请求携带 `X-User-Id`。
- 页面加载时调用 `GET /documents`。
- 展示当前用户历史导入记录。
- 展示文件名、上传时间、状态、解析状态、索引状态、chunk 数量。
- 展示查看详情。
- 失败节点映射为友好提示。
- 技术细节保留在详情里。

阶段 3.5 前端没有做：

- 不做登录、注册、退出。
- 不做用户切换 UI。
- 不做多知识库管理 UI。
- 不做删除文档、重建索引、禁用 chunk。
- 不做前端权限系统。
- 不做复杂前端自动化浏览器测试，只做轻量静态覆盖。

当前前端仍然是导入演示页，不是完整知识库后台。但它已经把阶段 3 的 document/task 元数据转化成了用户可见的“我的导入记录”。

# 第五部分：边界、测试与后续阶段依赖

阶段 3.5 很容易被误解成“已经实现多用户权限系统”。实际不是。

这一阶段只解决一个清晰问题：

```text
导入历史和状态查询按当前用户隔离。
```

它不解决：

```text
查询召回隔离
正式登录认证
多租户组织权限
dataset 成员管理
文档共享策略
聊天历史用户维度
```

## 1. 本阶段明确不做查询召回隔离

阶段 3.5 不改变 query 链路。

也就是说，下面这些查询流程仍然保持原有逻辑：

```text
query -> 主题识别 -> Milvus chunk 检索 -> rerank -> answer
```

原因是当前 chunk 还没有完整的用户维度字段。要做查询隔离，至少需要 Milvus chunk 中有：

```text
owner_user_id
tenant_id
visibility
dataset_id
document_id
```

阶段拆分应该是：

```text
阶段 3.5
    -> document/task 导入历史按用户隔离

阶段 4
    -> chunk 入库时写 owner_user_id / visibility / document_id

阶段 5
    -> 查询召回时按 public/shared + owner_user_id 过滤
```

如果阶段 3.5 现在强行改 query 过滤，要么无法可靠过滤，要么会影响现有 demo 公共知识库测试。

## 2. 本阶段不做生产级身份安全

`kb_user_id` 和 `X-User-Id` 是轻量身份方案，不是正式安全方案。

它适合当前阶段：

- 本地开发。
- Demo 验证。
- 前端刷新后找回自己的导入历史。
- 用 `user_a` / `user_b` 测试隔离。

它不适合直接作为生产安全边界：

- 用户可以伪造 header。
- localStorage 可以被清空或修改。
- 没有登录态校验。
- 没有服务端签发身份。
- 没有权限策略中心。

后续接入正式登录时，理想升级路径是：

```text
当前阶段：
X-User-Id -> owner_user_id

后续阶段：
JWT sub / 服务端认证用户 ID -> owner_user_id
```

这样 document/task 结构不需要推翻，只需要替换用户身份来源。

## 3. 本阶段对后续阶段的依赖价值

阶段 3.5 的价值不只在前端历史列表，它还给后续阶段铺了用户权限模型的底座。

对阶段 4 的价值：

- chunk 入库可以从 `ImportGraphState` 拿到 `owner_user_id`、`tenant_id`、`visibility`。
- chunk 可以稳定关联 `document_id`、`dataset_id`。
- 后续做 document_id 幂等、删除、重建时，可以知道操作对象属于哪个用户。

对阶段 5 的价值：

- 查询召回可以扩展过滤条件：

```text
dataset_id + subject_id + enabled=true
    + (visibility=public/shared 或 owner_user_id=当前用户)
```

对阶段 6 的价值：

- chunk 列表和启停 API 可以按用户权限过滤。
- 用户只能管理自己有权限的 chunk。

对阶段 7 的价值：

- dataset owner、dataset members、document owner、visibility 策略可以接到已有字段上。
- 聊天历史可以从 `session_id` 升级到 `user_id + session_id`。

对阶段 8 的价值：

- 评测数据可以区分公共 demo 数据和用户私有数据。
- 评测时可以固定 `X-User-Id: user_eval`，保证召回范围稳定。

## 4. 测试覆盖

阶段 3.5 补充了后端和前端轻量测试。

Repository 测试覆盖：

- 创建 document/task 时写入 `owner_user_id`。
- document 写入默认 `tenant_id`、`visibility`。
- task 写入默认 `tenant_id`。
- `list_documents` 只返回当前用户记录。
- `get_document` 不能读取其他用户文档。
- `get_task` 不能读取其他用户任务。
- owner 相关 Mongo 索引存在。

API 测试覆盖：

- `POST /upload` 缺少 `X-User-Id` 返回 400。
- `POST /upload` 写入并返回 `owner_user_id`。
- 后台 `invoke_graph` 接收 `owner_user_id`、`tenant_id`、`visibility`。
- `GET /documents` 按 owner 过滤用户 A/B。
- `GET /documents/{document_id}` 对其他用户文档返回 404。
- `GET /documents/{document_id}/tasks` 按 owner 过滤。
- `GET /status/{task_id}` 优先读 Mongo task。
- Mongo 不可用时，`GET /status/{task_id}` 可回退内存状态。
- Mongo 正常但 owner 不匹配时，`GET /status/{task_id}` 不回退内存，返回 404。

前端轻量测试覆盖：

- 导入页初始化并保存 `kb_user_id`。
- 请求里携带 `X-User-Id`。
- 页面调用 `GET /documents`。
- 页面渲染历史记录字段。
- 页面包含失败节点友好提示映射。

当前全量回归结果：

```text
uv run pytest -q
73 passed
```

## 5. 面试复盘表达

阶段 3.5 可以这样概括：

```text
阶段 3 已经把导入状态从内存推进到 Mongo 的 document/task 元数据闭环；
阶段 3.5 进一步把这个闭环从系统维度升级到用户维度。
我没有直接做完整登录权限，而是先用前端稳定匿名 user_id + X-User-Id header，
让 document/task 创建和查询都带 owner_user_id。
同时收紧 /status 的内存回退边界，避免 owner 不匹配时泄漏实时任务进度。
前端再用 GET /documents 渲染“我的导入记录”，并把 failed_node 映射成用户友好的失败摘要。
这一步既解决了刷新后找回导入历史的问题，也为后续 chunk 用户字段、查询召回过滤和正式权限模型铺好了数据结构。
```

这部分体现的工程能力不是“堆权限功能”，而是清楚地区分阶段目标：

- 当前阶段只做导入历史隔离。
- 查询召回隔离留到 chunk 字段落地之后。
- 正式认证授权留到后续管理 API。
- 先把数据归属字段、查询边界和前端历史入口打通。

这比一次性做复杂权限系统更符合当前项目节奏，也降低了对现有 query demo 和测试链路的冲击。
